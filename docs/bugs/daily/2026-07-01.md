### Production Symptom

The deployed window was exchange-flat with no open orders, but the follow-up
diagnosis still mixed several distinct process-quality classes:

- selected/dispatched entry candidates did not all become opens; eight samples
  were passive maker no-fill / reprice-not-tradeable terminal removals.
- `entry_market_evidence_summary` showed a large candidate-readiness tail
  dominated by quote stale, confirmed low OI, and structural OI suppression.
- passive-close maker zero-fill counts appeared even when the close later
  terminally resolved through normal maker polling.
- zero-fill reprice samples hit lifecycle/recovery protection such as
  `lifecycle_risk_only` or `recovery_ledger_blocked`.
- historical resolved close/order/residual artifacts could still color the
  conclusion as degraded even when current exchange truth and lifecycle state
  were clean.
- CL-140/CL-141/CL-142 had already been cloud verified at `ca2ede1`, but the
  bug ledger still said deploy pending.

### Root Cause

V2 had the right safety gates, but their diagnostic and runtime intake points
were not aligned to one business vocabulary.

Entry admission, selected-to-dispatch, passive maker submit, and zero-fill
reprice each emitted local reasons. Some reasons were discovered only after a
maker attempt had already consumed a no-fill cycle, so `selected != opened`
looked like an execution failure instead of a late viability block. The
diagnose layer then lacked a single `entry_execution_viability` bucket to
separate "not tradeable yet" from "maker terminal no-fill with full V1 proof."

Market-data readiness had the same issue. Quote stale, OI below floor,
structural OI suppression, and prewarm-pending evidence were all visible, but
they were not grouped as readiness/backoff evidence, so the volume could be
mistaken for order-path failure.

For passive close, zero-fill polling was overbroad. A close maker can have
normal zero-fill polling before it later fills or terminally resolves. Counting
that path with no-price or fallback zero-fill made cost diagnostics look worse
than the actual close quality.

Finally, diagnose conclusion logic did not consistently distinguish current
blockers from historical resolved artifacts after terminal flat/no-open-order
truth. The bug ledger had the analogous governance drift: deployed clusters
could remain marked `deploy pending`.

### V1 Decision

- Do not lower OI floors, quote freshness, liquidity, post-only, or lifecycle
  recovery gates to increase opens.
- `selected != opened` is not itself a bug. The bug is discovering a
  non-tradeable or protected state after entering maker work when it could have
  been explained as dispatch viability.
- A pending entry may terminalize as passive-unfilled only after V1 proof:
  maker terminal no-fill, no matching open order, and live position flat. If
  truth is unavailable, an open order exists, live exposure is nonzero, or any
  positive fill exists, retain/fail-closed or route to recovery/cleanup.
- Normal passive-close maker polling with later terminal resolution is not
  close-cost inefficiency. Only no-price/unmaintainable/fallback paths are
  unproductive cost evidence.
- Historical resolved order/residual artifacts remain audit evidence, but they
  must not reblock a current clean exchange-truth gate.

### Fix

- Added a shared `entry.dispatch_viability_blocked` event at entry dispatch
  gate, price-resolution, and zero-fill reprice boundaries.
- `_handle_pending_passive_zero_fill_completion()` now reports lifecycle /
  recovery reprice blockers through that shared viability event before
  terminal removal. The actual pending-entry removal still goes through the
  existing `_finalize_pending_entry()` V1 terminal proof.
- Diagnose now exposes `entry_execution_viability_summary` and
  `passive_unfilled_quality_summary` so late reprice blocks, maker terminal
  unfilled, and retained/recovery shapes are separate.
- Diagnose now exposes `market_data_readiness_summary` for quote stale, OI
  below floor, OI unavailable, OI structural suppression, and prewarm pending.
- Passive-close cost diagnostics now split
  `normal_maker_poll_zero_fill`, `resolved_after_zero_fill`,
  `unproductive_zero_fill`, and `maker_viability_rejected`.
- Conclusion building now checks whether order-error evidence is a current
  blocker before degrading a gate that already has current terminal flat /
  no-open-orders / lifecycle-closed proof.
- Bug docs were corrected for CL-140/CL-141/CL-142 cloud verification and this
  CL-143 ledger entry records the deployed/cloud-verified `a9269db` proof.

## Cluster CL-144 - ACK-only Close Truth Gap Explicit Lifecycle Follow-up

### Production Symptom

Post-deploy diagnosis was flat/no-open-orders and PASS, but close truth-gap
accounting still showed ACK-only close orders closing through legacy terminal
flat inference instead of explicit `exit.accepted_order_truth_gap_resolved`
events. That meant the trade was safe, but the close lifecycle was not fully
self-describing.

### Root Cause

`OrderSubmitError(UNCERTAIN)` with exchange accepted-order identity could be
logged as `order.uncertain` and then recovered by retry/live-flat reconciliation
without first registering a close accepted-order truth-gap work item. V1
semantics say an ACK is not a fill: the runtime must prove order detail,
position truth, and open-order truth before it can close the gap.

### V1 Decision

- ACK-only close responses create accepted-order truth work, not immediate fill.
- Order-detail fill proof wins before live-flat inference.
- Live-flat can close the gap only together with open-orders-empty proof.
- If live position truth is unavailable, open-order truth is unavailable, an
  open order remains, or live exposure remains nonzero, retain/fail-closed and
  do not emit a resolved event.
- Hyperliquid strict-readonly authorization is intentionally out of scope for
  this cluster.

### Fix

- `_submit_close_leg()` now preserves accepted order/client identity on
  uncertain close ACKs and marks them as `accepted_order_truth_gap`.
- `_submit_close_leg_with_retry()` routes ACK-only uncertain close results into
  a shared truth-gap resolver instead of blindly retrying.
- The resolver emits `exit.accepted_order_truth_gap_registered`, checks
  `fetch_order_fill_reconciliation()` first, emits explicit
  `exit.accepted_order_truth_gap_resolved(resolution_status=filled)` on fill
  proof, otherwise requires live position flat plus open orders empty before
  emitting `resolution_status=live_flat`.
- Open-order-present, non-flat, missing adapter, or unavailable truth paths emit
  `exit.accepted_order_truth_gap_retry_blocked` and retain the gap.
- Diagnose now surfaces `close_truth_gap_legacy_inferred` as
  `nonblocking_explicit_lifecycle_missing` so old logs stay PASS when exchange
  truth is clean, while new logs must provide explicit resolved events.
- Diagnose treats the existing CL-136
  `resolution_status=live_flat_after_single_leg_cleanup` event as explicit
  live-flat closure, not as legacy inference or unresolved debt.
