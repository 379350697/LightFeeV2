## Cluster CL-140 - Passive Close Maker Viability Cost Guard and Duplicate Truth-Gap Closure

Status: local verified; deploy pending.

### GitNexus Keys

- Fingerprints:
  `passive_close_maker_viability_missing_quote_zero_fill_cost`,

- Symbols: `PassiveCloseExecutor._submit_maker_order`,
  `PassiveCloseExecutor._maintain_maker_order`,
  `CloseExecutor._submit_close_leg_with_retry`,
  `BitgetAdapter.fetch_open_orders`,
  `_restore_state_from_snapshot_dict`,
  `_build_business_progression_quality_summary`
- Files: `lightfee/engine/passive_close.py`,
  `lightfee/engine/close_executor.py`, `lightfee/venues/bitget.py`,
  `lightfee/engine/state.py`, `lightfee/engine/recovery.py`,
  `scripts/diagnose_live.py`
- Watch: `exit.passive_close_maker_viability_rejected`,
  `execution.dual_taker_armed reason=maker_viability_rejected`,
  `exit.accepted_order_truth_gap_registered`,
  `exit.accepted_order_truth_gap_resolved resolution_status=live_flat`,
  `exit.accepted_order_truth_gap_retry_blocked`,
  `close_cost_inefficiency_summary.maker_viability_rejected_count`
- Card: [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Production Symptom

Recent passive-close cost review showed POWR-style maker routing could continue
through a complete zero-fill phase when close price/quote evidence was missing
or no longer maintainable. High-slippage and low-slippage maker phases could
therefore amplify the cost into multiple no-fill cycles before falling back.

Separately, duplicate-client or ACK-only close paths could prove live flat and
emit the legacy `exit.close_duplicate_client_order_resolved_live_flat` event,
but did not always emit explicit
`exit.accepted_order_truth_gap_resolved`. Bitget also lacked an adapter-level
`fetch_open_orders()` truth contract, so a live-flat duplicate close could not
prove the open-order-empty half of the close truth gap.

### Root Cause

Passive close maker submit/maintain treated missing quote or missing maintain
price evidence as a retryable maker condition instead of a maker-viability
failure. That preserved V1 safety, but wasted maker cycles after the system no
longer had enough proof to keep a post-only close order viable.

Close duplicate-client reconciliation had a second gap: when order detail was
insufficient and live position was flat, the branch returned terminal flat on
legacy live-flat evidence even if open-order truth was unavailable. This let
diagnose infer a clean result from terminal state instead of requiring an
explicit accepted-order truth-gap lifecycle close.

### V1 Decision

- ACK or duplicate-client reject is not a fill.
- Maker close may continue only with price, tick, and quote evidence sufficient
  to prove a post-only order is maintainable.
- Live-flat can close an accepted close truth gap only with fresh open-order
  empty proof; otherwise the gap remains fail-closed and retryable.
- Restart recovery must preserve maker-viability rejection evidence so the
  recovered runtime does not re-enter the same no-proof maker path.

### Fix

- Added `exit.passive_close_maker_viability_rejected` and phase-state evidence
  for missing close price hint, missing tick, or missing quote proof.
- Maker maintain now switches directly to dual-taker fallback on no-proof maker
  viability failure instead of burning a normal zero-fill cycle.
- Maker submit now requires quote proof before placing a post-only close order.
- Duplicate-client live-flat close now registers an accepted-order truth gap
  and emits explicit `exit.accepted_order_truth_gap_resolved(live_flat)` only
  when live position is flat and open orders are empty.
- If open-order truth is unavailable or an open order remains, duplicate close
  emits `exit.accepted_order_truth_gap_retry_blocked` and returns uncertain
  instead of terminal flat.
- Bitget adapter now exposes `fetch_open_orders()` through the official
  Mix V2 / UTA open-order contracts and parses pending-order rows.
- Diagnose now reports maker viability rejection and early fallback counts
  separately from true zero-fill maker no-fill cycles.
- Snapshot recovery restores maker-viability rejection evidence.

|---|---|---|
| local RED | duplicate-client live-flat without open-order truth | failed before fix by returning `terminal_flat` |
| local GREEN | same fixture after truth-gap fail-closed change | returns `uncertain`, emits registered + retry-blocked, no explicit resolved |
| local GREEN | Bitget `orders-pending` fixture | `fetch_open_orders("BTCUSDT")` calls `/api/v2/mix/order/orders-pending` with `productType`, `marginCoin`, and `symbol`, then parses `entrustedList` |
| local regression | passive close, close execution, diagnose, uncertainty, production health, lifecycle closure, Bitget profile, recovery | `558 passed` |

## Cluster CL-139 - Deploy-Window Exchange Truth Scope After Terminal Flat

Status: local verified; deploy pending.

### GitNexus Keys

  `since_deploy_exchange_truth_scope_partial_after_terminal_flat`,
  `diagnose_current_positions_only_truth_scope`,
  `hyperliquid_only_truth_pass_after_binance_bybit_aster_trades`
- Components: `diagnose-live`, `production-gate`, `exchange-truth`,
  `v1-parity`
- Symbols: `run_diagnose`, `_exchange_truth_venues_for_diagnose`,
  `_exchange_truth_scope_from_events`
- Files: `scripts/diagnose_live.py`, `tests/test_diagnose_live.py`
- Watch: `exchange_truth.available_venues`,
  `production_acceptance_gate.exchange_truth_flat`,
  `production_acceptance_gate.exchange_truth_no_open_orders`,
  recent `entry.opened`, `exit.passive_close_resolved`,
  `runtime.position_lifecycle_terminal`
- Cards: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md),
  [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Production Symptom

Latest deployed runtime was service-healthy, had no local open positions, no
pending entries, no pending passive closes, no pending reconciliations, and no
residual repairs. The same deploy window contained real completed lifecycle
events for `POWRUSDT` and `LABUSDT` across Binance/Bybit/Aster/OKX-style
venues.

`diagnose_live --since-deploy` still reported final PASS, but its
`exchange_truth.available_venues` contained only `hyperliquid`. That meant
the flat/no-open-orders proof was not covering the venues that had just
participated in the open/close lifecycle.

### Root Cause

`run_diagnose()` derived exchange-truth symbols and venues only from current
`local_state.positions`. After successful terminal flat, that list is empty.
When Hyperliquid strict-readonly metadata is present,
`_exchange_truth_venues_for_diagnose()` appended Hyperliquid and returned that
single venue instead of falling back to all relevant recent venues.

This made the production gate vulnerable to a partial-truth PASS: local
terminal flat plus Hyperliquid flat could mask the absence of fresh read-only
truth for the venues that actually traded in the selected deploy window.

### V1 Decision

- Exchange truth outranks local recovered state.
- Terminal local state must not shrink the truth scope below the owner venues
  that participated in the selected lifecycle window.
- A final PASS may use terminal lifecycle evidence, but only after the
  exchange-truth probe covers the materialized trade scope or explicitly
  reports unavailable evidence.

### Fix

- Added `_exchange_truth_scope_from_events()` for diagnose-only scope recovery.
- The helper extracts symbols and venues only from materialized trading
  lifecycle events: entry open/abort, pending-entry lifecycle, order truth,
  passive-close/exit events, recovery flat, and runtime position lifecycle
  events.
- `run_diagnose()` now merges that event-derived scope with current local
  position scope before building read-only exchange truth.
- Explicit `--venues` remains authoritative for operator-scoped probes.

| local GREEN | same fixture after diagnose scope merge | passed with `symbols=["LABUSDT"]`, `venues=["aster","bybit","hyperliquid"]` |
| local regression | `tests/test_diagnose_live.py` | `199 passed` |

## Cluster CL-138 - Active Open Diagnostic Scope and Passive-Close Truth-Gap Lifecycle Mapping

Status: local verified; deploy pending.

### GitNexus Keys

  `terminal_drift_corrected_reblocked_during_new_active_owner`,
  `exit_accepted_order_truth_gap_resolved_unmapped`
- Components: `diagnose-live`, `production-gate`, `v1-lifecycle-closure`
- Symbols: `_build_production_acceptance_gate`,
  `_active_owner_managed_scope`,
  `_terminal_overhedge_corrections_closed`,
  `map_lifecycle_event_kind`
- Files: `scripts/diagnose_live.py`,
  `lightfee/engine/v1_lifecycle_closure.py`,
  `tests/test_diagnose_live.py`,
  `tests/engine/test_v1_lifecycle_closure_table.py`
- Watch: `entry_overhedge_drift_corrected_present`,
  `active_positions_with_capacity`,
  `terminal_overhedge_corrections_closed`,
  `exit.accepted_order_truth_gap_resolved`,
  `v1_lifecycle_closure.unmapped_event_kinds`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Production Symptom

The latest deployed production ultimately passed with exchange truth flat,
no open orders, no pending entry/close/reconciliation/residual work, and no
unresolved close accepted-order truth gaps. During the audit window, however,
an active managed `LABUSDT` position was briefly reported as a blocker even
though exchange truth showed a balanced Aster long `3.0` / OKX short `3.0`
with no open orders.

The same diagnose window also showed historical
`runtime.position_drift_corrected` evidence as
`entry_overhedge_drift_corrected_present` while a later unrelated active owner
was open. Separately, `exit.accepted_order_truth_gap_resolved` appeared in
`v1_lifecycle_closure.unmapped_event_kinds` despite the passive-close
truth-gap lifecycle being explicitly resolved.

### Root Cause

The active-owner diagnostic scope treated `matched_quantity=0` as no managed
owner even when the exported position still carried a positive `quantity`,
owner id, symbol, long venue, and short venue. That made a normal active
position less authoritative than the live exchange pair truth.

The production gate also counted every since-deploy
`runtime.position_drift_corrected` as a current overhedge blocker whenever the
account was not globally terminal flat. It did not first check whether the
same position id had already emitted terminal flat lifecycle evidence
(`runtime.position_lifecycle_terminal` plus `recovery.flat`).

Finally, the CL-135/CL-136 passive-close explicit resolved event was emitted
by runtime/diagnose but was not registered in the V1 lifecycle event-kind
mapping.

### V1 Decision

- A managed open position is owned by its position id, symbol, venues, and
  exchange-pair truth; a transient or serialized `matched_quantity=0` must not
  erase ownership when `quantity` and both venues are present.
- Historical drift-correction evidence is blocking only until the same owner
  reaches terminal flat proof. A terminal-flat owner is closure evidence, not a
  current live-artifact blocker.
- ACK is not fill, but an explicit passive-close accepted-order truth-gap
  resolved event belongs to the passive-close lifecycle phase and must not be
  unmapped.

### Fix

- `_active_owner_managed_scope()` now falls back to positive `quantity` when
  `matched_quantity` is absent or zero, while still excluding `live-recovered:*`
  owners from managed-active green paths.
- `_build_production_acceptance_gate()` now recognizes terminal flat
  overhedge-correction owners when every drift-corrected position also has
  `runtime.position_lifecycle_terminal` and `recovery.flat`.
- `exit.accepted_order_truth_gap_resolved` is mapped to the V1
  `PASSIVE_CLOSE` phase.

### Verification

| local RED | active LAB-style owner with `matched_quantity=0`, `quantity=3`, balanced Aster/OKX truth | failed to mark owner-scoped correction resolved |
| local RED | historical drift owner had terminal flat proof while a new active owner was open | failed by keeping `entry_overhedge_drift_corrected_present` |
| local GREEN | focused RED/GREEN tests | `3 passed` |
| local regression | lifecycle closure, diagnose, production health suites | `264 passed` |

  `_payload_is_bybit_terminal_zero_qty_reduce_only`,
  `_build_resolved_close_order_error_summary`,
  `close_order_error_resolution_contract`

  `tests/test_passive_close.py`, `tests/test_business_contract.py`,
  `tests/test_diagnose_live.py`
- Watch: `exit.passive_close_post_maker_fill_live_flat_precheck`,
  `exit.passive_close_hedge_error exchange_code=110017`,
  `resolved_close_order_error_summary.reduce_only_terminal_flat_count`,
  `order_error_evidence`, `residual_events_present`
- Card: [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Production Symptom

Latest deployed production was currently flat and had no open orders, pending
entries, pending passive closes, pending reconciliations, or residual repairs.
However `diagnose_live --since-deploy` still failed the final gate with
`residual_events_present`. The concrete residual was `POWRUSDT`
`exit.passive_close_hedge_error` from Bybit:
`110017 current position is zero, cannot fix reduce-only order qty`.

Runtime had Binance maker progress terminal filled for `469`, then attempted a
Bybit reduce-only hedge for `469`. Exchange truth later proved both legs flat
and no open orders, so this was not an abnormal live position. It was a
post-maker-fill closure semantic gap and a diagnostic terminal-flat
classification gap.

### Root Cause

V2 computed terminal maker fill hedge catch-up from local maker/hedge fill
accounting before rechecking current live position truth. In the POWR shape,
the hedge leg was already live-zero by the time the retry branch ran. The code
therefore submitted a reduce-only Bybit order against an already flat position,
which Bybit correctly rejected with `110017`.

The second gap was diagnostic/business-contract drift. Existing reduce-only
terminal-flat closure required order identity to match terminal order truth.
That is correct for normal reduce-only rejects, but Bybit `110017 current
position is zero` is a no-order terminal reject: there is no accepted order to
match. When current exchange truth is clean and the position lifecycle is
terminal flat, this specific reject should close by position terminal truth.

### V1 Decision

- ACK or reject is not fill. Exchange truth still outranks local state.
- After terminal maker fill, if live positions are already flat and open-order
  truth is empty, close the pending owner as terminal flat instead of sending a
  new hedge.
- If live position truth is flat but open-order truth is dirty or unavailable,
  retain fail-closed and retry truth; do not clear locally.
- Only Bybit reduce-only zero-position rejects may resolve by position
  terminal truth without order terminal identity. Generic reduce-only rejects
  still require strong order/client identity.

### Fix

- Added a post-maker-fill live-position precheck before hedge catch-up in
  `drive_pending_passive_close`.
- If both live legs are zero, runtime calls the existing live-flat/open-order
  terminal proof path and emits
  `exit.passive_close_post_maker_fill_live_flat_precheck`.
- If the hedge leg live size is lower than the local unhedged delta, hedge
  catch-up is clamped to current live hedge quantity.
- If the hedge leg is already zero while the maker leg remains nonzero,
  runtime retains the pending close instead of submitting a nonsensical hedge.
- Business contract and diagnose now recognize Bybit `110017 current position
  is zero` / `cannot fix reduce-only order qty` as a reduce-only
  terminal-flat reject that may resolve by position terminal truth when current
  exchange truth is flat and no open orders.

| local RED | Bybit `110017 current position is zero` with clean exchange truth and position terminal | failed before contract/diagnose fix with unresolved residual |
| local GREEN | focused passive-close, business-contract, diagnose tests | `4 passed` |
