### Production Symptom

The latest deployed production ultimately passed with exchange truth flat,
no open orders, no pending entry/close/reconciliation/residual work, and no
unresolved close accepted-order truth gaps. During the audit window, however,
an active managed `LABUSDT` position was briefly reported as a blocker even
though exchange truth showed a balanced Aster long `3.0` / OKX short `3.0`
with no open orders.

The same diagnose window also showed historical
`runtime.position_drift_corrected` evidence as
`entry_overhedge_drift_corrected_present` while a later unrelated active owner
was open. Separately, `exit.accepted_order_truth_gap_resolved` appeared in
`v1_lifecycle_closure.unmapped_event_kinds` despite the passive-close
truth-gap lifecycle being explicitly resolved.

### Root Cause

The active-owner diagnostic scope treated `matched_quantity=0` as no managed
owner even when the exported position still carried a positive `quantity`,
owner id, symbol, long venue, and short venue. That made a normal active
position less authoritative than the live exchange pair truth.

The production gate also counted every since-deploy
`runtime.position_drift_corrected` as a current overhedge blocker whenever the
account was not globally terminal flat. It did not first check whether the
same position id had already emitted terminal flat lifecycle evidence
(`runtime.position_lifecycle_terminal` plus `recovery.flat`).

Finally, the CL-135/CL-136 passive-close explicit resolved event was emitted
by runtime/diagnose but was not registered in the V1 lifecycle event-kind
mapping.

### V1 Decision

- A managed open position is owned by its position id, symbol, venues, and
  exchange-pair truth; a transient or serialized `matched_quantity=0` must not
  erase ownership when `quantity` and both venues are present.
- Historical drift-correction evidence is blocking only until the same owner
  reaches terminal flat proof. A terminal-flat owner is closure evidence, not a
  current live-artifact blocker.
- ACK is not fill, but an explicit passive-close accepted-order truth-gap
  resolved event belongs to the passive-close lifecycle phase and must not be
  unmapped.

### Fix

- `_active_owner_managed_scope()` now falls back to positive `quantity` when
  `matched_quantity` is absent or zero, while still excluding `live-recovered:*`
  owners from managed-active green paths.
- `_build_production_acceptance_gate()` now recognizes terminal flat
  overhedge-correction owners when every drift-corrected position also has
  `runtime.position_lifecycle_terminal` and `recovery.flat`.
- `exit.accepted_order_truth_gap_resolved` is mapped to the V1
  `PASSIVE_CLOSE` phase.

## Cluster CL-137 - POWRUSDT Post-Maker-Fill Live-Zero Hedge Closure

- Card: [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Production Symptom

Latest deployed production was currently flat and had no open orders, pending
entries, pending passive closes, pending reconciliations, or residual repairs.
However `diagnose_live --since-deploy` still failed the final gate with
`residual_events_present`. The concrete residual was `POWRUSDT`
`exit.passive_close_hedge_error` from Bybit:
`110017 current position is zero, cannot fix reduce-only order qty`.

Runtime had Binance maker progress terminal filled for `469`, then attempted a
Bybit reduce-only hedge for `469`. Exchange truth later proved both legs flat
and no open orders, so this was not an abnormal live position. It was a
post-maker-fill closure semantic gap and a diagnostic terminal-flat
classification gap.

### Root Cause

V2 computed terminal maker fill hedge catch-up from local maker/hedge fill
accounting before rechecking current live position truth. In the POWR shape,
the hedge leg was already live-zero by the time the retry branch ran. The code
therefore submitted a reduce-only Bybit order against an already flat position,
which Bybit correctly rejected with `110017`.

The second gap was diagnostic/business-contract drift. Existing reduce-only
terminal-flat closure required order identity to match terminal order truth.
That is correct for normal reduce-only rejects, but Bybit `110017 current
position is zero` is a no-order terminal reject: there is no accepted order to
match. When current exchange truth is clean and the position lifecycle is
terminal flat, this specific reject should close by position terminal truth.

### V1 Decision

- ACK or reject is not fill. Exchange truth still outranks local state.
- After terminal maker fill, if live positions are already flat and open-order
  truth is empty, close the pending owner as terminal flat instead of sending a
  new hedge.
- If live position truth is flat but open-order truth is dirty or unavailable,
  retain fail-closed and retry truth; do not clear locally.
- Only Bybit reduce-only zero-position rejects may resolve by position
  terminal truth without order terminal identity. Generic reduce-only rejects
  still require strong order/client identity.

### Fix

- Added a post-maker-fill live-position precheck before hedge catch-up in
  `drive_pending_passive_close`.
- If both live legs are zero, runtime calls the existing live-flat/open-order
  terminal proof path and emits
  `exit.passive_close_post_maker_fill_live_flat_precheck`.
- If the hedge leg live size is lower than the local unhedged delta, hedge
  catch-up is clamped to current live hedge quantity.
- If the hedge leg is already zero while the maker leg remains nonzero,
  runtime retains the pending close instead of submitting a nonsensical hedge.
- Business contract and diagnose now recognize Bybit `110017 current position
  is zero` / `cannot fix reduce-only order qty` as a reduce-only
  terminal-flat reject that may resolve by position terminal truth when current
  exchange truth is flat and no open orders.
