### Unified Business Contracts

The corrections deliberately close each business concern at one shared
boundary:

1. **Order preparation:** every live Aster order route prepares the same
   normalized `OrderRequest` through `VenueTransport.prepare_order_request`; no
   separate private-client rounding rule is introduced.
2. **Passive-close terminality:** `PassiveCloseExecutor` owns the single
   terminal zero-fill decision. Exchange execution history can upgrade a
   terminal response to a positive fill; only the explicitly safe terminal
   statuses can advance without that history.
3. **Recovery-owner projection:** one `PendingCloseOwnerCounts` projection
   supplies ordinary, passive, and total `pending_close_owner_count` values to
   lifecycle/decision logic, diagnose, production health, and explain output.
   A pending owner is never accepted as a green health state.

### Follow-up: Audited Historical Billing-Evidence Import

The four historical `evidence_debt` owners are now repairable through one
typed, replay-safe control-plane path rather than by a manual state edit or
four ad-hoc code paths:

1. `lightfee-ops import-billing-evidence` accepts exactly one owner tuple
   (`position_id`, `kind`, `closed_at_ms`) and only replaces an existing
   `evidence_debt` item.
2. The shared state gate requires the runtime-required position snapshot, explicit
   complete entry-fee evidence, and close-leg identities on both snapshot
   routes. It cannot create an owner, change its tuple, or guess missing facts.
3. The import writes `exit.billing_evidence_imported` with a canonical
   SHA-256 evidence digest. Recovery replays that event idempotently through
   the same state gate.
4. Import is not a financial close. The normal live runtime still queries the
   exchange using the supplied order/client-order IDs; only complete exchange
   fill evidence emits `exit.reconciled`.

The CLI accepts the deployed config's explicit `event_log_path` and
`snapshot_path`, so it cannot accidentally target a generic local `data/`
directory. `lightfee-live` and every mutating `lightfee-ops` command now share
one single-host writer lease derived from that event-log path: an operation
fails before any read or mutation while live trading owns the persistence pair.
The operation and evidence schema are documented in
`docs/ops/billing-evidence-import.md`.

The import event is explicitly journal-only: it appears in replay diagnostics
and cannot be mistaken for the exchange-backed terminal `exit.reconciled`
event. Local regression covers exact-owner replacement, strict entry-fee
rejection, durable/idempotent replay, explicit persistence paths, `--apply`
acknowledgement, every control-plane command's single-writer refusal, event
classification/timeline visibility, and the post-import exchange lookup by both
leg order/client-order IDs. No historical production owner has been changed by
this code correction; each remains evidence-debt until its audited exchange
export is supplied.

### Review Closure: Control-Plane Writer and Import Event Contract

The follow-up review found two bounded closure gaps, neither of which changes
live exchange positions by itself:

1. only `import-billing-evidence` held the writer lease, although every
   `lightfee-ops` command appends a critical journal record and rewrites the
   same snapshot; concurrent live runtime and operator control could therefore
   lose one side's persisted state;
2. `exit.billing_evidence_imported` replayed correctly through engine recovery,
   but was unclassified by the projection contract and absent from the replay
   diagnostic timeline.

The root repair has one boundary, not command-specific workarounds:

- `lightfee-ops` acquires the same lease as `lightfee-live` before it reads a
  snapshot, for every mutating subcommand, and releases it on normal exit and
  errors. It is consequently an offline maintenance control plane while live
  owns the persistence pair.
- The import event is registered as `journal_only` in both classification
  boundaries and included in the diagnostic timeline. It still cannot project
  as a financial close or replace exchange-backed reconciliation.
