### Root-Cause Decisions

| Finding | Root cause | Decision |
|---|---|---|
| Aster precision rejection | Aster's private V3 `place_order` and `submit_passive_order` called the private client directly. That bypassed the existing transport preflight and its dynamic `exchangeInfo` symbol rules. V1's Aster path obtains live symbol metadata, floors to the quantity step, validates the request, and aligns the price tick before submission. | Sufficient evidence for a root fix. Both Aster private paths and the generic Aster transport path now use one `VenueTransport.prepare_order_request` contract. Live mode rejects when exchange-backed rules are unavailable, incomplete, or non-finite; it never sends a static-fallback precision guess. Static fallback is no longer cached, so a temporary `exchangeInfo` outage can recover on the next admission attempt. |
| Bybit rejected zero-fill passive close loops | With an order ID, the Bybit reconciliation path queries execution history. A rejected order with no executions therefore returns no execution record. The executor treated that missing execution record as proof unavailable even though the terminal order status already proved `REJECTED` and zero fill. V1 treats rejected/canceled terminal order states as terminal, while still reconciling fills where they can exist. | Sufficient evidence for one terminal-status policy. `REJECTED` and `EXPIRED` with zero local fill now advance through the existing zero-fill phase fallback using typed terminal-status evidence. `CANCELED` still requires execution-history truth because it may have prior fills; `FILLED + 0 fill` remains a contradiction and fails closed. |
| Passive-close count invisible to gates | Compact state export omitted `pending_passive_close_count`; lifecycle closure, production health, and diagnose recovery each fell back to ordinary `pending_close_count`. A state with one passive-close owner and zero ordinary close owners was therefore reported as clean by some read-only gates. | Sufficient evidence for one state-contract fix. `PendingCloseOwnerCounts` is the shared ordinary + passive projection. No trading state machine or exchange state was changed. |
| Legacy invalid reconciliation records | The records are missing venue-snapshot identity needed to determine which close leg/order they represent. The active queue is already empty, and current exchange truth is balanced. | Diagnosis is sufficient; mutation is not. Do not backfill venue identities from symbol, time, or quantity guesses. Preserve the records as legacy evidence and require a future record with complete venue/order identity before adding a repair migration. |
| Aster/TRUTH stale quote | The observed data proves staleness and rewarm outcomes, but not whether the root is upstream REST freshness, WS-BBO lease ownership, subscription coverage, or symbol mapping. | Evidence insufficient for a root fix. Keep stale quotes fail-closed and collect the next rewarm's source, timestamp, age, response, and symbol-mapping evidence. No TTL, admission, OI, liquidity, or strategy threshold is changed. |

### Unified Business Contracts

The corrections deliberately close each business concern at one shared
boundary:

1. **Order preparation:** every live Aster order route prepares the same
   normalized `OrderRequest` through `VenueTransport.prepare_order_request`; no
   separate private-client rounding rule is introduced.
2. **Passive-close terminality:** `PassiveCloseExecutor` owns the single
   terminal zero-fill decision. Exchange execution history can upgrade a
   terminal response to a positive fill; only the explicitly safe terminal
   statuses can advance without that history.
3. **Recovery-owner projection:** one `PendingCloseOwnerCounts` projection
   supplies ordinary, passive, and total `pending_close_owner_count` values to
   lifecycle/decision logic, diagnose, production health, and explain output.
   A pending owner is never accepted as a green health state.

### V1 and Exchange References

- V1 Aster order semantics: `LightFee/src/live/aster.rs` (dynamic metadata,

- V1 passive-close terminal handling: `LightFee/src/live/bybit.rs` and the V1

## Cluster CL-098-close-reconciliation-owner-contract-and-aster-v3-evidence

### 11:43 Re-audit Correction

This section supersedes this document's earlier **Reconciliation queue** row
and its conclusion that legacy reconciliation evidence was inactive. The later
read-only production check found the exchange account flat with no open orders
on all seven venues, but the durable full state still carried four COTI
`final` reconciliation owners. The compact current-state export omitted both
the queue and its summary, so `diagnose_live` and production-health read zero
and returned a false-clean result.

| Finding | Direct evidence | Decision |
|---|---|---|
| False-green close state | Full `live-state.json`: four final COTI reconciliation tasks, attempts `125`–`156`; compact `live-state-current.json`: no reconciliation summary and all close counts zero. | Root cause proven. Export and consume one close-work owner contract that includes ordinary closes, passive closes, and reconciliation. |
| Infinite legacy reconciliation retry | Each of the four owners lacks typed routing and/or durable close-leg identity. Repeating venue execution-history polling cannot recover facts that are absent from the task itself. | Root cause proven. Classify once as persistent `evidence_debt`; retain and block business closure, rather than back off forever or delete the record. |
| Runtime lifecycle while debt exists | V1 recovery keeps background reconciliation work visible but permits `RUNNING` when active positions are gone, unless fail-closed was requested. | Compatibility rule. Health/acceptance must be non-green, but this bookkeeping debt alone must not manufacture a trading `RISK_ONLY` transition. |
| Aster generic HTTP 400 | Two post-01:18 Aster order failures carried HTTP 400 but no exchange code/body in the available journal evidence. | Root cause not proven. Do not ascribe it to precision, credentials, symbol, or price. Add exact V3 response/rule evidence on the common private-order submit boundary. |

### Unified Root Fix

1. `PendingCloseOwnerCounts` is now the only close-work projection: ordinary,
   passive, and reconciliation owners feed current-state export,
   `diagnose_live`, production health, recovery decisions, and explain output.
   A compact snapshot now carries both
   `pending_close_reconciliation_count` and its summary.
2. `RecoveryLedger` is the only recovery-work source for that projection. Every
   core-decision boundary (startup, restart replay, passive-close completion,
   passive-close tick, residual-repair completion, diagnose, and health) now
   receives the same non-blocking `pending_close_reconciliation` work item.
   Its single core outcome is `background_close_reconciliation`: visible as a
   warning and non-green acceptance state, but not a global entry block. The
   existing candidate-level ledger gate still protects the same symbol/venue
   while accounting evidence is incomplete.
3. A final/partial reconciliation task is validated against the V1 typed-task
   contract before retry. Missing position ID, symbol, venue routing, or
   required close-order identity transitions once to `evidence_debt` with an
   operator action. It remains durable and non-green, and a later complete
   task may replace it; no guessed venue/order data is created.
4. `exit.billing_evidence_debt_registered` is projected as an entry/exit audit
   fact and unreconciled-billing signal, never as a physical close terminal;
   replay preserves the reconciliation owner.
5. Both Aster V3 aggressive and passive private submissions use one diagnostic
   emitter. It records the existing exchange-rule preflight plus HTTP status,
   response body when supplied, and submit class. This adds evidence only; it
   does not change order parameters or relax any admission rule.

### Final Release Review (Before Deployment)

The final code review found no additional P0/P1 defect in the unified
close-owner contract. In particular, the decision order still gives exchange
non-zero positions, open orders, unpaired live exposure, actual recovery work,
and operator fail-closed mode precedence over background close-accounting
reconciliation. The latter therefore cannot hide an abnormal live position or
open a conflicting same symbol/venue trade; it only avoids manufacturing a
global entry block for a proved-flat accounting debt.

the live-flat close-cleanup path. Journal replay consequently clears the local
terminal close owner while retaining the reconciliation owner. This matches the
event producer's live-flat invariant and is covered by restart/replay tests.
