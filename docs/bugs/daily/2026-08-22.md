## Cluster CL-118-unattributed-exchange-close-provenance

### Status

**Deployed on `1e66dc1`; production acceptance passed, but the specific
unattributed-leg scenario has not yet reoccurred, so this cluster is not
closed.**

The change is intentionally accounting/provenance-only.  It does not submit,
cancel, amend, or reconstruct an exchange order, and it does not mutate the
two historical evidence debts.  Production exchange truth remains the authority
for physical exposure.

### Observed Production Facts

The post-deploy ONG lifecycle was an `entry-*` V2 position.  Binance carried a
durable V2 close identity, while Bybit reported the short leg flat before V2 had
recorded any close order/client identity for that leg.  Read-only Bybit history
showed a reduce-only fill with an empty `orderLinkId`; V2 had no matching close
intent.  Both venues later had trusted flat position and open-order truth.

The original runtime handled the safety outcome correctly: it cleared the
physical position only after trusted exchange-flat proof and retained a final
accounting debt rather than inventing close PnL.  It nevertheless recorded the
case only as `missing_close_order_identity`, indistinguishable from an ordinary
legacy, ACK, or persistence identity gap.

### Authoritative Contract

V1 passive-close/recovery semantics make exchange truth authoritative for live
exposure, while unresolved close evidence remains a durable accounting owner.
Bybit's `orderLinkId` is a client-supplied correlation value, not an identity
that V2 may infer from symbol, side, time, or quantity.  Therefore, when
trusted live-flat truth observes a V2-owned position with a close leg that has
no local durable close identity, V2 must:

1. terminalize physical position state only from the existing trusted-flat
   proof;
2. retain a non-retryable accounting evidence debt for that V2 position;
3. record exactly which leg is exchange-observed but unattributed; and
4. require an exact operator evidence import before calculating or publishing
   a final close result.

`unattributed_exchange_execution` means “V2 cannot attribute this observed
exchange execution to a recorded V2 close intent.”  It does **not** claim a
specific external actor, and it does not authorize automatic matching.

### Root Cause and Shared Boundary

When a trusted live-flat observation followed a V2-owned passive close with a
missing close-leg identity, `PassiveCloseExecutor` collapsed that observed
unattributed leg into the generic `missing_close_order_identity` reason.  The
physical safety invariant held, but the first boundary that simultaneously has
trusted flat truth, V2 ownership, and both close-leg records discarded the
provenance required for diagnosis and audited remediation.  Earlier tests only
asserted fail-closed retention, so they did not distinguish this family from a
generic identity gap.

The repair changes the single live-flat reconciliation registration boundary:

```text
trusted positions + trusted empty open orders
  -> PassiveCloseExecutor live-flat registration
  -> durable reconciliation.unattributed_exchange_close_legs
  -> CloseRuntime evidence debt: unattributed_exchange_execution
  -> exact operator evidence import or retained debt
```

The generic debt path remains unchanged for records that do not originate from
this trusted live-flat observation.  Existing `live-recovered:*` pairs remain
the stricter `external_unattributed` recovery contract: they are not V2-owned
positions and must not be converted into a V2 debt.

### Counterexample Matrix

| Case | Required result |
|---|---|
| trusted flat; both V2 close legs have durable identities | ordinary identity reconciliation; no unattributed-leg marker |
| trusted flat; V2 long identity exists; short identity is absent | retain the V2 final owner; marker is `short`; debt reason is `unattributed_exchange_execution` |
| trusted flat; neither V2 close leg has an identity | retain both legs as unattributed evidence; never infer either fill |
| missing/failed position or open-order truth | retain pending physical state; do not register terminal reconciliation or provenance |
| complete prior partial supplies the missing final identity | CL-117 transfers the identity into one final owner; no unattributed-leg marker |
| `live-recovered:*` with no V2 entry/close identity | existing external-recovery audit path, not a V2 accounting debt |
| exact imported identities and fills for every required leg | import may replace the debt; runtime reconciles from those exact identities |
| matching symbol, side, time, or quantity only | never treated as an owned close identity |

## Cluster CL-119-terminal-close-debt-entry-gate-semantics

### Status

**Closed in production on `0474ca28` after three production REDs and the shared
order-contract root repair.**

This is a compatibility regression exposed by the post-CL-118 review.  The
historical COTI/ONG accounting debts are not themselves new positions or new
exchange incidents; they are the production examples that made the regression
permanent and observable.

Because this owner/gate family had already passed multiple fix/review cycles,
the root-cause protocol circuit breaker was applied: no additional point gate
was added.  The lifecycle, pair-gate, compact-state, health, and deployment
contracts were re-derived together before editing.

### Contract and Root Cause

V1 separates two decisions:

- the recovery lifecycle may remain `Running` when the only remaining work is
  close-accounting reconciliation; and
- unresolved physical close work may still block its matching pair.

V2 had three competing owners for that distinction: the recovery core, the
`RecoveryLedger`, and a direct `_gate_pending_close_reconciliation` predicate
called at multiple dispatch points.  The direct predicate treated terminal
`evidence_debt` exactly like retryable/missing close execution evidence.  Once
a physically flat record became a non-retryable debt, the matching pair could
therefore remain disabled forever even though no live position or order
existed.  Conversely, the ledger had classified every close reconciliation as
nonblocking, including active or truth-unavailable records.  The two errors
masked each other and could drift by call path.

The shared contract is now:

| Evidence | Runtime lifecycle | Matching-pair entry |
|---|---|---|
| active/missing/unknown close evidence, with no earlier account-wide live-artifact latch | may remain running with visible background close work, matching V1 | blocked |
| active/missing/unknown close evidence while an earlier account-wide live-artifact latch remains | risk-only until complete account truth can clear that latch | blocked |
| target-pair exchange truth missing or incomplete | cannot prove terminal debt releasable; it cannot clear an account-wide latch | blocked |
| `evidence_debt` plus high-confidence flat/no-open-order truth | running with accounting warning | allowed |
| any nonzero position or open order | managed recovery/risk state | blocked |

`RecoveryLedger` is the sole pair-scoped owner.  The duplicate direct gate and
its runtime/context forwarding surface were removed.  The recovery core owns
only global lifecycle classification and reconstructs compact summarized debt
without silently converting unknown records into background debt.
`pending_close_reconciliation` is scoped to the unordered exact venue pair:
reversing long/short venues is the same pair, while the same symbol on a
different complete venue pair is not blocked.  A missing venue identity fails
closed for that symbol.

The review also found that owner-count or method-entry fingerprints were not a
valid cache-invalidation contract.  A previous runtime lane could add a close
or residual owner, and the next processor could leave it unchanged; comparing
only that processor's before/after state missed the new owner.  The cached
ledger now records the close/residual semantic fingerprint from the instant it
is built.  Close reconciliation, passive close, normal exit, residual repair,
and pending-entry residual queuing all compare current owner semantics with
that ledger-build snapshot in `finally`/synchronous production boundaries.
This covers owner addition, active-to-debt transition, and terminal removal,
including exceptions, before another candidate can consume the cache.

This repair does **not** explain every no-entry scan in the observed deployment
window: most candidates were still rejected by funding/expected-edge/worst-case
strategy thresholds.  It closes the proven code path that could permanently
exclude COTI/ONG-equivalent pairs.

### Post-deploy circuit-breaker finding

Commit `2377193c` deployed the first CL-119 repair, but the first production
closure table disproved its claimed semantic closure.  Runtime reported
`entry_allowed=true` globally while both COTI/ONG
`pending_close_reconciliation` rows still had `blocking=true` and
`entry_policy=block_conflicting_new_risk`.  Exchange truth remained flat with
no open orders, so this was not historical exposure, a venue rejection, or a
strategy-threshold outcome; it was a same-family code regression.

The exact mechanism was a producer/consumer contract split.  The live recovery
producer emits symbol-scoped truth as `truth_scope`, `truth_supported`,
`truth_available`, `positions`, `open_orders`, `probe_evidence`, and `errors`.
The first repair's ledger predicate and tests instead required the diagnostics
projection `confidence=high`, `has_nonzero_position`, and `has_open_order`.
Those keys never exist on the live producer path, so a real runtime refresh
could never reclassify terminal flat debt as nonblocking.  Diagnostics-shaped
fixtures made the first implementation falsely green.

The repair-loop circuit breaker was therefore applied again.  The new shared
recovery-core predicate consumes both real contracts without guessing:

- account-wide truth remains the only evidence allowed to clear a historical
  account-level live-artifact latch;
- diagnostics truth remains account-wide and must be high-confidence,
  flat/no-order, and free of partial evidence;
- runtime symbol truth may release only the exact debt symbol and unordered
  two-venue pair after both position and open-order probes succeed, both
  position rows are finite zero, and no matching order exists;
- a target-pair timeout, unsupported/missing probe, malformed quantity,
  nonzero position, open order, missing venue/symbol identity, or contradictory
  unavailable result remains fail-closed;
- a located probe failure for a different symbol/venue does not widen this
  pair-scoped debt gate.  Any concrete unrelated live artifact is still
  classified separately by `RecoveryLedger`.

RED used the actual `_collect_recovery_ledger_exchange_truth()` output and
failed through both the ledger and live collector → closure → candidate-gate
path.  GREEN covers the exact release plus the complementary fail-closed
matrix and unrelated-probe isolation.  The focused adjacent recovery,

## Cluster CL-121-targeted-oi-refresh-rate-limit-causality

### Status

**Deployed in `2377193c`; awaiting a natural targeted-OI success or 429 sample.**

This is a newly confirmed market-data/diagnostic defect.  Production recorded
an Aster HTTP 429 while refreshing candidate OI, but the entry layer reported a
timeout.  The candidate still failed closed, so there is no erroneous-order or
exposure evidence; the defect hid the actual reason for a skipped opportunity
and made rate-limit remediation unreliable.

### Authoritative Contract and Root Cause

The targeted OI method reused the full Binance-style funding-ticker collector.
That collector first requested book ticker, premium index, and 24-hour ticker
data before OI.  A 429 from any preceding endpoint aborted the broad call, and
the outer refresher collapsed the exception into timeout.  A method named
“targeted OI refresh” therefore multiplied request weight and did not preserve
the exchange failure type.

The official [Binance USD-M Open Interest endpoint](https://developers.binance.com/docs/derivatives/usds-margined-futures/market-data/rest-api/Open-Interest)
is a symbol-scoped `GET /fapi/v1/openInterest`; the official
[Binance rate-limit contract](https://developers.binance.com/docs/derivatives/usds-margined-futures/general-info)
requires backing off on 429.  Aster's official
[V1 futures API document](https://github.com/asterdex/api-docs/blob/master/V1%28Legacy%29/EN/aster-finance-futures-api.md)
likewise defines IP-weighted limits, 429/418 handling, and backoff.  The
runtime must therefore preserve 429 and retry metadata, not call it timeout.

The repair makes the candidate path call only the per-symbol OI endpoint, uses
the already-owned snapshot mark price for quote conversion, keeps the existing
client limiter/cache/budget, and returns typed `rate_limited`, `http_error`,
`timeout`, `parse_error`, `unsupported`, or `available` evidence.  HTTP status
and `Retry-After` are carried through transport, refresher, runtime counters,
and the failed-refresh journal event.  All unavailable outcomes remain
fail-closed; no OI threshold, TTL, strategy threshold, or order behavior was
relaxed.  The client and both runtime fallbacks consume one shared error-to-OI
status classifier, and a no-target scan publishes zeroed OI fault counters so a
prior 429/timeout is not reported as a current-scan failure.

RED reproduced the unwanted book/premium/24h fanout and missing 429 metadata.
GREEN proves only `/fapi/v1/openInterest` is called, mark price is reused, and
429 appears as `rate_limited` with HTTP status/retry-after in the real runtime
event while the candidate remains blocked.
