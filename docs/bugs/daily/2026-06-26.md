- Card: [pending-entry-hedge-admission](../cards/pending-entry-hedge-admission.md)

### Production Symptom

After CL-120, current production trading truth was clean: account truth could be
funded, endpoint-zero was no longer treated as wallet capacity, real Aster
`-5018` rejects were symbol-scoped, and LAB sub-step rejects reported the
correct `1 LAB` minimum/step. The remaining issue was in since-deploy
diagnostics: `runtime.entry_admission_headroom_advisory` could still appear in
`production_acceptance_gate.v1_lifecycle_closure.unmapped_event_kinds`.

### Root Cause

Runtime and diagnose already used the new CL-120 business meaning:
`remainingOpenableNotionalValue=0` can be advisory when account truth, position
truth, and open-order truth prove submit is allowed. The V1 lifecycle closure
mapping table did not include the new runtime event, so the production gate saw
a historical advisory artifact as unmapped residue. The admission bug card also
still carried the older CL-115 rule that Aster max-notional evidence should arm
venue-scope cooldown, which drifted from the CL-120 scope contract.

### Fix

- Map `runtime.entry_admission_headroom_advisory` to `DIAGNOSTIC_ONLY` in the V1
  lifecycle closure table.
- Add lifecycle regression coverage so the event is absent from
  `unmapped_event_kinds`.
- Add a diagnose since-deploy regression for Aster advisory-zero account truth:
  `reason_counts.aster_headroom_advisory_zero == 1`, `scope_counts.none == 1`,
  and lifecycle `unmapped_event_kinds == []`.
- Update the admission card: Aster endpoint-zero is advisory with sufficient
  account truth; real `-5018` is `aster:SYMBOL`; `aster:*` is allowed only for
  account-level balance insufficiency, account-level permission/auth failure, or
  venue-wide private-truth unavailability.

## Cluster CL-122 - Pending-Entry Hedgeability and Gate Contract-Unit Closure

Status: code fix `641d166` deployed/cloud verified; final docs sync also
deployed.

### GitNexus Keys

- Fingerprint: `gate_progress_contracts_as_base + bybit_hedge_min_notional_pre_submit_gap + cleanup_filled_without_fresh_flat_truth`
- Components: `gate-transport`, `gate-private-ws`, `entry-dispatch-runtime`, `pending-entry-cleanup`, `diagnose-live`, `v1-lifecycle-closure`
- Symbols: `_parse_passive_order_progress`, `handle_gate_private_message`, `_dispatch_entry`, `_cleanup_failed_leg_exposure`, `map_lifecycle_event_kind`, `_build_business_progression_quality_summary`
- Files: `lightfee/venues/transport.py`, `lightfee/venues/gate_private_ws.py`, `lightfee/engine/entry_dispatch_runtime.py`, `lightfee/engine/runtime.py`, `scripts/diagnose_live.py`, `lightfee/engine/v1_lifecycle_closure.py`
- Watch: `runtime.entry_blocked_pre_submit_hedgeability`, `runtime.entry_pre_submit_hedgeability_advisory`, `entry.cleanup_leg_exposure_truth_blocked`, `maker_fill_increment_below_hedge_min_chunk`, `maker_cleanup_position_still_live_after_reduce_only`
- Card: [pending-entry-hedge-admission](../cards/pending-entry-hedge-admission.md)

### Production Symptom

SIRENUSDT showed a pending-entry path where Gate maker progress/fill evidence
and Bybit hedge min-notional handling disagreed. The visible result looked like
“Bybit hedge not filled / missing hedge below minimum notional,” but that was a
secondary symptom: some Gate progress paths reported contract counts into the
engine, while pending-entry business logic expects base quantity. Cleanup also
trusted a reduce-only IOC filled result too strongly before fresh flat position
truth was re-proved.

### Root Cause

Engine canonical quantity is base quantity. Gate order submit already converted
base to contract size and some REST fills were converted back to base, but Gate
passive progress and private WS order/position updates could still pass raw
contract counts into pending-entry maker progress. That made missing-hedge and
min-notional comparisons drift. Separately, `_cleanup_failed_leg_exposure`
treated a reduce-only fill covering target quantity as cleanup success without
requiring a fresh flat position probe, which could release pending-entry owner
state before exchange terminal truth was proven.

### Fix

- Gate REST passive progress converts `fill_total` contract count to base using
  cached contract multiplier; missing multiplier fails closed instead of using
  raw contracts as base.
- Gate private WS order and position handlers accept a contract multiplier map
  and convert `fill_total`/`size` to base at the adapter boundary.
- Add `StrategyConfig.pending_entry_pre_submit_hedgeable_fill_guard_enabled`
  default `true`. When enabled, passive maker submit is blocked if the smallest
  observable maker fill increment is below the hedge venue minimum hedgeable
  chunk or maker unit truth is unavailable. The blocker is symbol/candidate
  scoped, not venue-wide.
- When the guard is disabled, runtime keeps the old submit path but records
  `runtime.entry_pre_submit_hedgeability_advisory` with unit evidence.
- Cleanup now treats reduce-only fills as execution evidence only; fresh flat
  position truth is required before cleanup success/owner release.
- V1 lifecycle and diagnose now map/count pre-submit hedgeability blockers,
  disabled-guard advisories, and cleanup fresh-truth blockers.
