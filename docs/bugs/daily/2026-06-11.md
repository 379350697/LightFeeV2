## Cluster CL-070: 8 concurrent active-position capacity and scoped pending-close gate closure

### GitNexus Keys

- Fingerprint:
  `eight-concurrent-active-position-capacity-and-scoped-pending-close-gates`
- Components:
  `live-runtime`, `entry-selection`, `entry-dispatch`, `diagnose-live`,
  `production-observability`, `v1-parity`
- Symbols:

- Watch:
  `max_concurrent_positions`,
  `open_position_count`,
  `remaining_slots`,
  `active_positions_with_capacity`,
  `open_positions_exceed_configured_max`,
  `pending_close_reconciliation_conflict`,
  `passive_close_in_flight`

### Production Symptom

After deploy, one normal balanced active position could be interpreted by
diagnostics as `risk=high`/acceptance-gate blocking evidence. That drifted from
the intended production behavior: around settlement, multiple independent
positions can run concurrently, and the configured production capacity is 8.
A normal double-leg position is not itself an abnormal warehouse state.

### Root Cause

The runtime entry path already computed remaining capacity and skipped only the
same active symbol during selection. The pending close guards were also scoped
to matching symbol plus venue pair. The gaps were around evidence and tests:

- Diagnose could treat any active position as a high-risk production acceptance
  problem instead of distinguishing normal active lifecycle from single-leg,
  exchange/local mismatch, open-order residue, or over-capacity.
- Side values such as `Side.BUY`/`Side.SELL` could fail normalization and make a
  balanced position look mismatched.
- `last_scan` / `scan.no_entry_diagnostics` did not expose the slot context
  needed to explain whether no-entry came from capacity, candidate quality, or a
  code/data blocker.
- Regression coverage did not prove that an existing healthy position with
  spare slots still allows another symbol to select and dispatch, or that
  pending close/reconciliation gates do not spread globally.

### Source Truth

- V1 and prior production semantics allow several independent settlement-cycle
  positions to coexist until the configured max position count is reached.
- In V2, `can_enter_new_positions()` is lifecycle/risk-mode based; capacity is
  enforced separately by `remaining_slots = max_concurrent_positions -
  open_positions`.
- `_select_entry_candidates()` uses remaining slots and only suppresses
  candidates whose symbol is already active or pending entry.
- `_gate_pending_close_reconciliation()` and `_gate_passive_close_pending()`
  are same-symbol, same-venue-pair safety gates. They should prevent reopening
  the pair being closed, not put the entire engine into single-position mode.

### Fix

- `scripts/diagnose_live.py` now classifies healthy balanced active positions
  within `max_concurrent_positions` as active lifecycle/capacity evidence
  instead of high-risk abnormal state.
- Diagnose side matching now normalizes enum-style sides such as `Side.BUY` and
  `Side.SELL`.
- `lightfee/engine/runtime.py` and `lightfee/engine/loop_control.py` expose
  `max_concurrent_positions`, `open_position_count`, and `remaining_slots` in
  current state and no-entry diagnostics.
- `tests/test_runtime_entry_flow.py` now proves:
  - 1 healthy active position with `max_concurrent_positions=8` still selects
    and dispatches another symbol.
  - A pending close reconciliation blocks only the matching symbol/venue pair.
  - A pending passive close blocks only the matching symbol/venue pair.

### Non-Changes

- No strategy threshold change.
- No OI or liquidity filter change.
- No margin/admission relaxation.
- No WS-BBO budget or TTL increase.
- No production config change.
- No order submit, cancel, or runtime state mutation was used for the local
  fix.

## Cluster CL-069: Hyperliquid unified collateral diagnostic closure

### GitNexus Keys

- Fingerprint:
  `hyperliquid-unified-account-collateral-diagnostic-false-blocker`
- Components:
  `hyperliquid`, `diagnose-live`, `offline-analysis`, `exchange-truth`,
  `v1-parity`, `exchange-docs`
- Symbols:
  `_fetch_hyperliquid_balance_view`,
  `_hyperliquid_balance_view_payload`,
  `fetch_account_balance_snapshot`,
  `build_code_side_blocker_view`
- Watch:
  `runtime.entry_admission_venue_degraded reason=insufficient_margin_admission_prefiltered`,
  `classification=unified_collateral_available`,
  `userAbstraction=unifiedAccount`,
  `spotClearinghouseState`,
  `orderStatus=perpMarginRejected`

### Production Symptom

After the no-entry blocker view was added, Hyperliquid could still appear as
an account/admission blocker when `perp withdrawable=0` but spot USDC was
available. For a unified Hyperliquid account, that is misleading: the correct
next checks are trading preflight, candidate freshness, and final exchange
reject truth.

### Root Cause

V2 transport already had the safer account-admission behavior:

- Query the configured Hyperliquid account address, not the signer/API wallet
  address.
- Read `clearinghouseState` first.
- If `withdrawable<=0`, query `userAbstraction`.
- Only when `userAbstraction == unifiedAccount`, query
  `spotClearinghouseState` and use available USDC as admission collateral.
- Keep non-unified accounts fail-closed and do not treat spot balances as perp
  collateral.

The remaining drift was diagnostic. `diagnose_live.py` did not query
`userAbstraction`, so `withdrawable=0 + spot USDC>0` was still classified as
`usdc_present_margin_view_zero`, and the offline code-side view could still
count matching samples as `account/admission` blockers after strategy plus
OI/liquidity were excluded.

### Source Truth

- V1 Hyperliquid live adapter resolves and stores the configured
  `account_address`, then uses that actual account address for user state and
  order-status queries. That preserves the same safety boundary: account truth
  is not read from the signer/agent wallet identity.
- Hyperliquid official docs say info endpoint user data queries must pass the
  actual master/sub-account address, and warn that using an agent wallet
  address returns an empty result.
- Hyperliquid official `orderStatus` docs expose final exchange reject truths,
  including `perpMarginRejected` for insufficient margin. A real reject still
  wins over any local admission estimate.

### Fix

- `scripts/diagnose_live.py` now queries `userAbstraction` before building the
  Hyperliquid balance view.
- `unifiedAccount + spot USDC available + perp withdrawable zero` is classified
  as `unified_collateral_available`, with `spot.usdc_available` and
  `user_abstraction` included in sanitized diagnostics.
- The production acceptance gate no longer increments
  `hyperliquid_margin_view_zero_count` for unified collateral. It records
  `hyperliquid_unified_collateral_available_count` and emits advice to check
  trading preflight, candidate freshness, and exchange reject truth instead of
  suggesting manual collateral movement.
- `scripts/analyze_production_blockers.py --exclude-strategy
  --exclude-liquidity` subtracts Hyperliquid unified-collateral samples from
  `account/admission` blocker counts.
- `tests/test_venues_transport.py` adds a guard proving non-unified accounts
  do not read spot USDC for perp admission.
- `AccountBalanceSnapshot` now carries optional `balance_classification`,
  `user_abstraction`, and `spot_usdc_available`; Hyperliquid transport fills
  those fields from the unified-collateral resolver, and runtime
  `insufficient_margin_admission_prefiltered` samples preserve them for
  diagnose/offline analysis.
- Runtime admission reject classification recognizes official Hyperliquid
  terminal statuses `perpMarginRejected` and `insufficientSpotBalanceRejected`
  as exchange-truth insufficient-margin admission blocks with no evidence gap.

### Non-Changes

- No strategy thresholds changed.
- No OI/liquidity filters changed.
- No production config, runtime state, restart, deployment, order submit, or
  order cancel was performed.
- No signer/API wallet is treated as the account truth address.
- No local balance estimate overrides a later official exchange rejection such
  as `perpMarginRejected`.

## Cluster CL-068: Code-side no-entry blocker attribution closure

### GitNexus Keys

- Fingerprint:
  `post-deploy-one-open-code-side-blocker-attribution-gap + strategy-oi-liquidity-filtered-view`
- Components:
  `production-observability`, `diagnose-live`, `offline-analysis`, `ws-bbo`,
  `snapshot-freshness`, `recovery-probe`, `passive-close`, `v1-parity`,
  `exchange-docs`
- Symbols:
  `analyze_event_file`, `build_code_side_blocker_view`, `run_diagnose`
- Watch:
  `runtime.snapshot_freshness_decision reason=invalid_quote`,
  `entry_ws_bbo_quote_lease_budget_exhausted`,
  `recovery.live_position_bulk_diagnostic_error`,
  `runtime.live_scan_revalidate_required`,
  `exit.passive_close_hedge_ack_pending_reconcile`,
  `accepted_order_truth_gap`,
  `code_side_blocker_view`

### Production Symptom

The read-only production review for the previous deployment window found one
actual opened position and two KATUSDT entry attempts. After excluding strategy
gates and OI/liquidity filters, the remaining code-side evidence was not a
single open-blocking bug:

- `invalid_quote` dominated snapshot freshness blockers.
- `entry_ws_bbo_quote_lease_budget_exhausted` appeared as WS-BBO subscription
  budget evidence for a small number of candidates.
- `recovery.live_position_bulk_diagnostic_error` mostly represented best-effort
  bulk position probe timeouts, not required exchange truth failure.
- `runtime.snapshot_fallback_last_good` and
  `runtime.live_scan_revalidate_required` showed last-good sidecar revalidation
  paths.
- Bybit passive close returned ACK-only order acceptance before later exchange
  truth proved flat.

### Root Cause

The trading path already preserves the important V1/exchange semantics:

- Bybit create-order ACK-only is not a fill. The accepted ids must be
  reconciled through order status, executions, private WS, or live flat/no-open
  order truth.
- Invalid/crossed/zero quotes remain fail-closed. Only stale quote evidence may
  be resolved by fresh WS-BBO evidence.
- Best-effort bulk position probe failures are diagnostic health evidence
  unless required position truth has no fallback.

The remaining gap was attribution: production tools could show large no-entry
counts, but did not provide a first-class view that filtered strategy plus
OI/liquidity blockers and grouped only code/data-path evidence. That made
small code-side issues look like the primary reason for six to seven hours of
low opens, even when strategy/OI/liquidity/account filters were the larger
contributors.

### Fix

- `scripts/analyze_production_blockers.py` now accepts
  `--exclude-strategy` and `--exclude-liquidity`.
- The analyzer emits `code_side_blocker_view` with:
  `code_data_freshness`, `ws_bbo_budget`, `exchange_truth_probe`,
  `order_truth_gap`, and `account/admission` categories.
- OI is filtered with liquidity under `--exclude-liquidity`, but reported as
  its own `open_interest` filtered bucket.
- `scripts/diagnose_live.py` now exposes the same view through optional
  `code_side_blockers` / CLI filter parameters without changing health,
  production acceptance gate, exchange truth, or conclusion behavior.
- The shared code-side classifier treats nonblocking bulk probe timeouts as
  `exchange_truth_probe` evidence, not as a production gate failure.
- Review hardening fixed three diagnostic accuracy edges: disabled default
  views now stay empty, `runtime.snapshot_fallback_last_good` contributes to
  code/data freshness, and total fields are not double-counted with breakdown
  fields.

### Non-Changes

- No strategy thresholds changed.
- No OI/liquidity filters changed.
- No WS-BBO budget or TTL was increased.
- No Bybit ACK-only response is treated as a fill.
- No production config, runtime state, order submit, order cancel, restart, or
  deployment was performed for this local fix.
