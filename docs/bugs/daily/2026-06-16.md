## Cluster CL-091: Passive close terminal truth order-error and lifecycle drift

### GitNexus Keys

- Fingerprint:
  `post-cl090-passive-close-terminal-truth-order-error-lifecycle-drift`
- Components: `diagnose-live`, `v1-lifecycle-closure`,
  `production-acceptance-gate`, `bug-ledger`
- Watch: `resolved_close_order_error_summary`,
  `order_error_evidence`, `top_exchange_errors`,
  `v1_lifecycle_closure.unmapped_event_kinds`,
  `production_acceptance_gate.gate_passed`

### Summary

Post-CL-090 deployment review found production truth healthy: services were
green, exchange truth was flat/no-open-orders, and there was no abnormal
position, single-leg exposure, or open-order residue. The remaining drift was
diagnostic closure for one HOMEUSDT passive close lifecycle.

The close chain had terminal flat evidence, but diagnose still listed three
historical close-order artifacts as unresolved:

- Binance passive maker close `-5022` Post Only boundary reject with
  `post_only=true` and `reduce_only=true`.
- Binance reduce-only close `-2022 ReduceOnly Order is rejected.`
- A same-leg zero-fill uncertainty later followed by terminal reduce-only flat
  evidence.

The same since-deploy window also exposed close lifecycle events that had not
yet been mapped into the V1 lifecycle closure table:
`exit.retry_wait`, `exit.close_chunk_submitted`,
`exit.close_residual_detected`, and `exit.closed`.

### Root Cause

This was not an exchange-position problem. The root cause was that V2 had
separate diagnostic buckets for entry post-only boundary rejects, Bybit ACK
truth gaps, terminal zero-quantity reduce-only evidence, and residual repair,
but no unified close-terminal-truth bucket for reduce-only close errors whose
own lifecycle had already reached flat truth.

There was also a residual lifecycle key drift: `close_residual_detected` could
be keyed by `position_id`, while `execution.residual_repair_completed` used
`symbol` first. That left a clean terminal residual path looking unclosed in
the acceptance gate.

### Fix

- Mapped close lifecycle events into V1 semantics:
  `exit.retry_wait`, `exit.close_chunk_submitted`, and `exit.closed` are
  `PASSIVE_CLOSE`; `exit.close_residual_detected` is `RESIDUAL_REPAIR`.
- Added `resolved_close_order_error_summary` to diagnose. It only resolves
  reduce-only close errors when current exchange truth is clean, the same
  position has terminal flat lifecycle evidence, and strong order identity
  (`position_id`, `client_order_id`, or `order_id`) matches terminal evidence.
- Kept entry post-only `-5022` semantics separate: entry maker boundary reject
  still requires `post_only=true`, `reduce_only=false`, cooldown/reprice
  evidence, and clean exchange truth.
- Updated residual lifecycle matching to record both position and symbol keys,
  so terminal residual repair closes the same business lifecycle regardless of
  which identifier individual runtime events carried.

### Non-Changes

- No quote stale TTL was increased or bypassed.
- No OI floor, liquidity threshold, admission, sizing, order, close, recovery,
  or lifecycle guard was loosened.
- No exchange execution abstraction was unified.
- No production order, cancel, or runtime-state mutation is part of this fix.

### Verification

- RED first: lifecycle mapping test failed on the four close event kinds.
- RED first: HOMEUSDT terminal close diagnostic test failed because
  `order_error_evidence` still contained the close artifacts.
- GREEN locally: lifecycle mapping now returns no unmapped close event kinds,
  HOMEUSDT close artifacts move into `resolved_close_order_error_summary`, and
  `order_error_evidence` / `top_exchange_errors` are empty for the terminal
  flat case.

## Cluster CL-090: Side semantics, close-leg dedupe, quantity resolution, and quote rewarm evidence

### GitNexus Keys

- Fingerprint: `post-cl089-side-semantics-close-leg-quantity-quote-rewarm-drift`
- Components: `production-health`, `diagnose-live`, `close-reconciliation`,
  `entry-quote-truth`, `bug-ledger`
- Watch: `local_exchange_position_mismatch`,
  `duplicate_close_leg_suppressed_summary`,
  `resolved_quantity_adjustment_summary`,
  `quote_rewarm_after_rest_stale_summary`

### Summary

Post-CL-089 production truth was already healthy: flat/no-open-orders, no
abnormal positions, no single-leg exposure, and no lifecycle unmapped drift.
The remaining work was diagnostic and evidence closure, not trading relaxation.

Four drifts were fixed locally:

- `production_health` and `diagnose_live` used separate side matching helpers,
  so `Side.BUY`/`Side.SELL` exchange labels could still be compared differently
  from business `long`/`short`.
- Close reconciliation could count the same terminal close leg twice when ACK
  truth-gap evidence and later terminal maker truth described the same order.
- Quantity warnings for planner adjustment or exchange step rounding were still
  reported unresolved even when entry opened balanced and later closed flat.
- `rest_resolved_but_stale` quote fallback remained fail-closed but did not
  schedule/record the next sticky WS-BBO rewarm attempt.

### Root Cause

The root cause was semantic drift between local diagnostic helpers and the V1
business lifecycle contract. V1 maps business long/short to executable
buy/sell, but V2 diagnostic code had duplicated side normalization. Close
reconciliation aggregated raw evidence before checking stable close-leg
identity. Quantity warning diagnostics had reason buckets, but not terminal
clean truth demotion. Quote freshness diagnostics showed the stale REST
fallback, but not whether the next WS-BBO warm path healed it.

### Fix

- Added `lightfee/ops/position_side_semantics.py` and routed both production
  health and diagnose side matching through the same helper. Supported labels:
  `buy/sell`, `long/short`, `BUY/SELL`, `LONG/SHORT`, and enum-style
  `Side.BUY`/`Side.SELL`.
- Close reconciliation now de-duplicates by
  `position_id + leg + venue + order_id/client_order_id + quantity + average_price + filled_at_ms`
  before summing close quantities/PnL inputs. Suppressed duplicates are
  reported as `duplicate_close_leg_suppressed_count` and samples.
- Diagnose now reports terminal clean planner/rounding adjustments under
  `resolved_quantity_adjustment_summary`; active or unproven undercuts remain
  warnings.
- REST stale quote fallback still fails closed, but the affected venue/symbol
  is added to the sticky WS-BBO warm set and emits
  `runtime.entry_quote_rewarm_scheduled_after_rest_stale`. Diagnose aggregates
  scheduled/resolved/still-stale/timeout outcomes.

### Non-Changes

- No quote stale TTL was increased or bypassed.
- No OI floor, liquidity threshold, admission, sizing, order, close, recovery,
  or lifecycle guard was loosened.
- No exchange execution abstraction was unified.
- No production order, cancel, or runtime-state mutation is part of this fix.

### Verification

Local RED/GREEN focused verification covered:

- `Side.BUY`/`Side.SELL` exchange truth matching local long/short without false
  `local_exchange_position_mismatch`;
- duplicate close-leg suppression before close reconciliation quantities are
  summed;
- terminal balanced planner adjustment and terminal exchange-step rounding
  moving to resolved quantity summary while active undercut stays warning;
- REST stale fallback remaining fail-closed while scheduling sticky WS-BBO
  rewarm evidence;
- quote rewarm after REST stale diagnose summary.

Full focused/compile verification remains required before deploy.

### Summary

The post-CL-087 production account was flat/no-open-orders with no abnormal
position or single-leg exposure. OI/liquidity targeted refresh was deploy-usable

Binance entry Post Only `-5022` maker-boundary rejects could remain in active

### Root Cause

Binance documents `-5022 GTX_ORDER_REJECT` as Post Only order rejection when the
order cannot remain maker. V1 treats this class as passive maker boundary/requote
evidence, not as a live artifact by itself. V2 already armed a post-only cooldown
and kept entry fail-closed, but `diagnose_live` did not consume that resolved
shape, so clean-truth historical evidence looked like unresolved submit error.

warning payloads did not carry enough reason metadata for root-cause triage.

- `map_lifecycle_event_kind()` now maps the observed production event kinds:
  `reconciliation.entry_resolved`, `review.candidate_rejected`,
  `runtime.entry_post_only_bbo_repriced`,
  `runtime.entry_post_only_reject_cooldown`,
  `runtime.maker_event_no_ws_bbo_quote`, and
  `runtime.position_drift_skipped_passive_close_owner`.
- `diagnose_live` adds `resolved_post_only_reject_summary` and filters only
  Binance `-5022` Post Only entry rejects with `post_only=true`,
  `reduce_only=false`, matching cooldown evidence, and clean current exchange
  truth. Missing cooldown or unclean truth remains unresolved order evidence.
- Entry quantity plan events now include `quantity_plan_reason` and
  `venue_quantity_metadata` evidence. Pending-entry hedge undercut events now
  include `reason_family`, hedge price hint, and hedge min-notional evidence.
- `entry_quantity_terminal_summary` now reports
  `quantity_warning_reason_counts` and bounded `quantity_warning_samples`
  without suppressing warnings unless existing tolerated-dust evidence applies.

- No exchange execution abstraction was unified. The change is business

- No production trading-state mutation is required because exchange truth was

## Cluster CL-087: WS-BBO sticky warm and candidate-scoped OI targeted refresh

### GitNexus Keys

- Fingerprint:
  `ws-bbo-sticky-warm + candidate-scoped-oi-targeted-refresh`
- Components:
  `entry-quote-truth`, `ws-bbo`, `market-data`, `entry-liquidity`,
  `diagnose-live`, `offline-analysis`
- Watch:
  `runtime.entry_oi_targeted_refresh_started`,
  `runtime.entry_oi_targeted_refresh_resolved`,
  `runtime.entry_oi_targeted_refresh_failed`,
  `entry_outcome_summary.oi_targeted_refresh_summary`,
  `runtime.entry_quote_revalidate_failed.reason_bucket`,
  `runtime.entry_ws_bbo_top_candidate_rewarm_*`

### Summary

Production after CL-086 was operationally healthy but still showed that real
entry opportunities could be blocked by two code-path issues rather than by
risk intent: WS-BBO targets could cold-start between scans, and Binance/Aster
OI evidence inherited full-universe sidecar cap/timeout results even when a
finalist only needed two venue+symbol facts. This fix keeps all hard risk
constraints intact and repairs the evidence path.

### Root Cause

V2 intentionally replaced V1 local L2 with WS-BBO quote lease, but the warm
scope was too transient for finalist readiness. For OI, V1 semantics are
candidate-demand evidence; Binance official OI is per-symbol and Aster has no
confirmed reliable bulk V3 OI path, so full-universe enrichment must not be the
only path that can satisfy a finalist liquidity gate. Real public endpoint
smoke added one more concrete root cause: the sidecar enrichment budget is
intentionally 100ms so quote/funding publication stays fast, but Binance/Aster
candidate OI public calls were observed around 354-368ms for BTC/ETH. Reusing
the sidecar 100ms budget for entry-targeted refresh would deterministically
misclassify valid candidate OI as `timeout`.

### Fix

- WS-BBO entry warmup now keeps a short sticky warm set. Current candidate
  targets remain first in budget; recent targets are appended only within the
  same per-venue budget and freshness contract.
- `MarketDataClient.fetch_entry_open_interest_evidence()` refreshes only the
  requested candidate symbols through the existing public exchange data path.
- Entry-targeted OI refresh now uses a separate bounded public-data budget
  instead of reusing the sidecar 100ms enrichment budget. The sidecar fast path
  remains unchanged.
- Runtime calls targeted OI refresh before the snapshot freshness/liquidity
  filter. Available targeted evidence patches only OI fields on the current
  quote; stale quote, OI floor, admission, sizing, and order gates remain
  unchanged.
- `diagnose_live` and offline blocker analysis now separate sidecar OI cap
  pressure from entry targeted refresh outcomes.
- `runtime.entry_oi_targeted_refresh_started/resolved/failed` are mapped into
  the V1 lifecycle closure table as diagnostic-only entry-liquidity evidence, so
  targeted OI observability does not create new unmapped drift.

### Non-Changes

- No quote stale TTL was increased or bypassed.
- No OI floor, liquidity threshold, admission, sizing, order, close, recovery,
  or lifecycle guard was loosened.
- No global full-universe OI cap was raised.
- No exchange execution abstraction was unified.
