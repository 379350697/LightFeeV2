### Production Symptom

The latest production state was not an entry failure. `LABUSDT` had previously
opened as a managed Binance long / OKX short pair and later flattened, but
diagnose/state could replay stale lifecycle evidence as current `risk_only`.
Post-deploy truth later showed no positions, no pending entries, no pending
closes, and no order-truth gaps, while one Bitget `LABUSDT` non-reduce-only
open order remained live without a current owner:
`order_id=1454883357194874881`, side `buy`, quantity `1.0`, price `15.39`.

Hyperliquid was disabled with identity evidence, not because the account type
is categorically unsupported. Hyperliquid account data is read through
`/info` for the real account address, while signed trading uses `/exchange`.
API wallets sign for an account; they are not the account address itself. The
strict production policy for this incident is read-only: do not send a signed
noop just to prove authorization.

After the first deployed fix, cloud evidence also exposed a source split:
diagnose loaded `LIGHTFEE_HYPERLIQUID_WALLET_MODE` from systemd environment
files, while live runtime defaulted `config/live.toml` to `account_wallet`
when the TOML credential omitted `wallet_mode`. That made diagnose and runtime
describe the same identity with different wallet modes.

### Root Cause

1. Diagnose-style current-state exports can contain `positions` while
   `RecoveryOwnerIndex` only indexed `open_positions`. That allowed historical
   journal owner facts from a terminalized pending-entry live-truth conflict to
   be considered again when rebuilding V1 closure.
2. `owned_live_conflict_cleanup_succeeded` and
   `terminalized_after_single_leg_recovery` were not treated as owner-terminal
   events for current closure indexing, so old `owned_pending_entry_live_conflict`
   evidence could survive past cleanup.
3. Exported `lifecycle=risk_only` and `recovery_blocked_reason` could stay
   latched after current V1 closure had already allowed entry.
4. Aster real `-5018` needs symbol-scoped admission blocking. The existing
   runtime block was valid, but diagnose resolution required whole-account
   flatness and could keep old contained Aster rejects unresolved when another
   managed exposure existed elsewhere.
5. Hyperliquid identity had two separate proof classes: account-state read
   proof and signed trade authorization proof. `api_wallet` mode must not use
   the signer as the account, and strict-readonly production must not silently
   do a signed noop.
6. Hyperliquid credential mode loading was not fully shared: diagnose read the
   standard environment mode, but registry/runtime only consumed TOML
   `wallet_mode`.

### Fix

- Recovery owner indexing now accepts both `open_positions` and `positions` and
  skips historical journal position facts for pending-entry owners that already
  emitted terminal cleanup/recovery events.
- Runtime closure refresh now clears stale clearable recovery block reasons
  only when V1 closure says entry is allowed, there is no pending work, risk
  mode is still running, and the reason is in the core clearable set.
- Current-state export derives effective lifecycle and recovery block from the
  current V1 closure summary, without hiding real fail-closed recovery blocks.
- Diagnose distinguishes managed active exposure from abnormal exposure and
  resolves contained admission rejects by the same `(venue, symbol)` exchange
  truth identity instead of requiring global flatness.
- Hyperliquid transport now uses a shared credential identity resolver. In
  `account_wallet` mode, account/signer mismatch fails closed as
  `account_wallet_signer_mismatch`. In `api_wallet` mode, the signer is not
  treated as the account; by default no signed noop is sent and trading remains
  untrusted with
  `api_wallet_authorization_not_verified_strict_readonly`.
- Hyperliquid registry credential construction now reads either
  `wallet_mode_env` or the standard `LIGHTFEE_HYPERLIQUID_WALLET_MODE` fallback,
  matching diagnose's systemd environment-file source while preserving
  strict-readonly default.
- Hyperliquid strict-readonly now closes the diagnostic/admission loop:
  diagnose exports `account_state_readable`, `signer_matches_account`, and
  `trading_authorization_trusted`; strict-readonly is tagged as a policy block;
  retained logs are scanned for canonical Hyperliquid `order.*` /
  `entry.opened` evidence; and entry admission prunes Hyperliquid candidates
  before real submit when trading authorization is not trusted.

### Hyperliquid Timeline Addendum

- `cafdf0a` introduced identity preflight and correctly separated account-state
  reads from signed trading authorization, but the surfaced reason could still
  look like an account-wallet mismatch when runtime and diagnose disagreed on
  wallet mode.
- `7e058b0` fixed the wallet-mode source split so the same credentials are
  described as `api_wallet` by runtime and diagnose. From that point the
  production reason became the accurate strict-readonly policy block:
  `api_wallet_authorization_not_verified_strict_readonly`.
- This is not evidence that the Hyperliquid interface or account type suddenly
  stopped working. It means the currently configured account and signer are
  different, account state is readable, and signed API-wallet authorization has
  not been proven under the selected no-noop policy.
- Recovery path remains explicit: either use a signer that is the account
  wallet, or add a separately approved signed authorization proof to the state
  machine. Until then Hyperliquid is quote/exchange-truth only and must not
  reach real order submission.

### Acceptance

This cluster does not change strategy thresholds, risk limits, spread-reversion
filters, or order-truth semantics. It tightens the boundary: V1 closure owns
current lifecycle truth, Aster real max-notional rejects become symbol-scoped
admission evidence, Hyperliquid account read proof and signed trading proof are
separate, and strict-readonly production does not submit signed authorization
probes.
