# Bug Ledger - 2026-07-08

## Cluster CL-157 - Close Evidence Dedup and Lifecycle Accounting Backfill Gap

Status: local verified; production deployment and backfill dry-run pending.

### 2026-07-24 Historical Replay Retention and Integrity Root Fix

The 70-position correction was append-only in `live-events.jsonl`, but normal
journal rotation can eventually remove the original selected events and those
appended correction rows from `--history all`. The preserved correction audit
is a JSON array, while the rebuild CLI previously accepted only JSONL journal
inputs. That made a historical correction non-replayable after retention even
though its evidence artifact still existed.

`rebuild_lifecycle_truth.py` now accepts explicit read-only
`--correction-events <audit.json>` inputs, refuses to combine them with
`--apply` or exchange querying, treats the stored gated truth snapshot as
canonical during that replay, and writes a self-contained `.replay.jsonl`
evidence artifact on every future apply. A retained historical scope can
therefore replay its source JSONL plus correction audit without touching the
live journal or exchange.

The first implementation still had three root gaps: a deterministic SHA-256
checksum was self-recomputable and therefore did not prove who authored the
audit, a syntactically consistent unknown lifecycle classification could be
replayed, and the atomic writer did not `fsync` the parent directory after the
rename. These were root-cause gaps, not merely bad-file recovery cases.

The current format is schema v2: on the first gated `--apply`, the script
creates a random 32-byte key as the private, `0600` sidecar
`runtime/audits/lifecycle-truth-corrections/.audit-hmac-key`, then signs the
schema/kind/producer/events/checksum payload with HMAC-SHA256. No personal
server environment-variable configuration is required. Replays verify the
signature with constant-time comparison, accept only the closed
`LifecycleClassification` set, and fail closed for missing, corrupt,
out-of-scope, duplicate, unsigned, or semantically invalid snapshots. The
writer now does file `fsync`, atomic rename, and parent-directory `fsync`.
The hidden key must be retained with the correction artifacts for a later
verified replay. Replay also requires an explicit non-empty scope and exact
complete/phantom/bad counts.

The existing 70-position JSON-array artifact and the former schema-v1
self-checksum envelope have no independent integrity proof. They remain
available only through the explicitly non-passing forensic legacy flag; they
must not be used as evidence of a verified historical correction. A gated
exchange-truth apply after deployment will write the signed v2 format for every
future correction.

### Symptom

The 48h live trade audit appeared to show a sudden jump in abnormal single-leg
positions. Current exchange truth was flat/no-open-orders, and detailed
lifecycle replay showed many flagged rows had both close legs present, but raw
close coverage was exactly doubled: the same close order was counted once from
`exit.reconciled.long_legs/short_legs` and again from a derived `order.filled`
event carrying a `fill_event_id`.

### Root Cause

This is a CL-151 close-evidence dedupe coverage gap, not an entry single-leg
admission recurrence and not a failure of CL-154/CL-155 passive-close identity
recovery.

- `exit.reconciled` leg rows were aggregate close statement evidence but did
  not preserve `trade_id`, `exec_id`, or `fill_event_anchor_id` from
  `OrderFillReconciliation.metadata`.
- The derived `order.filled` events did carry `fill_event_id`, so
  `_fill_dedupe_key` bucketed them by event id while the parent
  `exit.reconciled` leg bucketed by order/client/quantity/price.
- Because those two keys could not meet, lifecycle raw close coverage counted
  the same real exchange close twice and reported overcoverage.
- A separate historical accounting gap remains for positions that have retained
  `entry.opened` events but no retained `exit.reconciled`; those must be
  handled through exchange-truth dry-run rebuild and append-only correction
  only after gates pass.

### Unified Business Decision

- Source elimination: close reconciliation payloads must carry stable exchange
  identity through `exit.reconciled` legs and derived `order.filled` events, so
  downstream ledgers see one semantic close fill identity.
- Post-fact handling: lifecycle dedupe must recognize old historical rows where
  `exit.reconciled` lacks anchor/id but matches the derived close fill by
  phase, leg, venue, order/client identity, quantity, and price.
- Safety boundary: distinct `trade_id`/`exec_id` close fills remain distinct;
  only matching non-aggregate derived evidence is suppressed when a matching
  aggregate close statement leg exists.
- Reporting semantics: accounting overcoverage and missing historical exit
  evidence must not be named as live single-leg exposure. PnL remains unknown
  until close evidence is complete or exchange-truth rebuild supplies explicit
  correction evidence.

### Fix

- `CloseRuntime._aggregate_close_reconciliation_fills` preserves
  `trade_id`, `exec_id`, and `fill_event_anchor_id` from reconciliation
  metadata into close leg payloads.
- `CloseRuntime._order_filled_events_from_close_reconciliation_payload` reuses
  the leg payload anchor when present instead of creating an unjoinable derived
  identity.
- `exchange_truth_ledger._dedupe_fills` compares aggregate close fills against
  non-aggregate derived close fills and suppresses duplicates before raw
  coverage is calculated.
- Close alias matching is scoped to close phase, leg, venue, quantity, and
  price, then identity. When both sides carry strong trade/exec/anchor
  identities they must intersect; when either side lacks strong identity, the
  historical order/client alias can still join the same close evidence without
  merging true split executions.

## Cluster CL-156 - Sidecar FD Exhaustion and Live Restart Cascade

Status: deployed/cloud verified on 2026-07-24; no fresh FD-stress recurrence observed.

### GitNexus Keys

- Fingerprints: `Too many open files`, `missing_limit_nofile`,
  `live_requires_sidecar_service`, `sidecar source close failed`
- Components: `sidecar`, `market-data`, `production-health`, `systemd`
- Symbols: `MarketDataClient._get_client`, `SidecarService.refresh_once`,
  `SidecarService.close`, `lightfee.apps.sidecar._run`,
  `lightfee.apps.spread_sidecar._run`, `SpreadSidecarService.__init__`,
  `analyze_systemd_unit`
- Files: `lightfee/venues/market_data.py`, `lightfee/sidecar/service.py`,
  `lightfee/apps/sidecar.py`, `lightfee/apps/spread_sidecar.py`,
  `lightfee/spread/service.py`, `lightfee/ops/production_health.py`,
  `deploy/systemd/lightfee-sidecar.service`,
  `deploy/systemd/lightfee-spread-sidecar.service`,
  `deploy/systemd/lightfee-live.service`
- Cards: [market-data-snapshot-freshness](../cards/market-data-snapshot-freshness.md)

### Symptom

Post-CL-155 trading truth was clean and owner recovery was effective, but the
cloud still showed a service-level instability path: sidecar could hit
`OSError: [Errno 24] Too many open files` while publishing snapshots, and
`lightfee-live.service` was coupled to `lightfee-sidecar.service` through
`Requires=`, so a sidecar restart could cascade into a live restart even when
current exchange truth was flat/no-open-orders.

### Root Cause

This was not a new entry or passive-close single-leg admission gap. The missing
boundary was operational IO lifecycle:

- Sidecar public source `httpx.AsyncClient` instances had a keepalive limit but
  no total `max_connections`, so cold-cache fanout could open too many
  concurrent public sockets before keepalive capping mattered. The cap must stay
  sidecar-scoped so it does not constrain credentialed `VenueTransport` order,
  position, or account IO.
- Spread-sidecar direct-market fallback and paper quote repair reused the same
  public exchange source family but initially did not inherit the new sidecar
  total connection cap, leaving the same source-level FD boundary uncovered.
- Liquidity lifecycle collection re-entered the same public funding/quote path
  after funding/market refresh had already produced usable quote snapshots,
  amplifying the fanout that led to FD pressure.
- `lightfee.apps.sidecar.main` did not close `SidecarService` on normal
  `--once`, loop exit, cancellation, or SIGTERM paths, so in-flight public
  clients and background OI tasks relied on process teardown instead of
  deterministic cleanup.
- `lightfee.apps.spread_sidecar.main` used a local infinite loop without the
  SIGTERM stop-event path, so systemd SIGTERM could terminate the process before
  `SpreadSidecarService.close()` ran.
- `SidecarService.close` stopped at the first source close exception, leaving
  later exchange/liquidity/transfer sources unclosed.
- Production unit templates lacked explicit `LimitNOFILE`, and the live unit
  used `Requires=lightfee-sidecar.service`, turning sidecar failure into a live
  runtime restart cascade. The production verifier checked sidecar/live units
  but initially missed `lightfee-spread-sidecar.service`.

### Unified Business Decision

- Source elimination: sidecar and spread-sidecar public market-data IO must have
  a hard total connection bound, reuse already fetched quote snapshots for
  liquidity lifecycle when available, and sidecar exits must close every source
  best-effort.
- Post-incident handling: if sidecar still fails, systemd may restart sidecar,
  but it must not restart live merely because the sidecar service failed. Live
  can still `Wants`/`After` sidecar startup without declaring it a hard runtime
  dependency.
- Production verification must reject unit templates without `LimitNOFILE` and
  reject live units that hard-require sidecar, so this class is caught before
  cloud rollout.

### Fix

- `MarketDataClient._get_client` now leaves total connections unbounded unless a
  caller explicitly passes `http_max_connections`; sidecar exchange, liquidity,
  and transfer sources pass `max_connections=32` with
  `max_keepalive_connections=4`.
- Spread-sidecar direct-market fallback and paper quote repair exchange sources
  pass the same sidecar public `max_connections=32` cap.
- `SidecarService.refresh_once` reuses same-cycle funding/market quote snapshots
  for liquidity lifecycle coverage instead of fetching the same public funding
  path a second time.
- `lightfee.apps.sidecar._run` wraps the refresh loop in `try/finally`, installs
  SIGINT/SIGTERM shutdown handlers, cancels in-flight refresh on shutdown, and
  always awaits `service.close()`.
- `lightfee.apps.spread_sidecar._run` now uses the same shutdown-aware refresh
  loop and always awaits `SpreadSidecarService.close()`.
- `SidecarService.close` closes exchange, liquidity, and transfer sources
  best-effort from source snapshots; one close failure or registry mutation is
  logged/isolated and does not prevent later cleanup.
- `SpreadSidecarService.close` closes the paper journal and every direct
  exchange source best-effort from a source snapshot; one cleanup exception or
  registry mutation cannot skip later source cleanup.
- `TransferSource.close` closes both underlying public clients best-effort; a
  `from` client close failure cannot leave the `to` client open.
- `deploy/systemd/lightfee-sidecar.service`,
  `deploy/systemd/lightfee-spread-sidecar.service`, and
  `deploy/systemd/lightfee-live.service` now set `LimitNOFILE=65536`.
- `deploy/systemd/lightfee-live.service` no longer uses
  `Requires=lightfee-sidecar.service`; it keeps sidecar as a wanted startup
  dependency only.
- `analyze_systemd_unit` now fingerprints `missing_limit_nofile` and
  `live_requires_sidecar_service`; `verify_production_services.py` checks
  sidecar, spread-sidecar, and live units.
- `diagnose_live.py` service-status evidence now includes
  `lightfee-spread-sidecar.service`, matching the production verifier.
