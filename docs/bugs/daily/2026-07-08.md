# Bug Ledger - 2026-07-08

## Cluster CL-156 - Sidecar FD Exhaustion and Live Restart Cascade

Status: local verified; deploy/cloud verification pending.

### GitNexus Keys

- Fingerprints: `Too many open files`, `missing_limit_nofile`,
  `live_requires_sidecar_service`, `sidecar source close failed`
- Components: `sidecar`, `market-data`, `production-health`, `systemd`
- Symbols: `MarketDataClient._get_client`, `SidecarService.refresh_once`,
  `SidecarService.close`, `lightfee.apps.sidecar._run`,
  `lightfee.apps.spread_sidecar._run`, `SpreadSidecarService.__init__`,
  `analyze_systemd_unit`
- Files: `lightfee/venues/market_data.py`, `lightfee/sidecar/service.py`,
  `lightfee/apps/sidecar.py`, `lightfee/apps/spread_sidecar.py`,
  `lightfee/spread/service.py`, `lightfee/ops/production_health.py`,
  `deploy/systemd/lightfee-sidecar.service`,
  `deploy/systemd/lightfee-spread-sidecar.service`,
  `deploy/systemd/lightfee-live.service`
- Cards: [market-data-snapshot-freshness](../cards/market-data-snapshot-freshness.md)

### Symptom

Post-CL-155 trading truth was clean and owner recovery was effective, but the
cloud still showed a service-level instability path: sidecar could hit
`OSError: [Errno 24] Too many open files` while publishing snapshots, and
`lightfee-live.service` was coupled to `lightfee-sidecar.service` through
`Requires=`, so a sidecar restart could cascade into a live restart even when
current exchange truth was flat/no-open-orders.

### Root Cause

This was not a new entry or passive-close single-leg admission gap. The missing
boundary was operational IO lifecycle:

- Sidecar public source `httpx.AsyncClient` instances had a keepalive limit but
  no total `max_connections`, so cold-cache fanout could open too many
  concurrent public sockets before keepalive capping mattered. The cap must stay
  sidecar-scoped so it does not constrain credentialed `VenueTransport` order,
  position, or account IO.
- Spread-sidecar direct-market fallback and paper quote repair reused the same
  public exchange source family but initially did not inherit the new sidecar
  total connection cap, leaving the same source-level FD boundary uncovered.
- Liquidity lifecycle collection re-entered the same public funding/quote path
  after funding/market refresh had already produced usable quote snapshots,
  amplifying the fanout that led to FD pressure.
- `lightfee.apps.sidecar.main` did not close `SidecarService` on normal
  `--once`, loop exit, cancellation, or SIGTERM paths, so in-flight public
  clients and background OI tasks relied on process teardown instead of
  deterministic cleanup.
- `lightfee.apps.spread_sidecar.main` used a local infinite loop without the
  SIGTERM stop-event path, so systemd SIGTERM could terminate the process before
  `SpreadSidecarService.close()` ran.
- `SidecarService.close` stopped at the first source close exception, leaving
  later exchange/liquidity/transfer sources unclosed.
- Production unit templates lacked explicit `LimitNOFILE`, and the live unit
  used `Requires=lightfee-sidecar.service`, turning sidecar failure into a live
  runtime restart cascade. The production verifier checked sidecar/live units
  but initially missed `lightfee-spread-sidecar.service`.

### Unified Business Decision

- Source elimination: sidecar and spread-sidecar public market-data IO must have
  a hard total connection bound, reuse already fetched quote snapshots for
  liquidity lifecycle when available, and sidecar exits must close every source
  best-effort.
- Post-incident handling: if sidecar still fails, systemd may restart sidecar,
  but it must not restart live merely because the sidecar service failed. Live
  can still `Wants`/`After` sidecar startup without declaring it a hard runtime
  dependency.
- Production verification must reject unit templates without `LimitNOFILE` and
  reject live units that hard-require sidecar, so this class is caught before
  cloud rollout.

### Fix

- `MarketDataClient._get_client` now leaves total connections unbounded unless a
  caller explicitly passes `http_max_connections`; sidecar exchange, liquidity,
  and transfer sources pass `max_connections=32` with
  `max_keepalive_connections=4`.
- Spread-sidecar direct-market fallback and paper quote repair exchange sources
  pass the same sidecar public `max_connections=32` cap.
- `SidecarService.refresh_once` reuses same-cycle funding/market quote snapshots
  for liquidity lifecycle coverage instead of fetching the same public funding
  path a second time.
- `lightfee.apps.sidecar._run` wraps the refresh loop in `try/finally`, installs
  SIGINT/SIGTERM shutdown handlers, cancels in-flight refresh on shutdown, and
  always awaits `service.close()`.
- `lightfee.apps.spread_sidecar._run` now uses the same shutdown-aware refresh
  loop and always awaits `SpreadSidecarService.close()`.
- `SidecarService.close` closes exchange, liquidity, and transfer sources
  best-effort from source snapshots; one close failure or registry mutation is
  logged/isolated and does not prevent later cleanup.
- `SpreadSidecarService.close` closes the paper journal and every direct
  exchange source best-effort from a source snapshot; one cleanup exception or
  registry mutation cannot skip later source cleanup.
- `TransferSource.close` closes both underlying public clients best-effort; a
  `from` client close failure cannot leave the `to` client open.
- `deploy/systemd/lightfee-sidecar.service`,
  `deploy/systemd/lightfee-spread-sidecar.service`, and
  `deploy/systemd/lightfee-live.service` now set `LimitNOFILE=65536`.
- `deploy/systemd/lightfee-live.service` no longer uses
  `Requires=lightfee-sidecar.service`; it keeps sidecar as a wanted startup
  dependency only.
- `analyze_systemd_unit` now fingerprints `missing_limit_nofile` and
  `live_requires_sidecar_service`; `verify_production_services.py` checks
  sidecar, spread-sidecar, and live units.
- `diagnose_live.py` service-status evidence now includes
  `lightfee-spread-sidecar.service`, matching the production verifier.
