## Cluster CL-128 - Complete-Truth Clear for Live-Mismatch Flatten Latch

Status: `c827b82` deployed/cloud verified.

### GitNexus Keys

- Fingerprint: `live_position_mismatch_flatten_failed_stale_after_complete_flat_truth`
- Components: `recovery-decision-core`, `restart-recovery`, `runtime-housekeeping`, `production-health`, `diagnose-live`
- Symbols: `LEGACY_MIGRATION_CLEARABLE_BLOCK_REASONS`, `COMPLETE_TRUTH_ONLY_CLEARABLE_BLOCK_REASONS`, `V1RecoveryDecisionCore._should_clear_core_block`, `clear_legacy_recovery_block_via_core`, `RecoveryStartupRuntime._maybe_recover_clean_live_positions`
- Files: `lightfee/engine/recovery_decision_core.py`, `lightfee/engine/recovery.py`, `lightfee/engine/recovery_startup_runtime.py`, `tests/engine/test_recovery_decision_core.py`, `tests/test_live_startup_preflight.py`
- Watch: `recovery_blocked_reason=live_position_mismatch_flatten_failed`, `RecoveryDecisionKind.RUNNING_CLEAN`, `clear_previous_block`, `risk_mode=fail_closed`, `lifecycle=risk_only`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Production Symptom

After deploying CL-127 as `2a5d5a9`, cloud manifest and singleton checks passed,
but `verify_production_services.py --json` failed. The first post-deploy
exchange truth found one Bitget `LABUSDT` non-reduce-only open order
(`1454717268326510593`) without a runtime owner, so V1 correctly kept the
runtime fail-closed with `orphan_maker_order`.

On the next fresh truth pass the open order was gone and exchange truth was
high-confidence flat/no-open-orders, but the exported state stayed
`lifecycle=risk_only`, `risk_mode=fail_closed`, with stale
`recovery_blocked_reason=live_position_mismatch_flatten_failed`. The recovery
core already returned `RUNNING_CLEAN`, `entry_allowed=true`, and no blocking
rows, but the prior block reason prevented the state from returning to running.

### Root Cause

`live_position_mismatch_flatten_failed` was protected from stale cleanup, which
is correct when truth is unavailable or only partial. However the allowlist did
not distinguish partial evidence from complete flat exchange truth. After the
exchange proved there were no positions and no open orders, the old mismatch
flatten failure reason remained outside the core-clearable set and kept
`clear_previous_block=false`.

After the first local semantic fix, cloud truth showed a second closure gap:
diagnose could recompute `RUNNING_CLEAN` from current exchange truth, but the
live housekeeping trigger only refreshed account truth for
`unpaired_live_position` and `owned_pending_entry_live_conflict`. A prior
`live_position_mismatch_flatten_failed` latch with no current live positions was
therefore never routed back through the runtime account-truth ledger refresh,
so `runtime/live-state-current.json` kept the stale
`recovery_blocked_reason` and `risk_only/fail_closed` state.

Together these made a resolved live-artifact incident stay fail-closed even
though V1 recovery semantics had reached `RUNNING_CLEAN`.

### Fix

- Added `live_position_mismatch_flatten_failed` to the recovery block reasons
  that may clear after a complete-truth core decision.
- Added `COMPLETE_TRUTH_ONLY_CLEARABLE_BLOCK_REASONS` and excluded it from
  evidence-gap clears, so unavailable or partial truth still preserves the
  fail-closed latch.
- Updated `clear_legacy_recovery_block_via_core` so complete-truth-only reasons
  require `RUNNING_CLEAN`; `RUNNING_WITH_EVIDENCE_GAP` cannot clear them.
- Extended runtime clean-live-position housekeeping so
  `live_position_mismatch_flatten_failed` triggers the same account-truth ledger
  refresh as other live-artifact recovery latches. The actual clear still goes
  through `V1RecoveryDecisionCore` plus `clear_legacy_recovery_block_via_core`;
  no manual state mutation or health-check bypass is introduced.

- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Production Symptom

After CL-125 restored V1 small-fill admission, production selected and
submitted a `LABUSDT` passive entry on Bitget -> OKX. The entry advanced past
pre-submit and reached maker/hedge fill evidence, but it did not become a valid
`entry.opened`. Live truth showed no Bitget long while OKX short was visible,
so the pending-entry terminalizer emitted `positive_fill_live_truth_conflict`,
flattened the owned OKX single leg, and removed the pending entry through V1
lifecycle closure.

The runtime cleanup was correct and current exchange truth was flat/no-open
orders, but diagnosis still reported the historical entry in
`phase_duration_summary.current_hard_over_budget_count`. The conflict event
also lacked a single structured payload tying together maker fill evidence,
direction-correct live position truth, and maker release evidence, making the
next venue-specific root-cause step depend on manually correlating events.

### Root Cause

Three shared semantic gaps were exposed after CL-125:

1. Bitget passive maker progress is a merged truth from REST detail, private
   order progress, and reconciliation lookup, but the shared
   `PassiveOrderProgress` contract did not carry the source/merge evidence.
   Runtime `passive_maintenance.maker_progress` therefore reported a maker
   fill without saying whether the quantity came from detail, private WS, or
   reconciliation.
2. `PendingEntryLiveTruth` already computed per-venue direction-correct
   position details, but the successful live-truth conflict path only journaled
   aggregate long/short/balanced quantities. The durable event contract did not
   carry the maker/hedge fill truth or the per-venue live details that explain
   why V2 correctly refused `entry.opened`.
3. `diagnose_live.py` treated `entry.opened`, `entry.aborted`, and
   `entry.passive_unfilled` as entry terminal events, but not
   `pending_entry.removed_by_v1_lifecycle_closure` or
   `pending_entry.terminalized_after_single_leg_recovery`. That drifted from
   the V1 lifecycle closure table and made a clean historical artifact look
   current.

### Fix

- Added optional `PassiveOrderProgress.evidence` and populated Bitget passive
  progress with REST detail/private WS/reconciliation participation, per-source
  quantities, merge source, final cumulative quantity, and final state.
- Propagated passive progress evidence into
  `passive_maintenance.maker_progress`, so later positive-fill/live-truth
  conflicts can be traced back to the exact exchange progress sources.
- Extended `PendingEntryLiveTruth` with `live_position_details` so the
  terminalizer decision boundary keeps the direction-correct live truth that
  was used for the decision.
- Added `maker_fill_truth` and `live_position_details` to
  `pending_entry.positive_fill_live_truth_conflict`.
- Added `maker_release_evidence` to successful owned single-leg cleanup events
  so release is proven by the same terminal maker/order evidence used before
  pending removal.
- Taught `phase_duration_summary` that V1 pending-entry lifecycle closure and
  single-leg recovery terminalization are entry terminal events, so historical
  recovered entries no longer count as current hard-over-budget work.

## Cluster CL-123 - Public OI Pre-HTTP Filter and Spread Sidecar Snapshot Sharing

Status: code fix `d2d89af` deployed/cloud verified.

### GitNexus Keys

- Fingerprint: `unsupported_open_interest_http_400 + spread_sidecar_duplicate_public_oi_fetch`
- Components: `market-data-client`, `sidecar-snapshot`, `spread-sidecar`, `diagnose-live`, `bug-ledger`
- Symbols: `MarketDataClient._fetch_binance_style`, `MarketDataClient._fetch_binance_style_entry_open_interest`, `SpreadSidecarService`, `publish_spread_snapshot`, `_build_entry_outcome_summary`
- Files: `lightfee/venues/market_data.py`, `lightfee/spread/service.py`, `lightfee/spread/models.py`, `lightfee/spread/publisher.py`, `scripts/diagnose_live.py`
- Watch: `symbol_not_listed_before_http`, `missing_bulk_premium_index`, `missing_bulk_book_ticker`, `missing_symbol_mark_before_http`, `premium_index_symbol_rejected_before_oi_http`, `spread_sidecar_source=sidecar_snapshot`, `direct_market_fallback`
- Card: [market-data-snapshot-freshness](../cards/market-data-snapshot-freshness.md)

### Production Symptom

Latest deployed runtime was flat/no-open-orders, but sidecar logs showed market
data pressure rather than order failure: Binance/Aster-compatible
`/fapi/v1/openInterest?symbol=...` calls returned 400 for unsupported or
non-effective symbols. The same public OI family was also observable from both
`lightfee-sidecar` and `lightfee-spread-sidecar`, meaning two processes could
pull identical public quote/OI data with separate process-local cache/inflight
state.

### Root Cause

The Binance/Aster full sidecar OI enrichment path used partial bulk catalog
truth as enough evidence to call symbol-level `openInterest`. If `premiumIndex`
still contained a symbol but bulk `bookTicker` did not confirm it as tradeable,
V2 could still call OI and receive exchange HTTP 400. If a requested symbol was
absent from both bulk catalogs, the first local fix avoided OI HTTP but did not
return a structured evidence row, so diagnose could not count it as filtered.
The candidate-scoped OI path also returned a generic unsupported/missing-mark
classification when symbol mark truth was absent or rejected, instead of a
shared pre-OI-HTTP filtered symbol status.

Separately, `SpreadSidecarService` constructed its own `ExchangeSource`
instances and fetched public quotes directly from exchanges. That made the main
sidecar snapshot and spread-sidecar direct fetch two independent public-data
truth paths, so process-local OI cache/inflight dedupe could not prevent duplicate
Binance/Aster OI pressure.

### Fix

- Full Binance/Aster-compatible OI enrichment now requires both bulk
  `premiumIndex` and bulk `bookTicker` evidence before calling
  `/fapi/v1/openInterest`. Missing book ticker evidence is classified as
  `symbol_not_listed_before_http` with reason `missing_bulk_book_ticker`;
  symbols absent from both bulk catalogs are retained as diagnostic evidence
  with reason `missing_bulk_premium_index`, while bookTicker-only non-perpetual
  symbols continue to be skipped.
- Candidate-scoped OI now classifies missing symbol mark truth as
  `symbol_not_listed_before_http` with reason
  `missing_symbol_mark_before_http`. Symbol-scoped `premiumIndex` invalid-symbol
  rejection is classified as `premium_index_symbol_rejected_before_oi_http`.
  Neither case counts as an OI HTTP refresh attempt.
- Spread sidecar defaults to `runtime.sidecar_snapshot_path` as the public
  quote/OI truth source. If the main snapshot is missing, malformed, or stale,
  it publishes an empty degraded spread snapshot instead of direct-fetching
  exchanges.
- A direct public fetch path remains available only when
  `spread_sidecar_source_mode="direct_market"` and
  `spread_sidecar_direct_fetch_enabled=true`; such snapshots carry
  `source_mode=direct_market_fallback`.
- Diagnose now reports `public_oi_pre_http_filtered_count` and
  `spread_sidecar_summary.spread_sidecar_source` so filtered unsupported symbols
  and spread source mode are visible without being misclassified as trading
  exposure.

## Cluster CL-124 - Private Truth Pre-HTTP Symbol Filter and Spread Source-State Diagnosis

Status: code fix `a839074` deployed/cloud verified.

### GitNexus Keys

- Fingerprint: `aster_private_truth_symbol_filter_gap + spread_source_transient_stale_classification`
- Components: `aster-adapter`, `venue-symbol-eligibility`, `diagnose-live`, `spread-sidecar-source-state`, `bug-ledger`

### Production Symptom

After CL-123, public Binance/Aster-compatible OI stopped producing unsupported
symbol HTTP pressure, and spread-sidecar no longer direct-fetched public OI.
However the same eligibility principle was not yet shared by Aster private
symbol-scoped truth probes. Diagnose/runtime symbol probes could still ask
Aster V3 private `positionRisk` or `openOrders` for cross-venue formatted or
catalog-unsupported symbols and then classify the exchange reject after HTTP.

Spread-source diagnostics also needed one more split: a historical
`sidecar_snapshot_stale` source sample should be current-degraded only when the
main sidecar snapshot is still stale or unavailable. If the current main
snapshot is fresh and spread has recovered to normal snapshot consumption, it is
a recovered transient, not a current trading blocker.

### Root Cause

V2 had fixed the public OI domain but had no shared venue-symbol eligibility
contract for private symbol truth. Aster private probes accepted arbitrary
canonical symbols and relied on the exchange response to prove invalidity. This
kept the business semantics leaky: a single unsupported symbol looked like
private truth pressure even though Aster account-level truth was healthy and the
unsupported fact was knowable from the adapter catalog before HTTP.

Diagnose also had only a single spread source string, so stale snapshots could
be read as current source degradation even after the main sidecar had already
published fresh truth. No-entry evidence from quote/OI admission belongs to
candidate admission; it must not drift into order failure or current exposure
without actual order/position/open-order truth.

### Fix

- Added shared `venue_symbol_eligibility(...)` semantics. For Aster, loaded
  adapter catalog truth can classify a symbol as
  `symbol_not_listed_before_private_truth_http` before any private HTTP.
  Missing catalog truth stays `truth_unavailable` so V2 does not invent flat
  truth from unavailable metadata.
- `AsterAdapter.fetch_position(symbol)` and
  `AsterAdapter.fetch_open_orders(symbol)` now use the shared eligibility gate.
  Unsupported symbol-scoped probes return flat/empty structured truth before
  Aster V3 HTTP; unfiltered account-level open-order truth still calls the V3
  private path.
- `diagnose_live` uses the same eligibility rule before symbol-scoped position
  and open-order probes, and reports
  `exchange_truth.private_truth_pre_http_filtered_count` separately from
  `public_oi_pre_http_filtered_count`.
- Spread-sidecar diagnosis now distinguishes
  `spread_sidecar_source_state=current_source_degraded` from
  `transient_stale_recovered` by checking whether the current main sidecar
  snapshot is fresh.
- Entry no-open reasons remain in `entry_market_evidence_summary` as candidate
  admission blockers. Public OI pre-HTTP filtered evidence and private truth
  pre-HTTP filtered evidence are diagnostic/data-truth facts, not order-submit
  failures or abnormal position evidence.

## Cluster CL-125 - Pending-Entry Admission Core Restores V1 Small-Fill Semantics

### Production Symptom

After CL-122 enabled `pending_entry_pre_submit_hedgeable_fill_guard_enabled`,
production stopped submitting passive maker entries. The deployed services were
healthy and exchange truth was flat/no-open-orders, but the live event stream
showed every planned `passive_incremental` entry ending at
`runtime.entry_blocked_pre_submit_hedgeability` before maker submit.

The no-open boundary started after `641d166` and before the spread-reversion
sidecar was introduced. Spread trading remained disabled in production config,
so the regression was not caused by spread strategy selection replacing the
normal funding entry path.

### Root Cause

CL-122 moved a post-fill hedge-delta condition into a pre-submit hard blocker.
The guard compared the smallest observable maker fill increment with the hedge
venue min hedgeable chunk. That blocked routes such as maker increment `0.001`
versus hedge chunk `0.3999` or `266+`, even when
`execution.entry_quantity_plan` had already aligned
`initial_maker_target_quantity` and `full_target_quantity` to hedgeable chunks.

That drifted from V1 pending-entry semantics. V1 allows small maker fills to
buffer until enough unmatched maker quantity is releasable as a legal hedge
chunk. Pre-submit admission must prove the planned clip can become hedgeable;
post-fill `pending_entry_hedge_delta` owns `buffer_small_fill` and release.

### Fix

- Added `lightfee/engine/pending_entry_admission.py` as the shared
  pending-entry admission decision core. It returns allow, advisory, or block
  decisions with a single event payload contract.

## Cluster CL-126 - Deploy Sync Cache Exclude and Version Preservation

### Production Symptom

During the CL-125 deploy, the local-to-cloud rsync path uploaded local
development artifacts such as `.gitnexus` cache data. The sync became much
heavier than the intended git-tracked runtime payload, and an interrupted
deploy window could also leave `.deploy_version` deleted until the later write
step ran.

The deployed runtime itself was healthy after manual closure, but the deploy
tooling had a reproducible fragility: generated rsync excludes did not cover
local code-index/test/lint caches or the remote deploy metadata file.

### Root Cause

`scripts/verify_deploy_manifest.py` owns the generated deploy script exclude
list. That list excluded `.deploy_manifest.json`, `.venv`, `.git`,
runtime/config/log paths, and docs, but it did not exclude `.deploy_version`,
`.gitnexus/`, `.pytest_cache/`, or `.ruff_cache/`.

Because `scripts/deploy.sh` is generated and untracked, fixing only a local
copy would not survive the next generation step or a cloud-side pull. The
durable fix had to land in the generator and be covered by a regression test
against the generated rsync line.

### Fix

- Added `.deploy_version`, `.gitnexus/`, `.pytest_cache/`, and `.ruff_cache/`
  to `EXCLUDE_PATTERNS` in `scripts/verify_deploy_manifest.py`.
- Added a RED/GREEN regression in `tests/test_verify_deploy_manifest.py` that
  asserts the generated rsync command preserves remote deploy metadata and
  skips local cache/index directories.
- Regenerated `.deploy_manifest.json`.
- On the cloud host, stashed the prior rsync-deployed tracked worktree diff,
  fast-forwarded `/opt/lightfee-v2` to `bc9deeb`, regenerated
  `scripts/deploy.sh` with the new generator, and deployed in remote-local
  mode.
