## Cluster CL-067: Passive-close terminal normalization and one-sided risk reduction

### GitNexus Keys

| Key | Value |
|---|---|
| Components | `passive-close`, `live-runtime`, `diagnose-live`, `venue-okx`, `venue-bybit`, `recovery-core`, `v1-parity`, `production-observability` |
| Fingerprint | `post-deploy-8-opens-6-passive-close-abnormal-terminal + one-sided-fast-flatten-risk + drift-owner-race` |

| Files | `lightfee/engine/passive_close.py`, `lightfee/engine/runtime.py`, `scripts/diagnose_live.py`, `tests/test_passive_close.py`, `tests/test_live_startup_preflight.py`, `tests/test_diagnose_live.py` |

### Production Symptom

Post-deploy review found 8 opened positions with 6 abnormal passive-close close-paths. Several positions became exchange-flat through compensation, drift cleanup, recovery, or fallback evidence rather than a standard passive close terminal. `SAHARAUSDT` also produced `exit.passive_close_live_one_sided_error`, but the event stream did not yet classify whether a one-sided reduce-only was submitted within the fast-flatten window after maker progress.

### Root Cause

V1 treats passive close completion, hedge failure compensation, hedge deadline, fallback, and live-flat cleanup as one close terminal: pending passive close is cleared, close execution semantics are projected, and the position is finalized. V2 had branch-specific terminal paths that could only emit `recovery.flat`, lifecycle terminal, or drift correction. Runtime drift could also take ownership while passive close was still the rightful owner after maker ids were cleared. For OKX amend failures, V2 did not immediately query the original order even though OKX amend defaults to keeping the original order alive when amend fails.

### Fix

- `_clear_live_flat_state` now emits `exit.passive_close_resolved` with `resolution_source`, `problem`, `exchange_truth`, and `single_leg_fast_flatten` fields before removing the passive close terminal state.
- `_amend_maker_order` now polls OKX original order truth after generic amend failures and retains the original order id/client id when the order is still `OPEN` or `PARTIALLY_FILLED`.
- `_maybe_check_active_position_drift` now records `runtime.position_drift_skipped_passive_close_owner` and does not flatten/fail-close while an active `pending_passive_close` owns the position.
- `_flatten_live_one_sided_position` now requires explicit open-order-flat proof on the affected venue before submitting reduce-only IOC; otherwise it records `exit.passive_close_live_one_sided_truth_gap` and retries.
- `diagnose_live.py` now reports `passive_close_terminal_summary` with passive resolved, problem resolved, fast flatten, passive-owned drift blocked, and stale fail-closed-after-flat counters.

## Cluster CL-066: MOVEUSDT Bybit ACK-only duplicate-CID diagnose closure

### GitNexus Keys

  `MOVEUSDT`,
  `lfxlbf3cf3338c41e406`

### Production Symptom

After deployment, the MOVEUSDT automatic close/recovery path produced two
Bybit order artifacts for the same close attempt:

- Bybit accepted a reduce-only close request and returned order/client ids, but
  the response was ACK-only and had no fill confirmation.
- A retry/reconcile attempt reused the same client id and Bybit returned
  `110072 OrderLinkedID is duplicate`.

Later runtime evidence proved the position terminal-flat through
`order.reconcile_result status=none/reason=duplicate_client_id`,
`next_action=clear_live_flat`, terminal lifecycle/recovery flat events, residual
repair `already_flat`, and current exchange truth flat/no-open-orders. Diagnose
still kept the ACK-only and duplicate-client-id artifacts as active order
errors, so the deployed system looked unhealthy even after the actual exchange
state had converged.

### Root Cause

This is an evidence-consumption and projection bug, not a new manual-close
failure.

The prior CL-062 rule correctly required ACK-only Bybit order responses to stay
unresolved until accepted-order truth-gap evidence plus later terminal/current
truth proved the outcome. The MOVEUSDT path exposed two missing closure edges:

- The deployed event sequence had `order.uncertain` with accepted ids,
  `order_ack_only=true`, and missing fill confirmation nested inside
  `exchange_error.extra`, but it did not have a separate explicit
  `accepted_order_truth_gap` event. Diagnose therefore never registered the
  ACK-only artifact as a truth gap that could later be resolved.
- The same close attempt then emitted Bybit `110072` for the same client id.
  The duplicate-client-id event shared the truth-gap identity, but diagnose did
  not bind nested `exchange_error.request_context` / `extra.request_context`
  ids to the later live-flat reconciliation and terminal lifecycle evidence.
- The close executor represented duplicate-client live-flat reconciliation as
  a zero-quantity `order.filled`, which made the ledger look like a fill
  happened when the real meaning was idempotent duplicate evidence plus current
  live-flat truth.

### Fix

- `diagnose_live.py` now treats ACK-only `order.uncertain` payloads with
  accepted ids and missing fill confirmation as implicit order-truth-gap
  registrations.
- Truth-gap identity extraction now includes nested `exchange_error`,
  `exchange_error.extra`, top-level `request_context`, and nested
  `request_context` fields, so accepted order id, client order id, symbol,
  venue, and position id line up across ACK-only, duplicate-client, reconcile,
  and terminal-flat events.
- Bybit `110072` duplicate-client-id artifacts are filtered from active order
  errors only when they match a resolved truth-gap identity and the resolution
  includes reconciliation/terminal/current exchange truth proving flat and no
  open orders.
- `CloseExecutor._submit_close_leg_with_retry()` now emits
  `exit.close_duplicate_client_order_resolved_live_flat` and returns
  `terminal_flat` when duplicate-client reconciliation finds no fill and live
  size is zero. It no longer emits a misleading zero-quantity `order.filled`
  for this branch.
- Partial duplicate reconciliation still returns a real reconciled fill and the
  other leg close path remains unchanged.

## Cluster CL-065: Hyperliquid exchange-truth account identity false-green

### GitNexus Keys

- Fingerprint:
  `hyperliquid-clearinghouseState-signer-false-empty + configured-account-overwritten + diagnose-false-green-flat`
- Components:
  `venue-hyperliquid`, `diagnose-live`, `exchange-truth`,
  `production-health`, `v1-parity`, `exchange-docs`
- Symbols:
  `_normalize_hyperliquid_credential`,
  `_load_venue_credential`,
  `_build_exchange_truth_async`,
  `_hyperliquid_credential_identity`
- Watch:
  `exchange_truth.positions.hyperliquid`,
  `exchange_truth.credential_identity.hyperliquid.account_matches_signer`,
  `LIGHTFEE_HYPERLIQUID_ACCOUNT_ADDRESS`,
  `LIGHTFEE_HYPERLIQUID_WALLET_MODE`,
  `assetPositions=[]`,
  `diagnose_live healthy` with known Hyperliquid live positions

### Production Symptom

Cloud Hyperliquid had 18 positions that were not closed, but repeated
post-deploy checks reported no issue because the V2 exchange-truth probe was
reading the signer/API-wallet address instead of the configured trading
account address. Direct read-only Hyperliquid `/info` `clearinghouseState`
against the configured account returned nonzero positions; the signer-derived
address returned an empty `assetPositions` array. That made production
diagnose/health evidence look flat even though exchange truth was not flat.

### Root Cause

This is an exchange-truth identity bug, not a closing-strategy bug.
Hyperliquid account data queries are keyed by the actual master/sub-account
address. API/agent wallets can sign requests, but their signer address is not
the same thing as the account whose positions must be read.

V2 violated that contract in two places:

- `_normalize_hyperliquid_credential()` overwrote an explicit
  `account_address` with the address derived from `wallet_private_key` unless
  the credential was already normalized as `api_wallet`.
- `diagnose_live.py` loaded Hyperliquid keys and account aliases but did not
  load `LIGHTFEE_HYPERLIQUID_WALLET_MODE`, so service-env diagnostics could
  silently enter the wrong normalization branch.

The result was a false-green production gate: local recovered state and the
wrong Hyperliquid account both looked flat, while the configured account still
had live exposure.

### Fix

- Hyperliquid `api_wallet` / `agent_wallet` mode now preserves the configured
  account address and signer private key for exchange truth.
- Hyperliquid account-wallet mode now preserves an explicit `account_address`;
  it derives the account from `wallet_private_key` only when no account address
  is configured.
- Account-wallet trading preflight fails closed when configured account and
  signer-derived account differ, instead of authorizing a mismatched signer.
- `diagnose_live.py` loads `LIGHTFEE_<VENUE>_WALLET_MODE`, normalizes
  `agent_wallet` to `api_wallet`, and passes wallet mode into `LiveCredential`.
- Hyperliquid exchange truth now includes sanitized credential identity:
  masked account/signer, short hashes, wallet mode, and
  `account_matches_signer`, without leaking full addresses or private keys.

### Production Symptom

Production read-only evidence showed local `open_position`, `pending_entry`,
`pending_close`, and residual state flat, while Bybit still had two
non-reduce-only maker open orders:

- `SUSHIUSDT` buy `144.2 @ 0.1664`,
  order `f37adbb4-caa1-4044-9e36-ba897bbba795`;
- `MEUSDT` buy `408.0 @ 0.0588`,
  order `57a9c1b4-0b73-4a73-ad24-080a424f2ed5`.

The same run first emitted deferred maker-open-order evidence, then later
emitted `reconciliation.entry_abandoned_flat` with
`reason=both_venues_zero` and refreshed recovery as if the account only had an
evidence gap. That dropped the pending owner before exchange open-order truth
proved the maker artifact was gone.

### Root Cause

This is a pending-entry terminality/live-truth recurrence, not a RecoveryLedger
classification bug. V2 had already learned that missing passive progress and
unavailable open-order truth must retain pending work, but one bypass remained:
when `query_passive_order_progress()` returned terminal no-fill progress
(`execution_not_found` represented as `canceled` / no fill), V2 treated
`pending.maker_completed()` or terminal passive state as proof that the maker
order could no longer be live.

That was too weak for Bybit-like eventual consistency. Execution history can
return no fill while `/v5/order/realtime` still returns the live maker order.
V1's semantic contract is that stale pending-entry clearing requires stronger
terminal exchange evidence; local flat position and terminal/no-fill order
history alone do not prove that a maker owner is gone.

### Fix

- `_pending_entry_has_unresolved_maker_order()` no longer returns terminal for
  `pending.maker_completed()` unless the maker fill quantity proves the maker
  target was actually filled.
- Terminal no-fill passive progress now checks realtime open-order truth. A
  matching order id or client id retains pending and emits
  `pending_entry.maker_open_order_retained`.
- If realtime open-order truth is unavailable, the runtime retains pending and
  emits `pending_entry.maker_terminal_evidence_unavailable`.
- Only explicit open-order truth with no matching maker order allows the
  terminal no-fill flat abandon path to continue.
- `_ensure_pending_entry_maker_not_open_before_abort()` uses the same
  actual-fill-only fast path before abort cleanup, so a canceled/rejected
  no-fill pending entry cannot bypass the maker-open-order guard.
- `_abort_pending_entry_fail_closed()` latches operator-requested fail-closed
  before abort cleanup so a subsequent recovery refresh cannot immediately
  clear the fail-closed state during the same abort path.

### Production Symptom

Post-deploy review showed no service crash and no current Local L2 mainline
blocker, but the deploy window still had several safety/diagnostic events:

- `runtime.quote_stale` from sidecar quote evidence just over the quote budget;
- low-volume `runtime.entry_blocked_ws_bbo_selection`;
- one `runtime.entry_blocked_post_only_bbo`;
- `runtime.snapshot_fallback_last_good` / `runtime.snapshot_degraded`;
- `l2_evidence.stale_rebuild_count=1` even though no
  `runtime.entry_blocked_local_l2_selection` recurrence existed.

### Root Cause

This is a CL-061 follow-up, not a rollback to Local L2. Production already uses
`entry_readiness_provider=ws_bbo_quote_lease`; the remaining gap was quote
evidence ownership and diagnosis vocabulary:

- candidate snapshot freshness still treated stale sidecar quotes as direct
  entry blockers even when the active provider had fresher WS BBO for the same
  venue and symbol;
- post-only BBO protection correctly blocked would-take maker prices, but did
  not first reprice from the same fresh WS BBO evidence;
- `diagnose_live.py` counted `runtime.snapshot_stale` and
  `runtime.snapshot_degraded` as Local L2 stale rebuild evidence.

V1 and exchange-doc semantics still require fail-closed behavior for new
opening risk when fresh BBO is unavailable. Bybit PostOnly orders may be
cancelled if they would execute immediately, and Hyperliquid documents
post-only / ALO price errors separately from quote-provider health. Therefore
the fix reduces false blockers and false Local L2 attribution without deleting
the entry safety gates.

### Fix

- Added a source-aware WS BBO entry quote resolver. Under
  `ws_bbo_quote_lease`, stale sidecar quote evidence is resolved only when the
  WS BBO cache has fresh valid BBO for the same venue/symbol. The runtime
  records `runtime.entry_quote_evidence_resolved_by_ws_bbo`, marks that quote
  metric as fresh WS BBO evidence, and keeps the candidate in the entry path.
- Sidecar missing/invalid quote remains fail-closed even if WS BBO has a fresh
  quote. If WS BBO evidence is missing, stale, invalid, or outside the
  quote-lease age budget, stale sidecar quote evidence also remains
  fail-closed through the existing quote-stale path.
- The WS BBO post-only guard now attempts one maker-side reprice when a fresh
  BBO proves the current maker price would cross. BUY reprices to best bid;
  SELL reprices to best ask. If the repriced price would still cross, or BBO
  evidence is missing/stale/invalid, the guard still emits
  `runtime.entry_blocked_post_only_bbo`.
- Dispatch writes the repriced maker hint back to the eventual order context and
  emits nonblocking `runtime.entry_post_only_bbo_repriced` evidence.
- `diagnose_live.py` now returns `snapshot_evidence` separately. Local L2
  evidence no longer counts snapshot stale/degraded events, and conclusion
  next-actions say "snapshot stale/degraded" instead of "L2 stale/rebuild" when
  there is no true Local L2 event.
