### Summary

The Binance candidate-discovery release `fbb6b39` was deliberately read-only:
it finds possible historical Binance close orders but does not import evidence,
replay accounting, or remove an owner. It therefore could not clear the three
historical COTI/COW/BICO accounting debts by itself.

The COTI owner has a separate deterministic V2 drift. Its first close segment
is a legitimate long-only partial; the later final owns the remaining short
segment. V2 validated the partial against the full snapshot, treated it as a
terminal bill, and never carried its realized PnL/fee into the final. It also
rejected every genuine `OrderFillReconciliation` as missing a close price,
because the contract exposes `average_price`, while the final check read a
nonexistent `price` field.

Subsequent read-only exchange proof establishes a distinct COW historical
shape. The persisted owner says `partial`, with Binance long close quantity
zero and no later final successor; its Bybit short leg is exact. However,
Binance `allOrders` plus `userTrades` identifies one reduce-only `SELL/LONG`
order for the complete 123 quantity, and Bybit execution history identifies
the persisted close order for the same 123 quantity. The two fills are 1.343 s
apart and carry the project's CIDs. Thus the physical close was complete; the
local record was classified from incomplete local fill observation. The old
journal no longer contains enough source data to distinguish a lost ACK,
process-stop window, or adapter omission, so that sub-cause remains unknown.

The recurrence mechanism is nevertheless known. When a close submit outcome
was uncertain but V1 compensation later saw both venue positions flat, V2
retained only positive local fill records when it registered billing work. It
discarded the CID of the unconfirmed submit, so a complete physical close could
be persisted as a `partial` with no exact identity for the missing leg. That
boundary, rather than any strategy or liquidity decision, is what the runtime
repair closes.

### Authoritative Contract

V1 recovery processes partial reconciliation before its later final. A partial
emits non-terminal accounting, propagates cumulative realized price PnL and
exit fee to the remaining owner, and only the final emits the terminal bill.
The V2 domain contract for exchange reconciliation is
`OrderFillReconciliation.average_price`; it is built from exact execution
evidence. Binance fills require the order plus its execution history for
commission evidence; Bybit likewise exposes executions separately. Sources:
[Binance account trade list](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/Account-Trade-List)
and [Bybit execution list](https://bybit-exchange.github.io/docs/v5/order/execution).

An exact exchange order ID remains authoritative, with its client ID carried
as auxiliary lookup identity, matching V1. Time/quantity/direction matching
can only discover a candidate; it never clears a bill without exact execution
evidence.

### Root Cause and Repair

1. Partial task quantities now come only from its recorded
   `original_payload.*_closed_qty`; a declared zero opposite leg is valid.
   A partial without those segment quantities remains fail-closed.
2. A reconciled partial emits `exit.partial_reconciled`, propagates cumulative
   accounting to the later final/open position, and is never terminalized
   without a successor. Journal and startup replay preserve the propagation.
3. The terminal price check now reuses `_recon_fill_price`, the same
   `average_price`-aware converter used by aggregation. This restores the
   actual `OrderFillReconciliation` contract rather than relaxing evidence.
4. Recovery queries now forward both order ID and CID as V1 does. Legacy
   finals lacking snapshot quantities retain their established two-positive-
   fill compatibility rule; partials do not get this fallback.
5. A later operator import cannot overwrite already-propagated partial PnL or
   exit fee with a stale final snapshot.
6. A separate, explicit operator action can migrate only an **orphaned legacy
   partial** to a final owner. It requires full exact-identity legs whose
   aggregate quantities equal both original snapshot legs, no local open
   position, and no final successor. The imported final remains pending until
   the normal runtime fetches both exchange executions and emits
   `exit.reconciled`; malformed, partial, or merely time/side/quantity-matched
   evidence still remains fail-closed.
7. For every new uncertain close submit, V2 now persists the generated CID as
   a zero-quantity **identity placeholder**. It is not a claimed fill and
   cannot emit `exit.closed`; it gives the normal reconciler the exact order
   history lookup key that V1 retains.
8. Only an exact re-fetch of both legs, whose aggregate quantities equal the
   original full snapshot, reclassifies this one observationally stale partial
   to the existing final bill path. Any missing, partial, duplicate, or failed
   re-fetch remains a pending debt.
9. That exact terminal transition clears its same-position residual-repair
   owner in both the live path and journal replay. It cannot later send a
   needless reduce-only repair against an already-flat pair.
10. If compensation cannot fetch venue position truth, V2 now fail-closes as
    V1 does, while first persisting every known fill and uncertain-submit CID
    for later reconciliation.

No strategy, liquidity/OI gate, sizing, entry, close submission, or normal
successful-close exchange request count changed. The exceptional
uncertain-submit path now performs the necessary exact order-history lookup;
the first order submit and all normal close ordering remain unchanged.
