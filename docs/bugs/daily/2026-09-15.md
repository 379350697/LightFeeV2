# Bug Ledger Daily - 2026-09-15

## CL-151 — 拆单平仓的补集证据闭环 (split-close complement evidence)

Status: **closed** (production-verified).

### Symptom

After CL-150's execution-window anchor repair, `entry-1788537122325-ONGUSDT`
still terminalized as `binance_user_trades_no_candidate` even though the
exchange held complete evidence for the whole 252 close.

Observed input/state (read-only exchange queries):

- close order `3274922181` (`lfex081f61015871220b`): `SELL LONG reduceOnly`,
  `origQty 252`, `executedQty 203`, terminal `EXPIRED` (IOC remainder
  canceled), commission `0.00386309` present only in `/fapi/v1/userTrades`;
- close order `3274923320` (`lfxlbf3c33694b54acf2`): `SELL LONG reduceOnly`,
  `49` `FILLED`, commission `0.00232995`;
- short leg: one complete 203 fill plus a zero-quantity stored leg whose
  exact lookup returns no fill.

Observed output/state transition: discovery for the full 252 found no single
group matching 252 → `binance_user_trades_no_candidate` → irrecoverable.

### Root cause

Three boundaries jointly made a close split across orders unsettleable:

1. The uniqueness contract compares one execution group against the full
   segment quantity; a split close (203 + 49) matches no single group.
2. The Binance exact recheck reads `/fapi/v1/order`, which carries no
   commission, so the stored 203 identity could never become fee-complete
   evidence (the completeness gate requires `fee_evidence_complete`).
3. A stored zero-quantity leg whose lookup finds no fill returned `None`
   and failed the whole leg recheck (`known_leg_exact_query_unavailable`),
   even though a zero-quantity leg carries no fill evidence by construction.

CL-150's own review had accepted "operator import" for this shape; that
conclusion is superseded here.

### Contract

For a leg whose exact recheck yields fee-complete fills covering only part of
the immutable close segment, automatic history discovery runs for the
complementary quantity, and the leg's evidence is the merged set, validated
against the full segment. The complement must be a distinct order (overlap is
contradictory evidence and fails closed). Binance fee evidence comes from the
order's own executions. A stored zero-quantity leg that finds no fill is
skipped; a positive-quantity leg that cannot be looked up still fails closed.

### Counterexample matrix

- Production shape settles: known 203 (fee-enriched) + complement 49 =
  252, both order ids on the billing record.
- Complement re-discovering a known order id → `complement_identity_overlap`,
  terminal, never double counted.
- Merged set incomplete (fee/price/identity/total) →
  `merged_complement_evidence_incomplete`, terminal.
- Zero-quantity leg lookup miss skips the leg; the same miss on a
  positive-quantity leg keeps the whole leg unavailable.
- Per-repair one-scan tiering: legacy `no_candidate` → window repair scan →
  post-anchor miss → complement repair scan → terminal forever; a
  capability-classified miss cannot re-arm the same repair.

### Repair (`3a50dcfb`)

- `CloseRuntime._fetch_automatic_historical_close_evidence`: keep fee-complete
  known fills, discover the missing quantity, merge and validate.
- `BinanceAdapter.fetch_order_fill_reconciliation`: per-order `/fapi/v1/userTrades`
  commission enrichment (missing/malformed rows stay incomplete; a present
  zero is complete).
- `CloseRuntime._fetch_close_leg_reconciliations`: stored-zero leg lookup miss
  skips instead of failing the leg.
- `_reactivate_history_discovery_upgrade`: grants are one scan per repair per
  debt, recorded via `automatic_history_reactivation_reason`; a post-anchor
  `binance_user_trades_no_candidate` miss on a binance leg earns the
  `binance_split_close_complement` scan exactly once.

### Verification

- RED on the pre-fix tree: three of four new tests fail without the change
  (the fourth is the one-scan guard, green on both trees by design).
- Full suite: failures byte-identical to the same-tree baseline (25
  pre-existing, zero new).
- GitNexus impact before editing (`_fetch_automatic_historical_close_evidence`
  LOW; adapter callers audited), `detect_changes` scope matched intent.
- Production `2026-09-15 19:11 CST`: seven seconds after restart the debt
  reactivated under `binance_split_close_complement` and reconciled in the
  same second — merged long legs `3274922181` (203, `0.00386309`) +
  `3274923320` (49, `0.00232995`), short recheck unblocked, billing `final`
  (exit fee `0.01692484`). Owners 5 → 3. Exchange truth stayed
  high-confidence flat/no-order; no order submitted or cancelled.

- `1788537122325-ONGUSDT` partial: operator import by design (automatic

## CL-152 — 空 owned 终债的无限重试 (empty-owned final debt retry loop)

Status: **closed** (production-verified).

### Symptom

`entry-1789091700691-ONGUSDT` (final, evidence debt) journaled
`reconciliation.pending_close_reconciliation_invalid
close_order_lookup_returned_no_fill` every ~5 minutes for four days
(1,287 attempts) without ever settling or terminalizing.

Observed input/state: the deadline fallback flattened both legs before any
fill identity was learned, so the record owns `{long: 0.0, short: 0.0}` with
zero-quantity stored identities (`db66ce99…` bybit, `1482124806810382426`
bitget, both zero-fill lookups).

Observed output/state transition: the automatic history path passed the
flat-truth gates, found both expected quantities `<= 1e-12`, resolved both
legs to empty fills, and returned `([], [], {})`; the caller's
both-fills-empty branch journaled the invalid event and backed off — forever.

### Root cause

When both legs of the immutable close segment are empty, no venue discovery
contract can run (they require a positive quantity) and no exact lookup can
produce evidence, so the shape can never leave the both-fills-empty branch —
yet that branch only retried. The designed V1-parity terminal for a
physically proven close without learnable fill evidence
(`_try_terminalize_billing_evidence_gap` →
`provisional_close_quantity_evidence_incomplete`) sat unreachable behind a
payload-build guard that required at least one non-empty fill list.

### Contract

A final close-reconciliation whose immutable owned segment is empty on both
legs, with two-leg flat truth and no open orders, terminalizes through the
existing provisional billing terminal: no manufactured `net_quote`, `price_pnl`,
exit fees, or average prices; known identities and quantities are carried;
billing reconciliation stays required for the operator. Non-flat legs, open
orders, non-final kinds, or a positive owned segment with empty fills keep
the previous retry/backoff semantics.

### Counterexample matrix

- Empty owned + flat + no open orders → provisional terminal, removed from
  pending (RED on the pre-fix tree).
- Empty owned + a live leg (292) or an open order → retained, backoff, no
  terminal event.
- Positive owned (292) + all-zero stored legs → the invalid
  close-lookup backoff is unchanged.

### Repair (`2be127cc`)

The payload-build guard in `_process_pending_close_reconciliations` admits
the empty-owned final shape (`(long_fills or short_fills) or
empty_owned_segment`), routing it through the existing payload builder —
which already yields `venue_statement_reconciled=false` for an empty segment —
and the existing evidence-gap terminalizer. No new state, classification, or
queue.

### Verification

- RED: the flat-terminal test fails on the pre-fix tree; the two safety
  counterexamples pass on both trees by design.
- Full suite: failures byte-identical to the same-tree baseline.
- Production `2026-09-15 21:52 CST`: four minutes after restart the debt
  settled — `exit.billing_evidence_unavailable` with
  `terminal_live_flat_incomplete_close_quantity_evidence`,
  `provisional_close_quantity_evidence_incomplete`, `long_live_size=0.0`,
  `short_live_size=0.0`, `open_order_truth_flat=true`, zero manufactured PnL
  keys, and removal from the pending list (owners 3 → 2). Seven-venue truth
  stayed high-confidence flat/no-order; no order submitted or cancelled.

### Final debt inventory

- `entry-1788403990217-CYSUSDT` final: Aster `aster_v3_no_candidate`
  terminal; operator import only.
- `entry-1788537122325-ONGUSDT` partial: automatic history does not support
  partial segments; operator import only.
