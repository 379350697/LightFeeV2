### V1 Comparison

This is the same root family as `BEATUSDT`/`OPGUSDT` rather than a new strategy issue.

- V1 does not repeat an identical terminal under-minimum hedge forever. It buffers while the maker can still accumulate; once maker terminality or attempt exhaustion is reached, it emits the min-notional abort path and compensates/flattens from live exchange truth.
- V1 residual repair is driven as normal housekeeping for non-paused tasks. It computes live excess on the repair venue and either sends a reduce-only repair, terminalizes official dust, or stays fail-closed when live truth is untrusted. V1 remains conservative once a task is locally paused; V2 therefore needs an explicit root-fix extension for production PARTI, guarded by trusted live position/open-order truth and retry backoff.
- V2 drift:
  - `PassiveCloseExecutor._submit_hedge_for_delta()` had a second terminal-maker branch that still treated `price_unavailable_for_min_notional` as a 5-second retry even after live-flat probing proved exposure remained.
  - `PassiveCloseExecutor._flatten_live_one_sided_position()` treats `price_unavailable_for_min_notional` as a retryable 5-second delay even with confirmed one-sided live exposure.
  - `Runtime._recover_residual_repairs()` refuses to submit a tradeable repair when a task is already locally paused or attempt-exhausted, leaving `residual_repair_live_position_nonzero` as a permanent gate.

### V1 Comparison

- Local-L2: V1 and V2 both require venue-documented sequence continuity for a trusted local order book. A broken previous-link is not safe to "root fix" by accepting the delta. The correct behavior is to reinitialize from a fresh snapshot and keep enough evidence to distinguish official reset/sequence behavior from parser drift.
- Terminal close errors: V1 treats terminal reduce-only or already-flat close rejections as a possible flatness signal only after live exchange truth proves both legs are flat. V2 current behavior matches this: `exit.passive_close_fallback_terminal_flat`, `recovery.flat`, and `runtime.position_drift_corrected` appeared, and no pending close/residual loop remained.
- Post-only maker rejects: V1 does not treat a deterministic maker/post-only reject as an opened entry. The latest `-5022` sample is an entry admission/order-placement outcome, not a close/residual bug.

### Exchange Docs

- Binance USD-M local orderbook docs require buffering depth events, applying a REST snapshot, processing the first bridged event, and then requiring each new event's `pu` to equal the previous event's `u`; otherwise the local book must be reinitialized: https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly
- Aster futures market-stream docs state the same local-orderbook rule: each new event's `pu` must equal the previous event's `u`; otherwise initialize again from the snapshot process: https://asterdex.github.io/aster-api-website/futures/websocket-market-streams/
- Binance USD-M error docs define `-5022 GTX_ORDER_REJECT` as post-only maker rejection when the order could not execute as maker: https://developers.binance.com/docs/derivatives/usds-margined-futures/error-code
- Binance developer FAQ documents `-2022 ReduceOnly Order is rejected` causes including no position to close or conflicting open reduce orders; V2 therefore must recheck flatness instead of retrying blindly: https://dev.binance.vision/t/why-do-you-get-reduceonly-rejection-errors/1198

### Root Fix Decision

No trading-path code change is required for the current evidence. The root fix is diagnostic/harness classification only, so future reviews do not misclassify Aster official continuity resets as unresolved V2 drift and do not over-classify arbitrary field-complete events as official-doc evidence.

1. Do not relax Binance/Aster `pu == previous u` continuity. That would violate exchange docs and can create a false-trusted book.
2. Share one strict helper across `diagnose_live.py`, `analyze_production_blockers.py`, and the Local-L2 incident harness.
3. Classify official rebuilds only when Binance/Aster evidence proves one of:
   - `raw_pu != expected_previous_sequence` with a valid sequence range.
   - `raw_pu == expected_previous_sequence` but `raw_U > expected_previous_sequence + 1`, proving a real skipped update.
   - REST snapshot boundary is not bridged.
4. Keep the V1 terminal close semantics: terminal reduce-only/already-flat errors can clear only after live exchange flatness verification.
5. Treat Binance `-5022` post-only maker reject as a normal maker-placement rejection unless it is followed by a stale pending/open-position drift. This run has no such drift.
6. If future rebuild volume becomes entry-blocking, open a separate bug only when `runtime.entry_blocked_local_l2_selection` lacks symbol/venue/readiness evidence or when a candidate is blocked despite fresh quote/local-L2 proof.
