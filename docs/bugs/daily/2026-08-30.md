# Bug Ledger Daily - 2026-08-30

## CL-135 — delayed owned maker fill was cleaned before hedge, and entry leverage was not proved for every live leg

Status: **local-green in the working tree; uncommitted and not deployed**. No
order, cancellation, runtime-state, service, or cloud deployment action was
performed for this repair.

### Evidence and authoritative contract

The COTI incident had an acknowledged owned maker order and an exchange-visible
maker position, but the first exact execution query returned no fill. Five
seconds later the existing zero-fill/live-position branch submitted a
reduce-only cleanup, even though the later exchange execution showed that the
maker fill had arrived before that cleanup. This was a loss of the normal
maker-fill → hedge path, not evidence of an externally owned orphan.

V1 keeps a pending owner when its passive maker order has not reached a
terminal fill decision. Once exact order/execution evidence arrives, normal tick
reconciliation applies maker progress and submits the existing hedge delta.
Only the terminalization budget owns the fail-closed cleanup of evidence that
never resolves. V2 had regressed by treating an owned live maker position plus
temporarily empty execution history as an immediate cleanup conflict.

The ONG incident independently proved that production configured
`live_target_leverage=4` while Bybit position truth was `10`. V2's live entry
preparation originally selected only Binance and Aster, so it never called
Bybit. Its first local repair replaced that tuple with an opt-in capability,
but only Binance, Aster, and Bybit opted in: OKX, Bitget, Gate, and
Hyperliquid could still silently open without leverage preparation.

V1 is the compatibility contract: every live entry leg calls
`ensure_entry_leverage`, with a single call when both legs use the same venue.
There is enough independent evidence to repair the whole family at the adapter
boundary: the official exchange mutation contracts are [Bybit
V5](https://bybit-exchange.github.io/docs/v5/position/leverage), [OKX
V5](https://www.okx.com/docs-v5/en/#trading-account-rest-api-set-leverage),
[Bitget Classic](https://www.bitget.com/api-doc/contract/account/Change-Leverage),
[Bitget UTA](https://www.bitget.com/api-doc/uta/account/Change-Leverage),
[Gate Futures](https://www.gate.com/docs/developers/apiv4/en/#update-position-leverage),
and [Hyperliquid Exchange](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint).

### Root repair and rejected patterns

`_ensure_pending_entry_open_fill_details` now lets its existing non-terminal
maker-evidence branch retain the pending owner and schedule its one-second
reconciliation when an acknowledged maker has a live exchange position but no
exact fill yet. The repair removes only the erroneous early finalization that
previously bypassed that branch. Existing hard-budget abort/cleanup remains
unchanged for evidence that never becomes exact.

Entry dispatch now requires the existing adapter boundary's explicit
`supports_entry_leverage_preparation` capability for **each** selected live
leg. A missing adapter, capability, or method is a rejected admission before
any setter or order; it is no longer a silent opt-out. The dispatch loop also
matches V1 by de-duplicating a same-venue pair.

The implementations are deliberately adapter-specific, not a generic Binance
transport extension:

- Binance and Aster retain the existing signed position/bracket/set response
  proof.
- Bybit reads `/v5/position/list`, sets both sides only when needed, and reads
  back; `110043` is accepted only after the exact target is observed.
- OKX reads the strict account position mode, reads the corresponding
  `leverage-info` rows, sets only non-target `net` or `long`/`short` sides, and
  reads the same rows back.
- Bitget resolves the existing Classic/UTA account family. UTA reads settings
  before and after its setter; Classic requires the documented
  `crossMarginLeverage` returned by its setter to equal the target.
- Gate retains V1's public catalog clamp and retries only its documented
  single-to-dual position-mode rejection; every accepted setter response must
  report the effective leverage.
- Hyperliquid retains V1's public `maxLeverage` clamp and requires a successful
  signed `updateLeverage` acknowledgement. A position readback is intentionally
  not invented: a first entry can have no `userState.assetPositions` row, while
  the acknowledged signed mutation is its authoritative completion proof.

Do not reintroduce either prior repair pattern:

- Do not flatten a live maker position merely because the first exact fill
  query is temporarily empty; that converts an order-history delay into a
  guaranteed realized loss and bypasses normal hedge recovery.
- Do not add a second hedge worker, blind retry, timer, or COTI-specific
  exception. The existing pending-entry reconciliation and budget paths own
  both outcomes.
- Do not hard-code an expanded venue tuple, silently skip a false capability,
  or trust a successful setter without its venue-specific proof. New live
  order adapters must implement the shared capability; dispatch blocks until
  they do.
- Do not route OKX, Bitget, Gate, or Hyperliquid through the Binance/Aster
  transport helper, add a blind write retry, or add an artificial Hyperliquid
  position readback. Those would either use the wrong exchange contract or
  reject valid first entries.

### CL-133 — shared public transport erased failure evidence and reused a failed client

#### GitNexus Keys

- Fingerprint: `shared-http-opaque-network-error-client-retirement`
- Components: `market-data`, `targeted-oi`, `venue-transport`, `sidecar`, `production-observability`
- Symbols: `MarketDataClient._public_request`, `MarketDataClient._retire_failed_client`, `VenueTransport._request`, `VenueTransport._request_listen_key`, `EntryOpenInterestRefresher.refresh_open_interest`, `MarketDataRuntime._refresh_entry_candidate_open_interest_evidence`
- Files: `lightfee/venues/market_data.py`, `lightfee/venues/transport.py`, `lightfee/engine/market_data_runtime.py`
- Commits: uncommitted
- Watch: `runtime.entry_oi_targeted_refresh_failed`, `open_interest_transport_error_type`, `open_interest_transport_error_cause_type`, `open_interest_client_generation`, `open_interest_client_retired`, process FD / `CLOSE_WAIT`

#### Symptom and evidence

The production review preceding this repair found repeated fail-closed OI and
account-HTTP failures. In particular, 37 targeted-OI refresh failures carried
messages equivalent to `network: GET /fapi/v1/openInterest: `: the exception
text was empty, so the journal could not distinguish a read-side peer close,
connect failure, pool exhaustion, or a venue response. Separate Hyperliquid
balance failures showed the same broader outbound HTTP family, but do **not**
prove that they share one socket-level cause. The earlier Aster attribution was
also not sufficient: a CDN endpoint alone cannot identify a venue-owned client.

The symptom was therefore confirmed; a venue-specific or retry-based remedy
was not. The earliest common boundary with enough information is
`MarketDataClient._public_request`, whose `httpx.NetworkError` formatting used
only `str(exc)`. A bare `httpx.ReadError` stringifies to empty text. The same
base client is inherited by `VenueTransport`, so a failed pooled connection
could remain reusable by both public and private REST calls.

#### Authoritative contract and V1 comparison

V1 keeps bounded persistent HTTP pools; it does not reset an Aster-only
transport or add a retry policy after an opaque failure. The compatible V2
contract is:

1. The current request remains failed and all trading/admission consumers stay
   fail-closed; it is never retried by this transport repair.
2. Every `httpx.NetworkError` records a safe request phase, exception class,
   deepest available cause class/message, shared-client generation, and whether
   that client was retired. Request URLs, signatures, and payloads are not
   copied into the diagnostic.
3. A client that produced a network failure is removed from future reuse. It is
   closed only after every request that had already borrowed it has released
   its lease. The next request constructs the normal bounded replacement
   client.
4. Timeout classification, HTTP status handling, rate limiting, signing,
   order semantics, and all retry ownership remain unchanged.

This is client-health handling, not a claim that any one exchange caused the
connection close.

#### Repair and full production path

`MarketDataClient` now owns the client generation and short-lived borrow/release
lease. `_public_request` emits typed `PublicTransportError` diagnostics, retires
only a proven `httpx.NetworkError` client, and releases it in `finally`.
Cancellation follows the same retirement/release path. `VenueTransport` uses
the existing base client, so its generic private REST and listenKey requests
also borrow/release that same lifecycle; this prevents a public failure from
closing a shared client while a private request is still using it. No Aster
branch, new retry, pool-size change, or second transport implementation was
added.

The OI evidence path preserves those fields through
`MarketDataClient.fetch_entry_open_interest_evidence` →
`EntryOpenInterestRefresher.refresh_open_interest` →
`MarketDataRuntime._refresh_entry_candidate_open_interest_evidence` →
`runtime.entry_oi_targeted_refresh_failed`. It still reports `http_error` and
blocks the candidate rather than converting unavailable OI to a safe value.

#### Rejected repair patterns

- Do not reset only the Aster client: the confirmed bug is in the shared base
  transport and endpoint attribution is not proven.
- Do not add automatic retries, relax admission, suppress failures, or repeat a
  write: retry ownership and order uncertainty remain with their existing
  callers.
- Do not close a shared client immediately while another request holds it; that
  turns one peer failure into an unrelated private REST failure.
- Do not reset every pooled client after any error or alter the normal bounded
  pool limits; retire only the client that produced `httpx.NetworkError`.
- Do not log query strings, signed headers, or bodies as diagnostic evidence.

## CL-134 — a normal matched hedge was globally blocked by unrelated close-accounting debt

Status: **deployed-awaiting-verification; commit `2111e36`, deployed through
`fe821142`**. The preceding commit `8a2def63` was deployed and safely
reproduced the missed complementary path; it is recorded as an incomplete
attempt, not as closure.

### Production evidence and authoritative contract

On the deployed `8a2def63` line, a natural `ZKPUSDT` position reached normal
exchange truth: OKX long `840`, Binance short `840`, and no open orders. The
pending entry terminalized into one normal local `OpenPosition`. Nevertheless
the exported lifecycle stayed `risk_only`, because a historical COTI final
close `evidence_debt` remained in `pending_close_reconciliations`.

V1 `process_pending_close_reconciliations` releases lifecycle to `Running`
when no active position remains **or** all active positions have private
confirmation; it does not turn a confirmed normal hedge into recovery work
solely because billing reconciliation remains. V2 deliberately uses a
stronger proof: complete, supported account REST truth must exactly match all
local long/short quantities and directions and must report no open orders.

### Root cause and repair

`8a2def63` added the exact normal-pair matcher, but
`V1RecoveryDecisionCore._has_only_close_reconciliation_work()` still required
`local_open_positions` to be empty before the matcher could run. That
contradicted the V1 active-position background-accounting branch and made the
earlier release code unreachable for the production case.

`2111e36` changes only that existing core predicate. A nonempty local position
set is acceptable only when the existing account-scoped matcher proves every
managed pair exactly normal. Pending entry/residual/passive/owner work,
incomplete truth, one-leg/wrong-side/wrong-quantity observations, and any open
order still select the existing blocking decisions. RecoveryLedger remains the
sole pair-scoped entry gate for close debt; no runtime branch, retry, or new
state was added.

### Counterexamples and verification

The real `LiveRuntime._complete_pending_entry_terminal_removal` path now carries
an unrelated terminal COTI close debt while the normal ONG pair is terminalized.
It was RED on `8a2def63` (`risk_only`) and is GREEN with `2111e36` (`running`).
The pure-core matrix pins matching pair release plus one leg, wrong side, wrong
quantity, and open-order retention. Focused recovery/startup/entry/diagnosis
coverage: `477 passed`; full suite: `4491 passed, 9 skipped, 1 warning`.

### Production acceptance after deployment

`fe821142` passed manifest verification and restarted both services once; both
are active with zero restarts. Post-deploy read-only diagnosis has high-
confidence all-venue flat/no-order truth and reports
`RUNNING_WITH_EVIDENCE_GAP`, `entry_allowed=true`, and the existing terminal
close debt as background work. The remaining proof is a natural **matched open
pair** beside that debt: it must remain `running`/entry-eligible globally,
while its exact pair is still governed by RecoveryLedger and any incomplete or
non-normal account truth remains `risk_only`. Do not force an order to produce
the observation.
