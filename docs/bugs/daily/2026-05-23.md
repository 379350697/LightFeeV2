## Cluster CL-001-passive-close-bybit-tick-v1-drift

### GitNexus Keys

- Fingerprint: `v2.passive-close.bybit-altusdt-static-price-tick-zero-aligned + v1-passive-order-tick-metadata-quote-fallback-drift`
- Components: `passive-close`, `venue-bybit`, `symbol-rules`, `local-l2`, `live-runtime`, `v1-parity`
- Symbols: `PassiveCloseExecutor._submit_maker_order`, `PassiveCloseExecutor._maintain_maker_order`, `PassiveCloseExecutor._get_passive_tick_size`, `PassiveCloseExecutor._get_symbol_rule_tick_size`, `PassiveCloseExecutor._infer_passive_tick_from_l2_quote`, `LiveRuntime._resolve_local_l2_quote`
- Files: `lightfee/engine/passive_close.py`, `lightfee/engine/runtime.py`, `tests/test_passive_close.py`
- Commits: working tree
- Watch: `exit.passive_close_invalid_aligned_price`, `aligned price <= 0 after tick alignment`, `maker_venue=bybit`, `symbol=ALTUSDT`, `price_hint=0.0078`, `tick_size=0.01`, `aligned_price=0.0`

### Summary

Cloud latest deploy was active but not effective for the current passive close. The run stayed in `risk_only` / `fail_closed` with an `ALTUSDT` open position and a pending passive close. The repeated blocker was:

`exit.passive_close_invalid_aligned_price`: Bybit maker short close, `price_hint ~= 0.0078`, `tick_size=0.01`, `aligned_price=0.0`.

Bybit public instruments info for `ALTUSDT` reports `priceFilter.tickSize=0.000001`. The local V2 path had the dynamic venue rule available at the transport layer, but passive-close pre-submit validation used the static `VenueSpec` / adapter tick first and failed before the transport order preflight could correct it.

### Review Finding

Self-review found the first local fix was incomplete. It added dynamic symbol-rule lookup before static tick, but still missed V1's second fallback: when passive order metadata is absent, infer tick size from quote precision (`best_bid`, `best_ask`) before any static fallback. That was a real V1 drift and would leave the close vulnerable if metadata fetch failed while local-L2 was hot.

Follow-up review found a second completeness gap: `SymbolRulesCache` returns `rule_source="spec_fallback"` when a venue has no dynamic fetch path or when the dynamic endpoint fails. Treating that as passive metadata would make the fix Bybit-shaped instead of V1-shaped. `_get_symbol_rule_tick_size()` now returns `0.0` for `spec_fallback`, forcing `_get_passive_tick_size()` to try quote inference before static tick for every venue.

### Shared Root Cause

V2 copied the passive price alignment behavior but not V1's passive tick source precedence.

V1 order:

1. `adapter.passive_order_metadata(symbol).tick_size`
2. infer price tick from quote best bid / best ask fractional precision
3. if needed, infer from target price distance / spread
4. otherwise no passive tick

V2 order before the fix:

1. static `VenueSpec.price_tick` or `adapter.price_tick_size`
2. align the passive close price
3. fail locally when static tick was larger than the sub-cent instrument price

The venue transport already knew how to fetch Bybit instrument metadata, but passive close blocked before submitting a request to that transport path.

### Fix Status

Deployed; production acceptance pending because the current run has no ALTUSDT passive close to exercise this path.

- `_submit_maker_order()` and `_maintain_maker_order()` now call async `_get_passive_tick_size(..., target_price=price_hint, side=maker_side)`.
- `_get_passive_tick_size()` resolves true dynamic symbol-rule tick via `get_symbol_rules_cache()` before static tick.
- `_get_symbol_rule_tick_size()` ignores `rule_source="spec_fallback"` so static defaults cannot masquerade as V1 passive metadata.
- `_infer_passive_tick_from_l2_quote()` matches the V1 quote fallback by deriving fractional tick precision from hot local-L2 `best_bid` / `best_ask`, with distance/spread fallback for integer quotes.
- `_get_passive_tick_size()` now returns `0.0` when neither true metadata nor quote inference is available. The old static adapter/spec fallback was removed from the passive close path because V1 does not use it for `passive_order_tick_size()`.
- `LiveRuntime.start()` injects `_resolve_local_l2_quote()` into `PassiveCloseExecutor`.
- `LiveRuntime._resolve_local_l2_quote()` returns hot local-L2 top-of-book bid/ask for the passive close executor.

## Cluster CL-002-passive-close-terminal-flat-probe-snapshot-fallback-drift

### GitNexus Keys

- Fingerprint: `v2.pending-passive-close.position-snapshot-missing-flat-probe-false + terminal-reduce-only-loop-bybit-110017-aster-2022`
- Components: `passive-close`, `close-executor`, `recovery`, `state-persistence`, `v1-parity`, `bybit`, `aster`
- Symbols: `PassiveCloseExecutor._fallback_to_aggressive_close`, `PassiveCloseExecutor._clear_if_live_flat`, `PassiveCloseExecutor._probe_live_flatness`, `CloseExecutor._classify_close_leg_error`
- Files: `lightfee/engine/passive_close.py`, `lightfee/engine/close_executor.py`, `tests/test_passive_close.py`, `tests/engine/test_close_semantic_parity.py`
- Commits: working tree
- Watch: Bybit `110017 current position is zero`, Aster `-2022 ReduceOnly Order is rejected`, repeated `HTTP 400`, `pending_passive_count=2`, `pending.position_snapshot=None`

### Summary

The latest cloud run recovered two stale pending passive closes:

- `entry-1779540996545-GMTUSDT`
- `entry-1779540996545-LYNUSDT`

Read-only exchange probes showed both Bybit and Aster positions were already zero and open orders were zero. The updated close executor classified the venue errors as terminal reduce-only flat, but the passive close fallback still retried every cycle and kept submitting reduce-only orders.

### V1 Comparison

Rust V1 does not have this recovery-source split in the passive close drive loop:

- `start_pending_passive_close()` stores `position_snapshot` inside `PendingPassiveClose`.
- `drive_pending_passive_close()` drives from `pending.position_snapshot.clone()`.
- Dual-taker fallback appends the aggressive close execution, marks the chunk complete, persists it, then the completed path clears pending passive close state.

V2 introduced recovery compatibility where `drive_pending_passive_close()` can recover a missing pending snapshot from `state.open_positions`, but `_probe_live_flatness()` still looked only at `pending.position_snapshot`. That made already-flat recovered positions look ambiguous and caused the retry loop.

This is the same class as the 2026-05-18 parity note for `_current_tracked_private_symbols()`: `position_snapshot=None` must fall back to `open_positions` for recovered pending passive closes. It is a new occurrence of that old recovery-shape drift, not the older ALTUSDT tick-size bug.

### Fix Status

Fixed, deployed, and cloud verified.

- `_clear_if_live_flat()` now passes the recovered `position` into `_probe_live_flatness()`.
- `_probe_live_flatness()` accepts an explicit `position_snapshot` override and falls back to `pending.position_snapshot`.
- Terminal reduce-only paths call `_clear_if_live_flat()` after nonretryable hedge errors, null aggressive results, and zero-fill/no-pending fallback results.
- The close executor classifies Bybit `110017/current position is zero` and Binance/Aster `-2022/ReduceOnly` as terminal reduce-only only when exchange flatness verifies true.
