# 2026-06-24 Bug Ledger

## Cluster CL-111 - Order Truth and Pending Entry Semantic Root Fix

Status: local green; deploy pending.

### Family

Shared order-truth / pending-entry semantic family. DEXEUSDT and LAYERUSDT
are symptoms of the same contract gap, not pair-specific closures.

### Evidence

- Binance new-order responses can be ACK/NEW with `executedQty=0` and an
  order id. That is accepted-but-uncertain evidence, not a confirmed zero fill.
- Pending-entry reconciliation could observe live hedge quantity but leave
  maker remainder FIFO slices untouched, causing `missing_hedge_quantity()` to
  stay nonzero and permitting a duplicate hedge drive.
- Residual repair could receive an order id with zero filled quantity and still
  emit `execution.residual_repair_completed` with `filled_quantity=0`.
- Diagnose counted `runtime.position_drift_corrected` as terminal quick-flat,
  hiding post-entry overhedge drift inside a close/flat bucket.

### Root Cause

The runtime had no single business contract for submit-result terminality and
hedge progress application. ACK/non-terminal order evidence was allowed to
cross into fill semantics, while live/order-truth hedge progress and FIFO
consumption were maintained by separate code paths.

The strict review follow-up found one remaining P1 gap in the same family:
startup/order-status/live-position recovery paths could still assign
`hedge_leg_filled` directly after the first semantic patch. That updated the
visible hedge total but bypassed maker-remainder FIFO consumption, so a restart
or forced reconciliation could re-create a missing-hedge signal even after live
truth had already proved the hedge leg was filled.

### Fix

- Binance MARKET submit now requests `newOrderRespType=RESULT`; ACK/NEW or
  other non-terminal zero-fill responses with an order id raise
  accepted-uncertain `OrderSubmitError` instead of returning `OrderFill(0)`.
- Hedge progress from order-query/live-position/execution reconciliation now
  uses a shared helper that applies the incremental hedge quantity and consumes
  maker remainder FIFO slices together.
- Residual repair zero-fill responses with an accepted order id and remaining
  live excess stay as `execution.residual_repair_inflight` / accepted-order
  truth gap instead of false completed repair.
- Diagnose splits `entry_overhedge_drift_corrected_count` from
  `quick_flat_count`; active overhedge drift is its own blocker.
- Startup order-status recovery, live-position hydration, force reconciliation,
  direct hedge submit, and order-truth reconciliation now all route confirmed
  hedge progress through one helper that updates total hedge quantity, consumes
  maker FIFO, preserves hedge order/price evidence, and records observation
  quality together.
