## Cluster CL-117 - Pending Positive-Fill Price-Gap Blocks Owned Single-Leg Cleanup

Status: local fixed; deploy pending.

### GitNexus Keys

- Fingerprint: `v2.pending_positive_fill_missing_maker_price_defers_before_live_truth_cleanup + synusdt_bitget_flat_binance_short_owned_pending_conflict`
- Components: `live-runtime`, `pending-entry`, `recovery-core`, `v1-parity`, `production-risk`
- Symbols: `PendingEntryRuntime._finalize_pending_entry`, `PendingEntryRuntime._handle_positive_fill_live_truth_conflict`, `LiveRuntime._ensure_pending_entry_open_fill_details`, `PendingEntryTerminalizer.decide`
- Files: `lightfee/engine/pending_entry_runtime.py`, `tests/test_pending_entry_v1_semantic_drift.py`
- Watch: `pending_entry.finalize_deferred_incomplete_fill missing_fields=["maker_fill_price"]`, `pending_entry.positive_fill_live_truth_conflict`, `pending_entry.owned_live_conflict_cleanup_*`, `owned_pending_entry_live_conflict`, `exchange_truth_nonzero_position`, `SYNUSDT`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Summary

After CL-116 was deployed, Gate sizing and Bitget duplicate close evidence did
not recur, but the latest cloud deploy was not green. Read-only diagnose found
one real `SYNUSDT` Binance short position with no paired Bitget long, no open
orders, and one local pending entry. The pending entry recorded both maker and
hedge quantities as filled, but the Bitget maker fill price was still `0`
because later order/fill truth classified the maker order as
`execution_not_found` and Bitget live position was flat.

### Root Cause

V2 already had the correct shared semantic authority for this family:
`PendingEntryTerminalizer` classifies positive-fill/live-truth mismatch as
`positive_fill_live_truth_conflict`, and
`_cleanup_positive_fill_live_truth_conflict()` flattens an owned single live leg
before releasing the pending entry. The production shape never reached that
path because `_finalize_pending_entry()` called
`_ensure_pending_entry_open_fill_details()` first. With
`maker_leg_filled=49`, `hedge_leg_filled=49`, `maker_fill_price=0`, and
`hedge_fill_price>0`, the ensure step emitted
`pending_entry.finalize_deferred_incomplete_fill` and returned before live
truth could prove `Bitget flat + Binance short`.

This is a sequencing drift, not a Gate/Bitget funding/cancel/sizing issue and
not a reason to loosen normal `entry.opened` requirements. A matched open still
requires complete fill price evidence. The exception is only for live-truth
conflict: when current exchange truth proves the local positive-fill record
cannot represent a balanced position, cleanup must run before price-completeness
defer can keep the pending entry stuck.

### V1 / Exchange Decision

- V1 opens matched positions from matched long/short fills with valid average
  prices.
- V1 also has a reduce-only single-leg flatten path for one-sided live exposure.
- V2 must therefore not create `entry.opened` when fill price evidence is
  incomplete, but it must prioritize current exchange truth and owner-scoped
  reduce-only cleanup when exactly one live leg remains.
- Not allowed: clear the pending entry without fresh flat/no-open-orders truth,
  synthesize a maker fill price, or downgrade the live Binance short to
  diagnostic residue.

### Fix

- Added a positive-fill price-gap precheck in
  `PendingEntryRuntime._finalize_pending_entry()`.
- If both local fill quantities are positive but either fill price is missing,
  runtime first asks `_pending_entry_positive_fill_live_truth()` and runs the
  shared terminalizer.
- Only when the terminalizer returns
  `positive_fill_live_truth_conflict` does runtime bypass the incomplete-price
  defer and call the existing owned single-leg cleanup path.
- If live truth is balanced, unavailable, open-order blocked, or otherwise not
  a conflict, the existing `_ensure_pending_entry_open_fill_details()` gate
  still applies and incomplete prices continue to fail closed.
- Extracted `_handle_positive_fill_live_truth_conflict()` so the normal
  balanced-quantity path and the new price-gap precheck emit the same conflict
  event and use the same cleanup function.

## Cluster CL-116 - Gate Contract-Size Quantity Drift And Bitget Duplicate ClientOid Truth Closure

Status: `4ddbd07` deployed/cloud verified.

- Card: [pending-entry-hedge-admission](../cards/pending-entry-hedge-admission.md), [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Summary

This cluster is separate from CL-113 funding and CL-114 Bitget cancel. After
Gate/Bitget candidates recovered, Gate open attempts showed an apparent
available-margin contradiction: account available balance was enough for the
intended small base notional, yet Gate rejected with availability/margin text.
That shape matches Gate futures contract `size` semantics drift: V2 sent engine
base quantity directly as Gate contract quantity. In the same production
family, Bitget close/recovery could leave `40786 Duplicate clientOid` as a
normal unresolved close error instead of routing it through duplicate-client
order truth reconciliation.

### Root Cause

V2 preserved base quantity in `OrderRequest.quantity`, but Gate REST futures
`size` is contract count. The previous transport path relied on static
`spec.contract_size=1.0` and `quantity_step=1.0`, so symbols with
`quanto_multiplier != 1` could submit an oversized contract count, parse
positions/fills inconsistently, and classify the exchange reject as generic
submit noise. V1 treats Gate `quanto_multiplier` as the base-per-contract
converter.

Bitget duplicate close handling was Bybit-specific. V2 already had a shared
order-truth ledger, but the close executor only recognized Bybit `110072`.
Bitget `40786 Duplicate clientOid` therefore bypassed the idempotency truth
path and could remain as `execution.close_failed` / order-error diagnostic
residue even when order detail and current live truth proved terminal flat.

### V1 / Exchange Decision

- Gate: engine quantity remains base quantity. Gate REST order `size` is signed
  contract quantity, computed as `floor(base_qty / quanto_multiplier,
  order_size_round)`. Position and fill quantities from Gate contract counts
  must convert back to base with the same multiplier.
- Gate: live mode requires official contract metadata. Missing multiplier or
  contract step is fail-closed; do not fall back to static quantity step for
  live Gate order sizing.
- Bitget: `40786 Duplicate clientOid` is an idempotency conflict. It must query
  order/fill truth by `clientOid` through the existing family-aware order-status
  contract and then use current position truth before clearing or retrying.
- Not allowed: shrink one leg to bypass a deterministic Gate admission reject,
  downgrade an unproven Bitget duplicate to success, or loosen pending/recovery
  live-truth gates.

### Fix

- Added `SymbolRule.contract_multiplier` and Gate contract metadata loading
  from `/api/v4/futures/usdt/contracts/{contract}` / cached contract metadata.
- Gate `normalize_quantity()`, passive maker submit, market/reduce-only submit,
  order-fill parsing, and position parsing now use the same
  base-to-contract/base-from-contract conversion.
- Gate live sizing now emits diagnostics including `base_qty`,
  `contract_qty`, `contract_multiplier`, `quantity_units`, and
  `venue_contract_qty`; missing contract metadata fails closed.
- Gate `INSUFFICIENT_AVAILABLE` is classified as admission/margin evidence once
  contract sizing diagnostics are present, allowing cooldown/suppression rather
  than repeated identical submit noise.
- Added a venue-neutral duplicate-client reconciliation helper backed by
  `ORDER_TRUTH_LEDGER`, and routed Bitget duplicate close/compensation through
  it while preserving the existing Bybit helper.
- Diagnose now recognizes Bitget `40786` duplicate-client evidence and matches
  both prefixed and bare client-order identities. V1 lifecycle maps
  `execution.close_failed` into `PASSIVE_CLOSE`.

  pending-entry terminality, recovery ownership, or live-truth gates.

Gate/Bitget were not globally broken; V2 market-data populated their
`funding_timestamp_ms` from observation time or lacked a true future funding
time source. Sidecar candidate construction uses the minimum funding timestamp
across both legs, so any combination containing the affected leg could reach
strategy discovery as already past its funding window and be classified as
`funding_window_passed`.

### Root Cause

Gate and Bitget ticker endpoints did not provide the authoritative next funding
timestamp used by the strategy window. The old parser filled the timestamp with
`_now_ms()`, which made a fresh quote look like a just-expired funding window.
The false timestamp was worse than missing evidence because it looked
well-formed and propagated into candidate pairing.

Gate also needs care on payload size. The public `/contracts` endpoint is the
usable unauthenticated source for `funding_next_apply`, but fetching the full
contracts payload every sidecar cycle would be unnecessarily heavy.

### Exchange Decision

- Bitget: use public
  `/api/v2/mix/market/current-fund-rate?productType=USDT-FUTURES`; `nextUpdate`
  is the next funding time and `fundingRate` is the authoritative current rate.
- Gate: use public `/api/v4/futures/usdt/contracts`; `funding_next_apply` is
  the next funding time and `funding_rate` is the contract funding rate.
- Rejected: funding history and premium-index endpoints. They do not provide
  the future funding window needed by sidecar pairing.
- Rejected: Gate batch funding-rate endpoint for this path. Live probe showed
  it requires signed headers, so it is not appropriate for credential-free
  public market-data.
- Fail-closed rule: if the true funding timestamp is absent, stale, or not far
  enough in the future, publish `funding_timestamp_ms=0`; never synthesize
  `now_ms` for Gate/Bitget.

### Fix

- Added `VenueSpec.funding_contracts_path` and configured Gate
  `/api/v4/futures/usdt/contracts`.
- Configured Bitget `funding_rate_path` to
  `/api/v2/mix/market/current-fund-rate`.
- Bitget parser now merges bulk ticker rows with bulk current-fund-rate rows,
  using `nextUpdate` for `funding_timestamp_ms`.
- Gate parser now merges bulk ticker rows with contracts metadata, using
  `funding_next_apply * 1000` for `funding_timestamp_ms`.
- Gate contracts funding metadata is cached with the existing 10-minute
  funding-cache TTL and 30-second future guard. A bulk contracts fetch stores
  all future contract funding rows, so a later symbol can reuse cached metadata
  without another full `/contracts` request.
- Existing quote/OI/admission thresholds, sidecar pairing, and strategy window
  rules were not changed.

## Cluster CL-112 - Active Owner-Managed Gate Scope And Order Truth Business State

Status: `d7bb4ad` deployed/cloud verified.

### Family

Shared order-truth / pending-entry / residual-repair diagnostic contract. The
recurrence is not pair-specific: HUSDT residual repair, LAYER/DEXE overhedge
correction, and Binance/Aster accepted-order uncertainty all depend on the same
business-level terminality vocabulary.

### Evidence

- Cloud after `c841d6c` showed current owner-managed active positions with
  exchange truth available and open orders empty, but diagnose still failed the
  production gate with historical/resolved `residual_events_present` and
  `entry_overhedge_drift_corrected_present`.
- The first local CL-112 review found two unsafe downgrade edges: a
  `live-recovered:*` position with `matched_quantity=0` could be treated as
  owner-managed, and an open-order fetch error could be treated as empty
  open-order truth.
- The old gate still used "global flat" as the proof boundary for these local
  corrections. That made a healthy active lifecycle look unhealthy whenever a
  resolved residual repair or post-entry hedge correction appeared in the same
  deploy window.
- `OrderTruthSuccessDecision` exposed fill truth and retry decisions, but not
  the shared business vocabulary (`accepted_uncertain`, `terminal_no_fill`,
  `truth_gap_fail_closed`, etc.) required by diagnose/runtime readers.

### Root Cause

CL-111 fixed the order-truth and pending-entry mechanics, but the acceptance
gate still had one semantic shortcut: "resolved" was tied to flat/no-open-orders
for the whole account. That is valid for terminal closure bugs, but not for
normal owner-managed active positions. A resolved residual or overhedge repair
must be scoped to the current position owner and symbol, then checked against
exchange truth for balanced live legs and empty open orders.

### Fix

- Added `OrderTruthBusinessState` and
  `OrderTruthSuccessDecision.business_state` so ACK/NEW/PENDING zero-fill
  evidence maps to `accepted_uncertain`, terminal live-flat maps to
  `terminal_no_fill`, partial confirmed fill maps to
  `terminal_partial_with_residual`, and unsupported/fail-closed evidence maps
  to `truth_gap_fail_closed`.
- Diagnose now recognizes current owner-managed active scope from local open
  positions plus exchange truth. Completed residual lifecycle events scoped to
  that active owner do not keep `residual_events_present` blocking.
- `runtime.position_drift_corrected` remains a blocker unless it is scoped to
  an active owner-managed position whose exchange truth is balanced and whose
  open-order truth is empty.
- `live-recovered:*` positions and zero matched-quantity rows are excluded from
  the owner-managed exception. Open-order fetch errors now keep
  `exchange_truth_no_open_orders=false` instead of masquerading as empty truth.
- Owner-scoped diagnostic downgrades require matching `position_id` when the
  event carries one; symbol-only fallback is used only for legacy events without
  owner ids.

## Cluster CL-111 - Order Truth and Pending Entry Semantic Root Fix

Status: `b9f35e3` deployed/cloud verified.

### Family

Shared order-truth / pending-entry semantic family. DEXEUSDT and LAYERUSDT
are symptoms of the same contract gap, not pair-specific closures.

### Evidence

- Binance new-order responses can be ACK/NEW with `executedQty=0` and an
  order id. That is accepted-but-uncertain evidence, not a confirmed zero fill.
- Pending-entry reconciliation could observe live hedge quantity but leave
  maker remainder FIFO slices untouched, causing `missing_hedge_quantity()` to
  stay nonzero and permitting a duplicate hedge drive.
- Residual repair could receive an order id with zero filled quantity and still
  emit `execution.residual_repair_completed` with `filled_quantity=0`.
- Diagnose counted `runtime.position_drift_corrected` as terminal quick-flat,
  hiding post-entry overhedge drift inside a close/flat bucket.

### Root Cause

The runtime had no single business contract for submit-result terminality and
hedge progress application. ACK/non-terminal order evidence was allowed to
cross into fill semantics, while live/order-truth hedge progress and FIFO
consumption were maintained by separate code paths.

The strict review follow-up found one remaining P1 gap in the same family:
startup/order-status/live-position recovery paths could still assign
`hedge_leg_filled` directly after the first semantic patch. That updated the
visible hedge total but bypassed maker-remainder FIFO consumption, so a restart
or forced reconciliation could re-create a missing-hedge signal even after live
truth had already proved the hedge leg was filled.

### Fix

- Binance MARKET submit now requests `newOrderRespType=RESULT`; ACK/NEW or
  other non-terminal zero-fill responses with an order id raise
  accepted-uncertain `OrderSubmitError` instead of returning `OrderFill(0)`.
- Hedge progress from order-query/live-position/execution reconciliation now
  uses a shared helper that applies the incremental hedge quantity and consumes
  maker remainder FIFO slices together.
- Residual repair zero-fill responses with an accepted order id and remaining
  live excess stay as `execution.residual_repair_inflight` / accepted-order
  truth gap instead of false completed repair.
- Diagnose splits `entry_overhedge_drift_corrected_count` from
  `quick_flat_count`; active overhedge drift is its own blocker.
- Startup order-status recovery, live-position hydration, force reconciliation,
  direct hedge submit, and order-truth reconciliation now all route confirmed
  hedge progress through one helper that updates total hedge quantity, consumes
  maker FIFO, preserves hedge order/price evidence, and records observation
  quality together.
