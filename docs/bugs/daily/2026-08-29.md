### CL-129 — Aster V3 historical close evidence was terminalized as unsupported

**Evidence and root cause.** The remaining Aster/ONG audit debt had trusted
flat position and no-open-order truth, but `CloseRuntime` called the inherited
adapter default because `AsterAdapter` had no V3 historical-discovery method.
It therefore recorded `history_discovery_unsupported` as an irreversible debt.
Aster's documented V3 `GET /fapi/v3/userTrades` exposes execution quantity,
fee and order ID; `GET /fapi/v3/order` is the exact order recheck.

**Repair.** The adapter now performs one bounded `userTrades` candidate scan
for the same symbol/side/position side/quantity/close-time window. It groups
partial executions by order ID, rejects a full 1,000-row response as
incomplete, requires exactly one group, then requires the exact `/order` row
to agree on identity, completed quantity, price, side, and position side.
Every commission must be a supported quote asset before the normal billing
gate receives an `OrderFillReconciliation`. Existing debts are reactivated
only when their terminal reason is exactly `history_discovery_unsupported` and
every nonzero leg now implements discovery. Ambiguous/no-candidate/incomplete
debt remains terminal.

**CL-136 follow-up — 2026-08-31.** This description omitted a real V3
one-way wire shape: `userTrades` may contain `positionSide=BOTH` while omitting
`reduceOnly`. The strict field is required from the exact `/fapi/v3/order`
recheck, not from candidate discovery. Requiring it at both layers caused the
known ONG close to be terminalized as generic `no_candidate` even though its
exact order and execution prove the close. The follow-up permits only an
*omitted* field on a candidate row, preserves the exact order proof gate, and
re-runs only legacy automatic Aster generic `no_candidate` debt once. A
post-repair `aster_v3_no_candidate`, ambiguous, incomplete, or non-Aster
result remains terminal; see [CL-136](2026-08-31.md#cl-136--aster-v3-one-way-history-row-was-misclassified-as-no-candidate).

**Review correction.** The first local implementation copied the broader
passive-order status normalizer into this strict accounting path, accepting
`CLOSED`, `FINISHED`, `COMPLETED`, and `DONE`. Aster V3 documents `FILLED` as
the only completed order status. The strict recheck now accepts only `FILLED`;
the broader compatibility mapping remains isolated to passive-order progress.
This was an **uncommitted local regression**, so it has no production footprint.

**Rejected directions.** Do not match a global history row by approximate
time/quantity, widen the window, accept a partial page, use a client ID as a
fill, infer a non-quote fee conversion, or reopen strict terminal outcomes.
Do not reuse a progress-state compatibility mapping as billing evidence.

### CL-130 — terminal audit debt drove recovery position-probe fanout

**Evidence and root cause.** `irrecoverable_audit_debt` means physical
position/order truth was already flat and only accounting evidence remained.
V2 nevertheless included its symbol in both startup and ordinary
truth-required recovery projections, producing repeated seven-venue position
probes. V1 treats this terminal accounting work as background-only.

**Repair.** A single persisted-state predicate identifies terminal automatic
history debt. Both recovery symbol collectors exclude it, and the later
recovery-ledger projection also excludes a close item already classified as
nonblocking background accounting. Nonterminal close reconciliation, pending
passive closes, residual repair, blocking ledger work, and explicit symbols
keep their existing probe behavior. The close runtime remains the sole owner
allowed to reactivate the narrowly defined capability-upgrade case above.

**Rejected directions.** Do not suppress all close debt, delete the audit row,
or add a second recovery allowlist. Only the already-terminal automatic-history
state is excluded.

**Regression provenance review.** The extra probe fanout is a prior V2 repair
regression: `b4b934e6` correctly added close debts to startup truth, but its
later collector did not exclude the new terminal accounting-only state added by
`ac9d536`. The missing Aster discovery is a capability gap exposed by
`ac9d536` terminalization, not a change to physical close behavior. The
diagnosis issue is an incomplete health repair—`ac9d536` added source-health to
the deployment verifier but did not wire the same analyzer into diagnosis. The
Quad100 alarm was introduced by the Tailscale environment, not by a business
code change.

### CL-131 — `diagnose_live` could still report a fresh wrapper snapshot green

**Evidence and root cause.** The deployment verifier already inspected the
sidecar snapshot's quote/funding/market/liquidity source evidence, but
`diagnose_live --since-deploy` accepted `snapshot_path` without reading it.
Consequently a one-second-old wrapper containing a degraded Aster/OKX source
could report healthy.

**Repair.** Diagnosis now resolves the runtime snapshot by default, obtains
the live config path from the systemd unit, and reuses the shared source-health
analyzer plus the same entry freshness budgets. Missing production snapshot or
unavailable production freshness policy is critical. Fixture runtime directories
without a snapshot remain explicitly unchecked rather than being mislabeled as
production health.

**Rejected directions.** Do not use only `published_at_ms`, duplicate a second
raw snapshot parser, silently fall back from an unreadable production config,
or change strategy freshness thresholds to make diagnostics pass.

### CL-132 — Tailscale Quad100 was a false-critical resolver alarm

**Evidence and root cause.** The cloud resolver is Tailscale Quad100
(`100.100.100.100` / `fd7a:115c:a1e0::53`), a local DNS stub. The health
allowlist only contained public resolvers, so a healthy Tailscale host failed
deployment acceptance even while venue DNS and HTTPS were usable.

**Repair.** The exact two Quad100 addresses are accepted as known local
resolver endpoints; no CIDR or arbitrary private resolver is trusted.

**Rejected directions.** Do not replace the server resolver, disable resolver
verification, or broadly allow `100.*` addresses.
