## Cluster CL-001-hyperliquid-wallet-key-v1-parity-drift

### GitNexus Keys

- Fingerprint: `v2.hyperliquid.exchange-signing.api-secret-used-as-wallet-private-key`
- Components: `venue-hyperliquid`, `exchange-signing`, `live-order`, `v1-parity`
- Symbols: `VenueTransport.place_order`, `build_hyperliquid_exchange_payload`, `LiveCredential.wallet_private_key`
- Files: `lightfee/venues/transport.py`, `tests/test_venues_transport.py`, `tests/test_venues_contract.py`
- Commits: `1029089`
- Watch: Hyperliquid signing errors containing `private key must be exactly 32 bytes`, `order.submit_failed`, `runtime.entry_aborted`

### Summary

Production hedge submit failed because the Hyperliquid signing path passed `api_secret` into the exchange payload signer. Live config validation already required `wallet_private_key`, and V1 resolves/signs Hyperliquid actions through the wallet key path (`LightFee/src/live/hyperliquid.rs::resolve_wallet`).

### Root Cause

V2 had a credential semantic drift: validation used `wallet_private_key`, but `VenueTransport.place_order()` signed Hyperliquid `/exchange` actions with `LiveCredential.api_secret`. When `api_secret` was empty, signing failed before the hedge order could be submitted.

### Fix Status

Fixed, committed, and deployed in `1029089`.

- `VenueTransport.place_order()` now passes `LiveCredential.wallet_private_key` to `build_hyperliquid_exchange_payload()`.
- Added a regression test proving live Hyperliquid order signing uses `wallet_private_key` even when `api_secret` is empty.
- Updated existing Hyperliquid live-order tests to put the valid signing key in `wallet_private_key`, preserving V1 credential semantics instead of teaching tests the old drift.

## Cluster CL-002-fail-closed-latch-v1-parity-drift

### GitNexus Keys

- Fingerprint: `v2.fail-closed-latch-clears-with-pending-work-or-sticks-in-clean-disabled-monitor`
- Components: `supervisor`, `risk-mode`, `recovery`, `pending-entry`, `v1-parity`
- Symbols: `Supervisor.update_global_risk_mode`, `Supervisor._fail_closed_can_clear`, `Supervisor.supervise`, `needs_reconciliation`
- Files: `lightfee/engine/supervisor.py`, `tests/test_supervisor_execution.py`
- Commits: `1029089`
- Watch: `risk.fail_closed_auto_resumed`, `risk_mode=fail_closed`, `pending_entry_count`, `open_position_count`, `pending_close_count`, `recovery_blocked_reason`

### Summary

V2 fail-closed recovery was not equivalent to V1. One path could clear the fail-closed risk mode while pending recovery work still existed; another path could leave a clean fail-closed latch sticky when `risk_monitor_enabled=false`, because `supervise()` returned before latch recovery.

### Root Cause

V1 `fail_closed_latch_can_clear()` is based on `state_is_safe_to_resume(recovery_work_snapshot())` plus no operator fail-closed override. V2 approximated this with a narrow check on `recovery_blocked_reason` and selected open-position flags, which missed pending entries/pending closes/reconcile work. V2 also skipped the V1 recompute/auto-resume path when the risk monitor was disabled.

### Fix Status

Fixed, committed, and deployed in `1029089`.

- `_fail_closed_can_clear()` now blocks on operator fail-closed, `recovery_blocked_reason`, and `needs_reconciliation(self.state)`.
- `update_global_risk_mode()` keeps `FAIL_CLOSED` latched when health recovers but recovery work is still present.
- `supervise()` now performs the clean fail-closed auto-resume path before returning when the risk monitor is disabled.

## Cluster CL-003-local-l2-exchange-semantics-root-fix

### GitNexus Keys

- Fingerprint: `v2.local-l2.exchange-semantics.snapshot-buffered + bitget-checksum-as-sequence + bybit-rest-wrapper-empty-side + unsupported-position-probe`
- Components: `local-l2-data-plane`, `local-l2-ws`, `venue-parsers`, `startup-recovery`, `bitget`, `bybit`, `exchange-semantics`
- Symbols: `LocalL2DataPlane.ingest_external_update`, `BitgetL2WsClient.parse_depth_message`, `parse_bitget_l2_update`, `parse_bybit_l2_update`, `LiveRuntime._fetch_startup_live_position_snapshots`, `BitgetAdapter.supported_symbols`
- Files: `lightfee/marketdata/local_l2_data_plane.py`, `lightfee/marketdata/local_l2_ws.py`, `lightfee/marketdata/local_l2_venues.py`, `lightfee/engine/runtime.py`, `lightfee/venues/bitget.py`
- Commits: N/A (working tree, not yet committed)
- Watch: `runtime.local_l2_snapshot_error`, `runtime.local_l2_buffer_overflow_rebuild`, `runtime.entry_local_l2_readiness_diagnostics`, `recovery.live_position_probe_error`, `recovery.live_position_probe_symbol_skipped`

### Summary

Post-`1029089` cloud evidence showed Hyperliquid signing and clean fail-closed were fixed, but local-L2 and Bitget startup probe noise remained. These were not V1 fail-closed/signing parity issues; they were exchange-semantics defects in the V2 local-L2 ingestion/parsing/probing layer.

### Root Cause

Four independent root causes were confirmed:

- Authoritative non-Binance snapshots were buffered while books were `BOOTSTRAPPING`/`REBUILDING`, so a valid exchange snapshot could fail to establish a HOT local book.
- Bitget WS parsing treated `checksum` as the book sequence, even though current Bitget UTA depth docs use `seq` and `pseq` for continuity and the 2026-05-12 Bitget changelog removes `checksum` from depth pushes.
- Bybit REST `/v5/market/orderbook` returns orderbook fields under `result` and represents a current snapshot; the parser only handled WS-style `data`, causing valid REST snapshots to look like empty-side books.
- Startup fallback position probes asked Bitget about symbols not present in its contract catalog, producing avoidable unsupported/delisted-symbol and rate-limit errors.

### Fix Status

Fixed locally.

- `LocalL2DataPlane.ingest_external_update()` applies authoritative `SNAPSHOT` updates immediately during bootstrap/rebuild, clears the pre-snapshot buffer, and transitions a successfully applied book to HOT.
- `BitgetL2WsClient.parse_depth_message()` and `parse_bitget_l2_update()` parse `seq`, `pseq`, `b/a`, and `checksum` according to current Bitget payloads.
- `parse_bybit_l2_update()` accepts REST `result` wrappers as snapshots and uses Bybit `u` as the update sequence.
- `LiveRuntime._fetch_startup_live_position_snapshots()` now loads a venue catalog when available and filters fallback per-symbol probes to symbols supported by that venue.
- `BitgetAdapter` exposes `supported_symbols()` and lazy `ensure_supported_symbols_loaded()` backed by the contract metadata loader.
