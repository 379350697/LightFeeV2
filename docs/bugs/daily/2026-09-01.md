# Bug Ledger Daily - 2026-09-01

## CL-138 — Gate/Bitget sidecar market-data contract drift

Status: **deployed-awaiting-verification**. `d18d016` was deployed in
`12d8e038ded93c46ded7771ef7b03d0266f3d0a6` on 2026-09-01. This repair makes
only credential-free public market-data requests; it does not submit, cancel,
or otherwise mutate exchange trading state.

### Evidence and authoritative contract

The ten-day production investigation found no Gate or Bitget entry dispatch,
but neither venue was disabled and there was no Gate/Bitget order rejection to
investigate. The barrier was earlier in the shared path:

- The current Bitget snapshot had 75/75 quote rows with `bid=ask=0`. A direct
  documented ticker response instead carries `bidPr`, `askPr`, `holdingAmount`,
  and `markPrice`; V2 read the obsolete `bestBid`, `bestAsk`, and
  `openInterest` aliases.
- Current Gate quote rows had prices, but all 367 Gate-involving raw candidates
  and 319 Bitget-involving raw candidates had a first funding time within about
  0.45 seconds *before* the snapshot publication. Both parsers wrote local
  `_now_ms()` because their ticker endpoint lacks a future funding schedule.
  `build_same_symbol_pairs` takes the earlier leg and the unchanged V1-derived
  discovery gate correctly rejected it as `FUNDING_WINDOW_PASSED` before order
  dispatch.
- Bitget's documented bulk
  [current funding rate](https://www.bitget.com/api-doc/classic/contract/market/Get-Current-Funding-Rate)
  response supplies `nextUpdate`; its documented
  [ticker](https://www.bitget.com/api-doc/classic/contract/market/Get-All-Symbol-Ticker)
  response supplies the live quote and holding fields. Gate's documented
  [futures contracts](https://www.gate.com/docs/developers/apiv4/en/futures/)
  response supplies `funding_next_apply` in seconds, while its ticker supplies
  `highest_size` and `lowest_size`.

V1 remains authoritative for this compatibility-sensitive decision. Its Bitget
adapter reads `bidPr`/`askPr`, treats `holdingAmount × markPrice` as quote OI,
and consumes the exchange funding time. Its Gate adapter obtains
`funding_next_apply` from contracts and converts seconds to milliseconds. The
contract is therefore: publish an otherwise valid quote if optional funding
metadata is unavailable, but set its funding time to `0` so the existing entry
gate remains fail-closed. A snapshot observation time is not a funding
schedule and cannot be substituted.

### Root cause and affected production path

The original V2 aliases were introduced in May. A correct narrow repair was
later present on the divergent `v3` branch but never became an ancestor of
`main`; this is integration drift, not a recent `main` change that removed a
previously working `main` implementation. Blindly cherry-picking that branch
would also import unrelated historical transport work, so it is not the repair
strategy.

Affected path:

`MarketDataClient._fetch_gate_style/_fetch_bitget_style` →
`ExchangeSource.fetch_all` → `build_same_symbol_pairs` →
`discover_tradeable_candidates` → existing V1-compatible funding-window entry
gate. The repair does not enter leverage preparation, order creation, order
reconciliation, closing, or risk limits.

### Root repair and rejected patterns

- Add the two explicit public endpoint fields to `VenueSpec`, rather than
  creating a venue-specific sidecar or alternative client.
- Bitget reads documented quote/OI fields plus one bulk current-funding request
  and uses its future `nextUpdate`. Its market rate falls back to the ticker
  only when the funding response is unavailable; its timestamp remains `0`.
- Gate reads documented quote-size fields, normalizes its contracts timestamp
  from seconds, and reuses the existing ten-minute funding cache for the bulk
  contracts response. A failed/missing/stale contract row leaves the timestamp
  at `0`.
- Register the additional Bitget request with the existing market rate-limit
  scope; no rate limit, pool limit, retry policy, or sidecar cadence changes.

Do not restore `_now_ms()` as a funding-time fallback, loosen the funding
window, add a per-symbol fan-out/poller, reset a venue client, or cherry-pick a
divergent branch wholesale. Each would either reintroduce a false schedule,
change unrelated safety behavior, or repeat the prior integration mistake.

## CL-139 — Bitget canceled maker misread as fill; cancel and reconciliation contract gaps

Status: **reopened after a production-path RED; corrected locally, pending
deployment verification**. The prior implementation was deployed in `66b4b76`,
but production still emitted `HTTP 400` / Bitget `40109` while reconciling the
ZORA maker. It has not submitted, canceled, or changed any production order,
state, or deployment.

### Evidence and authoritative contract

The affected Bitget Classic maker order
`1478408313786478593` / client ID
`5fc9a39af59f0bf2e029436c5e512146fac0` was canceled with `size=2496` and
`baseVolume=0`; its Bybit hedge had already become a 2,400-unit naked short.
`size` is the submitted quantity, while `baseVolume` is the executed base
quantity in Bitget's documented Classic
[order detail](https://www.bitget.com/api-doc/classic/contract/trade/Get-Order-Details)
response. A present zero is therefore execution truth, not an absent alias.

The authoritative V1 paths are `src/live/bitget.rs` passive-progress and
fill-reconciliation parsers: their `json_f64` accepts a reported zero and
does not fall through to the next alias. V1 also sends the Classic cancel
contract fields. Bitget documents `productType` as required for Classic
[cancel](https://www.bitget.com/api-doc/classic/contract/trade/Cancel-Order),
which directly explains the 2,071 `400172 productType cannot be empty`
responses. For a terminal order that has disappeared from detail (`40109` or
`43001`), Classic
[order history](https://www.bitget.com/api-doc/classic/contract/trade/Get-Orders-History)
allows exact IDs; UTA
[history](https://www.bitget.com/api-doc/uta/trade/Get-Order-History) is a
documented bounded list and must be matched locally by exact identity.

### Root cause and complete production path

When a Bitget terminal row reported `baseVolume=0` and `size>0`, V2's passive
progress parser rejected zero as unusable, fell through to `size`, and raised
the maker high-water fill to the submitted quantity. Entry recovery then saw a
false maker fill and submitted the Bybit hedge, producing the ZORA naked short.
The same V2 Bitget operation registry omitted Classic cancel's required
`productType`. The first reconciliation repair added the bounded,
identity-safe history branch, but put it after `self._request()`: real Bitget
`40109`/`43001` responses use HTTP 400, so `_request()` raised
`REQUEST_REJECTED` before its parsed JSON could reach that branch. Its test
mocked `_request()` to return `{"code":"40109"}`, which could not exercise
the production HTTP boundary. Earlier parser tests also covered zero-filled
reconciliation rows but not the production passive-progress route where the
positive-only alias fallback existed.

The repaired path is:

`Bitget REST/private row` → `VenueTransport` cumulative-quantity normalization
→ passive progress / order-status reconciliation → `OrderReconciler` terminal
zero **or terminal execution-evidence-unavailable** marker → pending-entry
state correction only if the maker's current exchange position is flat →
existing owned-single-leg reduce-only cleanup.

The history path is reached only after detail returns `40109`/`43001`, makes
one correct-family request per eligible reconciliation attempt, and accepts no
row unless the exchange order ID or client ID matches exactly. It never scans
unbounded history, guesses from a nearby row, or turns an unavailable result
into flat truth. Existing V1-compatible reconciliation backoff and live-size
terminalization own any later retry.

### Root repair and non-goals

- One shared Bitget cumulative-quantity normalizer now treats the first
  present finite non-negative execution field—including zero—as authoritative.
  It is used by both REST passive progress and fill reconciliation. The
  existing private-WS parser already had this V1 behavior and was verified
  rather than rewritten.
- The registry now owns Classic/UTA cancel and history requirements: Classic
  cancel sends `productType=USDT-FUTURES` and `marginCoin=USDT`; UTA sends only
  `category=USDT-FUTURES`. This prevents family-field drift at every cancel
  caller without a Bitget-specific retry wrapper.
- At the Bitget order-status boundary, only a `REQUEST_REJECTED` whose retained
  HTTP body is documented missing-order code `40109` or `43001` enters the
  existing one-request, correct-family history branch. Generic HTTP behavior
  and every nonmatching 400 remain fail-closed.
- A terminal row whose cumulative execution fields are all absent or malformed
  is carried as a distinct unavailable-evidence marker. Only that marker makes
  pending recovery retain its owner and use the existing reconcile backoff; it
  cannot terminalize dust, submit a hedge, or invoke reduce-only cleanup.
- Runtime may erase an old maker-fill high-water mark only when that exact
  terminal-zero evidence and a fresh flat maker position agree. If exactly one
  physical leg remains, it reuses the existing owned-conflict reduce-only
  cleanup. Nonzero, missing, malformed, stale, or identity-mismatched evidence
  remains fail-closed and cannot trigger this cleanup.
- The correction updates the existing `PendingEntry.passive_order` owner to
  `CANCELED`, so the normal terminal lifecycle sees the same state as V1.

Do not reintroduce positive-only alias fallback, use `size` as a replacement
for a reported zero, query unrestricted history on every reconcile loop, add
unsupported UTA ID query parameters, special-case ZORA/Aster/another symbol,
or submit a new hedge from stale maker state. This repair does not itself alter
the already-live ZORA position; after deployment, only fresh exchange truth may
drive the existing reduce-only cleanup path.
