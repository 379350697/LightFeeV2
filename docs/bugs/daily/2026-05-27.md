## Cluster CL-008-passive-maker-zero-fill-and-live-acceptance

### Summary

Production after the 2026-05-27 deploy showed repeated passive maker entries that selected, submitted a post-only maker order, received zero fill inside the maker try window, canceled the maker order, and then emitted `entry.aborted` with `passive_maker_canceled_zero_fill`. That made the engine safe-flat, but it also depressed maker fill rate and caused noisy fail-closed/risk-mode recovery cycles.

The root behavior should match V1: zero-fill inside the maker try window is a passive-entry lifecycle outcome. It should cancel stale maker liquidity, record the zero-fill cycle, wait the configured retry delay, repost/reprice within the repost budget, and only terminalize cleanly as unfilled after budget exhaustion. It is not itself a health failure.

### Root Fix

- `LiveRuntime._maintain_pending_entry_passive_orders()` no longer skips recovered terminal zero-fill pending orders behind the `cancel_requested && maker_completed` guard.
- New zero-fill completion handling records `passive_maintenance.zero_fill_cycle`, waits `maker_cycle_retry_delays_ms`, respects maker venue budget, reposts with a fresh compact client order id, and increments `repost_count`.
- Repost-budget exhaustion calls `_finalize_pending_entry()`, which already has the V1 zero-fill branch that emits `entry.passive_unfilled` and `pending_entry.pending_entry_finalized` without creating an open position.
- Zero-fill cancel/repost paths no longer call `_abort_pending_entry_fail_closed()` when there is no fill and exchange truth remains flat.
- `diagnose_live.py` and `analyze_production_blockers.py` expose `passive_maker_zero_fill_count`, fill rate, fail-closed abort count, and production acceptance gate fields.

## Cluster CL-009-okx-recovery-probe-rate-limit-and-catalog-gate

### Summary

Recovery probing generated high OKX private-position noise: timeouts, `50011`/HTTP 429 rate limits, and unsupported/instrument-missing symbols such as OKX contracts without usable `ctVal`. V2 drifted from V1 by allowing a clean startup state to expand toward the full configured universe and by falling back to per-symbol probes after bulk OKX failure.

### Root Fix

- Clean local state no longer contributes the full configured/resolved symbol universe to startup recovery probing.
- Recovery probe symbols come from actual recovery work: open positions, pending entries/closes/passive closes, residual repairs, live-recovery pairs, and explicitly touched/recent symbols.
- OKX `supported_symbols()` and `ensure_supported_symbols_loaded()` expose the official SWAP instrument catalog for recovery catalog gating.
- OKX bulk position probe failures classified as rate-limited emit venue-level cooldown evidence and do not fan out to per-symbol position probes in the same window.
- Unsupported symbols are aggregated in `recovery.live_position_probe_unsupported_symbols` with endpoint, requested symbols, skipped catalog symbols, and symbol counts.

### Official Docs Used

- OKX REST account positions endpoint rate limits are by User ID; production `50011`/HTTP 429 is classified as rate-limited private-position evidence.
- OKX public instruments metadata supplies `ctVal` and `ctType`; missing or unsupported contracts are catalog/metadata evidence, not retryable live-position truth.

## Cluster CL-012-okx-single-symbol-position-regression

### Summary

Acceptance review found a new regression introduced while reducing OKX recovery-probe fanout: `VenueTransport.fetch_position()` called `fetch_all_positions()` when no OKX position cache existed. That bypassed the existing single-symbol private request with `params={"instId": "CHIP-USDT-SWAP"}` and broke tests that prove OKX instrument metadata/`ctVal` is used for base-quantity normalization.

### Root Fix

- Keep `_all_positions_cache` as an optimization only after an explicit successful `fetch_all_positions()` call.
- If no fresh all-position cache exists, `fetch_position()` follows the original single-symbol request path and sends `instId`.
- A missing symbol in a fresh all-position cache still returns a cached zero snapshot, avoiding repeated private-position calls during recovery windows.
