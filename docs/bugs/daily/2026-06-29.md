### Production Symptom

After the latest deploy, production held one pending entry:
`entry-1782694536378-SKYAIUSDT`. Local and exchange truth showed Aster maker
filled `171`, Gate hedge filled `160`, target quantity
`171.56337122024448`, and passive maker progress state `filled`. Runtime
entered `fail_closed/risk_only` and repeated Aster `DELETE /fapi/v3/order`
cancel attempts, which returned HTTP `400` for an already terminal/non-active
maker order. The result was an Aster maker/Gate hedge asymmetry rather than a
simple open-error recurrence.

### Root Cause

The abort path treated `pending.maker_completed()` as insufficient unless
`maker_leg_filled >= pending.target_quantity`. That compared the terminal
passive maker order target (`171`) against the higher entry target
(`171.563...`). Because `171 < 171.563...`, V2 tried to cancel an already
terminal Aster maker order before querying open-order/progress truth. The same
semantic family also existed around hard-ceiling terminalization: maker
completed plus positive fill and missing hedge could jump to abort before
reusing the existing missing-hedge/dust/cleanup decision.

Follow-up P3 review found one remaining read-only decision helper,
`_pending_entry_has_unresolved_maker_order()`, still carried the old
entry-target comparison and treated any positive passive progress, including
terminal `FILLED` progress, as unresolved. Its callers are flat-abandon and
force-terminal guards, so the old branch did not reintroduce the Aster cancel
loop, but it kept a second semantic track that could retain a stale flat
pending entry after maker terminal truth and open-order absence were already
proved.

### V1 / Exchange Decision

- V1 semantics: positive maker fill is never fake-flat. A terminal maker order
  must be treated as terminal by maker/order truth, then missing hedge, dust,
  or cleanup decides the pending entry.
- Exchange semantics: Aster cancel is for active orders. Filled/canceled/
  rejected/expired or non-existent cancel results are follow-up truth signals,
  not proof that the pending entry should loop in cancel failure.
- Not allowed: require maker filled quantity to equal the entry target before
  accepting maker terminal proof; silently open or clear a positive-fill
  asymmetric pending entry; hide lifecycle blockers behind partial clean
  exchange truth.

### Fix

- Added shared maker terminal proof logic for abort and single-leg release:
  local passive terminal state, open-order truth, passive progress, cancel, and
  cancel-failure follow-up now share the same decision contract.
- Removed the false `maker_filled >= target_quantity` gate. A SKYAI-shaped
  passive maker `FILLED` with open-order truth absent is terminal even if entry
  target is slightly larger than the passive maker order target.
- Cancel failure now records structured error evidence (`error_status_code`,
  `error_body`, `exchange_code`, `exchange_msg`) and follows up with
  open-order/progress truth. If follow-up proves terminal and no open order, it
  continues instead of looping fail-closed on cancel.
- Hard-ceiling terminalization for positive-fill pending entries now first tries
  existing terminal hedge-dust rules, then drives the missing hedge. If the
  hedge fills and maker is terminal, it finalizes/removes the pending entry;
  legacy hedge-inflight deadline cleanup keeps the previous path.
- P3 follow-up `b6004dd` closes the old read-only helper drift:
  `_pending_entry_has_unresolved_maker_order()` no longer compares maker fill
  to the entry target and no longer treats terminal `FILLED` progress as
  unresolved. It now resolves local maker-completed evidence or terminal
  passive progress only after realtime open-order truth proves the maker order
  absent; matching open orders or unavailable open-order truth still retain
  fail-safe.

### Production Symptom

The deploy window showed four close-side accepted-order truth gaps and one
Bitget close hedge reconcile 400. The account did not remain open: production
eventually reached flat/no-open-orders and the acceptance gate could pass with
`unresolved_order_truth_gap_count=0`. However, runtime registered
`exit.accepted_order_truth_gap_registered` without always emitting explicit
`exit.accepted_order_truth_gap_resolved`; diagnose then inferred closure from
terminal live-flat events. That made summaries show confusing
`resolved_order_truth_gap_count=3/4` style drift even though current exchange
truth was clean.

### Root Cause

Two adjacent semantics were incomplete:

- The `_handle_hedge_truth_gap_result` live-flat shortcut cleared the passive
  close through exchange truth but did not close the accepted-order truth-gap
  lifecycle itself. The close was safe, but the truth-gap owner had no explicit
  terminal event.
- Bitget reduce-only ACK can omit `orderId`; official Bitget docs say the
  client must use `clientOid` to query details in that case. V2 allowed the
  string `"None"` / `"null"` to pass as a real `orderId`, producing Bitget
  `40017 Parameter verification failed None` instead of a clientOid-only truth
  probe.

### V1 / Exchange Decision

- V1 semantics remain unchanged: accepted ACK is not fill truth. It creates an
  owner-scoped truth-gap task that must end in confirmed fill, live-flat truth,
  or retained fail-closed state.
- Exchange truth still outranks local state. Live-flat plus open-orders-empty
  may resolve a close truth gap, but runtime must emit the explicit
  `exit.accepted_order_truth_gap_resolved` event.
- Historical terminal-flat inference remains diagnostic-only compatibility for
  old logs. New logs must prove explicit registered/resolved parity.

### Fix

- Added shared order identity normalization so `None`, empty string, `"None"`,
  and `"null"` are treated as absent order/client identifiers.
- Applied that normalization to accepted-order truth resolution, passive-close
  accepted truth-gap identity extraction/registration, Bitget order-status
  truth queries, and diagnose identity matching.
- Changed Bitget order-status truth query to use `clientOid` alone when
  `orderId` is absent and to avoid a private HTTP query when both identifiers
  are absent.
- Closed the passive-close live-flat shortcut by removing the active
  accepted-order reconciliation and emitting
  `exit.accepted_order_truth_gap_resolved` with `resolution_status=live_flat`,
  venue, leg, accepted ids, and exchange-truth payload.
- Split diagnose truth-gap closure summary into explicit and legacy inferred
  counts so old logs remain explainable while current deploys can require
  explicit registered/resolved parity.

### Production Symptom

Aster passive-close hedge could return an accepted order identity with zero
reported fill. A later Aster reduce-only submit could return
`-2022 ReduceOnly Order is rejected` after the exchange position had already
become flat. The previous partial fix could make diagnose partially green, but
the business closure was not fully semantic: the accepted order identity and
the terminal flat evidence were not forced through one explicit accepted-order
truth-gap resolution.

### Root Cause

V2 had a Bybit-specific branch for accepted 0-fill close ACK reconciliation.
For Aster, an accepted ACK with `order_id` / `client_order_id` could fall
through as ordinary `zero_fill`. That left the passive close without a pending
accepted-order truth-gap owner and left diagnose to rely on later terminal-flat
evidence. The business contract already required strong order/client identity
for reduce-only close artifact downgrade, but Aster did not always emit the
terminal identity chain needed to satisfy that contract.

### V1 / Exchange Decision

- V1 semantics: an exchange-accepted close order is not a failed close and is
  not a terminal fill until order/fill truth or live-flat truth closes the
  owner. The local pending close must remain owned while truth is unresolved.
- Exchange semantics: Aster `-2022 ReduceOnly Order is rejected` can be
  compatible with an already-flat position, but the error code alone is not
  success evidence.
- Not allowed: downgrade an Aster reduce-only close artifact only because the
  same position later emitted terminal flat. The downgrade needs strong
  order/client identity or an accepted-order truth-gap resolution that carries
  that identity.

### Attempts

| Attempt | Status | Why |
|---|---|---|
| Position-only terminal-flat downgrade | ineffective / rejected | Would hide unmatched Aster `-2022` artifacts and drift from the existing business contract. |
| Copy V1 semantic owner flow into V2 accepted ACK handling | effective locally | Accepted 0-fill ACK now creates accepted-order truth-gap work and resolves only through `filled` or `live_flat` truth. |

### Fix

- Generalized the accepted 0-fill ACK reconciliation branch in
  `PassiveCloseExecutor._submit_hedge_for_delta` for venues that expose
  `fetch_order_fill_reconciliation`. If reconciliation is missing, zero, or
  unavailable while an accepted order identity exists, the hedge result becomes
  `accepted_order_truth_gap_pending` instead of ordinary `zero_fill`.
- Registered `accepted_order_truth_gap` pending close reconciliation with the
  accepted `order_id` / `client_order_id`, requested quantity, venue, leg, and
  next action `reconcile_accepted_order_or_probe_live_position`.
- Propagated accepted/order/client identity into
  `exit.passive_close_resolved` when terminal live-flat cleanup closes the
  accepted-order gap.
- Taught diagnose that `exit.accepted_order_truth_gap_resolved` is complete
  only when `resolution_status` is `filled` or `live_flat`; unresolved or weak
  statuses remain visible.
- Added positive and negative regressions: Aster accepted 0-fill ACK must
  register a truth gap without resubmitting, and Aster `-2022` may resolve only
  when the accepted order identity matches terminal truth.
