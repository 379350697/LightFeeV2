### Symptom

After the latest SIRENUSDT passive-close cycle, the runtime correctly blocked
new risk, but Bitget still had a one-sided short exposure with a live
reduce-only close order that local owner recovery could not recognize as owned.
The visible blocker was ownerless reduce-only open-order evidence, not a new
entry single-leg admission path.

### Root Cause

CL-100/CL-101/CL-103/CL-142/CL-152/CL-153 covered the owner ledger, terminal
truth, one-sided flatten gates, entry single-leg invariant, and close-truth
kwargs compatibility. The uncovered boundary was lower-level order identity IO:
passive ACK, cancel, detail/progress query, amend, and passive-close state could
still preserve a missing venue order id as the string `"None"`.

For Bitget cancel/detail contracts, `orderId` and `clientOid` are alternatives
and `orderId` has priority when both are present. Sending truthy `orderId=None`
therefore prevents the intended client-id fallback and can make the close owner
ledger lose the only stable identity. The lifecycle layer then fail-closes
correctly, but it cannot adopt the live close order by the polluted order id.

### Unified Business Decision

- Order identity normalization is a hard boundary for all passive order truth
  IO. `None`, `"None"`, `"null"`, and empty strings are absent identities.
- If a venue order id is absent, Bitget cancel/detail/progress must use
  `clientOid` alone; it must not send `orderId=None`.
- Passive-close state, identity history, and journal events must store only
  normalized order/client identities so owner adoption never receives polluted
  identity strings.
- Reduce-only adoption remains fail-closed: match by normalized
  `orderId`/`clientOid` first, then by venue/symbol/reduce-only/side/quantity
  coverage when the open order and pending close are consistent. Unproven open
  orders still block new risk.

### Fix

- `VenueTransport` now normalizes passive ACK identities, Bitget
  cancel/detail/progress inputs, and passive amend request/ACK identities.
- `PassiveCloseExecutor` now normalizes maker submit, amend, cancel-replace,
  identity-history, journal, and reduce-only adoption paths before persisting or
  matching order ids.
- Existing Bitget UTA and Classic contract-family payloads keep their current
  product/category semantics while choosing `clientOid` when the venue order id
  is absent.
