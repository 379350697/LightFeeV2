### WT-20260903-1 — terminal maker close could advance before live-flatness

**Symptom and evidence.** The CYS lifecycle briefly had one live leg after the
maker close reached a terminal zero-fill result; the delayed hedge leg was
eventually flattened and the account ended flat. This is a close-lifecycle
window, not evidence of a remaining position after the final reconciliation.

**Contract and root cause.** V1's passive-close terminal path may consume a
maker phase budget only after the live account truth has been checked. V2
cleared the terminal maker identity and advanced the phase before checking both
legs. A delayed hedge fill could therefore be left to a later pass without the
maker identity that explains the close. The shared owner is
`PassiveCloseExecutor`'s terminal non-filled maker branch.

**Repair.** The branch now resolves both live legs before clearing the maker
identity. A flat maker plus live hedge is flattened through the existing
reduce-only IOC path; unavailable/partial truth retains the owner and retries;
only trusted live-flatness continues the existing phase budget. No order is
created by the truth probe itself.

**Counterexamples and regression.** Rejected zero-fill maker + delayed
one-sided hedge now performs one reduce-only IOC and clears the close only
after both legs are flat. Existing unavailable-truth retention and terminal
phase-budget tests remain green. Production observation after deployment is
still required.

### WT-20260903-2 — Gate Local-L2 `U..u` was treated as a `pu` link

**Symptom and evidence.** The deployed log contained approximately 6,025 Gate
`runtime.local_l2_sequence_gap_rebuild` events. A representative update had
`book_seq=1348433194`, raw `U=1348433195`, `u=1348433204`; the parser derived
`pu=1348433195` and rejected a valid overlapping range. Gate documents define
`U` as the first update ID and `u` as the final update ID. V1's Gate path
accepts an update when the expected next sequence lies within that range.

**Root cause and repair.** Both V2 Gate parsers populated the generic
`previous_sequence` field from `U`, activating a `pu` continuity check that
Gate does not provide. Both parser owners now leave `previous_sequence` absent
and retain `first_sequence=U`, `sequence=u`; the existing data-plane range
overlap rule is therefore authoritative.

**Regression.** A real `GateL2WsClient` message with snapshot sequence 100 and
`U=100,u=101` applies without rebuild and advances to 101. The documented
payload parser parity test also asserts the absence of a fabricated `pu`.

### WT-20260903-3 — Aster `-5018` evidence was lost at entry admission

**Symptom and evidence.** Aster returned 18 HTTP-400 `-5018` maximum-notional
rejections for AKEUSDT after deployment. The entry attempts were aborted, but
no venue-wide cooldown event was emitted, so the same class could be retried
on other symbols.

**Contract and root cause.** The exchange-owned code/message/body returned by
the existing order-submit error contract must survive the entry executor
boundary so the existing admission classifier can apply its venue-wide
max-notional rule. `EntrySyncExecutor` retained only the human string
`reject_reason`, discarding `exchange_error`; this was a producer/consumer
boundary loss, not an Aster retry-policy defect.

**Repair.** `EntryExecutionResult` now carries the structured rejection
evidence. Runtime admission classification consumes that evidence while
preserving the old string fallback for legacy executors. The existing cooldown
owner and fail-closed behavior are unchanged; no extra Aster-specific parser or
retry loop was introduced.

**Regression.** A production-shaped rejected entry carrying Aster `-5018`
sets one `aster:*` `max_notional_admission_blocked` cooldown, records the raw
evidence, and blocks an unrelated symbol before a second executor call.

### WT-20260903-4 — terminal automatic-history debt was reopenable

**Symptom and evidence.** Historical close evidence debt could reappear after a
later close observation supplied an order identity. The account remained flat,
but the accounting owner changed from a bounded terminal conclusion to a new
retryable record, making the same historical problem recur in every diagnosis.

**Contract and root cause.** A strict automatic-history terminal debt is an
accounting-only owner. Ordinary close registration must not replace or reopen
it; only another terminal record or the explicit operator evidence-import path
may supersede it. The generic reconciliation deduper compared identity
coverage before checking this terminal owner, so a later ordinary record could
replace it.

**Repair.** `EngineState.enqueue_pending_close_reconciliation` now rejects a
non-terminal incoming record when the existing record is a terminal automatic
history debt. The existing explicit import and terminal-to-terminal enrichment
paths remain available; no unbounded polling or speculative attribution was
added.

**Regression.** A terminal ONGUSDT debt followed by an ordinary late-identity
observation remains exactly one terminal debt. Existing exact-history,
temporary-failure, and crash-replay coverage remains green.

### WT-20260903-5 — diagnosis judged a fresh snapshot against an old clock

**Symptom and evidence.** `diagnose_live --since-deploy` could report missing or
future source timestamps even while the deployment verifier was healthy. The
sidecar publishes snapshots concurrently, so a new snapshot could be written
after diagnosis captured its initial `generated_at_ms`.

**Contract and root cause.** Snapshot source-age checks must use the clock at
the point the snapshot is read. `run_diagnose` built sidecar health before the
read-only exchange probes and passed the early window timestamp, creating a
false negative based on clock skew rather than data quality.

**Repair.** Sidecar snapshot health is now built after the probes and uses a
fresh `_now_ms()` in production; explicit `now_ms` replay callers remain
deterministic. The source-age budgets and health owner are unchanged.

**Regression.** A production-path `run_diagnose` test advances the clock during
the probe and verifies that snapshot health receives the post-probe timestamp.
The existing stale/degraded source matrix remains green.

  snapshot, and do not weaken freshness thresholds to make the report green.

  trusted live-flatness or the existing reduce-only cleanup has completed.
