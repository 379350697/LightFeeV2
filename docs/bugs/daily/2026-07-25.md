### Issue CL-159-A: Global Account-Truth Deadline Starves Every Entry

#### Fingerprint

`runtime.entry_account_truth_pending` while candidates are otherwise present,
with no `execution.entry_selected`, `runtime.entry_dispatched`, `entry.opened`,
or `exit.passive_close_resolved` in the post-deploy window.

#### Evidence

- Deployed live configuration sets `live_recovery_rest_probe_timeout_ms=2000`.
- The runtime entry preparation wraps the full recovery-ledger account-truth
  refresh in that one 2-second deadline.
- That refresh asks each configured venue for positions and then open orders.
  A read-only, unfiltered all-seven-venue run on the production host completed
  successfully in approximately 6.367 seconds, more than three times the
  configured aggregate budget.
- The current scan reported `candidate_count=3`, `tradeable_count=0`,
  `selected_candidate_count=0`, `dispatched_candidate_count=0`, and
  `no_entry_reason=entry_account_truth_pending`.
- Since this live process started, journal counts included 170
  `runtime.entry_account_truth_pending` records and one
  `runtime.entry_account_truth_not_ready_before_dispatch`; no exchange
  `order.rejected` or `order.uncertain` was observed.

#### Root Cause

V2 made a global recovery-style account sweep a per-entry dispatch
prerequisite, while retaining a 2-second recovery REST deadline. Each venue
performs position and open-order truth sequentially inside its task, so the
aggregate is at least fourteen logical private reads. The all-venue operation
is valid for recovery, but its scope and deadline are incompatible with normal
entry liveness.

This is a V1 semantic drift. V1 first uses fresh private position state and
only probes missing venues concurrently with per-venue bounds; it does not make
an unrelated venue's position-plus-order REST latency a global entry blocker.
The current fail-closed decision is safe, but the global proof requirement
causes starvation rather than a targeted safe block.

#### Failed / Ineffective Attempt

| Attempt | Status | Why |
|---|---|---|
| Reuse the startup/recovery full-account receipt before every dispatch under one 2-second timeout | ineffective | Production all-seven truth is healthy but exceeds the aggregate budget, so the generic `pending` result prevents every candidate from reaching order submission. |

#### Root Fix

1. Keep full-account reconciliation for startup, recovery, and background
   monitoring; do not synchronously make it the all-venue entry gate.
2. Carry fresh per-venue private truth receipts (positions and open orders,
   duration, error, and last-good timestamp). For a selected candidate, require
   fresh complete truth only for its two execution venues.
3. Probe those two venues concurrently with
   `entry_account_truth_per_venue_timeout_ms` (default 2000ms). The initial
   `entry_account_truth_probe_timeout_ms` spelling remains a nullable
   compatibility alias only.
   A stale or failed non-participating venue must be visible as an evidence gap,
   but must not block an unrelated candidate when it has no live artifact.
4. If either selected leg has incomplete truth, retain the present fail-closed
   no-submit rule for that candidate.
5. Emit explicit `runtime.entry_account_truth_timeout` or
   `runtime.entry_account_truth_incomplete` records containing required venues
   plus sanitized per-venue receipt summaries instead of only the generic
   `runtime.entry_account_truth_pending`.

#### Required Regression Proof

- With seven-venue full truth taking longer than two seconds and both selected
  legs fresh within their own budgets, a candidate reaches normal dispatch
  preparation.
- A selected long or short venue with missing position/open-order truth remains
  blocked and submits no order.
- A slow non-participating venue does not block a candidate whose two legs have
  complete fresh truth and no global recovery artifact.
- Startup/recovery still blocks on a real unpaired position or open order from
  any venue.

#### Acceptance

Locally verified. The full all-venue preparation sweep no longer uses the
ordinary-entry aggregate deadline; it remains complete/fail-closed in the
background. Candidate dispatch uses independent target-venue 2-second bounds,
one task per venue, and a short failed-receipt cache that can only repeat a
no-submit result. A target-leg position or open order immediately enters the
existing global recovery path and starts full truth collection. Target timeout,
staleness, missing receipt, position, or open order remains zero-submit.

`tests/test_runtime_entry_flow.py` covers target-only truth, candidate progress
while a global sweep is still pending, target singleflight, target timeout
no-submit, and global-artifact recovery; `tests/test_config.py` covers the
canonical timeout and compatibility alias. A local-only fix is not production
closure: cloud proof needs at least one normal candidate to pass targeted truth
preparation, followed by a controlled, explicitly authorized real open-to-close
lifecycle test.

### Issue CL-159-B: Intermittent Market-Evidence Deadlines Remove Candidates

#### Fingerprint

`runtime.snapshot_degraded`, `runtime.snapshot_fallback_last_good`,
`runtime.snapshot_unavailable`, `runtime.entry_oi_targeted_refresh_failed`,
or `runtime.entry_quote_revalidate_failed` with
`entry_evidence_deadline_exceeded`.

#### Evidence and Root Cause

The post-deploy interval recorded 373 degraded snapshots, 288 last-good
fallbacks, 171 unavailable snapshots, 31 targeted-OI refresh failures, and 93
quote revalidation failures. These are entry-admission events, not order-path
errors: the current audit snapshot later recovered to fresh, and the compact
BBO plane had current quotes from all seven venues.

Some liquidity blocks are expected structural decisions, for example confirmed
`perp_open_interest_structural`; others are unavailable/stale OI or quote
evidence. The unresolved source-side issue is a tight timing envelope between
public acquisition, enrichment/publication, the 3-second sidecar refresh, and
the 4-second market-age gate. The audit does not establish that relaxing either
threshold is safe.

#### Root Fix and Local Implementation

Preserve fail-closed admission. The existing candidate-leg final BBO/OI
revalidation remains authoritative; broad snapshot degradation is no longer
used as a substitute for that proof. The sidecar now records optional,
non-admission timing evidence in `candidate_build_diagnostics`: refresh start,
per-venue quote observation, OI completion and per-venue OI receipt,
candidate-build start/completion, entry publish/install stages, and a rolling
128-sample p50/p95/p99 refresh latency window. The compact entry projection
preserves the pre-install fields and its installed manifest ready clock is the
install-completion proof. No quote TTL, OI floor, liquidity threshold, or
final-revalidation deadline was widened.

#### Acceptance

Local regression coverage verifies original venue receipt times are not
re-dated, timing survives the entry projection, and the rolling latency window
is emitted. Safety behavior remains fail-closed; production evidence is still
needed to show that transient public-source latency no longer suppresses an
otherwise qualified candidate.

### Issue CL-159-C: Hyperliquid Is Strict Read-Only and Shares a Rate-Limit Risk

#### Fingerprint

`api_wallet_authorization_not_verified_strict_readonly` and Hyperliquid
`POST /info` HTTP `429`.

#### Evidence and Root Cause

The live runtime intentionally reports
`hyperliquid_trading_disabled_reason=api_wallet_authorization_not_verified_strict_readonly`.
It can read account state but cannot open or close a Hyperliquid trade. The
same post-deploy journal also has intermittent `429` responses from
`https://api.hyperliquid.xyz/info`; current BBO output later recovered, so this
is not a continuous venue outage.

The authorization block is a deliberate safety policy, not an exchange reject.
The 429 evidence proves public-request budget pressure on the IP, but does not
by itself prove LightFee is the only consumer. Hyperliquid documents an
IP-weighted Info-endpoint limit; request weight varies by request type.
See the [official Hyperliquid rate-limit documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits).

#### Root Fix and Local Implementation

Do not bypass strict read-only. Enable trading only after an explicit,
operator-authorized wallet/account identity and permission verification. All
LightFee `POST /info` read-only paths now use a locked, config-rooted shared
state directory: main sidecar, WS-BBO REST fallback, live adapter, diagnostics,
and the standalone L2 probe. It enforces the 250ms minimum interval, shares
`Retry-After` plus capped exponential 418/429 cooldown across processes, and
resets the failure sequence only after a confirmed 2xx response. Only public
`meta`/`metaAndAssetCtxs` responses are short-cacheable and retain their
original receipt timestamp; account truth is never cached. The environment
directory remains an explicit operator/test override. Hyperliquid-specific
evidence stays candidate-scoped and `api_wallet_authorization_not_verified_strict_readonly`
remains unchanged.

#### Acceptance

Local regression tests cover multi-process pacing, shared exponential cooldown
and 2xx reset, public-metadata-only caching, config-root resolution, and the
strict-readonly boundary. Trading authorization remains open by
operator/configuration choice; production closure still requires a sustained
window without 429-caused candidate evidence loss under the intended process
set.

### Issue CL-159-D: `diagnose_live` Symbol Scope Can Produce a False Truth Gap

#### Fingerprint

An unrelated event symbol, such as Bybit `YFIUSDT`, is passed to a different
venue's private symbol probe and causes medium/partial truth confidence despite
the account-wide probe being clean.

#### Root Cause and Root Fix

`scripts/diagnose_live.py` aggregates symbols from events globally, then passes
that union to every venue's account-truth builder. A venue that does not list
the symbol can return an unsupported-symbol error, which is then reported as a
private-truth gap. The isolated Bitget account-wide read and the later
unfiltered all-seven truth run were both high-confidence flat.

Account truth must always start from unfiltered positions and all open orders.
Optional symbol-scoped queries may only target the candidate's own venue and
must never lower the confidence of a successful unfiltered account result.
Add a regression in which a Bybit-only `YFIUSDT` event does not change Bitget
flat account truth from high confidence.

The adapter boundary should continue using Bitget's account-wide
[positions](https://www.bitget.com/api-doc/classic/contract/position/get-all-position)
and [open-orders](https://www.bitget.com/api-doc/uta/trade/Get-Order-Pending)
endpoints as the primary truth source.

#### Acceptance

Locally verified. `diagnose_live` now always calls account truth with no symbol
filter; event symbols are retained only for venue-scoped auxiliary context.
The Bybit-only `YFIUSDT`/Bitget regression proves an unrelated event cannot
downgrade an already successful Bitget all-account truth result. This remains a
diagnostic correctness fix, not evidence of a position or open order.

### Issue CL-159-E: Production Verifier Has a CWD-Dependent False Failure

#### Fingerprint

`strategy_entry_policy production_config_unreadable` or spread-BBO config
unavailable only when `verify_production_services.py` runs outside the project
directory.

#### Root Cause and Root Fix

The configured research manifest is relative and schema validation resolves it
against the process current working directory. The verifier therefore reports a
false failure from `/root`, while the same verifier run from `/opt/lightfee-v2`
returns zero critical and warning findings.

Resolve relative artifact paths against the loaded config/project root, rather
than the caller CWD, and add an arbitrary-CWD verifier regression. Do not cure
this by hardcoding one cloud path into deployment configuration.

#### Acceptance

Locally verified. Relative artifact paths now resolve from the loaded config
root (or the config directory when no project root is inferable), absolute
paths retain their meaning, and arbitrary-CWD verifier coverage no longer
depends on the caller's working directory. Deployed service health is
unchanged until deployment.

### Issue CL-159-F: Historical Invalid Pending-Close Reconciliation Noise

#### Fingerprint

`reconciliation.pending_close_reconciliation_invalid` with
`missing_position_snapshot_venues` for historical records.

#### Evidence, Root Cause, and Local Implementation

The post-deploy event window contains 60 such records for historical position
identities including `VANRY`, `SKL`, and `1000XEC`. The persisted records lack
complete two-leg venue/order identity and are therefore intentionally invalid
for active close supervision. At audit time the pending reconciliation queue
was empty and all seven exchanges were flat with no open orders.

Current terminal truth therefore closes the live-risk aspect, but repeated
historical warning emission obscures active problems. Malformed historical
records are now archived once only after complete, fresh, unfiltered account
positions and open-orders truth proves every configured venue flat. The archive
event carries the configured venue set, deterministic truth hash, archive key,
and evidence-gap reason; it is then removed from the active scheduling queue.
Incomplete, stale, or non-flat truth retains the record and suppresses repeated
meaningless invalid-record warnings. No local-state absence can cause archival.

#### Acceptance

Local regression tests cover complete-flat archival and stale/incomplete/nonflat
retention. Current exposure closure was a prior read-only cloud observation;
the new archival behavior is not deployed.
