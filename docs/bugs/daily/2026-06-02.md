### Production Evidence

| Samples | Bybit `EDGEUSDT`, Aster `GUAUSDT`, OKX `OPGUSDT`, Binance `ZECUSDT`/`HIVEUSDT` had `price_hint=0.0` while venue `tick_size` was present |

The live state later had no stuck local open/pending/passive/residual work, so
this was not a dirty-state closure bug. It was a price-evidence availability
bug: passive close could not place the post-only maker leg until retries
escalated to aggressive close.

### Root Cause

The entry side had been decoupled from Local-L2 by switching to
`ws_bbo_quote_lease`, but normal close price hints were still hard-coupled to
`LiveRuntime._resolve_local_l2_mid`. When Local-L2 was missing, stale, or in
rebuild for the close venue/symbol, the resolver returned `0.0`. The passive
close executor then correctly failed closed because a post-only reduce-only
maker order must have both a valid limit price and venue tick size.

The evidence was enough for a narrow root fix because the failure samples had
known positive tick sizes and only the price hint was missing. The correct
replacement part is fresh provider top-book evidence, not a wider Local-L2
threshold and not a passive-close order semantic change.

### Fix

- `LiveRuntime._resolve_local_l2_mid` still prefers a HOT, non-stale Local-L2
  book when available.
- If Local-L2 cannot provide a positive mid and the active entry readiness
  provider is `ws_bbo_quote_lease`, the runtime now checks `ws_bbo_cache` for a
  fresh top-book quote on the same venue/symbol.
- The WS BBO fallback uses the existing quote-lease age budget
  (`min(runtime.max_market_age_ms, strategy.entry_quote_lease_ttl_ms)`) and
  only returns `(bid + ask) / 2` when bid/ask are positive, non-crossed, and
  inside that budget.
- Fresh fallback evidence is recorded as
  `runtime.close_price_evidence_fallback`; stale/invalid BBO fallback evidence
  is rejected as `runtime.close_price_evidence_stale`.
- No post-only bypass, no tick-size change, no passive executor change, no
  order submit/sizing/residual/recovery change. Default `local_l2` provider
  behavior remains unchanged.

## Cluster CL-032-local-l2-hot-ws-lifecycle-coverage

### Production Evidence

After deploy `087d73a`, the provider and close-price families were stable, but
Local-L2 still emitted stale-HOT rebuild noise:

| Window | Evidence |
|---|---:|
| Post live restart `since_ms=1780398768000` through `last_ts_ms=1780402987348` | `runtime.local_l2_hot_stale_rebuild=30` |
| Same window | `reason=subscription_missing=26`, `reason=clock_skew=4` |
| Same window | dominated by Bybit `LABUSDT=14` and `HUSDT=13`, with `pool=hot_exec`, `status_before=hot`, `status_after=rebuilding`, `policy_bridge_mode=ws_snapshot_authoritative` |
| First CL032 deploy attempt `2583b11` | `runtime.local_l2_hot_stale_rebuild=2` after restart, both `subscription_missing`, Bybit `LABUSDT/HUSDT`; no `runtime.local_l2_dynamic_ws_started` in the same short scan |

There was no dirty local state and no exchange-truth mismatch, so this was not
an entry/close/pending-state bug. The recurring symptom was Local-L2 lifecycle
noise for active HOT execution books.

### Root Cause

`LiveRuntime._ensure_l2_active_for_candidates` treated a HOT, fresh, non-crossed
book as fully active and immediately skipped the rest of activation. For
WS-authoritative venues such as Bybit, that skipped the only runtime path that
registers and connects Local-L2 WS streams. A book could therefore be HOT from a
snapshot/bootstrap, look fresh during candidate activation, but have no WS
client maintaining it. Roughly five minutes later, `sync_snapshots()` correctly
classified the stale HOT book as `subscription_missing` and rebuilt it.

A second lifecycle gap existed for already-registered but disconnected streams:
`start_ws_streams()` intentionally returns `0` for duplicates, and the runtime
only called `connect_ws_streams()` when the registered count was positive. That
left duplicate registered/disconnected streams un-reconnected.

The first deploy attempt proved one more branch: startup activation runs before
`_restore_local_l2_state()`. The activation phase starts WS only for retained or
open-position targets, then restore can resurrect `local_l2_books_snapshot`
entries with `pool=hot_exec`. Those transient entry books have no retained/open
owner after restart, but they can still be REST-refreshed to HOT and then stale
five minutes later as `subscription_missing`.

This was not solved by exchange docs because the missing fact was internal
ownership: whether the runtime had actually registered/connected a stream for a
book it considered active.

### Fix

- `LocalL2DataPlane.ws_stream_state()` now exposes per venue/symbol WS
  lifecycle evidence: registered, connected, freshness-state presence, and last
  subscription/delta/keepalive/book-confirmation timestamps.
- During dynamic Local-L2 activation, HOT/fresh/non-crossed books still skip
  rebuild/bootstrap, but WS-authoritative and stream-only policies now verify
  WS lifecycle first.
- If a HOT WS-authoritative book lacks a registered or connected stream, the
  runtime registers the stream and requests a connect without re-bootstrapping
  the book.
- If a needed symbol already has a registered but disconnected stream,
  `start_ws_streams()` may still return `0`, but runtime now detects the
  disconnected state and calls `connect_ws_streams()` anyway.
- Startup restore now skips transient `hot_exec`/`warm` full-book snapshots
  that have no retained/open/pending/passive-close owner. This prevents old
  entry HOT books from being resurrected after restart without a WS lifecycle.
- Stale/crossed books keep the old rebuild path. REST-buffered venues such as
  Binance/Aster are not newly forced into this HOT-book WS lifecycle branch.
- No quote-provider, order submit, sizing, close, residual repair, recovery, or
  stale-threshold semantics changed.

The `stale_quote_lease` payloads showed that the failure had moved from
provider selection to the final execution gate. The live config used
`entry_quote_lease_ttl_ms=1500` and `max_market_age_ms=30000`; samples had
quote lease creation-to-check delays with median about `1852ms`, and some leg
quote ages from `2433ms` to `5849ms`.

### Root Cause

CL-029 refreshed WS BBO quotes only when provider validation considered the
cached quote stale by `runtime.max_market_age_ms`. That fixed very old tracked
quotes, but it left a semantic mismatch:

1. `ws_bbo_quote_lease` provider validation accepted cached BBO quotes up to
   `max_market_age_ms=30000`.
2. The execution gate correctly required both lease lifetime and leg quote age
   to fit inside `entry_quote_lease_ttl_ms=1500`.
3. A lease could therefore be created from a quote that was already older than
   the lease execution budget, or expire while the candidate moved from
   selection to dispatch.
4. The execution gate had no just-in-time refresh path, so it failed closed as
   `stale_quote_lease` even when a current WS cache quote or REST top-book
   refresh could prove fresh executable prices.

This is not a reason to widen TTL. The stale gate is correct; the quote
evidence was being acquired too early or against the wrong freshness budget.

### Fix

- `WsBboQuoteLeaseEntryReadinessProvider` now applies
  `entry_quote_lease_ttl_ms` as the quote freshness budget for lease-backed WS
  BBO quotes. If a tracked quote is older than the lease TTL, it is refreshed
  through the existing REST top-book path before a lease is created.
- `LiveRuntime._dispatch_entry` now retries the current
  `ws_bbo_quote_lease` provider exactly once when the final execution gate
  returns `expired_quote_lease` or `stale_quote_lease`.
- The refreshed lease is sent back through the same
  `_entry_quote_lease_execution_check`. If refresh fails, blocks, raises, or
  still produces stale/invalid evidence, the original fail-closed
  `runtime.entry_blocked_quote_lease` path remains in force with structured
  refresh evidence.
- No TTL widening, no post-only bypass, no Local-L2, sizing, order submit,
  close, residual repair, or recovery semantics changed.

### Root Cause

CL-028 correctly stopped untracked budget-out candidates from inflating generic
`missing_quote`; deployment evidence has `tracked_false_missing_stream_refs=0`.
The remaining branch is tracked quote freshness:

1. The WS BBO provider treats a cached top-book quote older than
   `runtime.max_market_age_ms` as unsafe, which is correct for entry.
2. Some official top-book streams are event-driven. If best bid/ask does not
   change, the stream may not refresh `observed_at_ms` inside the entry TTL.
3. The provider had no independent top-book refresh path at this boundary, so
   it could only fail closed as `entry_ws_bbo_quote_lease_stale_quote` even
   when public REST top-book could prove a fresh valid quote.
4. A one-sided REST top-book response such as Aster `COSUSDT` `bid=0` must
   remain fail-closed; this is not a reason to widen TTL or accept stale WS
   evidence.

This is not a Local-L2 regression, not a strategy threshold change, and not a
reason to relax quote freshness. It is a missing evidence-refresh path in the
new provider.

### Fix

- Add `RestTopBookQuoteRefresher`, a short-timeout public REST top-book reader
  for Binance-compatible venues, Bybit linear tickers, and OKX ticker.
- In `WsBboQuoteLeaseEntryReadinessProvider`, when a quote is missing or stale
  but the venue/symbol stream is already tracked, refresh that leg through REST
  top-book before provider quote validation.
- REST responses must pass the same positive bid/ask and non-crossed checks as
  WS cache updates. Invalid, crossed, one-sided, unsupported, timed-out, or
  errored REST responses leave the old fail-closed path unchanged.
- Refreshed quotes are written back into the existing `ws_bbo_cache`; quote
  leases still use the same provider, same TTL, and same execution gate.
- Untracked candidates still block before provider validation as
  `entry_ws_bbo_quote_lease_waiting_for_subscription`; no Local-L2, order
  placement, sizing, close, residual repair, or recovery semantics changed.

### Root Cause

1. Production did not explicitly configure `entry_ws_bbo_per_venue_budget`, so

2. Real candidate sets were much larger than four symbols per venue.
3. Budget-out candidates could still reach final entry provider decision.
4. Those candidates had no cached quote and no tracked BBO stream, so the
   provider correctly failed closed as `entry_ws_bbo_quote_lease_missing_quote`.

This is not a Local-L2 regression and not wrong-price entry. It is opportunity
coverage loss plus noisy missing-quote diagnostics.

### Fix

- Increase the default `entry_ws_bbo_per_venue_budget` from `4` to `10`.
- Add a WS BBO subscription coverage guard before provider quote validation:
  if a candidate has no cached quote and its venue/symbol stream is not tracked,
  block it as `entry_ws_bbo_quote_lease_waiting_for_subscription` with stream
  state evidence instead of calling the provider and reporting generic
  `missing_quote`.
- Preserve normal fail-closed behavior for tracked streams with missing quotes
  or stale quotes. Those remain provider-level quote failures and keep their
  evidence.
- Update example configs so operators see the explicit `ws_bbo_quote_lease`
  option and the new budget default.

No Local-L2, order placement, sizing, close, residual repair, or recovery
semantics changed.
