## Cluster CL-085: Aster/Binance WS-BBO quote lease and OI evidence closure

### GitNexus Keys

- Fingerprint:
  `aster-binance-ws-bbo-quote-lease-readiness + oi-liquidity-evidence-cache-cap`
- Components:

  `scan.no_entry_diagnostics.quote_lease_failure_counts`,
  `execution.entry_liquidity_blocked.open_interest_evidence_status`,
  `entry_outcome_summary.quote_lease_failure_counts`,
  `entry_outcome_summary.oi_liquidity_evidence_counts`

### Summary

This is a follow-up to the latest production review, not an order-path change.
The account state was not showing abnormal positions from this branch. The
remaining issue was that selected-to-open loss was still too hard to attribute:
quote stale could mean untracked WS, disconnected WS, subscribed-with-no-message,
stale WS quote, REST throttling, or invalid REST fallback; OI/liquidity blocks
could mean cache miss, refresh cap deferral, timeout, 429/rate limit, unsupported
endpoint, parse failure, or missing mark price.

### Root Cause

V2 intentionally replaced V1 local L2 with WS-BBO quote lease for entry
readiness, but some diagnostic fields still behaved as if there were only a
single generic quote-stale blocker. Binance/Aster market data had the correct
fast-path direction after CL-084 style fixes, but OI was not fully represented as
V1-style bounded enrichment evidence. Binance officially exposes bulk
`premiumIndex`/mark/funding but per-symbol `openInterest`; Aster exposes
bookTicker paths and no confirmed bulk V3 OI endpoint in the referenced docs.
So V1 semantics must be reproduced as cache + capped unresolved refresh, not as
full-universe per-symbol OI on the hot path.

### Fix

- `VenueBboDataPlane.stream_state()` now reports quote lease readiness:
  tracked/subscribed/connected/message count, last quote age, lease state, and
  reason bucket.
- Entry quote revalidation keeps existing fail-closed behavior but adds stable
  `reason_bucket` evidence for WS and REST branches. REST throttle no longer
  looks like invalid quote.
- `scan.no_entry_diagnostics` full and compact payloads include
  `quote_lease_failure_counts`, matching the runtime event buckets.
- Binance/Aster-style OI enrichment now uses an in-process cache, a per-refresh
  cap, explicit timeout/rate-limit/http/parse/unsupported/missing-mark statuses,
  and `deferred_by_cap` for symbols beyond the unresolved refresh budget.
- `diagnose_live`, offline daily reports, and blocker analysis aggregate quote
  lease buckets separately from OI/liquidity evidence status.

### Non-Changes

- No quote stale, liquidity/OI, admission, sizing, strategy, order submit, close,
  or lifecycle guard was loosened.
- The implementation does not restore V1 full local L2; V1 is used as the
  business contract: finalist-scope fresh market truth before entry,
  cache/cap enrichment for slow domains, and fail-closed entry when required
  evidence is unavailable.
- Exchange-specific APIs remain exchange-specific. Business semantics are
  unified, not the transport implementation.

## Cluster CL-084: OKX funding enrichment blocked sidecar snapshot publication

### GitNexus Keys

- Fingerprint:
  `okx-cold-cache-per-symbol-funding-blocks-sidecar-snapshot`
- Components:
  `market-data`, `sidecar`, `production-health`
- Symbols:
  `MarketDataClient._fetch_okx_style`, `SidecarService.refresh_once`,
  `analyze_sidecar_snapshot`
- Watch:
  `snapshot_stale_or_missing_timestamp`, `quote_venue_count_lt_7`,
  `missing_venues=["okx"]`, sidecar logs with long per-symbol
  `public/funding-rate?instId=...` sequences

### Summary

After deploying CL-083, `diagnose_live.py --since-deploy` showed a healthy
trading state: no positions, no open orders, no order errors, and no unmapped
lifecycle events. `verify_production_services.py` still failed because the
sidecar snapshot stayed stale and OKX was missing from the quote venue set.

### Root Cause

OKX ticker quote collection is already bulk: V2 calls
`/api/v5/market/tickers?instType=SWAP` once and receives bid/ask data for the
swap universe. The later funding-rate enrichment is not bulk in V2. On a cold
cache after restart, `_fetch_okx_style` issued per-symbol
`/api/v5/public/funding-rate?instId=...` requests and awaited the whole
enrichment gather before returning any OKX quote rows to the sidecar.

This drifted from the intended V1-compatible business contract. V1 keeps OKX
funding in a cache and updates it through the funding-rate channel/cache
workers; a slow funding refresh must not block publication of usable bid/ask
quote truth.

### Fix

- Added an OKX funding-rate enrichment budget after the bulk ticker response.
- Kept the exchange-specific per-instId funding implementation; no forced
  cross-exchange abstraction was added.
- If funding enrichment exceeds the budget, unfinished funding tasks are
  cancelled and the quote rows still publish with bid/ask/mark from ticker
  data and funding as unavailable/zero for that refresh.
- Existing cache-hit behavior and fast funding fills are preserved.

## Cluster CL-083: Bybit 110017 submit-time terminal zero-qty close drift

### GitNexus Keys

- Fingerprint:
  `bybit-110017-orderqty-truncated-after-submit +
  passive-close-deadline-fallback-unmapped-drift`
- Components:
  `passive-close`, `venue-transport`, `diagnose-live`,
  `v1-lifecycle-closure`, `runtime`
- Symbols:
  `PassiveCloseExecutor._submit_maker_order`, `_require_bybit_success`,
  `_build_order_error_evidence`, `_build_passive_close_terminal_summary`,
  `LiveRuntime._arm_overdue_passive_close_fallbacks`,
  `map_lifecycle_event_kind`
- Watch:
  `exit.passive_close_terminal_zero_qty_reduce_only_evidence`,
  `exit.passive_close_maker_submit_error`,
  `runtime.passive_close_deadline_fallback_armed`,
  `terminal_zero_qty_reduce_only_count`,
  `unmapped_event_kinds`

### Summary

Latest deployed HOMEUSDT lifecycle `entry-1781531687393-HOMEUSDT` closed to
flat/no-open-orders, but the close path exposed a semantic gap. Bybit returned
`110017 orderQty will be truncated to zero` on a reduce-only passive maker
submit after earlier live truth had not yet proven the short maker leg flat.
The fallback later flattened/cleared through live truth, but diagnostics still
showed the exchange error as a generic submit failure and exposed
`runtime.passive_close_deadline_fallback_armed` as an unmapped lifecycle event.

### Root Cause

The existing CL-025 fix covered the pre-submit case: if live truth already
shows the maker leg flat, do not submit a doomed Bybit reduce-only maker. The
new incident hit the submit-time race instead. Bybit applies reduce-only,
position, and lot-size constraints at order admission; when the live reducible
short quantity is already zero by then, official error `110017` means the order
quantity would truncate to zero. V2 treated that as an ordinary maker submit
reject before the next dual-taker/live-truth loop, and the Bybit guard did not
preserve the raw response body for diagnose.

### Fix

- Bybit nonzero retCode rejects now attach `exchange_response_body`, allowing
  diagnose to parse `retCode`, `retMsg`, and evidence completeness from the
  real exchange response.
- Bybit reduce-only close `110017/orderQty will be truncated to zero` now emits
  `exit.passive_close_terminal_zero_qty_reduce_only_evidence` and immediately
  routes to existing V1 live-truth closure.
- If live truth proves maker leg flat and the other leg live, the existing
  one-sided flatten path closes the live leg; if both legs are flat, existing
  flat cleanup clears; if live truth is incomplete, pending close is retained.
- Diagnose filters the old submit error out of active `order_error_evidence`
  only when the same position has terminal-zero evidence and a passive close
  terminal resolution. Current exchange truth remains in the summary as
  diagnostic metadata so later normal lifecycles do not resurrect the old
  resolved close error.
- `runtime.passive_close_deadline_fallback_armed` is mapped to `PASSIVE_CLOSE`
  and no longer re-emits for a pending close already in `DUAL_TAKER`.

## Cluster CL-082: Entry diagnostics selected-to-open semantic closure

### GitNexus Keys

- Fingerprint:
  `entry-diagnostics-selected-to-open-semantics +
  lifecycle-unmapped-drift`
- Components:
  `entry-funnel`, `diagnose-live`, `v1-lifecycle-closure`,
  `production-health`, `pending-entry`

  `_build_production_acceptance_gate`, `_build_entry_outcome_summary`

  `execution.passive_small_fill_buffer_expired`,

### Summary

The latest deployed cloud state before this fix was operationally healthy:
local state was running, current exchange truth was high-confidence
flat/no-open-orders, there were no pending entries, closes, residual repairs,
or live conflicts, and the three opened lifecycles in the long window had
closed. The remaining bug was diagnostic semantics, not trading execution.

Three surfaces were incomplete:

1. `blocked_candidate_samples` was emitted from entry selection, but the field
   name could be misread as a full-pipeline blocker sample.
2. `reconciliation.entry_abandoned_flat` was a valid pending-entry terminal
   cleanup event, but lifecycle closure did not map it, so
   `diagnose_live --since-deploy` could show unmapped drift.
3. Selected-to-open low conversion did not have a compact outcome summary for
   zero-fill repricing followed by `lifecycle_risk_only`, making it hard to
   separate lifecycle-risk guard behavior from quote stale, liquidity/OI, or
   finalization-window-too-early blockers.

During deployment review, a fourth same-family gap appeared in the historical
window: `execution.passive_small_fill_buffering` came from pending-entry
hedge-delta management and also needed lifecycle mapping. The paired expiry
event was mapped at the same time to avoid a one-sided future recurrence.

### Root Cause

The runtime business behavior had already converged toward the V1 contract, but
the diagnostic vocabulary was still scattered. Entry selection blockers,
pending-entry terminal cleanup, pending-entry hedge-delta buffering, and
selected-to-open outcomes were emitted as independent event names without one
shared lifecycle/diagnose projection. That made the production state safe but
made review ambiguous: an entry-selection blocker could be read as an
end-to-end no-open reason, and valid pending-entry terminal events could look
like unmapped drift.

### Fix

- Kept legacy `blocked_candidate_samples` unchanged for compatibility.
- Added `selection_blocked_candidate_samples`, where each sample carries:
  `stage="entry_selection"`, `selection_blocker`, and `reason_family`.
- Added diagnose `entry_outcome_summary` with selected, dispatched, opened,
  selected-not-opened, passive-unfilled, and zero-fill lifecycle-guard counters.
- Aggregated
  `candidate_not_tradeable_after_zero_fill_reprice + lifecycle_risk_only`
  under `zero_fill_lifecycle_guard_*` fields instead of mixing it with quote or
  liquidity blockers.
- Mapped `reconciliation.entry_abandoned_flat`,
  `execution.passive_small_fill_buffering`, and
  `execution.passive_small_fill_buffer_expired` to `PENDING_ENTRY` in the V1
  lifecycle closure table.

### Non-Changes

- No V1 risk gate was relaxed.
- No strategy threshold, sizing, quote/OI/liquidity threshold, exchange order
  path, cancel path, close path, residual repair path, or account state was
  changed.
- Exchange implementations remain venue-specific; only the business diagnostic
  semantics were unified into the V1 lifecycle/order-truth contract.

### Summary

The HOME fixes on 2026-06-14 proved the immediate live artifact can be owned and
cleaned, but the evidence stack still had a systemic weakness: different
runtime surfaces could interpret order status, ACK, local fill fields, live
position truth, and fill/execution reconciliation independently. That made it
too easy for an exchange-specific partial fix to close one symptom while a
neighboring lifecycle path kept treating weak evidence as success or terminal
flatness.

CL-081 makes order success a shared resolver decision. Consumers must read an
explicit result instead of inferring truth from `None`, ACK presence, order
detail status, or positive non-fill counters.

The follow-up pending auto-repair audit keeps the proof boundary explicit:
positive-fill/live-truth cleanup is production-proven by the cloud
`positive_fill_live_truth_conflict -> owned_live_conflict_cleanup_attempt ->
owned_live_conflict_cleanup_succeeded -> removed_by_v1_lifecycle_closure`
event chain. Zero-fill live-artifact cleanup is closed in code and tests, and
the deployed cloud line contains that fix, but the latest post-deploy window did
not contain a fresh zero-fill sample that hit the specialized direct-cleanup
event path. The stale HOME zero-fill artifact was cleared through the abort
cleanup path and recovery core returned to `RUNNING_CLEAN`. A later read-only
docs-backfill recheck saw a separate HOME matched open position, so the docs
must not overstate either direct production exercise of the zero-fill-specific
branch or current flat/no-open-orders acceptance.

### Root Cause

The old shape had two layers of drift:

1. Venue adapters were moving toward official exchange evidence, but runtime
   callers still had local predicates like `reconciliation is not None and
   quantity > 0`. That predicate is only safe if every adapter always guarantees
   the reconciliation came from a fill/execution endpoint. It is unsafe when an
   exchange order detail can contain cumulative quantities without matching
   fills, or when ACK/realtime status is accepted but not executed.
2. Lifecycle closure had new production events that were meaningful, but not
   mapped. Unmapped events made diagnose/health reason about evidence closure
   differently from runtime cleanup and pending-entry retention.

### Exchange Evidence Matrix

| Venue | Fill success evidence | Weak evidence that cannot confirm fill | Fail-closed / truth-gap rule |
|---|---|---|---|
| Binance / Aster | `FILLED` plus positive executed quantity, or adapter-normalized fill truth | `NEW`, zero executed quantity, ACK/order status alone | `NEW/zero` remains `truth_gap` until open-order/live-position truth closes it. |
| OKX | `/api/v5/trade/fills` or fills-history with `ctVal` conversion where needed | `/trade/order` or history detail with positive `accFillSz` but empty fills | Empty fills or missing `ctVal` is `truth_gap`, not a fake maker fill. |
| Bybit | `/v5/execution/list` positive execution quantity | ACK, `/v5/order/realtime`, or order history without execution | ACK/realtime-only remains pending reconciliation. |
| Bitget | Family-resolved fill truth with valid side | Detail quantity without side or unresolved account family | Missing side/family is `unsupported_fail_closed`. |
| Gate | Order detail/open-order/position truth jointly proving fill or no-fill | Ambiguous detail without fill/open/live closure | Ambiguity remains `truth_gap`. |
| Hyperliquid | Configured account `orderStatus`/historical order/open-order/clearinghouse evidence with unambiguous oid/cloid | Agent/account mismatch or unclear oid/cloid | Account identity mismatch is `unsupported_fail_closed` / `truth_gap`. |

### Fix

- Added `OrderTruthFillStatus`, `OrderTruthEvidenceStatus`, and
  `OrderTruthSuccessDecision` to the shared order truth ledger.
- Added `OrderTruthLedger.resolve_order_success()` as the single local decision
  point for order success evidence:
  - `confirmed_fill` requires positive fill/execution reconciliation.
  - `truth_gap` retains work for ACK/detail/realtime evidence without fill truth.
  - `unsupported_fail_closed` covers missing side, unresolved account family,
    or Hyperliquid account identity mismatch.
  - `live_position_present` and `live_flat` are explicit outputs, not implied
    by `None`.
- Runtime pending-entry hedge recovery, live hedge driving, and finalize-open
  reconciliation now consume the resolver. Weak reconciliation can add evidence
  and retain pending work, but cannot mutate leg-filled state as a confirmed
  open.
- Pending-entry live-truth cleanup remains centralized in the finalizer path:
  unresolved live artifacts route through the shared owned single-leg cleanup
  helper, and pending removal still goes through the V1 lifecycle closure
  removal authority rather than scattered `pending_entries.pop()` calls.
- Passive close ACK/error reconciliation now consumes the same resolver before
  recording a filled hedge. ACK-only and realtime-only evidence registers
  pending reconciliation rather than terminal success.
- Lifecycle closure maps the newly observed production events:
  `exit.accepted_order_truth_gap_registered`,
  `exit.pending_close_reconciliation_registered`, `exit.reconciled`,
  `runtime.position_drift_corrected`, and
  `reconciliation.entry_abandon_retained_unresolved_maker`.
- The docs-backfill cloud recheck exposed one more mapped-pending-entry event:
  `reconciliation.entry_flat_not_found_terminal_cleared` is the flat/not-found
  branch after `_finalize_pending_entry()` authoritatively clears a zero-fill
  pending entry, so it maps to `PENDING_ENTRY` rather than remaining an unmapped
  lifecycle diagnostic.

### Non-Changes

- No strategy threshold, quote/OI threshold, sizing, leverage, order-submit,
  cancel, close lifecycle, residual-repair lifecycle, or cloud trading-state
  mutation changed.
- No production order was submitted or cancelled during this local fix.
- This does not weaken CL-078/CL-079/CL-080 live-truth cleanup rules; it moves
  their evidence assumptions into one reusable resolver.
