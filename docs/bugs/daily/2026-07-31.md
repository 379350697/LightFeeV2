# Bug Ledger - 2026-07-31

## Cluster CL-169 - Funding-Interval Proof Cache and Bounded Cold Warmup

Status: local root fix verified; deployment and live evidence pending

### Evidence and Root Cause

The Binance/Aster-compatible ticker endpoints do not provide an explicit
funding interval for every contract. V2 attempted to infer it by requesting two
historical funding settlements for every missing symbol during the public
sidecar refresh. At eight concurrent requests under a three-second total budget,
a cold process covered only an initial fraction of a several-hundred-symbol
market; all remaining rows became `funding_interval_ms_invalid` and were
subsequently described by the liquidity lifecycle as
`liquidity_quote_unavailable`. The latter was derived from the discarded funding
quote, not evidence that BBO or OI had failed.

Prior restart handling compounded this: it copied an interval from the prior
snapshot into memory with the current process time. The snapshot did not retain
a source-specific interval-proof timestamp, so restart could extend unverified
evidence as if the exchange had just supplied it.

### Root Fix

1. Persist only validated exchange-derived interval proof in a compact, atomic
   sidecar sibling cache: venue, symbol, interval, proof source, and original
   observation timestamp.
2. On restart, validate and load only configured-venue entries while preserving
   their original timestamp. A legacy snapshot is no longer allowed to create
   fresh cadence proof.
3. A valid local proof suppresses historical funding-rate HTTP during normal
   scans. Missing or expired proof uses a deterministic rotating batch of at
   most 48 symbols no more than once per 30 seconds, instead of a full-universe
   fan-out per refresh.
4. There is no default Binance/Aster interval. A symbol without current
   venue-derived proof remains interval-unknown and is excluded by the existing
   funding admission contract. BBO, Local-L2, OI, liquidity, account-truth, and
   final execution checks are unchanged.
5. Remove the unreferenced `LiquiditySource` and its
   `MarketDataClient.fetch_perp_liquidity()` wrapper. It was a second public
   client that could re-enter the funding fetch path without sidecar-owned
   cadence proof; OI/volume remain supplied by the sole `ExchangeSource` path.

### Regression Proof and Remaining Boundary

Focused market-data, sidecar, source, snapshot-freshness, and funding-entry
degradation suites pass: 290 passed, 10 skipped. Tests cover bounded rotating
cold repair, cache schema/venue validation, atomic persist shape, preservation
of the original proof clock, and rejection of the old snapshot-as-fresh path.

Deployment must verify the cache is populated after a healthy interval proof,
survives a sidecar restart, and leaves Binance/Aster coverage stable without
all-symbol `fundingRate` bursts. A new interval change or cache expiry must
remain fail-closed until refreshed venue proof arrives.

## Cluster CL-170 - Funding-Window Waiting Was Misreported as Deploy-Critical

Status: local root fix verified; deployment pending

### Evidence and Root Cause

The deployed snapshot had 169 retained candidates, not zero candidates. Every
one was blocked by `outside_scan_window`: the earliest settlement was 36.2
minutes away while production is configured to scan only from 35 to 3 minutes
before settlement. This is the V1 temporal lifecycle state, not a data-plane
failure. However, the V2 deployment-health check collapsed every
zero-unblocked-candidate state into the critical
`funding_entry_readiness_no_unblocked_candidates` fingerprint, preventing an
otherwise safe deployment outside the normal funding scan window.

### Root Fix

The health contract now recognizes a complete candidate blocked only by
`outside_scan_window` as `waiting_for_funding_window`: the report is healthy
for deployment but `funding_entry_ready=false`. A candidate with incomplete
economics, malformed market evidence, or another non-temporal reason does not
count as this proof and still produces the original critical fingerprint when
no timing-only candidate exists. The trading-time candidate and final-entry
gates are unchanged.

### Regression Proof and Remaining Boundary

Production-health and snapshot suites cover both branches: an all-window
frontier is deploy-healthy and not trade-ready; an incomplete-economics
frontier remains critical. Deployment must verify the status transition around
the real 35-minute boundary and the subsequent selected-pair final gates.

## Cluster CL-171 - Restart Hydration Dropped OI Proof and Stalled Sidecar Publication

Status: local root fix verified; deployment and live evidence pending

### Evidence and Root Cause

The deployed funding sidecar process remained running, but its V5 publisher
rejected every replacement snapshot with
`quote_oi_observed_proof_invalid` for Binance, OKX, and Aster rows. The last
readable opportunity-input snapshot then remained frozen for more than twelve
hours; live correctly treated it as stale and produced no executable frontier.
This was a data-plane outage, not evidence that no market opportunity existed.

The restart cache path introduced in `408b1db` reconstructed an in-memory
`FundingTicker` with an OI scalar and `observed` status, but omitted the raw
value, unit, conversion, and identity fields that make V5 OI evidence
verifiable. The next ordinary fast scan reused that contradictory cache record.
The publisher correctly refused the malformed row, but treating one restored
row as a global publication error turned a pair-scoped cache defect into a
whole-sidecar outage.

### Root Fix

Restart hydration now transfers the complete persisted OI proof verbatim:
value, raw value/unit, contract multiplier, conversion mark, timestamps,
source, sample identity, and venue symbol. It verifies the same proof before
the item enters the slow cache. A legacy or corrupted `observed` record is
downgraded to pair-scoped `unavailable`, with all numeric/provenance fields
cleared and a durable reason; the normal asynchronous OI refresh may repair
that pair later. Non-observed legacy rows are normalized the same way.

The V5 publisher remains strict. There is no relaxation of selected-pair
BBO, Local-L2, OI, funding, account-truth, or final execution admission. The
change repairs cache transport so a valid restored observation remains valid
and an invalid one cannot block publication for unrelated pairs. If a future
producer defect nevertheless reaches the strict publisher, the long-running
sidecar logs that rejected refresh, retains the last atomic snapshot, and
retries at its existing scheduled cadence rather than exiting into a systemd
restart loop. The unchanged snapshot becomes stale and fail-closed under the
normal entry freshness contract; it is never treated as new market data.

### Regression Proof and Remaining Boundary

The source regression tests cover valid OI proof round-trip through restart
hydration, fast-scan cache merge, quote serialization, and actual V5 snapshot
publication. They also cover incomplete historical proof becoming pair-scoped
unavailable rather than global poison, plus a rejected refresh followed by a
successful scheduled retry in the same sidecar process. Sidecar source/service,
snapshot, production-health, stale-fallback, and market-data suites pass: 385
passed.

Deployment must verify a fresh `published_at_ms` continues advancing across a
sidecar restart, the journal has no `quote_oi_observed_proof_invalid` publish
rejections, and candidates resume according to the normal funding window.

## Cluster CL-172 - First Binance/Aster Snapshot Bridge Rejected by Raw `pu`

Status: local root fix verified; deployment and live evidence pending

### Historical Classification and Root Cause

This is not a new exchange behavior introduced by the latest deployment. It is
a recurrence of the historical CL-001-D/CL-010 fingerprint whose root cause was
not closed. The original DEXE/EDEN record lacked the raw sequence fields needed
to distinguish the first REST bridge from a later WebSocket-link break, so it
was classified too broadly. Commit `1f00a665` on 2026-05-26 then made every
replayed event require `pu` to equal the REST snapshot sequence. The diagnostic
classifier added by `7ee4c72e` on 2026-05-29 encoded the same interpretation.

That historical cluster actually mixed two different shapes. The later JTO
fixture contains a broken link after one accepted WebSocket event and must
still rebuild. The current production evidence fails on the first buffered
event: `U <= snapshot + 1 <= u`, while raw `pu` points to the preceding
WebSocket event and can legitimately be lower than the independently sampled
REST sequence. V1 and Binance's local-book contract use the `U..u` range for
this first REST-to-WebSocket bridge and enforce `pu ==` the previous accepted
`u` only on subsequent events.

The prior tests missed the regression because the first-range case either
omitted previous-link metadata or chose `pu == snapshot`; the historical
mismatch fixture starts failing on its second buffered event. Retained rotated
production logs prove this exact first-event shape was already occurring by
2026-07-29 13:25:57 CST, before the latest deployment. The restart/bootstrap
cycle made it much more visible; it did not introduce the defect. In the
original audited post-deploy window, 104 Binance snapshot errors all failed
before one event was replayed and all had a valid first `U..u` bridge, while raw
`pu` did not equal the REST snapshot.

### Root Fix

Binance and Aster replay now admit the first buffered event by its documented
`U..u` snapshot bridge. A non-mutating replay copy anchors that first apply to
the REST sequence while preserving raw `pu` in the buffered event and failure
evidence. Every subsequent buffered event still requires strict `pu` chaining.
Gate retains its previous strict first-link behavior, and the existing
unbridged snapshot-boundary failure remains fail-closed.

The incident classifier now recognizes only a zero-replayed, index-zero valid
Binance/Aster snapshot bridge as non-official-failure evidence. It still reports
historical later-event `previous_link_mismatch`, real gaps, and unbridged
snapshot boundaries.

### Regression Proof and Remaining Boundary

Focused replay, V1-parity, historical fixture, diagnostics, and live-harness
suites pass: 47 passed. The complete Local-L2-related suite passes: 470 passed,
3 explicit live-probe skips. New tests cover production-shaped Binance and
Aster first bridges with raw `pu` behind the REST snapshot. Existing tests
prove that a later broken `pu` chain and a real unbridged snapshot boundary
still rebuild.

No production order, cancellation, state mutation, service restart, or deploy
was performed during this fix. Deployment acceptance must observe successful
Binance/Aster bootstrap replay, disappearance of this exact index-zero valid
bridge error, unchanged fail-closed behavior for later-link mismatches, and
normal entry/close exchange truth before declaring the cluster closed.
