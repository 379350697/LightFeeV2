## Cluster CL-007-biousdt-exchange-truth-false-green-root-fix

### GitNexus Keys

- Fingerprint: `v2.bybit-biousdt-live-recovery-cleanup-duplicate-cid-full-misclassified + local-state-false-green-exchange-nonzero`

- Related regressions: CL-001 passive-close duplicate, CL-001 post-deploy risk-only regressions, CL-005 zero-fill ghost/residual, CL-002 recovery live-position probe evidence quality.

### Summary

This was a V2 semantic drift from V1 exchange-truth priority. A clean local state was treated as green even when exchange truth showed a nonzero Bybit position. The live recovery cleanup then reused the same Bybit `orderLinkId`, received official retCode `110072` duplicate, reconciled an old filled order, and incorrectly emitted success while the live position remained nonzero.

### Root Fix

- Production health and `diagnose_live.py` now mark local-clean/exchange-nonzero as critical with `exchange_truth_mismatch` and `nonzero_live_position`.
- Bybit duplicate cleanup always rechecks live position. Old order fill evidence only clears state if the live position is flat; if live quantity remains, cleanup schedules a fresh reduce-only CID retry or backs off/fail-closes with evidence.
- Pending residual repairs are lifecycle recovery work and are exported through current state, so BIOUSDT-style one-sided exposure cannot silently disappear behind `open=0/pending=0`.
- Bybit trading agreement rejects (`110123`, `110125`, `110126`) are admission blocks. Official docs describe these as trading-terms agreement requirements, so the runtime caches the symbol/account block and exposes it instead of retrying LITEUSDT.
- Aster `-2027` is handled as official leverage/max-position admission. Official Aster docs define `-2027 MAX_LEVERAGE_RATIO` and expose leverage brackets via `GET /fapi/v1/leverageBracket`; V2 now treats the reject as `leverage_admission_blocked` and stops repeated ESPORTSUSDT order attempts.
- OKX recovery bulk metadata/rate-limit failures no longer explode into unsupported per-symbol probes in the same window; metadata missing is aggregated and 429/50011/50061 enters venue-level cooldown diagnostics.

### Official Docs Used

- Bybit V5 error docs: `110072 OrderLinkedID is duplicate`; `110123/110125` require agreeing to trading terms. Bybit changelog documents Sign Agreement endpoint updates.
- Aster API docs: `POST /fapi/v1/leverage`, `GET /fapi/v1/leverageBracket`, and `-2027 MAX_LEVERAGE_RATIO`.

## Cluster CL-005-live-shutdown-systemd-stop-timeout-root-fix

### GitNexus Keys

- Fingerprint: `v2.lightfee-live.systemd-stop-timeout.status-9-kill + sigterm-no-explicit-shutdown-path + background-task-unbounded-join`
- Components: `live-runtime`, `systemd`, `shutdown`, `background-tasks`, `state-persistence`, `network-close`
- Symbols: `main`, `async_main`, `LiveRuntime.stop`, `_cancel_tasks_with_timeout`, `_cancel_tasks_without_wait`

- First seen: 2026-05-26 deployment restart evidence.
- Watch: `Main process exited status=9/KILL`, `Failed with result timeout`, `shutdown stage=signal_received`, `shutdown stage=cancel_tasks`, `shutdown stage=close_network`, `shutdown stage=flush_state`, `shutdown stage=exit_complete`, `status=timeout`

### Summary

Deployment restart of `lightfee-live` hit the systemd stop timeout. Evidence showed `Main process exited status=9/KILL` and `Failed with result timeout`, while the service was otherwise healthy after restart. That classifies the issue as a graceful-shutdown/lifecycle defect, not a trading-semantics defect.

### Shared Root Cause

The live process did not have a single explicit SIGTERM-owned shutdown path. Signal handling cancelled the main task, but background work could remain outside bounded ownership. Runtime network close and adapter shutdown awaited cooperative cancellation, so WS/listen-key/sidecar/recovery/scan style tasks or cancellation-hostile adapter shutdowns could keep the process alive until systemd killed it.

### Failed / Ineffective Attempts

- Increasing `TimeoutStopSec` alone would only hide the hang. It was not used as the fix.
- Plain `asyncio.wait_for()` around a shutdown coroutine is insufficient when the coroutine catches `CancelledError` and delays forever during cleanup; the outer wait can still be held hostage by cancellation cleanup.
- A final `main()` cleanup that waits again for all pending tasks adds another hard stop delay after the real shutdown path already timed out.

### Fix Status

Fixed locally in this workstream.

Implemented behavior:

- `main()` records `SIGTERM`/`SIGINT` into a shutdown event instead of directly cancelling the main task.
- `async_main()` owns the shutdown sequence, logs `shutdown stage=signal_received`, handles signals during startup and run loop, and cancels runtime-created background tasks with the configured shutdown grace period.
- `LiveRuntime.stop()` logs and journals real shutdown stages in execution order: `close_network`, `flush_state`, `exit_complete`.
- Network/venue close operations are bounded by deadline-based task waits, including local-L2 WS stop, private WS/listen-key stop, and per-adapter shutdown.
- Stuck shutdown work is logged with task names such as `adapter.shutdown:binance` and `status=timeout`.
- The final `main()` loop cleanup no longer performs a second hard wait. It cancels already-reported pending tasks without blocking process exit.
- No systemd timeout increase is part of the fix.
