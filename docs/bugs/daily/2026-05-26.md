- Watch: `recovery.live_position_probe_error`, `recovery.live_position_probe_unsupported_symbols`, `recovery.live_position_probe_metadata_missing`, `recovery.live_position_bulk_probe_metadata_missing`, `okx_contract_metadata_missing_ct_val`, `classification=instrument_missing`, `classification=metadata_missing`

### Summary

Production logs showed `recovery.live_position_probe_error` emitted at high volume, many with `error=""`, and many caused by unsupported symbols that should never have reached per-symbol private position probes. OKX also emitted `okx_contract_metadata_missing_ct_val` without enough classification to distinguish an unsupported instrument row from an instrument row missing required contract metadata.

### Shared Root Cause

V1 first filtered scan/recovery symbols through the venue-supported contract catalog, then probed private live positions. V2 correctly filtered scan candidates elsewhere, but the recovery bulk-failure fallback could still issue per-symbol private position probes for symbols unsupported by that venue. Unsupported catalog misses were therefore mixed into probe error evidence.

The OKX path also treated missing contract metadata as a generic normalization failure. OKX official docs define FUTURES/SWAP/OPTION contract notional through instrument metadata such as `ctVal`/`ctType` from `GET /api/v5/public/instruments` and account instruments. V2 needed to preload/cache this metadata before parsing OKX contract positions or normalizing OKX SWAP order quantity.

### Fix Status

Fixed locally in this workstream.

- Recovery bulk-probe fallback now calls the same venue catalog filter before per-symbol probes.
- Unsupported symbols are journaled once as `recovery.live_position_probe_unsupported_symbols` with `venue`, `unsupported_count`, `sample_symbols`, and `sample_venue_symbols`; repeated diagnostics are rate-limited by venue.
- Unsupported symbols are no longer represented as `recovery.live_position_probe_error`.
- Probe exceptions now include non-empty `error`, `exception_class`, `endpoint`, `normalized_symbol`, `venue_symbol`, `retCode`, `retMsg`, `body_summary`, `retryable`, and transport category/status when available.
- OKX live transport preloads SWAP metadata from `/api/v5/public/instruments?instType=SWAP`, falling back to `/api/v5/account/instruments?instType=SWAP`, then caches rows by `instId` and canonical symbol.
- Missing OKX instrument row is classified as `instrument_missing`; present row without usable `ctVal` is classified as `metadata_missing`.
- All OKX `okx_contract_metadata_missing_ct_val` exits now use one helper so final fallback paths cannot emit an unclassified empty probe error.

## Cluster CL-003-no-entry-stale-liquidity-domain-root-fix

### GitNexus Keys

- Fingerprint: `v2.lightfeev2.no-entry.opened-zero + stale_liquidity_global_skip_entry + sidecar_perp_liquidity_budget_3000_vs_20s_publish`
- Components: `live-runtime`, `sidecar`, `snapshot-freshness`, `candidate-filtering`, `local-l2`, `observability`, `v1-parity`
- Symbols: `LiveRuntime._candidate_snapshot_freshness_failures`, `LiveRuntime._filter_candidates_by_snapshot_freshness`, `SidecarService.refresh_once`, `LiquidityLifecycle`, `CandidateInput`
- Files: `lightfee/engine/runtime.py`, `lightfee/sidecar/service.py`, `lightfee/sidecar/snapshot.py`, `lightfee/sidecar/publisher.py`, `lightfee/sidecar/v1_compat.py`, `lightfee/config/schema.py`, `tests/test_runtime_snapshot_freshness.py`, `tests/sidecar/test_v1_parity_lifecycle.py`
- First seen: 2026-05-26 deployment evidence: `entry.opened=0`, `runtime.position_opened=0`, `scan.no_entry_diagnostics.reason=no_tradeable_candidates`, and high-frequency `runtime.snapshot_freshness_decision` with `reason=stale_liquidity`, sample `age_ms~=19971`, `budget_ms=3000`, `decision=skip_entry`, `fallback_source=fresh_sidecar`.
- V1 reference: `docs/parity/v1_semantic_contract_catalog.md` snapshot freshness and degraded domain semantics.

### Summary

The live scan had fresh quotes and fresh/local execution L2 evidence available, but a coarse sidecar perp-liquidity lifecycle row refreshed on a slower cadence than the hardcoded 3000 ms budget. V2 treated that liquidity-domain staleness as a candidate-global `skip_entry`, producing `no_tradeable_candidates` and preventing new opens.

### Shared Root Cause

V2 collapsed V1's per-domain freshness model into a global candidate hard gate. A sidecar liquidity lifecycle row represented advisory/coarse perp-liquidity coverage, but the runtime treated any stale liquidity lifecycle as execution-required data for every candidate. Sidecar also reported liquidity publish timing with global batch state, so one venue's successful liquidity refresh could make another venue's timeout/degraded row look freshly published.

### Failed / Ineffective Attempts

- Raising the sidecar snapshot max age alone is insufficient because it does not distinguish quote freshness, execution L2 freshness, and coarse perp-liquidity freshness.
- Treating all degraded liquidity rows as blocking is too broad; partial symbol degradation must not poison unrelated candidate symbols.
- Recording only `stale_liquidity` does not expose whether the stale data was advisory coarse liquidity or execution-required sizing data.

### Fix Status

Fixed locally in this workstream.

Implemented behavior:

- Runtime now distinguishes `runtime.quote_stale`, `runtime.execution_l2_stale`, `runtime.perp_liquidity_stale_advisory`, and `runtime.perp_liquidity_stale_blocking`.
- Coarse sidecar perp liquidity is advisory unless the candidate explicitly declares `sizing_liquidity_source` / related source as `sidecar_perp_liquidity`.
- Required sidecar perp liquidity blocks only when the relevant venue/symbol row is missing, stale, has no usable coverage, or has a degradation reason matching the candidate symbol.
- A degraded liquidity row for another symbol, such as `ETHUSDT: fetch failed`, no longer blocks a `BTCUSDT` candidate.
- Sidecar liquidity lifecycle now carries `domain`, `source`, `publish_interval_ms`, and `published_at_ms`.
- `SidecarService.refresh_once()` tracks liquidity publish timing per `(domain, source, venue)`; failed/degraded venues no longer inherit another venue's healthy publish interval.
- `sidecar_perp_liquidity_budget_ms` defaults to 30000 ms and liquidity budget also considers refresh cadence, liquidity timeout, and observed publish interval.
- Runtime `last_scan` exposes snapshot freshness age, budget, and publish interval maps by `venue|symbol|domain`.

### Issue CL-001-A: BEATUSDT passive close dust fallback loops instead of V1 compensate/flatten

#### Fingerprint

`v2.passive-close.beatusdt-maker-small-fill-below-min-notional-enters-dual-taker-loop-instead-of-v1-abort-compensate`

#### Evidence

- `2026-05-25T23:56:56.759` production event `recovery.live_detected` recovered `live-recovered:BEATUSDT:okx->bybit` with OKX long `20` and Bybit short `20`.
- `2026-05-25T23:57:00` passive close routed for `funding_capture`; maker leg selected `long`; OKX maker submitted quantity `20` around price `1.0211`.
- Maker progress reached cumulative fill `2`, then hedge for Bybit short close requested quantity `2`.
- Hedge notional was around `2.04 USDT`, below venue min-notional policy, so V2 emitted `exit.passive_close_hedge_dust_aborted` with `reason=min_notional_rejected`.
- Fallback then repeatedly emitted `exit.passive_close_fallback_aggressive`, `exit.passive_close_hedge_dust_aborted`, and `exit.passive_close_fallback_unhedged_failed`.
- Later live truth showed OKX BEATUSDT flat and Bybit BEATUSDT short `20`, while local state still retained the recovered matched position.

#### V1 Comparison

V1 does not retry the same under-min hedge forever after maker terminality. In `/opt/lightfee/src/engine/exit.rs`, small maker fills below min-notional are accumulated while possible; once maker is terminal or attempts are exhausted, V1 logs the abort path and calls compensation/full-flatten behavior.

The V1 regression test `normal_funding_capture_close_small_fill_below_min_notional_compensates_flat` expects:

- `execution.min_notional_accumulating`
- `execution.min_notional_abort_and_flatten`
- `exit.compensated`
- no retained open position after the compensation path

V2 has partial parity in `_submit_hedge_for_delta()`, but `_fallback_to_aggressive_close()` calls it for `unhedged_residual` without reaching equivalent V1 abort-and-compensate semantics, so the fallback lane loops.

#### Exchange Docs

Bybit official `GET /v5/market/instruments-info` exposes `lotSizeFilter.minNotionalValue`, `minOrderQty`, and `qtyStep` as order constraints. Live public metadata for BEATUSDT showed the requested 2-BEAT hedge was below the exchange min-notional threshold, so the local min-notional rejection is correct; the bug is the post-rejection state machine, not the rejection itself. Source: https://bybit-exchange.github.io/docs/v5/market/instrument

#### Root Fix Required

- Preserve the local pre-submit min-notional guard.
- In fallback/dual-taker mode, if a hedge delta is below min-notional and maker is terminal or the fallback lane has exhausted meaningful accumulation, do not schedule an identical retry.
- Re-read live positions before every fallback drive and rebuild the close target from exchange truth.
- If live truth is already one-sided, close the actual remaining live exposure with reduce-only taker semantics, subject to exchange min quantity/notional rules.
- If live truth is flat, clear pending passive close and local open state with the existing live-flat recovery payload.
- Persist state only after clearing both pending and open records.
- Add V2 RED/GREEN tests that port the V1 small-fill-below-min-notional compensation scenario and a BEATUSDT-style stale matched-local / live-one-sided scenario.

#### Fix Status

Fixed in this session.

Implemented in V2 passive close:

- `_submit_hedge_for_delta()` now routes terminal maker dust below min-notional through V1-style `execution.min_notional_accumulating` → `execution.min_notional_abort_and_flatten` → `exit.compensated` semantics instead of merely arming `dual_taker`.
- `_fallback_to_aggressive_close()` now reads live positions before each fallback drive and rebuilds the close target from exchange truth.
- Live flat truth clears both `pending_passive_closes` and `open_positions`, including matching `last_error`.
- Live one-sided truth submits one reduce-only IOC taker close for the actual remaining exposure, not the stale local matched delta.
- Live both-nonzero-but-imbalanced truth computes live matched quantity plus actual excess exposure; under-min excess routes to V1 abort/compensate instead of stale local retry.
- Under-min live/delta exposure enters compensate/flatten semantics and does not schedule the same under-min residual for another fallback retry.

### Issue CL-001-B: UBUSDT recovery cleanup reuses duplicate Bybit client id

#### Fingerprint

- Attempts 2 and 3 reused the same client id, so the cleanup repeatedly failed and ended in `recovery.live_mismatch_flatten_failed` / `recovery.blocked`.

#### V1 / Existing V2 Comparison

The exact duplicate-id class was already fixed for passive close hedge reconciliation in the 2026-05-24 CL-001 branch: duplicate client id must be reconciled by client order id before being treated as failure. The recovery cleanup path did not receive the same semantic handling, so this is an old root class recurring in a different path.

#### Exchange Docs

Bybit official V5 error code `110072` is `OrderLinkedID is duplicate`. Source: https://bybit-exchange.github.io/docs/v5/error

#### Root Fix Required

- Extend duplicate client-order-id reconciliation to `Runtime._cleanup_failed_leg_exposure()` or centralize it below all order-submit call sites.
- On Bybit `110072`, query by `orderLinkId` across open orders, order history, and executions.
- If reconciliation proves the order filled or live exposure is flat, mark cleanup successful and unblock recovery.
- If reconciliation cannot find the order and live exposure remains, generate a new attempt-scoped cleanup client id or cancel/resolve the old id before retrying.
- Never blindly retry the same duplicate cleanup id.
- Add RED/GREEN tests for duplicate-filled, duplicate-not-found-live-still-nonzero, and duplicate-not-found-live-flat branches.

#### Fix Status

Fixed in this session.

Implemented in V2 recovery cleanup:

- `Runtime._cleanup_failed_leg_exposure()` now treats Bybit `110072` as an idempotency/reconciliation event, not as a normal cleanup failure.
- Runtime cleanup reuses the existing Bybit duplicate `orderLinkId` detector and the venue adapter `fetch_order_fill_reconciliation()` contract used by passive close / close execution.
- Bybit duplicate cleanup reconciliation records the attempted `client_order_id`, attempt number, reconciliation endpoints, live exposure, reconciled quantity, original error, and final decision.
- If reconciliation proves the cleanup order filled, cleanup returns success.
- If reconciliation cannot find the order but the live position is already flat, cleanup returns success so recovery mismatch flattening can complete instead of blocking.
- If reconciliation cannot find the order and live exposure remains, the next retry uses an attempt-scoped cleanup client id. The same duplicate id is not blindly resubmitted.
- After three unresolved duplicate attempts with live exposure still present, cleanup fails explicitly with `decision=failed_live_exposure_remaining`.

### Issue CL-001-C: Aster listenKey invalidation is warned but needs active rotation

#### Fingerprint

`v2.aster-private-ws.listenkey-1125-keepalive-invalid-without-forced-ws-rotation`

#### Evidence

Current run emitted repeated warnings of the form:

- `aster listenKey keepalive failed: HTTP 400: {"code":-1125,"msg":"This listenKey does not exist."}`

This recurred multiple times between `2026-05-25 22:07 CST` and `2026-05-26 00:22 CST`.

#### V1 / Exchange Comparison

Aster behaves like Binance-style listenKey user streams. Binance official error `-1125 INVALID_LISTEN_KEY` says the listenKey does not exist and instructs clients to recreate it with `POST /fapi/v1/listenKey`. Source: https://developers.binance.com/docs/derivatives/usds-margined-futures/error-code

#### Root Fix Required

- Classify `-1125` as terminal invalid-listen-key, not a generic transient keepalive warning.
- When keepalive receives `-1125`, actively close the current Aster private websocket and restart the listenKey acquisition loop.
- Emit structured events for listenKey creation time, last keepalive success, invalidation reason, reconnect count, and private-stream silent age.
- Ensure the reconnect path re-subscribes all private streams and does not leave stale user-data tasks alive.
- Add tests that simulate a keepalive `-1125` and assert websocket closure, new listenKey creation, and resumed private stream.

#### Fix Status

Fixed in this session.

Implemented in V2 Aster private WS:

- `_keepalive_aster_listen_key()` now classifies Binance/Aster-style `-1125` as terminal `invalid_listen_key_-1125`.
- `_aster_private_ws_loop()` now treats terminal listenKey invalidation as a forced rotation: close the active private WS, stop the old keepalive task, delete/retire the old listenKey best-effort, POST a fresh listenKey, reconnect, and resume private stream processing.
- Generic transient keepalive failures are recorded as `aster.listen_key_keepalive_failed` with `reconnect_result=not_rotated`; they do not create an unbounded listenKey churn loop.
- Structured diagnostics now include `listenKey_created_at`, `last_keepalive_ok_at`, `invalid_reason`, `rotation_count`, `private_ws_silent_age`, and `reconnect_result`.
- Reconnect after invalidation records private WS failure with an immediate unhealthy threshold, so the private stream is not reported healthy while waiting for a new listenKey/session.

### Issue CL-001-D: Binance local-L2 sequence rebuilds recurred, but current evidence matches exchange continuity rules

#### Fingerprint

`v2.local-l2.binance-buffered-replay-previous-link-mismatch-rebuild-evidence-not-semantics-relaxation`

#### Evidence

- Current run had `runtime.local_l2_snapshot_error=2`, both Binance `buffered_replay_previous_link_mismatch` for DEXEUSDT and EDENUSDT.
- Current run had `runtime.local_l2_sequence_gap_rebuild=238`.
- Current run had `runtime.local_l2_hot_stale_rebuild=35`.

#### V1 / Exchange Comparison

This should not be fixed by relaxing sequence continuity. Binance official local order book rules require the first processed event to bridge the REST snapshot and require each later event's `pu` to equal the previous event's `u`; otherwise the local book must be reinitialized from a fresh snapshot. Source: https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly

#### Root Fix Required

- Keep the strict continuity rule.
- Improve evidence by logging raw `U`, `u`, `pu`, snapshot `lastUpdateId`, buffered count, buffer age, and rebuild attempt id for snapshot replay failures.
- Add per-symbol aggregation thresholds so occasional exchange-valid rebuilds do not page as root bugs.
- If the same symbol repeatedly fails replay, inspect buffer window size, stream latency, and snapshot fetch latency before changing state-machine semantics.
- Add tests for valid bridge, invalid bridge, `pu` mismatch after hot, and stale hot rebuild evidence payloads.

#### Fix Status

Fixed in this session as observability hardening, not as a semantic relaxation.

Implemented:

- Preserved strict Binance buffered replay continuity: `pu` must equal the previous accepted `u`; range overlap no longer excuses a broken previous-link chain.
- Preserved HOT promotion correctness: books are promoted only after a valid snapshot bridge and strict buffered replay.
- Snapshot replay failures now emit raw `U`/`u`/`pu`, snapshot `lastUpdateId`, expected previous sequence, buffered count, buffer age, rebuild attempt id, venue/symbol, and status transition evidence.
- HOT stream-gap rebuild evidence now includes raw `U`/`u`/`pu`, expected previous sequence, previous-link presence, snapshot/book sequence evidence, and rebuild attempt id.
- Added per-symbol buffered replay failure aggregation; ordinary exchange-valid rebuilds stay info-level evidence with `root_bug_suspected=false`, and only repeated failures for the same symbol cross the alert threshold.

Verification:

- Split "last_good may be used for diagnostics" from "fresh enough to price maker/taker decisions".

- Close/risk paths may use last-good only as auxiliary evidence; live position and current venue order book must drive actual close decisions.

- Close price hints now reject stale HOT local-L2 books by `max_liquidity_snapshot_age_ms`; close/risk paths can retain last-good diagnostics, but order prices must come from fresh local book evidence or remain unavailable.

### Issue CL-001-F: Binance post-only would-take rejects are expected but need bounded cooldown evidence

#### Fingerprint

`v2.entry.binance-post-only-5022-would-take-cooldown-evidence`

#### Evidence

Current run had Binance post-only would-take rejects. The official Binance error `-5022 GTX_ORDER_REJECT` means the Post Only order could not execute as maker and is rejected. Source: https://developers.binance.com/docs/derivatives/usds-margined-futures/error-code

#### Root Fix Required

- Do not treat `-5022` as an exchange outage.
- Ensure each post-only reject creates a bounded symbol/venue cooldown.
- Before maker submit, verify local BBO freshness and price would not cross under the latest quote.
- Ensure rejected post-only orders do not leave pending local order state.
- Add tests for `-5022` classification, cooldown, and no pending-state leak.

#### Fix Status

Fixed in this session.

- `-5022` / `GTX_ORDER_REJECT` is classified as post-only would-take, not outage.
- Post-only would-take rejects create bounded symbol+venue cooldown evidence with maker price, BBO, freshness, and `cooldown_until`.
- Passive maker submit now requires fresh local BBO and a non-crossing maker price before submit.
- Deterministic post-only rejects do not register local pending entry state.
- Regression tests added in `tests/test_runtime_entry_flow.py`.

#### Regression Watch

### Issue CL-001-G: order reconciliation uncertain remains too broad

#### Fingerprint

`v2.order-reconcile.uncertain-too-broad-without-venue-specific-resolution-evidence`

#### Evidence

Current run had about `191` `order.reconcile_result:uncertain` events, concentrated in symbols including DEXEUSDT, HUSDT, HOME, XAN, XCN, FIDA, and BEAT.

#### Root Fix Required

- Add venue-specific uncertain subtypes: submit timeout, open-order not found, closed-order not found, execution not found, duplicate client id, stale accepted order, and live-position-confirmed.
- Include `venue`, `symbol`, `client_order_id`, `exchange_order_id`, queried endpoints, endpoint responses, and live-position delta in each uncertain diagnostic.
- If later live truth proves the order filled or had no effect, emit a follow-up reconciliation event and clear the uncertain state.
- Do not let a generic uncertain result drive fail-closed without exposing which exchange query failed.
- Add tests for Bybit duplicate, Binance timeout/accepted-later, OKX order-not-found, and live-position-confirmed resolution.

#### Fix Status

Fixed in this session.

Implemented:

- `order.reconcile_result` now carries venue-specific uncertainty subtype/evidence instead of generic `uncertain`.
- Supported subtypes: `submit_timeout`, `open_order_not_found`, `closed_order_not_found`, `execution_not_found`, `duplicate_client_id`, `stale_accepted_order`, `live_position_confirmed`, and `live_no_effect_confirmed`.
- Every reconcile diagnostic now includes `venue`, `symbol`, `client_order_id`, `exchange_order_id`, `queried_endpoints`, endpoint response classifications, live position delta, and `next_action`.
- Follow-up `order.reconcile_resolution` is emitted when later exchange/live truth proves an uncertain order filled or had no live effect; those resolutions set `clears_uncertain_state=true`.
- Live-position proof is terminal evidence only when adapter/venue evidence explicitly classifies the live truth as matching that uncertain order; a generic nonzero live position no longer resolves as filled.
- Flat live position after endpoint not-found/no-execution evidence resolves as `live_no_effect_confirmed`.
- Binance and OKX adapters now implement `fetch_order_fill_reconciliation()` through venue-specific REST query paths instead of inheriting the default `None`.
- Binance order reconciliation queries `/fapi/v1/order` by `orderId` or `origClientOrderId` and classifies filled, stale accepted, missing, and transport-timeout outcomes.
- OKX order reconciliation queries `/api/v5/trade/order` then `/api/v5/trade/orders-history` by `ordId` or `clOrdId`, preserving open/closed not-found evidence.
- Bybit reconciliation now records `/v5/order/realtime`, `/v5/order/history`, and `/v5/execution/list` query evidence for filled and no-execution/not-found branches.
- Generic `uncertain` diagnostics preserve the legacy `endpoint=fetch_order_status` field, but no longer invent abstract adapter endpoints in `queried_endpoints`; venue-specific endpoint evidence is used only when an exchange query actually ran.
- Generic `uncertain` no longer clears state without subtype and endpoint/live-truth evidence, and terminality evidence is available before any fail-closed decision path consumes the result.
