# Bug Ledger Daily - 2026-09-02

## CL-140 — Automatic hedge-deadline stop was persisted as an operator stop

Status: **deployed-awaiting-verification**. This repair changes no order or
cancel path. It corrects the persisted control-state meaning used after an
existing hedge-deadline safety abort.

### Contract and evidence

The production snapshot at `49de86a` had no positions, no open orders, no
pending/recovery work, and complete high-confidence account truth. Its
recovery decision was nevertheless `RUNNING_CLEAN`/`entry_allowed=true` while
the exported state stayed `risk_only`/`fail_closed`. The persisted operator
field was `requested_mode=fail_closed`; the corresponding journal decision was
`OPERATOR_FAIL_CLOSED_PRESERVED`.

`operator.requested_mode` is the durable result of an explicit operator
`fail_closed` command and is intentionally preserved by the recovery core. In
contrast, V1's `abort_pending_entry_fail_closed` enters automatic fail-closed
before cleanup but does not write an operator override. The authoritative
contract is therefore:

- A hedge-deadline abort must immediately become fail-closed and retain all
  existing cleanup behavior.
- Only a deliberate operator command may set the durable operator latch.
- An automatic stop may resume only through the existing recovery core after
  supported, complete, account-wide flat position and order truth. Any
  non-flat, partial, missing, or timed-out truth remains fail-closed.

### Root cause and minimal repair

V2's `_abort_pending_entry_fail_closed` set both automatic `risk_mode` and
`operator.requested_mode`. Its only production caller is the hard hedge
deadline branch in pending-entry reconciliation. That rewrote an automatic
safety event as an operator decision; every later clean recovery correctly
preserved the wrongly typed latch. This is V1 semantic drift introduced by the
V2 extra assignment, not a recovery-core defect.

### Why it first became visible now

This was not introduced by deployment `49de86a`. Source history shows the
incorrect write was first added on `main` by `e6c52598` (2026-06-10), and was
still present when `404d126c` moved the pending-entry runtime delegation on
2026-06-13. A correct removal exists in `79f35e93` (2026-06-18), but that
commit is contained by the historical `v3`/`codex/recovery-v1-baseline` lines,
not `main`; it therefore never repaired the deployed mainline. Treat a fix on
another branch as non-existent until its commit is an ancestor of the release
SHA.

The bad write was dormant because only the hard hedge-deadline production path
calls it. Retained production events show `entry-1788205927138-ZORAUSDT`
entered `pending_entry.hedge_deadline_breached` at
2026-09-01 03:52:35.820 +08:00: the recorded hedge elapsed time was 31,792 ms
against the 1,200 ms deadline. That automatic safety path set the durable
operator field. Later ZORA cleanup made exchange truth fully flat, so recovery
correctly reached `RUNNING_CLEAN`; the wrongly typed historical latch then
became the only remaining reason that lifecycle stayed `risk_only`.

There is no retained `ops.command_applied` event for this latch. Rotation means
that absence alone is not proof that no human command ever occurred, which is
why the already-persisted production latch must not be cleared automatically.
The code path plus the timestamped automatic event are sufficient to repair
future occurrences, but provenance loss keeps the old state an audited
operator-recovery decision.

The repair removes only that assignment. It retains `enter_fail_closed`, the
existing abort/cleanup owner, the operator command path, and the recovery
core. Do not add a second reset mechanism, clear all old latches at startup,
or weaken the account-truth gate: the current persisted value cannot safely
prove whether it came from a former bug or a genuine human command.

| Explicit operator fail-closed, then complete flat truth | `OPERATOR_FAIL_CLOSED_PRESERVED`; remains locked | `test_operator_fail_closed_is_not_released_by_complete_account_truth` |

The direct runtime-path regression and three complementary lifecycle checks
passed (`4 passed`), as did the adjacent operator-control checks (`4 passed`).

### Historical state and deployment condition

The already persisted production latch is not migrated automatically. It has

After deployment, take fresh full account truth. If it is complete and flat

## CL-142 — Audited `resume-if-safe` could not release a clean risk-only latch

Status: **local-green** in `82e859c`. This is a control-plane repair only:
it changes neither order submission nor cancellation.

### Contract, cause, and boundary

V1's `ResumeIfSafe` clears the deliberate operator control state and enters
`running` whenever its recovery-work snapshot has no resume-blocking work. It
does not require that the lifecycle already be `running`, and a retained
diagnostic string is not itself recovery work.

V2 violated that contract at both parts of its control path. Its operator
transition returned unchanged from `risk_only`, and its offline CLI derived
`has_blocking_recovery` from the historical `recovery_blocked_reason` field.
The deployed CL-140 snapshot has no positions, entries, passive closes, or
residual work, but retains `owned_pending_entry_live_conflict` for diagnostics;
V2 therefore printed `Cannot resume` and persisted the unchanged lock. The
pre-fix production-shaped CLI reproduction confirmed that failure.

The minimal repair changes the existing command boundary only:

- `resume-if-safe` returns `running/running` from any lifecycle when the
  existing V1-aligned lifecycle-work predicate is false;
- the CLI supplies that actual-work predicate instead of interpreting a stale
  diagnostic as an active recovery owner.

It retains blocks for real local positions, pending entries, or pending passive
closes. The CLI remains an offline maintenance operation protected by the
single-writer lease; it does not query exchanges itself. A fresh complete-flat
exchange-truth verification remains required immediately before use.

### Counterexamples and verification

| Case | Required result | Evidence |
|---|---|---|
| `risk_only/fail_closed`, retained old reason, no real work | persist `running/running`, clear request latch, append `ops.command_applied` | new real CLI regression |
| Same command with a persisted live position | preserve `risk_only/fail_closed` and position | new real CLI regression |
| Direct explicit resume transition | clears the operator latch from `risk_only` | updated V1-semantics regression |
| Existing operations, risk, startup recovery and pending-entry branches | retain their established behavior | `222 passed` adjacent; `237 passed` pending-entry/recovery; close profile `481 passed`; full profile `1,604 passed` |

The initial real CLI RED reproduced unchanged `risk_only/fail_closed` and
`requested_mode=fail_closed` despite an exit code of zero. `82e859c` is local
green: the two production-path CLI regressions pass and the complete validation
profile reports `1,604 passed`. Closure still requires deployment, the
user-authorized command's matching journal event, and post-restart account
truth.

The first user-authorized production attempt after `82e859c` exposed the
separate persistence-identity defect tracked by CL-143: the command printed
`Resumed`, but it wrote the generic `runtime/journal.jsonl` /
`runtime/snapshot.json` pair rather than the configured authoritative
`runtime/live-events.jsonl` / `runtime/live-state.json` pair. The real
snapshot therefore remained untouched. That non-authoritative attempt is
preserved as audit evidence, not treated as CL-142 closure.

## CL-143 — State-mutating `lightfee-ops` could target a non-authoritative default pair

Status: **local-green** in `5d64b5a`. This is a control-plane integrity repair
only; it neither submits nor cancels exchange orders.

### Contract, cause, and boundary

Every durable operator action must identify the same configured event-log and
snapshot pair owned by `lightfee-live`. It must reject before acquiring a
writer lease when that identity is absent. A directory environment variable is
not sufficient: it cannot encode a deployment's configured filenames.

V2 violated that contract in the shared `lightfee.apps.ops._resolve_paths`
boundary. If no pair was supplied, it derived `journal.jsonl` and
`snapshot.json` from `LIGHTFEE_DATA_DIR` (or `data`) even though production is
configured for `runtime/live-events.jsonl` and `runtime/live-state.json`.
Five control parsers did not accept a persistence pair at all, and the billing
import parser accepted omission. Thus every state-mutating operation —
`pause-entry`, `reduce-only`, `fail-closed`, `reconcile-now`,
`resume-if-safe`, and `import-billing-evidence` — shared a silent alternate
state path. The first actual `resume-if-safe` showed the result: exit zero and
an audit event in the side pair, with no authoritative state transition.

The earlier CL-142 tests used the same generic filenames, so they proved the
operator transition but not that the CLI selected the deployed persistence
identity. This was a real-path coverage gap, not a V1 lifecycle-semantics
regression. V1's control operation is conceptually bound to the engine's
durable store; it does not define a second generic state store.

The minimal repair removes the default entirely and reuses one parser helper
for all six mutating subcommands. Both `--event-log-path` and
`--snapshot-path` are required. The read-only
`discover-binance-close-evidence` branch remains deliberately separate: it
does not take a writer lease or mutate persistence and still requires only its
snapshot input.

### Counterexamples and verification

| Case | Required result | Evidence |
|---|---|---|
| Any of the five operator controls lacks the pair | parser exits before writer lease; actual live-named snapshot is byte-identical and no generic side files exist | production-shaped six-command CLI matrix (five controls plus billing import) |
| Billing import lacks `--apply` but supplies the pair | reject without mutation | existing real CLI import regression |
| Clean stale `risk_only` resume with the exact live-named pair | append `ops.command_applied`, persist `running/running` | updated real CLI regression |
| Live position resume with the exact pair | retain `risk_only/fail_closed` and position | updated real CLI regression |
| Any mutating command while live owns that exact pair | reject on the existing writer lease | parameterized five-control lease regression |
| Read-only Binance candidate discovery | no lease, journal, or snapshot mutation | existing discovery regression |

The RED matrix on the predecessor showed all five control commands exiting
zero through the generic default path. The GREEN matrix rejects the six
mutating forms before a write; `tests/ops/test_billing_evidence_import.py`
reports `46 passed`. The close validation profile reports `481 passed`; the
pre-amend full release profile reported `1,604 passed` and the final amend
changed only the sixth parser-rejection test. `compileall` and
`git diff --check` passed. GitNexus maps the change to the CLI entry and its
tests only, with low risk and no affected runtime process.

Deployment must preserve the incorrectly targeted pair from the first attempt
as an audit artifact, then take fresh complete-flat exchange truth, stop the
live writer, back up the authoritative live pair, and run exactly one explicit
`resume-if-safe` against `runtime/live-events.jsonl` and
`runtime/live-state.json`. Only that event and its post-start verification may
close CL-142/CL-143.

## CL-141 — Private-WS churn health counted a prior service generation

Status: **closed**. This is diagnostics-only; it neither changes private
WebSocket lifecycle nor exchange connectivity.

### Contract and evidence

One private worker per venue is expected at an intentional live-service start.
The churn metric must count reconnects in the *current service generation*,
not workers from the service that a deliberate deploy replaced. Production
reported 12 starts (two per venue) in the one-hour window after a normal
deployment, despite `NRestarts=0`.

The verifier already intended to use `ActiveEnterTimestampUSec` as the lower
bound. The first local repair added display-string parsing but left the command
asking only for that property. The actual production systemd omits that `*USec`
property entirely and exposes only `ActiveEnterTimestamp` as
`Wed 2026-09-02 01:18:21 CST`; the parser therefore received no value and still
silently fell back to the preceding hour. This production check is the RED
counterexample the first repair missed.

### Root cause and minimal repair

The shared timestamp reader now requests both the numeric `*USec` and matching
display properties in one call, prefers a positive numeric value, then accepts
the host-local display form (with or without fractional seconds). For the
display form it deliberately parses the wall clock in the same host-local
timezone that rendered it; it does not interpret the ambiguous zone abbreviation
as a different region. An absent or malformed value still returns zero,
retaining the existing conservative wide-window behavior rather than hiding
worker churn.

No threshold, worker lifecycle, retry policy, service unit, or exchange client
was changed. In-generation restarts remain visible and continue to trigger the
existing alert.

### Why it first became visible now

`f390fbdf` (2026-08-26) correctly introduced a current-generation lower bound,
but its parser and its test fixture both assumed the command supplied one usable
`*USec` value. The deployed host instead omits that property and exposes only
the display value through a separate property. The first follow-up corrected
the parser but not the property request; it therefore still selected the
ordinary one-hour lookback.

This has a narrow visibility condition: it is wrong only when a health check
runs within one hour of a deliberate service replacement. On 2026-09-01 the
normal deployment starts around 23:24 and 23:53 both fell in that wide window,
so six expected venue workers per generation appeared as 12 starts. The unit's
`NRestarts=0` proved these were not crash/reconnect churn. Once the older
generation aged out, the same old verifier again reported six, which is why the
fault can appear to come and go without any WebSocket behavior changing.

The regression test did not model the host's actual systemd property absence,
so it validated the intended numeric/display parser rather than the production
command contract. The new production-shaped fixture returns an empty result
unless `ActiveEnterTimestamp` is requested beside `*USec`; it closes that exact
gap.
