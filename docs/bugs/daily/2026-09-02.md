# Bug Ledger Daily - 2026-09-02

## CL-140 — Automatic hedge-deadline stop was persisted as an operator stop

Status: **local-green; not deployed**. This repair changes no order or cancel
path. It corrects the persisted control-state meaning used after an existing
hedge-deadline safety abort.

### Contract and evidence

The production snapshot at `49de86a` had no positions, no open orders, no
pending/recovery work, and complete high-confidence account truth. Its
recovery decision was nevertheless `RUNNING_CLEAN`/`entry_allowed=true` while
the exported state stayed `risk_only`/`fail_closed`. The persisted operator
field was `requested_mode=fail_closed`; the corresponding journal decision was
`OPERATOR_FAIL_CLOSED_PRESERVED`.

`operator.requested_mode` is the durable result of an explicit operator
`fail_closed` command and is intentionally preserved by the recovery core. In
contrast, V1's `abort_pending_entry_fail_closed` enters automatic fail-closed
before cleanup but does not write an operator override. The authoritative
contract is therefore:

- A hedge-deadline abort must immediately become fail-closed and retain all
  existing cleanup behavior.
- Only a deliberate operator command may set the durable operator latch.
- An automatic stop may resume only through the existing recovery core after
  supported, complete, account-wide flat position and order truth. Any
  non-flat, partial, missing, or timed-out truth remains fail-closed.

### Root cause and minimal repair

V2's `_abort_pending_entry_fail_closed` set both automatic `risk_mode` and
`operator.requested_mode`. Its only production caller is the hard hedge
deadline branch in pending-entry reconciliation. That rewrote an automatic
safety event as an operator decision; every later clean recovery correctly
preserved the wrongly typed latch. This is V1 semantic drift introduced by the
V2 extra assignment, not a recovery-core defect.

### Why it first became visible now

This was not introduced by deployment `49de86a`. Source history shows the
incorrect write was first added on `main` by `e6c52598` (2026-06-10), and was
still present when `404d126c` moved the pending-entry runtime delegation on
2026-06-13. A correct removal exists in `79f35e93` (2026-06-18), but that
commit is contained by the historical `v3`/`codex/recovery-v1-baseline` lines,
not `main`; it therefore never repaired the deployed mainline. Treat a fix on
another branch as non-existent until its commit is an ancestor of the release
SHA.

The bad write was dormant because only the hard hedge-deadline production path
calls it. Retained production events show `entry-1788205927138-ZORAUSDT`
entered `pending_entry.hedge_deadline_breached` at
2026-09-01 03:52:35.820 +08:00: the recorded hedge elapsed time was 31,792 ms
against the 1,200 ms deadline. That automatic safety path set the durable
operator field. Later ZORA cleanup made exchange truth fully flat, so recovery
correctly reached `RUNNING_CLEAN`; the wrongly typed historical latch then
became the only remaining reason that lifecycle stayed `risk_only`.

There is no retained `ops.command_applied` event for this latch. Rotation means
that absence alone is not proof that no human command ever occurred, which is
why the already-persisted production latch must not be cleared automatically.
The code path plus the timestamped automatic event are sufficient to repair
future occurrences, but provenance loss keeps the old state an audited
operator-recovery decision.

The repair removes only that assignment. It retains `enter_fail_closed`, the
existing abort/cleanup owner, the operator command path, and the recovery
core. Do not add a second reset mechanism, clear all old latches at startup,
or weaken the account-truth gate: the current persisted value cannot safely
prove whether it came from a former bug or a genuine human command.

## CL-141 — Private-WS churn health counted a prior service generation

Status: **first repair deployed but production RED; follow-up local-green**.
This is diagnostics-only; it neither changes private WebSocket lifecycle nor
exchange connectivity.

### Contract and evidence

One private worker per venue is expected at an intentional live-service start.
The churn metric must count reconnects in the *current service generation*,
not workers from the service that a deliberate deploy replaced. Production
reported 12 starts (two per venue) in the one-hour window after a normal
deployment, despite `NRestarts=0`.

The verifier already intended to use `ActiveEnterTimestampUSec` as the lower
bound. The first local repair added display-string parsing but left the command
asking only for that property. The actual production systemd omits that `*USec`
property entirely and exposes only `ActiveEnterTimestamp` as
`Wed 2026-09-02 01:18:21 CST`; the parser therefore received no value and still
silently fell back to the preceding hour. This production check is the RED
counterexample the first repair missed.

### Root cause and minimal repair

The shared timestamp reader now requests both the numeric `*USec` and matching
display properties in one call, prefers a positive numeric value, then accepts
the host-local display form (with or without fractional seconds). For the
display form it deliberately parses the wall clock in the same host-local
timezone that rendered it; it does not interpret the ambiguous zone abbreviation
as a different region. An absent or malformed value still returns zero,
retaining the existing conservative wide-window behavior rather than hiding
worker churn.

No threshold, worker lifecycle, retry policy, service unit, or exchange client
was changed. In-generation restarts remain visible and continue to trigger the
existing alert.

### Why it first became visible now

`f390fbdf` (2026-08-26) correctly introduced a current-generation lower bound,
but its parser and its test fixture both assumed the command supplied one usable
`*USec` value. The deployed host instead omits that property and exposes only
the display value through a separate property. The first follow-up corrected
the parser but not the property request; it therefore still selected the
ordinary one-hour lookback.

This has a narrow visibility condition: it is wrong only when a health check
runs within one hour of a deliberate service replacement. On 2026-09-01 the
normal deployment starts around 23:24 and 23:53 both fell in that wide window,
so six expected venue workers per generation appeared as 12 starts. The unit's
`NRestarts=0` proved these were not crash/reconnect churn. Once the older
generation aged out, the same old verifier again reported six, which is why the
fault can appear to come and go without any WebSocket behavior changing.

The regression test did not model the host's actual systemd property absence,
so it validated the intended numeric/display parser rather than the production
command contract. The new production-shaped fixture returns an empty result
unless `ActiveEnterTimestamp` is requested beside `*USec`; it closes that exact
gap.
