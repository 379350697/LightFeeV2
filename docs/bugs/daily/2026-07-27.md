# Bug Ledger - 2026-07-27

## Cluster CL-161 - Private WebSocket Lifecycle Churn Follows Ephemeral Candidates

Status: locally fixed and regression-tested; not deployed.

### Fingerprint

`runtime.private_ws_started` and `runtime.private_ws_stopped` with
`reason=no tracked symbols` repeatedly alternate for the same credentialed
venue while the live process remains healthy and has no open position, pending
entry, pending passive close, or residual repair.

### Production Evidence

- Cloud audit on deployed `a2c93aa4` found no live position or open order on
  any queried venue and no local pending exposure. It also found no submitted
  trading order in the audit window; this is a lifecycle/observability defect,
  not an observed bad fill or abnormal position.
- In the same active deployment window, journal counts recorded private-worker
  starts of Binance 87, Bitget 55, Bybit 84, and Gate 77; corresponding
  `no tracked symbols` stops were Binance 66, Bitget 41, Bybit 40, and Gate
  53.
- Binance HTTP access logs also show repeated `POST` and `PUT`
  `/fapi/v1/listenKey` calls. Binance documents that a listenKey lasts 60
  minutes and should be kept alive with `PUT`; each request consumes IP weight.
  See the [official Binance USD-M user-data-stream documentation](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/user-data-streams).

### Root Cause

V2 calls `LiveRuntime._ensure_private_ws_started()` after every runtime tick.
It computes a symbol set from transient primary entry pairs plus active
positions and recovery work. An empty set stops the private worker; any set
change replaces it. Candidate discovery naturally alternates that set between
empty and nonempty, so a private account/order stream is repeatedly destroyed
and recreated even though the venue credential and live process have not
changed.

The comment that labels this behavior “V1” is not supported by the V1
implementation. V1 activates a private stream once at live startup when no
worker exists, then the worker owns a reconnect loop and a 30-minute Binance
listenKey keepalive. It does not make the worker lifetime depend on each scan's
candidate set. Relevant sources are V2
`lightfee/engine/runtime.py::_ensure_private_ws_started`, V1
`src/live/binance.rs::live_startup_activate_private_streams`, and V1
`src/live/binance.rs::start_private_ws`.

### V1 / Business Contract

- Preserve all entry admission, order sizing, order submission, passive-close,
  residual-repair, recovery, and exchange-truth rules.
- A venue private account stream is adapter/credential scoped, not a candidate
  scoped trading decision. It may remain connected while no candidate is
  eligible; no order is created merely because the stream is alive.
- A true transport error, explicit service shutdown, credential/configuration
  change, or unsupported private-stream capability may still stop/reconnect
  the worker using the existing bounded backoff.

### Root Fix

1. After a venue has first been activated with a valid tracked symbol, retain
   its worker through no-candidate intervals.  Candidate removal is no longer
   allowed to stop a private worker; explicit runtime shutdown remains the
   normal stop owner.
2. Maintain a transport-owned, monotonic vendor-symbol map.  Binance, Bybit,
   Bitget, and Hyperliquid use their account-wide private topics with that map
   updated in place.  Gate and OKX consume new vendor symbols as signed/in-band
   subscription additions, so a change in candidates does not replace the
   worker.
3. Keep Binance's listenKey with the existing bounded periodic keepalive; only
   request a new listenKey after explicit shutdown or a real worker reconnect.
4. Add per-venue singleflight ownership and telemetry for starts, stops,
   reconnect reason, listenKey create/keepalive, and worker age. Alert on a
   non-shutdown start/stop rate above a small configured budget.

### Required Regression Proof

- Repeated empty/nonempty primary-pair cycles start an eligible venue worker at
  most once and never stop it merely because the current candidate set is
  empty.
- An open position, pending entry, passive close, or residual repair continues
  to receive private truth across candidate-set changes.
- Account-wide venues apply a newly tracked symbol to the running parser;
  Gate/OKX emit only an in-band symbol subscription update.  Neither operation
  stops/restarts the worker.
- A real private transport failure performs the existing bounded reconnect;
  shutdown still terminates the worker.
- Entry gates, submitted-order payloads, close/recovery decisions, and
  exchange-truth results remain byte-for-byte unchanged for an identical test
  fixture.

### Local Verification

- `tests/test_v1_private_ws_parity.py`: 84 passed.  New regression coverage
  proves that an empty candidate interval produces no private-worker stop, a
  new symbol is updated in place rather than restarting the worker, and the
  Gate/OKX subscription-update queue is limited to symbol-scoped venues.
- `git diff --check`: passed.

### Acceptance

After deployment, observe a continuous live window with stable private-worker
counts, no `no tracked symbols` stop after startup settle, and Binance
listenKey creation only at startup/reconnect. Confirm exchange truth remains
high-confidence and that the normal no-candidate state still submits no order.

## Cluster CL-162 - Production HTTP Access Logs Expose Private Query Material

Status: root cause confirmed; safe to fix in code; credential rotation requires
separate operator authorization.

### Fingerprint

Production `httpx` INFO access logs include complete private request URLs whose
query strings contain authentication signatures, timestamps, and other
credential-adjacent material.

### Root Cause

The live entrypoint configures the root logger at INFO. HTTPX therefore emits
access logs with the complete request URL. Several exchange private REST
contracts put HMAC authentication fields in their query string.

### Root Fix

Set the `httpx` logger to WARNING in production or install a mandatory URL
redaction formatter that removes signature, listenKey, timestamp, API-key, and
other authentication fields before a record reaches stderr/journal. Add a
regression test using a signed URL and assert that no secret-bearing query
field appears in the emitted log.

### Business Contract

This is logging-only hardening: it must not change request method, endpoint,
signature generation, retry, order, cancel, close, recovery, or admission
behavior. Review and rotate potentially exposed exchange credentials through
the normal security process; do not delete logs solely to hide the evidence.

## Current Triage Decision

CL-161 is the primary trading-runtime root-fix candidate: its production
fingerprint, V2 control flow, V1 contrast, exchange lifecycle rules, and safe
non-business-flow-changing design are all established. CL-162 is independently
ready as a security hardening change. The remaining OI/quote candidate
starvation has strong symptoms but still requires latency attribution by
venue/request phase before selecting a root fix; thresholds and trading flow
must not be relaxed on the present evidence.
