## Cluster CL-023-production-observability-log-volume

### GitNexus Keys

- Fingerprint: `post-90fa2bc.production-observability.event-log-unbounded + no-entry-large-payload + snapshot-freshness-invalid-quote-repeat`
- Components: `journal`, `live-runtime`, `production-observability`

- Watch: `runtime/live-events.jsonl` size, `scan.no_entry_diagnostics.compact`,
  `runtime.snapshot_freshness_decision.compact`, `suppressed_count`,
  `suppressed_full_payload_count`

### Production Split

The production watch after CL-022 found no service warnings and no local
open/pending/residual work, but the active JSONL event log had grown to about
577 MiB. The last 3 days had roughly 686k JSONL records with no parse errors.
The largest byte contributors were:

- `scan.no_entry_diagnostics`: about 158 MiB, mostly repeated
  `tradeable_candidates_waiting_for_entry_finalization_window_too_early` full
  candidate payloads.
- `runtime.snapshot_freshness_decision`: about 117 MiB, mostly repeated
  `invalid_quote` decisions for the same venue/symbol/domain source.
- Other high-frequency runtime evidence events such as Local-L2 freshness and
  private-WS lifecycle records remain useful follow-up optimization candidates,
  but were not changed in this closure.

This is an observability/ops issue, not a V1 trading semantic drift. No
strategy thresholds, admission rules, order submission behavior, close timing,
or recovery state transitions were changed.

### Fix

- `LiveRuntime.__init__` now passes the existing persistence config fields
  `event_log_compaction_max_bytes`, `event_log_archive_count`, and
  `event_log_retention_hours` into `Journal`.
- `Journal` now rotates active JSONL files before an append would exceed the
  configured byte limit, keeps count-based archives like
  `live-events.jsonl.1`, and prunes expired archives by retention age.
- `runtime.snapshot_freshness_decision` still records the first event for a
  venue/symbol/domain/reason. Repeated events within 60 seconds are suppressed
  and the next emitted event carries `compact=true` plus `suppressed_count`.
  Filtering metrics, blocker samples, and candidate decisions still run for
  every candidate.
- `scan.no_entry_diagnostics` still writes a full first payload and a full
  payload when the high-level blocker family changes or every 5 minutes.
  Repeated blocker-family records emit compact payloads at most once per minute
  with current counts and `suppressed_full_payload_count`, omitting the large
  per-candidate sample array.

## Cluster CL-021-staggered-first-stage-capture-runtime-drift

### GitNexus Keys

- Fingerprint: `v2.staggered-first-stage-funding-captured-not-advanced + exit-after-first-stage-config-not-persisted + recovered-prl-open-held-past-first-funding`
- Components: `live-runtime`, `entry-dispatch`, `normal-exit`, `funding-capture-state`, `v1-parity`
- Symbols: `LiveRuntime._dispatch_entry`, `LiveRuntime._maybe_process_normal_exits`, `standard_close_reason`, `update_position_funding_capture_state`
- Files: `lightfee/engine/runtime.py`, `tests/test_runtime_entry_flow.py`
- Watch: `runtime.funding_capture_state_updated`, `runtime.staggered_exit_mode_backfilled`, `runtime.normal_close_routing_passive reason=first_stage_capture`, `entry.opened.exit_after_first_stage=true`

### Summary

After CL-020, production correctly stopped closing before settlement, but the
post-deploy `PRLUSDT` position remained open after first funding settlement:

- It opened at `2026-05-31 02:56:25.971 CST`.
- First funding timestamp was `2026-05-31 03:00:00 CST`.
- Second funding timestamp was `2026-05-31 04:00:00 CST`.
- Production config had `staggered_exit_mode=after_first_stage`.
- The persisted position had `exit_after_first_stage=false` and
  `funding_captured=false`, so `standard_close_reason()` returned `None`.

Root cause:

- V2 had the V1 pure helper `update_position_funding_capture_state()`, but
  runtime normal-exit ticks never called it before `standard_close_reason()`.
- `LiveRuntime._dispatch_entry` copied candidate funding timestamps into
  `EntryContext`, but did not copy the V1 config-derived
  `staggered_exit_mode=after_first_stage` decision into
  `EntryContext.exit_after_first_stage`.
- Existing recovered positions opened before the fix could keep the stale
  `exit_after_first_stage=false` latch even though the current V1 config says
  to exit after first stage.

### V1 Decision

This is another V2/V1 semantic drift. V1 updates funding-capture state during
normal runtime housekeeping before evaluating close reasons, and staggered
first-stage exit is a strategy-config decision that must be present on the open
position used by close decision logic.

### Fix

- `LiveRuntime._dispatch_entry` now sets `EntryContext.exit_after_first_stage`
  from `strategy.staggered_exit_mode == "after_first_stage"` for staggered
  candidates and includes the value in entry-selection evidence.
- `LiveRuntime._maybe_process_normal_exits` now backfills recovered staggered
  positions from the same config when the persisted latch is missing, with
  `runtime.staggered_exit_mode_backfilled` evidence.
- The same normal-exit path now calls V1 `update_position_funding_capture_state()`
  before `standard_close_reason()`, and emits
  `runtime.funding_capture_state_updated` whenever stage state changes.
- No close reason ordering changed: `standard_close_reason()` remains the V1
  authority for first-stage and second-stage close decisions.

## Cluster CL-020-funding-capture-before-settlement-timestamp-drift

### GitNexus Keys

- Fingerprint: `v2.entry-open-position.funding-timestamp-zero + funding-capture-before-settlement + candidate-opportunity-type-dropped`
- Components: `live-runtime`, `entry-sync`, `exit-decision`, `state-persistence`, `v1-parity`
- Symbols: `LiveRuntime._dispatch_entry`, `LiveRuntime._finalize_pending_entry`, `EntryContext`, `build_open_position`, `PendingEntry`, `standard_close_reason`, `aligned_settlement_delay_elapsed`, `force_close_due`, `update_position_funding_capture_state`
- Files: `lightfee/engine/runtime.py`, `lightfee/engine/entry.py`, `lightfee/engine/entry_sync.py`, `lightfee/engine/exit_decision.py`, `lightfee/engine/state.py`, `lightfee/engine/recovery.py`
- Watch: `entry.opened`, `entry.opened.funding_timestamp_ms=0`, `exit.close_submitted reason=funding_capture`, `funding_capture` before candidate first funding timestamp, `runtime.pending_entry_registered.funding_timestamp_ms=0`

### Summary

Production did open and close real positions after deployment. The key counterexample was `MAGMAUSDT`:

- Entry opened at `2026-05-31 01:58:28 CST`.
- It closed at `2026-05-31 01:58:40 CST` with reason `funding_capture`.
- That was before the funding settlement time visible in the candidate lifecycle evidence, so the close reason was not V1-compatible.

Root cause:

- `CandidateInput` already had funding lifecycle fields: `opportunity_type`, `funding_timestamp_ms`, `first_funding_timestamp_ms`, per-leg funding timestamps, and `second_funding_timestamp_ms`.
- `LiveRuntime._dispatch_entry` did not carry those fields into `EntryContext`.
- `EntrySyncExecutor._make_pending_entry` and `LiveRuntime._finalize_pending_entry` could not preserve those fields through the pending entry path.
- `build_open_position` therefore created `OpenPosition` with default `funding_timestamp_ms=0` and default `opportunity_type="aligned"`.
- `aligned_settlement_delay_elapsed()` treated `now_ms >= 0 + settlement_delay_ms` as true, so a newly opened position could close immediately as `funding_capture`.

### V1 Decision

This is a V2/V1 semantic drift, not an exchange-rule or market-data threshold issue.

V1 close semantics require a real funding timestamp before aligned settlement delay or force-close timing can be considered elapsed. Missing funding time is missing evidence, not proof that settlement happened.

### Fix

- Added funding lifecycle fields to `EntryContext` and `PendingEntry`.
- `LiveRuntime._dispatch_entry` now copies funding lifecycle fields from the selected `CandidateInput` into `EntryContext` and entry-selection journal evidence.
- `EntrySyncExecutor._make_pending_entry` persists those fields for passive/pending entry flows.
- `LiveRuntime._finalize_pending_entry` restores those fields when building `OpenPosition` from a completed pending entry.
- `build_open_position` now writes `funding_timestamp_ms`, `second_funding_timestamp_ms`, `opportunity_type`, `second_stage_enabled_at_entry`, and entry edge fields onto `OpenPosition`.
- `EngineState.to_dict()`, `build_persistent_state_view()`, and `_restore_state_from_snapshot_dict()` now preserve the pending/open funding semantics.
- `remaining_close_delay_active()`, `aligned_settlement_delay_elapsed()`, `force_close_due()`, and `update_position_funding_capture_state()` now return fail-closed when `funding_timestamp_ms <= 0`.
