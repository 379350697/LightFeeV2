## Cluster CL-020-funding-capture-before-settlement-timestamp-drift

### GitNexus Keys

- Fingerprint: `v2.entry-open-position.funding-timestamp-zero + funding-capture-before-settlement + candidate-opportunity-type-dropped`
- Components: `live-runtime`, `entry-sync`, `exit-decision`, `state-persistence`, `v1-parity`
- Symbols: `LiveRuntime._dispatch_entry`, `LiveRuntime._finalize_pending_entry`, `EntryContext`, `build_open_position`, `PendingEntry`, `standard_close_reason`, `aligned_settlement_delay_elapsed`, `force_close_due`, `update_position_funding_capture_state`
- Files: `lightfee/engine/runtime.py`, `lightfee/engine/entry.py`, `lightfee/engine/entry_sync.py`, `lightfee/engine/exit_decision.py`, `lightfee/engine/state.py`, `lightfee/engine/recovery.py`
- Watch: `entry.opened`, `entry.opened.funding_timestamp_ms=0`, `exit.close_submitted reason=funding_capture`, `funding_capture` before candidate first funding timestamp, `runtime.pending_entry_registered.funding_timestamp_ms=0`

### Summary

Production did open and close real positions after deployment. The key counterexample was `MAGMAUSDT`:

- Entry opened at `2026-05-31 01:58:28 CST`.
- It closed at `2026-05-31 01:58:40 CST` with reason `funding_capture`.
- That was before the funding settlement time visible in the candidate lifecycle evidence, so the close reason was not V1-compatible.

Root cause:

- `CandidateInput` already had funding lifecycle fields: `opportunity_type`, `funding_timestamp_ms`, `first_funding_timestamp_ms`, per-leg funding timestamps, and `second_funding_timestamp_ms`.
- `LiveRuntime._dispatch_entry` did not carry those fields into `EntryContext`.
- `EntrySyncExecutor._make_pending_entry` and `LiveRuntime._finalize_pending_entry` could not preserve those fields through the pending entry path.
- `build_open_position` therefore created `OpenPosition` with default `funding_timestamp_ms=0` and default `opportunity_type="aligned"`.
- `aligned_settlement_delay_elapsed()` treated `now_ms >= 0 + settlement_delay_ms` as true, so a newly opened position could close immediately as `funding_capture`.

### V1 Decision

This is a V2/V1 semantic drift, not an exchange-rule or market-data threshold issue.

V1 close semantics require a real funding timestamp before aligned settlement delay or force-close timing can be considered elapsed. Missing funding time is missing evidence, not proof that settlement happened.

### Fix

- Added funding lifecycle fields to `EntryContext` and `PendingEntry`.
- `LiveRuntime._dispatch_entry` now copies funding lifecycle fields from the selected `CandidateInput` into `EntryContext` and entry-selection journal evidence.
- `EntrySyncExecutor._make_pending_entry` persists those fields for passive/pending entry flows.
- `LiveRuntime._finalize_pending_entry` restores those fields when building `OpenPosition` from a completed pending entry.
- `build_open_position` now writes `funding_timestamp_ms`, `second_funding_timestamp_ms`, `opportunity_type`, `second_stage_enabled_at_entry`, and entry edge fields onto `OpenPosition`.
- `EngineState.to_dict()`, `build_persistent_state_view()`, and `_restore_state_from_snapshot_dict()` now preserve the pending/open funding semantics.
- `remaining_close_delay_active()`, `aligned_settlement_delay_elapsed()`, `force_close_due()`, and `update_position_funding_capture_state()` now return fail-closed when `funding_timestamp_ms <= 0`.
