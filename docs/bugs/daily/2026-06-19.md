# 2026-06-19

## Cluster CL-098 - Venue private auth admission and single-leg recovery closure

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed locally; cloud deploy pending | critical | venue private health + paired-entry admission + single-leg exposure recovery | entry-admission, pending-entry, recovery-executor, diagnose-live | `lightfee/engine/venue_private_health.py`, `lightfee/engine/entry_dispatch_runtime.py`, `lightfee/engine/runtime.py`, `lightfee/engine/pending_entry_runtime.py`, `lightfee/engine/entry_gate_runtime.py`, `scripts/diagnose_live.py` |

### Fingerprint

`venue private auth failure bypassed paired-entry admission; single-leg exposure recovery action not fully executed`

### Evidence

- Bybit private order precheck could return `33004` for an expired API key, but
  V2 did not classify this as a venue private capability state before paired
  entry selection. The failure could remain a symbol-level order rejection
  instead of isolating the whole Bybit venue for new-risk candidates.
- A paired entry whose maker leg had already filled and whose hedge venue then
  failed private auth could lose the owner-specific pending-entry recovery path
  and degrade toward generic unpaired live-position handling.
- Existing reduce-only cleanup semantics were available, but runtime did not
  emit single-leg recovery evidence (`submitted`, `succeeded`, `failed`,
  `terminalized`) as the source of truth for diagnostics.
- If a venue credential failure also blocked reduce-only cleanup, the correct
  state is a critical cleanup blocker, not a contained admission warning and
  not a silent terminalization.

### Fix

- Added a shared venue private health classifier with stable statuses:
  `auth_invalid`, `permission_denied`, `truth_unavailable`,
  `order_permission_unavailable`, and `healthy`.
- Bybit `33004 api key expired` and similar private auth/permission errors now
  become `runtime.entry_admission_blocked` with
  `reason=venue_auth_invalid`, `source=venue_private_health_precheck`,
  `cooldown_scope=venue`, `block_scope=venue`, and
  `venue_private_health_status=auth_invalid`. The candidate gate now prefers
  venue-scope cooldown evidence over same-TTL symbol evidence, so all Bybit
  new-risk candidates are evicted during the TTL while other venues remain
  selectable.
- Pending hedge admission rejects caused by venue private health now keep the
  original pending entry owner and enter
  `single_leg_exposure_recovery:<reason>`. When live truth is high-confidence,
  no-open-orders, and shows a single maker-side exposure, runtime uses the
  maker venue reduce-only cleanup path and emits
  `pending_entry.single_leg_exposure_recovery_started`,
  `pending_entry.single_leg_flatten_submitted`,
  `pending_entry.single_leg_flatten_succeeded|failed`, and
  `pending_entry.terminalized_after_single_leg_recovery`.
- Reduce-only cleanup failures caused by the same private auth family now emit
  `cleanup_blocked_by_venue_auth_invalid` with `severity=critical`, the failed
  action, venue, symbol, entry id, and raw error evidence.
- Diagnose now exposes `venue_private_health_summary`,
  `single_leg_exposure_recovery_summary`, and `cleanup_blocker_summary`.
  Clean exchange truth can resolve contained Bybit auth-invalid opening rejects
  out of `order_error_evidence`, but cleanup blockers remain explicit.
- Review hardening closed two diagnostic drift gaps: unfinished single-leg
  recovery now remains visible through
  `single_leg_exposure_recovery_summary.unresolved_count` until
  `pending_entry.terminalized_after_single_leg_recovery` exists, and
  `venue_private_health_summary` separates raw `event_count` from de-duplicated
  incident `count` so the paired `runtime.entry_admission_blocked` plus
  `runtime.venue_cooldown_started` events do not inflate incident totals.
- Runtime regression coverage now locks the three negative single-leg recovery
  branches: live truth unavailable, maker open order still present, and
  reduce-only cleanup failure. All three must retain the pending owner, keep
  `risk_only`, emit explicit failure evidence, and avoid terminalizing as clean.

### Non-goals

- No strategy thresholds, quote TTLs, funding logic, sizing, or unrelated venue
  behavior changed.
- Venue private auth failure remains venue-scoped for new risk. It is not a
  global operator fail-closed and does not block reduce-only cleanup unless the
  venue itself rejects or prevents that cleanup action.

## Cluster CL-099 - Aster headroom pre-submit, single-leg fee-drag guard, and active handoff quality

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed locally; main deploy pending | critical | paired-entry admission + single-leg fee drag + business phase handoff | entry-admission, runtime-candidate, pending-entry, diagnose-live, venue-transport | `lightfee/engine/entry_dispatch_runtime.py`, `lightfee/engine/runtime.py`, `lightfee/engine/v1_lifecycle_closure.py`, `lightfee/venues/aster.py`, `lightfee/venues/transport.py`, `scripts/diagnose_live.py` |

### Fingerprint

`Aster remaining_openable_notional=0 discovered too late; maker leg can fill before deterministic hedge admission block; candidate or quote-rewarm phase lacks active takeover evidence`

### Evidence

- The production sample showed that the risk was not only visible
  `order.submit_result` errors. A real online-ready review also had to prove
  whether each business phase actively handed work to the next phase or stayed
  idle until a later hard ceiling or cleanup path intervened.
- Aster max-notional / remaining-openable-notional evidence can be deterministic
  before order submission. If the hedge leg has no headroom, submitting the
  maker first creates avoidable single-leg exposure and can repeat into
  fee-drag if cleanup immediately flattens and the same route is selected
  again.
- Existing pending-hedge admission handling was still necessary as a fallback,
  but deterministic admission blocks were being treated too much like ordinary
  retryable hedge failures. That inflated useless retries and made cleanup look
  like the normal path instead of the last defense.
- Diagnostics had phase duration evidence, but did not yet expose a
  production-grade business quality view for: pre-submit admission blocks,
  single-leg creation, cleanup after deterministic admission block, and whether
  a route violated cooldown by submitting a maker again while the hedge leg was
  still guarded.
- Candidate and quote-rewarm phases needed explicit active takeover evidence.
  A candidate that stays in lease past the hard budget must be expired and
  rescanned; quote rewarm that stays stale past its budget must terminalize into
  cooldown/stale evidence. Diagnose must distinguish these from passive
  over-budget drift.

### Root Cause

- The V2 entry path could verify maker-side submit readiness and still miss the
  hedge venue/symbol headroom contract immediately before maker submission.
  That is a semantic gap for paired entry: both legs must be admissible before
  the first non-reduce-only leg is allowed to create new exposure.
- Aster V3 headroom truth lives behind the dedicated V3 signer client. Generic
  Binance-compatible transport classification is not enough for the current V3
  private account-risk contract.
- The runtime had fallback cleanup for single-leg exposure, but no hard
  fee-drag invariant tying cleanup-after-admission-block to a route cooldown
  that prevents the same maker/hedge path from immediately reopening.
- `diagnose_live.py` could report errors and durations, but not the business
  progression quality questions operators actually need after a 10-hour
  production sample: was the phase actively advanced, was it abandoned until a
  hard ceiling, and did a cleanup path turn into repeated fee churn?

### Fix

- Added a two-leg admission precheck in entry dispatch after entry selection and
  before maker submit. A deterministic hedge-side block now emits
  `runtime.entry_blocked_admission_selection` /
  `runtime.entry_admission_blocked` and no `order.passive_submitted` maker leg
  is sent.
- Added Aster headroom admission support through the dedicated V3 signer path
  and the direct transport fallback. `remaining_openable_notional=0`,
  max-notional, and error-only `max_notional_admission_blocked` shapes are
  classified before order submit where truth is available; reduce-only cleanup
  remains allowed.
- Preserved V1 safety semantics: uncertain exchange truth still fails closed,
  deterministic admission blocks do not masquerade as success, and cleanup is a
  last-resort loss-control path rather than a routine retry strategy.
- Added single-leg fee-drag diagnostics with
  `business_progression_quality_summary`: `pre_submit_blocked`,
  `single_leg_created`, `single_leg_cleanup`,
  `cleanup_after_admission_block`, and `repeated_single_leg_guarded`.
  A maker submit on the same route while the hedge venue/symbol is still under
  cooldown is reported as production issue
  `repeated_single_leg_fee_drag_after_cooldown`.
- Added candidate lease active takeover. A tradeable candidate older than the
  configured `candidate_lease` budget emits
  `runtime.candidate_lease_expired`, records
  `review.candidate_rejected rejected_stage=candidate_lease`, drops out of the
  current tick, and forces rescan instead of lingering passively.
- Extended phase diagnostics with `phase_handoff_quality` for candidate lease
  and quote rewarm. Over-budget phases without terminal/takeover evidence are
  marked as production issues; terminal stale/expired evidence is counted as
  active takeover instead of passive drift.
- Post-deploy review caught one diagnostic false positive: catalog-level
  `runtime.candidate_symbol_skipped reason=unsupported_symbol` is already a
  pre-candidate rejection, not a candidate lease start. Diagnose now treats it
  as terminal/takeover evidence only when a candidate lease already exists, and
  does not manufacture a missing-takeover issue from a catalog skip alone.
- Follow-up production-readiness review closed the "recovered but still
  operationally bad" gap. Symbol-scope deterministic admission blocks such as
  `insufficient_balance_admission_blocked` are now filtered in
  `_filter_candidates_by_entry_admission()` before selection, not left to
  repeat through dispatch. Venue-scope Aster `aster:*` cooldown remains a
  route-level no-new-risk signal for any opening route whose hedge venue is
  Aster.
- `runtime.entry_blocked_admission_selection` evidence now keeps the actual
  `block_scope` (`venue`, `symbol`, or `mixed`) and samples preserve the
  source cooldown scope. This keeps operator evidence without flooding the
  ledger with dozens of identical HUSDT/Bybit-style candidate attempts.
- Quote rewarm hard-expiry and active-position normal-exit scheduling were
  locked with regression tests. Existing runtime behavior already suppresses
  same venue/symbol rewarm scheduling while terminal stale cooldown is active,
  and active-position ticks already enter the normal-exit lane before the next
  full periodic tick. No strategy permission, quote freshness, or V1
  `standard_close_reason` semantics changed.
- Passive close terminal/no-fill evidence now includes compatible
  `exchange_code`, `exchange_msg`, and `raw_error` fields on
  `exit.passive_close_maker_terminal_no_fill`, so future reviews can separate
  reduce-only terminal zero quantity, post-only reject, and ordinary no-fill
  evidence while keeping final flatness exchange-truth gated.
- Diagnose now separates current active stuck work from recovered process
  issues. `business_progression_quality_summary` includes
  `candidate_takeover_count`, `quote_rewarm_terminalized_count`,
  `recovered_but_counted_issue_count`, and `active_stuck_count`. A zero-fill
  maker attempt followed within seconds by cancel plus `entry.aborted` remains
  counted as a fee/quality incident, but no longer becomes a false current
  hard-over-budget stuck issue.
- Review follow-up closed one diagnostic false-negative edge case:
  soft-over-budget quote/candidate terminalization no longer subtracts from
  `active_stuck_count`. Only hard-over-budget terminalized candidate/quote
  records can offset hard-over-budget work, so a separate pending close or
  recovery artifact that is still hard-stuck remains visible.
