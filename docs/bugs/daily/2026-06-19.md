## Cluster CL-098 - Venue private auth admission and single-leg recovery closure

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed and deployed in `c35dd35`; current cloud recovered | critical | venue private health + paired-entry admission + single-leg exposure recovery | entry-admission, pending-entry, recovery-executor, diagnose-live | `lightfee/engine/venue_private_health.py`, `lightfee/engine/entry_dispatch_runtime.py`, `lightfee/engine/runtime.py`, `lightfee/engine/pending_entry_runtime.py`, `lightfee/engine/entry_gate_runtime.py`, `scripts/diagnose_live.py` |

### Fingerprint

`venue private auth failure bypassed paired-entry admission; single-leg exposure recovery action not fully executed`

### Evidence

- Bybit private order precheck could return `33004` for an expired API key, but
  V2 did not classify this as a venue private capability state before paired
  entry selection. The failure could remain a symbol-level order rejection
  instead of isolating the whole Bybit venue for new-risk candidates.
- A paired entry whose maker leg had already filled and whose hedge venue then
  failed private auth could lose the owner-specific pending-entry recovery path
  and degrade toward generic unpaired live-position handling.
- Existing reduce-only cleanup semantics were available, but runtime did not
  emit single-leg recovery evidence (`submitted`, `succeeded`, `failed`,
  `terminalized`) as the source of truth for diagnostics.
- If a venue credential failure also blocked reduce-only cleanup, the correct
  state is a critical cleanup blocker, not a contained admission warning and
  not a silent terminalization.

### Fix

- Added a shared venue private health classifier with stable statuses:
  `auth_invalid`, `permission_denied`, `truth_unavailable`,
  `order_permission_unavailable`, and `healthy`.
- Bybit `33004 api key expired` and similar private auth/permission errors now
  become `runtime.entry_admission_blocked` with
  `reason=venue_auth_invalid`, `source=venue_private_health_precheck`,
  `cooldown_scope=venue`, `block_scope=venue`, and
  `venue_private_health_status=auth_invalid`. The candidate gate now prefers
  venue-scope cooldown evidence over same-TTL symbol evidence, so all Bybit
  new-risk candidates are evicted during the TTL while other venues remain
  selectable.
- Pending hedge admission rejects caused by venue private health now keep the
  original pending entry owner and enter
  `single_leg_exposure_recovery:<reason>`. When live truth is high-confidence,
  no-open-orders, and shows a single maker-side exposure, runtime uses the
  maker venue reduce-only cleanup path and emits
  `pending_entry.single_leg_exposure_recovery_started`,
  `pending_entry.single_leg_flatten_submitted`,
  `pending_entry.single_leg_flatten_succeeded|failed`, and
  `pending_entry.terminalized_after_single_leg_recovery`.
- Reduce-only cleanup failures caused by the same private auth family now emit
  `cleanup_blocked_by_venue_auth_invalid` with `severity=critical`, the failed
  action, venue, symbol, entry id, and raw error evidence.
- Diagnose now exposes `venue_private_health_summary`,
  `single_leg_exposure_recovery_summary`, and `cleanup_blocker_summary`.
  Clean exchange truth can resolve contained Bybit auth-invalid opening rejects
  out of `order_error_evidence`, but cleanup blockers remain explicit.
- Review hardening closed two diagnostic drift gaps: unfinished single-leg
  recovery now remains visible through
  `single_leg_exposure_recovery_summary.unresolved_count` until
  `pending_entry.terminalized_after_single_leg_recovery` exists, and
  `venue_private_health_summary` separates raw `event_count` from de-duplicated
  incident `count` so the paired `runtime.entry_admission_blocked` plus
  `runtime.venue_cooldown_started` events do not inflate incident totals.
- Runtime regression coverage now locks the three negative single-leg recovery
  branches: live truth unavailable, maker open order still present, and
  reduce-only cleanup failure. All three must retain the pending owner, keep
  `risk_only`, emit explicit failure evidence, and avoid terminalizing as clean.

## Cluster CL-099 - Aster headroom pre-submit, single-leg fee-drag guard, and active handoff quality

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed and deployed through `039d52c`; current cloud recovered | critical | paired-entry admission + single-leg fee drag + business phase handoff | entry-admission, runtime-candidate, pending-entry, diagnose-live, venue-transport | `lightfee/engine/entry_dispatch_runtime.py`, `lightfee/engine/runtime.py`, `lightfee/engine/v1_lifecycle_closure.py`, `lightfee/venues/aster.py`, `lightfee/venues/transport.py`, `scripts/diagnose_live.py` |

### Fingerprint

`Aster remaining_openable_notional=0 discovered too late; maker leg can fill before deterministic hedge admission block; candidate or quote-rewarm phase lacks active takeover evidence`

### Evidence

- The production sample showed that the risk was not only visible
  `order.submit_result` errors. A real online-ready review also had to prove
  whether each business phase actively handed work to the next phase or stayed
  idle until a later hard ceiling or cleanup path intervened.
- Aster max-notional / remaining-openable-notional evidence can be deterministic
  before order submission. If the hedge leg has no headroom, submitting the
  maker first creates avoidable single-leg exposure and can repeat into
  fee-drag if cleanup immediately flattens and the same route is selected
  again.
- Existing pending-hedge admission handling was still necessary as a fallback,
  but deterministic admission blocks were being treated too much like ordinary
  retryable hedge failures. That inflated useless retries and made cleanup look
  like the normal path instead of the last defense.
- Diagnostics had phase duration evidence, but did not yet expose a
  production-grade business quality view for: pre-submit admission blocks,
  single-leg creation, cleanup after deterministic admission block, and whether
  a route violated cooldown by submitting a maker again while the hedge leg was
  still guarded.
- Candidate and quote-rewarm phases needed explicit active takeover evidence.
  A candidate that stays in lease past the hard budget must be expired and
  rescanned; quote rewarm that stays stale past its budget must terminalize into
  cooldown/stale evidence. Diagnose must distinguish these from passive
  over-budget drift.

### Root Cause

- The V2 entry path could verify maker-side submit readiness and still miss the
  hedge venue/symbol headroom contract immediately before maker submission.
  That is a semantic gap for paired entry: both legs must be admissible before
  the first non-reduce-only leg is allowed to create new exposure.
- Aster V3 headroom truth lives behind the dedicated V3 signer client. Generic
  Binance-compatible transport classification is not enough for the current V3
  private account-risk contract.
- The runtime had fallback cleanup for single-leg exposure, but no hard
  fee-drag invariant tying cleanup-after-admission-block to a route cooldown
  that prevents the same maker/hedge path from immediately reopening.
- `diagnose_live.py` could report errors and durations, but not the business
  progression quality questions operators actually need after a 10-hour
  production sample: was the phase actively advanced, was it abandoned until a
  hard ceiling, and did a cleanup path turn into repeated fee churn?

### Fix

- Added a two-leg admission precheck in entry dispatch after entry selection and
  before maker submit. A deterministic hedge-side block now emits
  `runtime.entry_blocked_admission_selection` /
  `runtime.entry_admission_blocked` and no `order.passive_submitted` maker leg
  is sent.
- Added Aster headroom admission support through the dedicated V3 signer path
  and the direct transport fallback. `remaining_openable_notional=0`,
  max-notional, and error-only `max_notional_admission_blocked` shapes are
  classified before order submit where truth is available; reduce-only cleanup
  remains allowed.
- Preserved V1 safety semantics: uncertain exchange truth still fails closed,
  deterministic admission blocks do not masquerade as success, and cleanup is a
  last-resort loss-control path rather than a routine retry strategy.
- Added single-leg fee-drag diagnostics with
  `business_progression_quality_summary`: `pre_submit_blocked`,
  `single_leg_created`, `single_leg_cleanup`,
  `cleanup_after_admission_block`, and `repeated_single_leg_guarded`.
  A maker submit on the same route while the hedge venue/symbol is still under
  cooldown is reported as production issue
  `repeated_single_leg_fee_drag_after_cooldown`.
- Added candidate lease active takeover. A tradeable candidate older than the
  configured `candidate_lease` budget emits
  `runtime.candidate_lease_expired`, records
  `review.candidate_rejected rejected_stage=candidate_lease`, drops out of the
  current tick, and forces rescan instead of lingering passively.
- Extended phase diagnostics with `phase_handoff_quality` for candidate lease
  and quote rewarm. Over-budget phases without terminal/takeover evidence are
  marked as production issues; terminal stale/expired evidence is counted as
  active takeover instead of passive drift.
- Post-deploy review caught one diagnostic false positive: catalog-level
  `runtime.candidate_symbol_skipped reason=unsupported_symbol` is already a
  pre-candidate rejection, not a candidate lease start. Diagnose now treats it
  as terminal/takeover evidence only when a candidate lease already exists, and
  does not manufacture a missing-takeover issue from a catalog skip alone.
- Follow-up production-readiness review closed the "recovered but still
  operationally bad" gap. Symbol-scope deterministic admission blocks such as
  `insufficient_balance_admission_blocked` are now filtered in
  `_filter_candidates_by_entry_admission()` before selection, not left to
  repeat through dispatch. Venue-scope Aster `aster:*` cooldown remains a
  route-level no-new-risk signal for any opening route whose hedge venue is
  Aster.
- `runtime.entry_blocked_admission_selection` evidence now keeps the actual
  `block_scope` (`venue`, `symbol`, or `mixed`) and samples preserve the
  source cooldown scope. This keeps operator evidence without flooding the
  ledger with dozens of identical HUSDT/Bybit-style candidate attempts.
- Quote rewarm hard-expiry and active-position normal-exit scheduling were
  locked with regression tests. Existing runtime behavior already suppresses
  same venue/symbol rewarm scheduling while terminal stale cooldown is active,
  and active-position ticks already enter the normal-exit lane before the next
  full periodic tick. No strategy permission, quote freshness, or V1
  `standard_close_reason` semantics changed.
- Passive close terminal/no-fill evidence now includes compatible
  `exchange_code`, `exchange_msg`, and `raw_error` fields on
  `exit.passive_close_maker_terminal_no_fill`, so future reviews can separate
  reduce-only terminal zero quantity, post-only reject, and ordinary no-fill
  evidence while keeping final flatness exchange-truth gated.
- Diagnose now separates current active stuck work from recovered process
  issues. `business_progression_quality_summary` includes
  `candidate_takeover_count`, `quote_rewarm_terminalized_count`,
  `recovered_but_counted_issue_count`, and `active_stuck_count`. A zero-fill
  maker attempt followed within seconds by cancel plus `entry.aborted` remains
  counted as a fee/quality incident, but no longer becomes a false current
  hard-over-budget stuck issue.
- Review follow-up closed one diagnostic false-negative edge case:
  soft-over-budget quote/candidate terminalization no longer subtracts from
  `active_stuck_count`. Only hard-over-budget terminalized candidate/quote
  records can offset hard-over-budget work, so a separate pending close or
  recovery artifact that is still hard-stuck remains visible.

## Cluster CL-100 - Open/close lifecycle owner truth and reduce-only adoption

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed and deployed in `106f47e`; waiting-event evidence payload is local to the event | critical | open/close owner ledger + passive-close reduce-only adoption + diagnose gate truth | passive-close, recovery-ledger, v1-lifecycle-closure, entry-admission, diagnose-live | `lightfee/engine/passive_close.py`, `lightfee/engine/recovery_owner_index.py`, `lightfee/engine/recovery_ledger.py`, `lightfee/engine/runtime.py`, `lightfee/engine/v1_lifecycle_closure.py`, `scripts/diagnose_live.py` |

### Fingerprint

`Bybit reduce-only close order remains live after passive close terminal/no-fill or 110017; local maker ids can be cleared before adopting the exchange open order; diagnose can explain open orders as generic or false-green instead of owner-bound close work`

### Current Abnormal Shape

- A live position or live open order is never safe unless it has an owner. A
  reduce-only Bybit close order that is already resting on the exchange is not
  an orphan if it matches a pending passive close by order id, client id, or
  symbol/side/reduce-only/quantity evidence.
- `110017 orderQty will be truncated to zero` is not terminal-flat proof by
  itself. It is only terminal flat when exchange position truth and open-order
  truth are both flat. If live position remains nonzero and a matching
  reduce-only close order exists, the correct state is covered-by-existing
  close order and passive maintenance continues.
- Bybit `110007 ab not enough for new order` is an opening admission block.
  It arms a symbol-level opening cooldown and must be filtered before the next
  maker submit. It does not block reduce-only close maintenance.

### Root Cause

- Passive-close terminal/no-fill and Bybit `110017` handling could clear local
  maker order ids before querying active open orders for an already-resting
  reduce-only close order. That created a semantic race: the local pending close
  lost the owner fields while exchange truth still had a valid close order.
- Recovery owner indexing only treated local pending passive close state as the
  close owner. If local pending state was compacted or missing but the journal
  contained `exit.passive_close_maker_submitted`, a live reduce-only close order
  could be misclassified as generic pending-entry work or orphan risk.
- One-sided flatten could see open orders not flat and proceed toward generic
  handling instead of first trying to adopt the matching reduce-only close
  order. Ownerless open orders must block new risk; owned reduce-only close
  orders must be maintained, not duplicated.
- Diagnostics had the pieces, but not a single business-quality contract for
  ownerless open orders, owned pending passive close work, adopted close orders,
  duplicate reduce-only submit prevention, and deterministic rejects after
  submit.

### Fix

- Passive close now probes active open orders before clearing maker ids after
  terminal/no-fill/reject progress. A matching reduce-only close order is
  adopted back into `PendingPassiveClose.phase_state`, emits
  `exit.passive_close_existing_reduce_only_order_adopted`, and remains under
  passive maintenance without duplicate maker submit or taker flatten.
- Bybit `110017` is split into terminal-flat only when exchange truth proves
  position flat and open orders flat. If a live position remains and a matching
  reduce-only close order covers the quantity, runtime emits
  `exit.passive_close_reduce_only_quantity_covered_by_open_order` and retains
  the pending close.
- One-sided flatten first attempts reduce-only close-order adoption when open
  orders are present. Adoption keeps the passive close owner; failure emits
  `exit.passive_close_open_order_ownerless_blocked` and remains fail-closed
  rather than guessing with IOC flatten.
- Recovery owner indexing now treats passive-close journal events as
  `journal_passive_close`. Recovery ledger maps both local and journal passive
  close owners to `owned_pending_passive_close`, and V1 lifecycle closure
  projects that as a `PASSIVE_CLOSE` blocking row with
  `manage_owned_pending_passive_close`.
- Bybit `110007` opening admission now emits
  `runtime.entry_admission_symbol_cooldown_armed` with `reduce_only=false`;
  the existing candidate/selection cooldown filter prevents the same opening
  route from reaching maker submit during TTL.
- Diagnose now exposes
  `ownerless_open_order_count`, `owned_pending_passive_close_count`,
  `adopted_reduce_only_order_count`,
  `duplicate_reduce_only_submit_blocked_count`, and
  `deterministic_reject_after_submit_count`. Production gate also derives
  ownerless/open-close owner counts from V1 lifecycle rows, so `health.ok`
  cannot mask `gate_passed=false`.

### Fingerprint

`passive close resolved before exchange position/open-order truth is explicit; diagnose keeps recovered hard-over-budget artifacts as active stuck after production gate is green`

### Evidence

- Read-only cloud verification after `c35dd35` showed the current trading truth
  was recovered: services singleton passed, exchange truth was flat/no-open

- The same since-deploy diagnosis still reported historical process quality

### Root Cause

- The terminal contract was still partly duplicated: passive-close local fill
  completion, recovery owner work, V1 lifecycle projection, and diagnose

- `business_progression_quality_summary` was built before
  `production_acceptance_gate`, so it could not know that the current state was
  exchange-flat, open-order-flat, and lifecycle-clean. It treated historical
  hard-over-budget artifacts as currently active unless a matching event-level
  terminal proof happened to exist.

### Fix

- Live passive close finalization now calls the live flat/open-order truth gate
  before clearing `pending_passive_close`, removing the owner, or emitting
  `exit.passive_close_resolved`.
- If maker and hedge fills are locally complete but live truth is not yet
  jointly proven flat, runtime retains the pending owner, schedules another
  probe, and emits `exit.passive_close_waiting_exchange_flat_truth`.
- Recovery ledger maps completed/waiting passive close work as
  `owned_pending_passive_close`, preserving the close owner and blocking new
  risk while passive close maintenance continues.
- Diagnose now treats `exit.passive_close_resolved` without explicit
  `exchange_truth` position-flat and open-order-flat proof as
  `passive_close_resolved_without_terminal_truth_count`.
- Diagnose builds business progression quality with production-gate context.
  When the current gate is green, exchange truth is flat, open orders are flat,
  and lifecycle blocking rows are zero, historical hard-over-budget artifacts
  move into `recovered_but_counted_issue_count` /
  `historical_hard_over_budget_recovered_count` instead of
  `active_stuck_count`.
- Review follow-up keeps the waiting event self-contained: when local
  maker+hedge fills are complete but live truth has not jointly proven terminal,
  `exit.passive_close_waiting_exchange_flat_truth` now carries an
  `exchange_truth_attempt` with position truth, open-order truth, and explicit
  missing evidence instead of requiring operators to join sibling diagnostic
  events by hand. Missing position-snapshot waiting events use the same payload
  shape with `missing_evidence=["position_snapshot"]`.

## Cluster CL-102 - Business Contract Centralization And Process-Issue Counters

### Status

### Process Problems Added To Ledger

- HOMEUSDT-style open sizing residual: entry quantity planning already floors
  OKX/contract-size routes to a common hedgeable quantity, but the journal did
  not explicitly state whether the selected raw quantity was fully hedgeable,
  adjusted to a hedgeable size, or blocked. That made later reviews depend on
  residual-repair evidence even when no residual repair was part of the normal
  path.
- Passive close reconciliation evidence gap: `exit.reconciled` could set
  `evidence_gap=true` without explaining whether the missing proof was a venue
  statement delay, one missing trade side, both missing trade sides, or a
  duplicate-leg suppression artifact. Gate green still depends on exchange
  position/open-order truth, but process quality needs this missing evidence
  classified.
- Quote rewarm counter drift: terminal stale quote rewarm events must count as
  terminalized process takeover and must not be reinterpreted later as active
  still-stale work when production gate is already green.
- Pending-entry dual taker fallback drift: `execution.dual_taker_armed` is a
  V1-compatible pending-entry terminal fallback event. It must map through the
  business contract before lifecycle closure consumes it, not by adding another
  one-off diagnose exception.
- Reduce-only close-error drift: SAHARAUSDT-style `-2022` reduce-only close
  rejections can be called resolved only when current exchange truth is flat and
  has no open orders, plus terminal position/order evidence matches. The fix
  keeps this as terminal truth, not an order-error whitelist.
- Admission noise: repeated deterministic admission degradation for the same
  venue/symbol/reason/scope should carry an aggregation key and suppressed
  count instead of forcing operators to manually group equivalent degraded
  events.

### Fix Direction

- Added `lightfee/engine/business_contract.py` as the centralized pure-function
  contract for entry admission block semantics, entry quantity hedgeability,
  passive-close terminal truth, close reconciliation evidence-gap
  classification, and diagnose process-issue counts.
- Added unified classification contracts for runtime events and terminal truth:
  `classify_business_event_kind`, `quote_rewarm_handoff_contract`, and
  `close_order_error_resolution_contract`. Runtime, diagnose, and V1 lifecycle
  projection consume those results instead of maintaining separate local
  interpretations.
- `execution.entry_quantity_plan` now carries
  `quantity_contract_status` and `unhedgeable_residual_quantity`. A raw
  HOMEUSDT `1856` shape on an OKX `100` base step is explicitly recorded as
  `hedgeable_adjusted` to `1800`, not as a normal path that expects residual
  repair.
- Quote rewarm hard expiry now carries contract-backed `action_taken` and
  `action_evidence_kind` so `phase_duration_summary` has no blank takeover
  action for the ALICEUSDT-style stale rewarm sample.
- `execution.dual_taker_armed` maps through the business contract to V1
  `PENDING_ENTRY` with `terminal_fallback_armed` terminality.
- Resolved close-order errors now call the business contract and still require
  current flat/no-open-orders exchange truth before reduce-only, zero-fill, or
  post-only close boundary rejects move into resolved summaries.
- Review follow-up tightened that contract to preserve the production journal
  shape: reduce-only terminal classification reads nested
  `exchange_error.exchange_code`, `exchange_error.exchange_msg`, `raw_body`, and
  nested/top-level `request_context.reduce_only`. A bare `-2022` without
  reduce-only close context is not treated as resolved.
- `exit.reconciled` now carries `evidence_gap_reason`,
  `statement_probe_status`, and `trade_probe_status`. This does not block gate
  green when exchange truth is flat/no-open-orders; it moves the missing
  statement/trade proof into historical process quality.
- `runtime.entry_admission_venue_degraded` now carries `aggregation_key`; the
  business progression summary counts `admission_degraded_suppressed_count`.
- `business_progression_quality_summary` adds:
  `entry_quantity_contract_blocked_count`,
  `close_reconciliation_evidence_gap_count`, and
  `admission_degraded_suppressed_count`.
