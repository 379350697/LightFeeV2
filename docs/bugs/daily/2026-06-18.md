## Cluster CL-096 - Active stale risk-state alignment and order-error closure

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed locally; cloud deploy pending | critical | stale recovery alignment + venue precision + post-only classification | recovery-startup, ops, aster-v3, diagnose-live, production-health | `lightfee/engine/recovery_startup_runtime.py`, `lightfee/engine/runtime.py`, `lightfee/ops/auto_fail_closed_repair.py`, `lightfee/apps/ops.py`, `lightfee/venues/aster.py`, `scripts/diagnose_live.py`, `scripts/verify_production_services.py`, `lightfee/ops/production_health.py` |

### Fingerprint

`stale unpaired recovery records prevented active risk/lifecycle alignment; Aster V3 precision normalization gap caused BAD_PRECISION; post-only rejects needed resolved-truth classification`

### Evidence

- Production could reach `risk_mode=running` while `lifecycle=risk_only` and
  `recovery_blocked_reason=unpaired_live_position` stayed latched because
  active stale unpaired recovery records were treated as local work that blocked
  the same account-truth refresh needed to terminalize them.
- High-confidence exchange truth flat/no-open-orders is the authoritative fact
  source for this shape; historical active recovery records are evidence to
  reconcile, not a permanent veto after account truth is clean.
- Aster private V3 order submission bypassed the common Binance-style preflight
  path used by transport-level submits, so symbols such as `HUSDT` and
  `ESPORTSUSDT` could reach the exchange with over-precise price or quantity
  and produce `-1111 BAD_PRECISION`.
- Binance entry `-5022 GTX_ORDER_REJECT` is a maker/post-only boundary reject,
  not proof of an abnormal position. It must remain warning/unresolved only
  when cooldown evidence or clean exchange truth is missing.

### Fix

- Runtime startup now has a truth-gated stale-risk alignment path. If the only
  local blocker is active `unpaired_live_position` recovery records and
  account-level exchange truth is high-confidence flat/no-open-orders, it
  refreshes the recovery ledger, marks stale records terminal-flat, clears the
  blocker, and lets `V1RecoveryDecisionCore` derive the final lifecycle/risk
  state. Incomplete truth, live positions, open orders, or real operator
  fail-closed evidence remain blocked.
- New events `runtime.stale_risk_state_alignment_started`,
  `runtime.stale_risk_state_aligned`, and
  `runtime.stale_risk_state_alignment_blocked` make automatic alignment visible
  as a strong audit trail instead of a silent state jump.
- `repair-stale-risk-state` was added as a default dry-run ops command. It
  classifies state as `safe_to_align_stale_risk_state`,
  `operator_latch_must_preserve`, or `unsafe_truth_or_cleanup_required`; apply
  only terminalizes stale records and re-runs recovery-core derivation, never
  hand-edits the state directly to `running`.
- Aster private V3 submits now go through the same symbol-rule preflight as
  transport submits: price tick, quantity step, and min-notional validation are
  applied before exchange submission. Local precision rejection emits
  `order_error.precision_rejected_before_submit`.
- Diagnose now includes `stale_risk_state_alignment_summary` and resolved
  post-only virtual events under
  `order_error.resolved_post_only_reject`; production health preserves recent
  stale-risk alignment as detail-only evidence when current exchange truth is
  clean.

## Cluster CL-095 - Auto fail-closed operator latch and cleanup visibility

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed locally; cloud deploy pending | critical | auto fail_closed + operator latch + recovery cleanup visibility | live-runtime, ops, production-health, diagnose-live, projection-contracts | `lightfee/engine/runtime.py`, `lightfee/ops/auto_fail_closed_repair.py`, `lightfee/apps/ops.py`, `scripts/diagnose_live.py`, `scripts/verify_production_services.py`, `lightfee/ops/production_health.py`, `lightfee/persistence/projection_contracts.py` |

### Fingerprint

`auto fail_closed incorrectly persisted as operator fail_closed; fail_closed blocked cleanup visibility`

### Evidence

- V2 automatic pending-entry abort path called `enter_fail_closed()` and also
  wrote `state.operator.requested_mode = fail_closed`. That made a system
  accident look identical to a real operator `fail-closed` command.
- True operator fail-closed still has an authoritative source: only
  `ops.command_applied command=fail_closed` and journal replay may set the
  operator latch.
- Because stale cleanup helpers intentionally preserve operator fail-closed,
  the false operator latch could keep a terminal-flat stale blocker from being
  released even when exchange truth was flat/no-open-orders.
- After cleanup succeeded, diagnostics could show current state as green while
  hiding the recent automatic fail-closed incident.

### Fix

- `_abort_pending_entry_fail_closed()` now enters automatic fail-closed without
  writing `operator.requested_mode`; it emits `runtime.auto_fail_closed_entered`
  with `source=auto_pending_entry_abort`.
- Automatic cleanup success emits `runtime.auto_fail_closed_recovered`; cleanup
  failure emits `runtime.auto_fail_closed_cleanup_failed` and preserves
  residual blockers.
- `diagnose_live.py` and `verify_production_services.py` expose
  `auto_fail_closed_summary` so a recovered incident remains visible without
  turning a clean running state into a false critical.
- `repair-auto-fail-closed-latch` was added as a default dry-run ops command.
  It classifies state as `safe_to_repair_auto_latch`,
  `operator_latch_must_preserve`, or `unsafe_truth_or_cleanup_required`.
  Apply only clears the pseudo operator latch and stale blocker after
  high-confidence exchange flat/no-open-orders truth and no real operator
  fail-closed evidence; it does not directly force `running`.
- New runtime events are journal-only in projection contracts.

## Cluster CL-094 - ZECUSDT entry route semantic closure after latest deploy

| Status | Severity | Family | Modules | Files |
|---|---|---|---|---|
| fixed locally; cloud deploy pending | high | venue-contract + maker-event-admission + pending-entry-hard-ceiling + diagnostic-lifecycle-drift | aster-v3, passive-maker, pending-entry, diagnose-live, v1-lifecycle-closure | `lightfee/venues/aster_v3.py`, `lightfee/engine/passive_maker_runtime.py`, `lightfee/engine/runtime.py`, `scripts/diagnose_live.py`, `lightfee/engine/v1_lifecycle_closure.py` |

### Evidence

- Latest cloud deploy `94487e4` ended safe: local pending/open/close/residual
  counts were zero and exchange truth was high-confidence flat/no-open-orders.
- The since-deploy window was not semantically clean. Two ZECUSDT entries
  aborted only after pending lifetimes around 208-214 seconds, beyond the V1
  pending-entry hard ceiling of 120 seconds.
- Aster V3 hedge submit failed with `-1106 PARAM_NOT_REQUIRED` because the
  MARKET/IOC hedge body sent `timeInForce=IOC`, which Aster rejects for that
  request shape.
- Bybit maker reprice/cancel-replace repeatedly produced `110007 Available
  balance is insufficient`; the maker-event lane treated this as a repeatable
  generic error instead of a terminal opening-risk admission block.
- `phase_duration_summary` showed hard-over-budget samples with empty
  `action_taken`, and V1 lifecycle closure did not map
  `entry.hedge_drive_cancel_replace`, `runtime.maker_event_lane_wake`,
  `runtime.maker_event_reprice`, or `runtime.maker_event_reprice_error`.

### Fix

- Aster V3 now omits `timeInForce` for MARKET/IOC hedge or cleanup requests;
  passive limit submits still send the required post-only TIF.
- Maker-event reprice classifies Bybit `110007` as
  `insufficient_balance_admission_blocked`, marks that entry route as
  terminally blocked for new opening reprice attempts, and keeps reduce-only
  close/recovery paths separate.
- Pending-entry hard ceiling no longer grants a 30s local retention extension
  after the 120s hard limit. Positive-fill pending entries emit
  `pending_entry.hard_ceiling_reconcile_before_abort` and then immediately
  continue through the existing abort/cleanup truth path.
- `diagnose_live.py` exposes top-level `phase_duration_summary` and fills
  hard-over-budget `action_taken`/`action_evidence_kind` fields so final
  flatness cannot hide missing budget actions.
- V1 lifecycle closure now maps the maker-event and hedge-drive events to the
  correct phases, removing the unmapped-event drift.
