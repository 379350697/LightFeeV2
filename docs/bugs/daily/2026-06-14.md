## Cluster CL-078: HOME positive-fill/live-truth conflict and owned single-leg cleanup

### GitNexus Keys

- Fingerprint:
  `HOMEUSDT-positive-fill-live-truth-conflict +
  okx-order-detail-not-fill-truth + bybit-ioc-ack-not-fill +
  owned-pending-entry-live-conflict`
- Components:
  `venue-reconciliation`, `pending-entry`, `recovery-owner-index`,
  `recovery-ledger`, `recovery-decision-core`, `v1-lifecycle-closure`,
  `diagnose-live`, `production-health`
- Watch:
  `detail_found;fills_empty`, `execution_not_found`,
  `pending_entry.positive_fill_live_truth_conflict`,
  `owned_pending_entry_live_conflict`,
  `okx fill evidence conflicts with okx live flat`,
  `live position owned by pending conflict`,
  `entry.opened`, `unpaired_live_position`, `orphan_maker_order`

### Production Symptom

The HOME evidence looked contradictory: local/pending state had matched positive
maker and hedge quantities, while current exchange truth did not show a matched
pair. OKX was flat, and Bybit carried the remaining single short exposure. This
cannot be summarized as a normal open/close bug or as only "maker succeeded,
hedge failed". The root problem is that local order evidence and live account
truth disagreed, and the live single leg needed an owner and cleanup path
instead of drifting as a generic orphan.

### Root Cause

The recurrence had three coupled roots:

1. Venue fill evidence was too weak in some paths. OKX order detail
   `accFillSz/fillSz` is cumulative order-detail evidence, not final fill truth.
   It must be cross-checked through `/api/v5/trade/fills` and converted from
   contracts to base with `ctVal`. A detail row with positive `accFillSz` but
   empty fills, especially while live position is flat, is an evidence gap.
2. Hedge/market ACK was still semantically dangerous. Bybit market orders are
   IOC-style and ACK only means accepted; executions must be reconciled through
   `/v5/execution/list`. Binance default ACK and other venue ACK-only paths have
   the same risk class: accepted is not filled.
3. Owner governance stopped too early. A pending entry with positive fill
   evidence can temporarily own a live single leg, but that ownership must not
   downgrade the artifact to ordinary owned work. It must block all new entry
   risk, route to flatten/block cleanup, and release only after account flat
   plus open-order truth is available.

### Fix

- OKX order reconciliation now queries `/api/v5/trade/order` or
  `/api/v5/trade/orders-history` only to resolve `ordId/clOrdId/state`, then
  queries `/api/v5/trade/fills` and only aggregates actual fills into
  `OrderFillReconciliation`. Empty fills record
  `detail_found;fills_empty`, `execution_not_found`, and
  `next_action=check_live_position`; they do not terminalize `entry.opened`.
- OKX fill and passive-progress quantities now convert contracts to base with
  `ctVal`; missing `ctVal` makes passive progress an evidence gap instead of a
  trusted base quantity.
- Bybit reconciliation remains execution-list based: order id/client id
  resolution is only an input to `/v5/execution/list`; empty executions return
  no fill. ACK-only market/IOC evidence cannot count as hedge filled.
- Bitget positive fill with missing or invalid side now fails closed with
  `REQUEST_REJECTED` instead of defaulting positive quantity to `buy`.
- Pending positive-fill entries are indexed by expected live leg owner keys.
  If exchange truth reports a live position owned by a pending entry, the ledger
  creates `owned_pending_entry_live_conflict` rather than generic
  `unpaired_live_position`.
- `owned_pending_entry_live_conflict` is now a live-artifact blocker in
  `V1RecoveryDecisionCore`, runtime entry gating, startup flat-truth release,
  and V1 lifecycle closure projection. It blocks all new risk, routes to
  flatten/block management, and clears only through fresh account flat plus
  open-order truth.
- Diagnose and production health list pending maker/hedge local fills, expected
  legs, live quantities/sides, open orders, owner, conflict reasons, and
  `next_action=owned_pending_entry_live_conflict_cleanup`.

### Non-Changes

- No symbol-specific HOME freeze.
- No strategy, threshold, OI/liquidity, WS-BBO/Local-L2 budget, sizing, close
  executor, residual-repair submit policy, credential, or production config
  change.
- No order submit/cancel/manual flatten was performed during local evidence
  gathering or tests.
- Hyperliquid account/signer identity remains its existing preflight/env truth
  requirement; this pass only keeps signer/account mismatch from being used as
  current-runtime fill or position ownership.

## Cluster CL-079: HOME historical positive-fill conflict owner survives pending removal

### GitNexus Keys

- Fingerprint:
  `HOMEUSDT-historical-positive-fill-conflict-owner-drop +
  pending-removed-live-position-unpaired`
- Components:
  `recovery-owner-index`, `recovery-ledger`, `startup-recovery`,
  `v1-lifecycle-closure`, `diagnose-live`, `production-health`
- Watch:
  `pending_entry.positive_fill_live_truth_conflict`,
  `journal_pending_entry`, `owned_pending_entry_live_conflict`,
  `unpaired_live_position`, `exchange_truth_nonzero_position`

### Production Symptom

After CL-078 was deployed at `6209fac`, read-only cloud evidence still showed a
historical HOME live artifact: local state had no current open positions and no
pending entries, OKX was flat, Bybit had HOME short `1600`, and open orders were
empty. The service correctly stayed in risk-only/non-green state, but the
remaining live short could be diagnosed as an unpaired live position once the
current pending entry was gone.

### Root Cause

CL-078 indexed current pending-entry owner facts and journal order owner facts,
but did not persist journal position owner facts for
`pending_entry.positive_fill_live_truth_conflict`. That meant ownership was
available while the pending entry still existed, but could be lost after pending
removal, restart, or current-state compaction. The historical live position was
then still blocked, but as an orphan `unpaired_live_position` rather than an
owned `owned_pending_entry_live_conflict` cleanup item.

### Fix

- `RecoveryOwnerIndex` now extracts durable journal position facts from
  `pending_entry.positive_fill_live_truth_conflict` and terminalizer decisions
  with outcome `positive_fill_live_truth_conflict`.
- Journal position ownership matches exchange live positions by symbol,
  normalized side, and exact live quantity. A matching historical HOME Bybit
  short remains owned by `journal_pending_entry` even when no current pending
  entry remains.
- Startup recovery now includes symbols that have journal position owner
  evidence, so historical owned live conflicts are re-evaluated after restart.
- `diagnose_live.py` and production health closure rebuilds pass the same
  journal-derived owner index, preventing read-only diagnostics from drifting
  back to `unpaired_live_position`.
