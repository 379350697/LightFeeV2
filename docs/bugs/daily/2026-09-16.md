## CL-153 — Gate 双向模式 set_leverage 校验把成功当失败 (dual-mode leverage verification)

Status: **local-green**.

### Symptom

`runtime.entry_admission_blocked` reason `entry_leverage_unavailable` fired
2,499 times since deploy, all gate×LSKUSDT, with raw error
`Gate entry leverage prepare failed: Gate set-leverage response is malformed`.
Real failures: 9-15 13:56 FFUSDT, 9-16 00:52 / 06:52 / 12:52 LSKUSDT — each
armed a symbol-scope 6 h TTL block that killed the following gate→bybit
funding-capture windows (~100 bps expected edge).

Observed input/state (read-only probes with the production credentials, no
orders): the Gate account answers `position_mode: "dual"`,
`in_dual_mode: true`, `enable_new_dual_mode: true`;
`GET /futures/usdt/positions/LSK_USDT` returns an **array** of
`dual_long`/`dual_short` Position rows where the applied value lives in
`lever` while the legacy `leverage` field reads `"0"`. The rows' `update_time`
equals the failure second and `lever=4` — Gate **applied** the leverage; the
verification rejected the success response.

### Root cause

When the Gate account is in dual position mode, `GateAdapter.ensure_entry_leverage`
violates the leverage-postcondition contract because
`_gate_set_leverage_response` accepts only a single Position dict with an
integer `leverage`; Gate's documented dual-mode wire shape is
`Array<Position>` with `lever` carrying the applied value (Gate changelog
v4.106.12: `lever` gradually replaces `leverage`). V1 ignores the response
body entirely (`LightFee/src/live/gate.rs` `set_gate_entry_leverage_for_mode`:
`let _ = signed_request_json(...)`), so the strict verification had no V1
basis. Tests missed it because the contract suite had zero Gate
`ensure_entry_leverage` success-shape coverage (the single dual-retry test
returned the dict fixture).

### Contract

`_gate_set_leverage_response` normalizes both documented shapes — one
Position object (single mode) or a Position array (dual-mode) — reading
`lever` first and falling back to `leverage`; every row must parse to the
effective leverage (a positive integer) or the prepare fails closed. The
`position_mode` diagnostic label derives from the observed response shape.

### Counterexample matrix

- dict `{"leverage": "4"}` / `{"lever": "4"}` / array rows with `lever`
  (dual production shape) → verified.
- empty array, non-object rows, row without leverage evidence, fractional
  leverage, zero leverage, one row off the effective value → rejected.
- dual-mode 400 conflict → unchanged dual_long/dual_short retry path
  (pre-existing test still green).

### Repair

- `lightfee/venues/gate.py`: `_gate_set_leverage_response` returns per-row
  applied values (dict or array, `lever`→`leverage` alias order);
  `ensure_entry_leverage` compares every row and labels `position_mode`
  from the response shape.
- `tests/test_venues_contract.py::TestAdditionalVenueEntryLeverage::`
  `test_gate_verifies_leverage_from_every_documented_response_shape`:
  RED on the pre-fix tree (production dual-array shape reproduced the exact
  raw error), GREEN after.

### Validation

`tests/test_venues_contract.py` + `TestBybitEntryLeverage` +
`TestAdditionalVenueEntryLeverage`: 16 passed. Full suite recorded in the
2026-09-16 batch entry. GitNexus impact for `_gate_set_leverage_response`:
LOW, 1 direct caller (`ensure_entry_leverage`), lightfee-live dispatch path.

## CL-154 — fallback 平仓后 executor 成交腿证据被孤儿丢弃 (executor leg evidence orphaned)

Status: **local-green**.

### Symptom

`entry-1789498326920-LSKUSDT` (03:05 close) and
`entry-1789502150664-LSKUSDT` (04:05 close) registered as `final` billing
owners and have retried every ~5 minutes with
`reconciliation.pending_close_reconciliation_invalid`
reason `close_order_lookup_returned_no_fill` — 181 and 172 failures by
18:15 — while seven-venue truth shows the position flat.

Reconstruction from the journal (03:20 finale): the deadline fallback
cancelled the unfilled maker and the dual-taker drive closed both legs
(binance `2679230467`/`lfxl22e8d318a44e665e` filled 62, bybit
`cfd5d547`/`lfxs5d68fe21b44d9473` filled 62 via the 110072
duplicate-OrderLinkedID reconcile). `CloseExecutor._writeback_to_state`
registered a PendingClose carrying exactly those executed legs
(`exit.pending_close_registered` 03:20:04). One second later the
passive-close side terminalized the position, and the next reconciliation
pass orphaned that PendingClose (`reconciliation.pending_close_orphaned`
03:20:05) without merging its legs. The reconciliation record kept only the
passive zero-fill identities (owned segment `long 62 / short 0`, snapshotted
mid-writeback), so the exact recheck could never find the fills.

### Root cause

When the passive-close fallback terminalizes a position while the
CloseExecutor's uncertain-leg PendingClose is still pending, the pending-close
reconciliation loop's orphan (`open_positions` miss) and `close_resolved_flat`
paths drop the PendingClose without handing its durable leg records to the
`pending_close_reconciliation` billing owner for the same position. Same
bug family as CL-150's phantom identity (evidence anchored on orders that
never filled) with a new trigger path. Tests missed it because no regression
covered the "uncertain executor legs + passive-close terminalization"
ordering.

### Contract

A PendingClose leaving the queue must hand its durable leg evidence to the
existing billing reconciliation owner for the same position: executed leg
identities merge into `long_legs`/`short_legs` (identity dedupe, a proved
fill upgrades a stored zero-fill intent, never the reverse), and the
executor's proven `long_closed`/`short_closed` totals upgrade the
mid-writeback `owned_close_quantities` segment (never downgraded). With no
billing owner for the position, the orphan stays a pure no-op. Incomplete
evidence after the merge keeps the owner fail-closed
(`known_close_fill_temporarily_unavailable` evidence debt), never settles it.

### Counterexample matrix

- Production shape: orphan merges 2 legs + short-owned upgrade (merged 3);
  the next billing cycle finds both fills, `owned_close_quantities`
  (62, 62), and settles `exit.reconciled` with
  `venue_statement_reconciled=true`; the invalid loop does not re-fire.
- No reconciliation owner → merge is a no-op; orphan unchanged (also green
  on the pre-fix tree by design).
- Merged identities the venue cannot prove (lookup `None` on a
  positive-quantity leg) → owner retained as an evidence debt, never
  released.

### Repair

- `CloseRuntime._merge_pending_close_leg_evidence` (new): legs + owned
  segment merge with journal event `reconciliation.pending_close_evidence_merged`.
- `PendingEntryRuntime._reconcile_pending_state`: merge before the orphan
  drop and before the `close_resolved_flat` resolution.
- Engine wrapper `_merge_pending_close_leg_evidence` on the runtime class.
- `tests/test_pending_close_evidence_merge.py`: RED on the pre-fix tree
  (2/3 fail; the no-owner counterexample passes on both trees by design).

### Validation

`tests/test_pending_close_evidence_merge.py` 3 passed;
`tests/test_pending_entry_v1_semantic_drift.py` failures byte-identical to
the clean-tree baseline (14 pre-existing). GitNexus impact: new method (no
upstream); call sites inside `_reconcile_pending_state`, production caller
runtime housekeeping only.

## CL-155 — 风险警告按 tick 刷屏（V1 转换语义漂移）(per-tick risk warning storm)

Status: **local-green**.

### Symptom

830 `risk.warning_triggered` events since deploy (650
`long_snapshot_unavailable` + 180 `short_snapshot_unavailable`), 1–2 per
second for the whole life of the LSK/ZIL positions, while zero
`runtime.risk_snapshot_fetch_error` events show the degraded snapshots are a
stable account-shape condition, not flapping.

### Root cause

`Supervisor._update_warning_state` journals `risk.warning_triggered` on
every supervision tick while `warning_condition` holds. V1
(`LightFee/src/engine/risk.rs:376` `update_warning_state_for_position`)
tracks `risk_warning_positions` and journals the warning only on the
transition into the warning state, plus `risk.warning_cleared` on the way
out. V2 dropped the transition gate and never emits `warning_cleared`
(an events-table entry exists with no emitter). Compatibility-sensitive live
semantics: V1 is authoritative.

### Contract

`risk.warning_triggered` fires once per position on entering the warning
state; `risk.warning_cleared` fires once on leaving it. Persistent
degradation journals once; the risk actions themselves are unchanged and
still evaluate per tick.

### Counterexample matrix

- Enter degraded → 1 triggered (payload carries `degraded_reason`).
- Persist degraded across ticks → no new events.
- Recover healthy → exactly 1 cleared; stay healthy → no more.
- Re-degrade → 1 further triggered (transition state re-armed).

### Repair

- `Supervisor`: `risk_warning_positions` set; `_update_warning_state`
  journals on transitions and emits `risk.warning_cleared` (payload mirrors
  V1: ids, ratios, min ratio).
- `tests/test_supervisor_execution.py::TestWarningStateTransitions::`
  `test_warning_journaled_on_transition_not_every_tick`: RED on the pre-fix
  tree, GREEN after.

### Validation

`tests/test_supervisor_execution.py` 26 passed. GitNexus impact
`_update_warning_state`: LOW, 1 direct caller (`supervise_position`).
