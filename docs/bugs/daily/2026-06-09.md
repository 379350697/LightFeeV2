### Production Symptom

Deployment-window events were not showing service crash or WS BBO-caused
trading abnormality. The drift was in interpretation:

- WS BBO provider admission blockers such as Hyperliquid insufficient margin
  could still be represented by the old Local L2 selection event family.
- Historical old-name selection events were classified by provider before
  admission reason, so an account/exchange admission blocker could look like
  WS BBO readiness.
- Bybit ACK-only passive close errors were shown in `top_exchange_errors` even
  after the runtime had registered accepted-order truth work and later proved
  reconciliation/terminal flatness with current exchange truth.
- `entry.opened` without a `position_id`, or older opened lifecycle evidence
  whose residual/recovery branch had already completed, could leave
  `entry_or_position_opened_without_fixture_finalized_evidence` even when
  current local/exchange truth was flat/no-open-orders.

### Root Cause

This is a CL-061 follow-up, not a new Local L2 recurrence. The original Bybit
trading-terms failure was not main order endpoint/signature drift, but the new
admission precheck path had one deterministic endpoint drift: the implementation
used the older `/v5/order/pre-check-order` path, while the current Bybit V5
pre-check endpoint is `/v5/order/pre-check`. The cloud dry-run reproduced HTTP
404 on the older path and accepted after the local endpoint correction.

Bybit order ACK is asynchronous; ACK-only is not fill proof and must remain an
`accepted_order_truth_gap` until order/execution/private-WS/live-position truth
resolves it. Hyperliquid `Insufficient margin to place order` is an exchange
admission/account-capacity error, not WS BBO quote evidence and not Local L2
readiness.

### Fix

- WS BBO provider admission blockers now emit
  `runtime.entry_blocked_admission_selection`.
- Admission payloads carry
  `provider/source/domain/blocker_family`, with
  `source=entry_admission`, `domain=entry_admission`, and
  `blocker_family=exchange_admission`.
- `scan.no_entry_diagnostics` now includes
  `entry_admission_blocker_counts` and an `entry_admission` stage bucket.
- Offline analyzer and dry-run audit classify admission first, then WS BBO,
  then true Local L2. Old
  `runtime.entry_blocked_local_l2_selection` records with admission payloads no
  longer count as Local L2 or WS BBO recurrence.
- `diagnose_live.py` builds a `resolved_order_truth_gap_summary`. An ACK-only
  close error is removed from active `order_error_evidence` only when all are
  true: accepted-order truth gap was registered, a matching reconciliation or
  terminal-flat event appeared, and current exchange truth is flat with no open
  orders. Missing any piece keeps the error unresolved.
- The production acceptance gate exposes
  `resolved_order_truth_gap_count` and marks the conclusion
  `closed_by_current_exchange_truth` only for resolved cases.
- Recovery lifecycle summary now closes opened positions by exact lifecycle
  key, symbol-linked terminal evidence, or current high-confidence exchange
  flat/no-open-orders truth after residual/recovery lifecycle evidence is
  complete. The existing fail case is preserved: opened evidence with no
  terminal/recovery proof is still blocked even when current exchange truth is
  flat.

### Production Symptom

Production already explicitly configured
`entry_readiness_provider="ws_bbo_quote_lease"`, while Local L2 remained enabled
as a retained module. That created two confusing surfaces:

- WS BBO selection blockers were still journaled as
  `runtime.entry_blocked_local_l2_selection`;
- close/passive price hints could read Local L2 first, even though the entry
  mainline had moved to WS BBO quote leases.

The result was not a single Local L2 data bug. It was an ownership drift in the
business chain: A module (Local L2) was retained, but B module (WS BBO) was not
fully exclusive in logs and close-price evidence.

### Fix

- WS BBO selection blockers now emit
  `runtime.entry_blocked_ws_bbo_selection`.
- WS BBO blocker payloads carry stable
  `provider/source/domain/blocker_family` evidence.
- `scan.no_entry_diagnostics` now has `entry_ws_bbo_blocker_counts` and
  `entry_ws_bbo_blocker_samples`; Local L2 readiness fields are emitted only
  when the active provider is `local_l2` or `ws_top_book`.
- Pending-entry passive quote inference and close price hints use fresh WS BBO
  first under `ws_bbo_quote_lease`.
- When WS BBO quote evidence is missing/stale, close/passive/residual risk
  reduction does not fail-closed on the hint. It returns no hint and lets the
  existing market snapshot, venue rule, reduce-only, and live-truth fallback
  paths continue.
- Passive close accepts source-aware resolver returns, so price evidence can be
  labeled `ws_bbo_quote_lease_best_ask`,
  `ws_bbo_quote_lease_best_bid`, or `ws_bbo_quote_lease_mid`.
- Passive close maker-leg diagnostics use
  `exit.passive_close_maker_leg_quote_evidence_missing` for WS BBO source gaps,
  while retaining `exit.passive_close_maker_leg_l2_missing` for true Local L2.
- WS BBO quote resolver missing/stale/invalid paths emit non-blocking
  `runtime.close_price_evidence_missing` / `runtime.close_price_evidence_stale`
  instead of silently returning no quote evidence.
- Diagnostic/offline scripts classify historical old-name
  `runtime.entry_blocked_local_l2_selection` records with
  `provider=ws_bbo_quote_lease` as WS BBO, not Local L2 recurrence.
- Dry-run audit text output now prints WS BBO selection blockers separately from
  Local L2 selection blockers.
- Local L2 runtime/data-plane/session code was not deleted. It remains active
  only for explicit legacy providers or diagnostics.

### Production Symptom

After the prior deploy, production exchange truth was high-confidence flat with
no open orders on all venues, services were active, `risk_mode=running`, and
`V1RecoveryDecisionCore` evaluated the current state as `RUNNING_CLEAN`.
However the exported runtime lifecycle still showed `risk_only`, so verifier
and diagnose correctly reported the service unhealthy even though there was no
current live trading artifact.

The important distinction is that this was not a new live position or open
order. It was a stale local lifecycle latch after pending-entry/passive maker
state had already been terminalized.

### Root Cause

V2 had copied the front half of the V1 safety contract:

- cancel ACK / REST timeout is not terminal;
- maker order must be terminal before zero-fill removal;
- position and open-order truth gaps retain pending work;
- residual/passive repair uses truth before completion.

The missing copy was the current-state release loop after local recovery work
was already gone. `_try_abandon_stale_entry()` and adjacent terminal paths could
remove a pending entry after proving flat, but did not consistently rebuild the
recovery ledger, run `V1RecoveryDecisionCore`, and apply a lifecycle/risk-mode
clear in the same closure. A later runtime tick could therefore have no local
work and clean exchange truth, while the old `risk_only` lifecycle remained.

A second review found one related old release path: the `unpaired_live_position`
flat-position cleanup branch synthesized `open_orders=[]`. That violated the
closed-loop contract because open-order truth must be queried; position-flat
truth alone cannot prove an order artifact is gone.

### V1 / Exchange Decision

V1 semantics are current-state and truth driven:

- terminal pending-entry removal is safe only after order/fill/position truth
  proves no remaining live artifact;
- release from recovery must return through the same recovery decision core;
- live-artifact blockers such as `unpaired_live_position` and
  `orphan_maker_order` cannot be cleared by evidence-gap or position-only truth.

Exchange documentation supports this as a truth contract, not as a local latch
fix. Bybit and OKX expose position and open-order truth endpoints; those
endpoints must be used before clearing recovery state. They do not by
themselves release V2 lifecycle state.

### Fix

- Added narrow runtime helper
  `_clear_stale_recovery_lifecycle_if_core_clean(reason, now_ms, exchange_truth)`.
- The helper only releases when all conditions hold:
  `lifecycle=risk_only`, `risk_mode=running`, operator is not fail-closed, no
  open/pending/residual/passive work exists, current exchange truth is
  available, positions are flat, open orders are empty, and the current
  `V1RecoveryDecisionCore` result is `RUNNING_CLEAN`.
- Startup recovery ledger refresh and runtime clean-position housekeeping pass
  explicit lifecycle-clear reasons into the ledger/core path.
- Pending-entry terminal removal now routes through a shared terminal-complete
  helper which removes local pending state, refreshes recovery truth, and lets
  the core apply `recovery.ledger_clear` / `recovery.lifecycle_clear`.
- The old `unpaired_live_position` runtime flat-position release no longer
  synthesizes empty open-order truth. It now uses bounded symbol recovery-ledger
  refresh, so open-order truth present or unavailable remains fail-safe.
- `diagnose_live.py` adds `lifecycle_release_not_applied` for the exact state
  where current core/exchange truth is clean but runtime lifecycle remains
  `risk_only`. Historical required-truth events are downgraded only when
  current core truth proves the blocker is resolved.

### Production Symptom

After deploying `b2d0706`, production still failed the top-level health gate.
The state dump showed:

- `lifecycle=risk_only`;
- `risk_mode=fail_closed`;
- `recovery_blocked_reason=unpaired_live_position`;
- all local work counts zero.

At the same time, `diagnose_live.py --json --since-deploy` proved all venues
flat with empty open orders through unfiltered account-level private truth, and
`production_acceptance_gate.gate_passed=true`.

### Root Cause

CL-059 fixed the stale `fail_closed` guard, but the old live-artifact blocker
was still present. For `unpaired_live_position`, runtime tried to refresh the
recovery ledger through `_refresh_recovery_ledger_for_symbols()` using startup
and journal candidate symbols.

That is correct for bounded symbol-owned recovery work, but not for releasing a
historical account-level live-artifact blocker after local work is gone. In
production the candidate set included historical or venue-formatted symbols
that some venues rejected as unsupported. Those unsupported symbol probes
created an evidence gap, while the account truth used by diagnose had already
proved the current account state was flat/no-open-orders.

The deterministic gap was therefore not Bybit, Aster, or a V1 core decision
bug. It was a mismatch between the runtime release evidence source and the
production diagnose evidence source.

### Fix

- Added `_refresh_recovery_ledger_from_account_truth()` and
  `_collect_recovery_ledger_account_truth()`.
- Account truth uses `fetch_all_positions()` for position truth.
- Account open-order truth uses the same unfiltered private surfaces as
  diagnose where available:
  Binance `/fapi/v1/openOrders`, Aster `/fapi/v3/openOrders`, Bybit
  `/v5/order/realtime`, OKX `/api/v5/trade/orders-pending`, Bitget
  `/api/v2/mix/order/orders-pending`, Gate
  `/api/v4/futures/usdt/orders`, and Hyperliquid `/info openOrders`.
- Adapter `fetch_open_orders(None)` remains the fallback for test adapters and
  compatible venue implementations.
- The `unpaired_live_position` runtime cleanup branch now refreshes the
  recovery ledger from account truth instead of sweeping dirty historical
  symbols.
- Live open orders and open-order truth errors still block release; no local
  state-only cleanup was added.

## Cluster CL-059: recovery fail-closed release latch after core-clean truth

### GitNexus Keys

- Fingerprint: `recovery-fail-closed-release-latch-core-clean-flat-truth`
- Components:
  `live-runtime`, `recovery-core`, `production-health`, `diagnose-live`
- Symbols:
  `LiveRuntime._clear_stale_recovery_lifecycle_if_core_clean`,
  `LiveRuntime._refresh_recovery_ledger_from_exchange_truth`
- Files:
  `lightfee/engine/runtime.py`,
  `tests/test_live_startup_preflight.py`
- Commits: `b2d0706`, deployed via `78a0feb`
- Watch:
  `recovery.lifecycle_clear`,
  `runtime.stale_fail_closed_cleared`,
  `lifecycle=risk_only`,
  `risk_mode=fail_closed`,
  `V1RecoveryDecisionCore=RUNNING_CLEAN`

### Production Symptom

During post-`3a59a53` deployment verification, sidecar and live were active,
the deploy version matched, singleton passed, and `diagnose_live.py
--since-deploy` proved all venues flat with empty open orders:
`binance`, `bybit`, `aster`, `okx`, `bitget`, `gate`, and `hyperliquid` all
had successful unfiltered position and open-order probes. The production
acceptance gate reported `gate_passed=true`.

The top-level health gate still failed because exported current state remained
`lifecycle=risk_only`, `risk_mode=fail_closed`, even though
`recovery_decision.kind=RUNNING_CLEAN`, `entry_allowed=true`,
`block_reason=null`, `open_position_count=0`, `pending_entry_count=0`,
`pending_close_count=0`, and `pending_residual_repair_count=0`.

### Root Cause

CL-057 added the right current-truth release loop, but one guard was too narrow:
`_clear_stale_recovery_lifecycle_if_core_clean()` returned early unless
`risk_mode=running`. That covered stale `risk_only/running`, but not the
production state `risk_only/fail_closed` after the recovery block reason had
already been cleared.

The result was deterministic: the recovery core could prove
`RUNNING_CLEAN`, but the state-application helper refused to call
`clear_risk_mode_for_recovery()` because fail-closed was still latched.

### Fix

The release helper now allows stale `risk_mode=fail_closed` to enter the same
core-gated release path as `risk_mode=running`. It still refuses to clear when:

- operator requested fail-closed;
- recovery block reason exists;
- local open/pending/passive/residual work exists;
- exchange truth is unavailable;
- live positions are nonzero;
- live open orders exist;
- the recovery decision core is not `RUNNING_CLEAN` with `entry_allowed=true`.

The state mutation remains centralized in `clear_risk_mode_for_recovery()`, so
the helper is not an independent local stale cleaner.

### Production Symptom

Production saw an OKX maker / Bybit hedge candidate on `CLUSDT` fail because
Bybit returned `110125` with the crude-oil trading-terms requirement. The same
window had successful Bybit order-path behavior on other symbols, so the
failure was not a Bybit endpoint, timestamp, signature, or category regression.

### Root Cause

The existing pending-hedge admission classifier handled deterministic Bybit
trading-terms rejects after a hedge submit, but that was too late for a maker
leg that could create exposure first. The missing guard was a pre-entry
non-mutating Bybit admission check for non-reduce-only orders.

### Fix

- Added Bybit `/v5/order/pre-check` support in venue transport. The original
  CL-058 local patch used `/v5/order/pre-check-order`; the later active-probe
  dry-run proved that path now returns HTTP 404 in production, so the working
  tree follow-up corrects it to the current V5 precheck endpoint.
- Runtime calls the precheck before non-reduce-only Bybit entry exposure when
  the live adapter supports it.
- `110125`, `110126`, `110123`, and matching trading-terms text are classified
  through the existing deterministic admission contract.
- The block emits `runtime.entry_admission_blocked` with
  `source=pre_entry_bybit_precheck` and prevents maker dispatch.
- Reduce-only close, cancel, passive close, and residual repair paths are not
  changed by the precheck.
