## Cluster CL-093-confirmed-replay-fill-owner-terminalization

### GitNexus Keys

- Fingerprint: `pending-entry.confirmed-positive-fill-removal-before-finalization`
- Components: `pending-entry`, `startup-recovery`, `entry-reconciliation`, `v1-parity`, `lifecycle`
- Symbols: `LiveRuntime._reconcile_pending_entries_force`, `PendingEntryRuntime._reconcile_pending_state`, `PendingEntryRuntime._finalize_pending_entry`, `PendingEntry.has_any_fill`
- Files: `lightfee/engine/runtime.py`, `lightfee/engine/pending_entry_runtime.py`, `tests/test_pending_entry_v1_semantic_drift.py`
- Commits: baseline `e46fcf3`; deployed fix `3c42aea`
- Watch: `pending_entry.hedge_submit_result`, `entry.opened`, `pending_entry.removed_by_v1_lifecycle_closure`, `force_reconcile_pending_entry_resolved`, `pending_entry_reconcile_resolved`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Summary

A deterministic local replay showed that a journal-confirmed, fully matched
hedge fill could be restored with `uncertain_outcome=false` and then be removed
by either startup force reconciliation or the normal runtime tick. The removal
occurred before the existing V1-style finalizer created `OpenPosition` or
recorded `entry.opened`. This is a lifecycle-owner loss; it is not an exchange
or a new cloud incident claim.

### Root Cause

The two direct-removal gates used `not pending.uncertain_outcome` as though it
proved terminality. That field only describes submit certainty. Journal replay
can make a positive maker or hedge fill certain while the pending entry still
owns exposure that must be reconciled against exchange truth and finalized,
residualized, or retained fail-closed.

### V1 / Exchange Decision

- V1 reference: `src/execution_core/entry_sync.rs` finalizes a pending entry
  after balanced truth is established; it does not discard the pending owner
  merely because prior submit/fill evidence is certain.
- Exchange truth remains authoritative for live positions and order/fill
  reconciliation. This local regression uses synthetic adapter truth and does
  not submit, cancel, or mutate any exchange order.
- Rejected direction: do not add a separate replay-only state or special-case
  journal branch. The common ownership rule is positive fill -> reconciliation
  -> V1 finalizer/residual/fail-closed decision -> removal only after terminality.

### Attempts

| Attempt | Status | Why |
|---|---|---|
| Journal replay restored confirmed quantities but left `uncertain_outcome=false` | partial / ineffective | The restored quantity was correct, but both removal gates interpreted certainty as permission to delete the owner. |
| Require known zero fill for the existing direct-removal fast path | deployed; cloud health verified | Full and partial known fills now enter the existing reconciliation/finalizer path; no new parallel lifecycle is introduced. Commit `3c42aea` is live; a new replay-fill production trigger has not occurred in the deployment window. |

### Fix

Both startup and normal reconciliation now use the same direct-removal rule:
only a known zero-fill pending entry can bypass exchange reconciliation. Every
pending entry with any fill, including a journal-confirmed partial or full
hedge fill, remains owned until the existing finalizer opens managed state,
creates residual work, or defers/fails closed. The shared finalizer continues
to provide the single terminality decision.

### Root Cause and Fix

The lifecycle table is the shared V1 compatibility projection used by runtime,
state export, production health, and diagnose. It had an incomplete explicit
map for current production event kinds. The missing entries created false
operational drift (`unmapped_event_kinds`) but did not alter order submission,
close execution, recovery ownership, or risk gates. This cluster completes the
projection rather than adding a parallel lifecycle path.

For Hyperliquid, an adapter returning `None` was previously cached as a
successful result even though the caller immediately treated it as unavailable.
That lost the failure classification in the cache and made a later successful
fresh fetch impossible to correlate with the earlier degradation. The fix stores
`(False, "hyperliquid_account_balance_unavailable")` for that branch. A later
fresh success after an expired cached failure emits
`runtime.entry_admission_venue_recovered` with the prior timestamp, duration,
truncated prior error, source and availability flag. The new event is also
`DIAGNOSTIC_ONLY`, preventing this observability improvement from creating a
new unmapped-event regression.

## Cluster CL-095-passive-close-billing-recovery-symbol-and-joint-entry-grid

### Scope and Evidence

Read-only production review found three connected lifecycle defects. They are
local code defects, not a claim that an exchange misreported a fill:

| Finding | Sufficient evidence | Root decision |
|---|---|---|
| A normal passive close emitted `exit.passive_close_resolved` after both legs were flat, but emitted neither `exit.closed` nor `exit.billing_evidence_unavailable` | The event is intentionally operational-only and is excluded from ledger-close projection. The resulting position bill stayed open despite a completed close. | Root fix is required in the passive-close terminal writer, not in projection or diagnose. |
| Exchange truth proved both legs and open orders flat, but the local passive close carried no usable close order/client-order identity | Local state was removed and lifecycle terminal events were written, while reconciliation could not produce a venue statement or a terminal billing event. | Write the existing provisional `exit.billing_evidence_unavailable` terminal instead of silently treating state cleanup as a financial close. |
| OKX returned `HOME-USDT-SWAP` while local state stored `HOMEUSDT`, producing an orphan/unpaired live-position decision | V2's owner keys uppercased raw strings but did not apply the already-defined venue symbol conversion on the exchange/local comparison boundary. | Canonicalize symbols per venue only when building/comparing recovery identity keys. Unknown formats remain raw and fail-closed. |
| A maker filled `5146` while the corresponding OKX hedge was normalized to `5100`, creating a `46` residual repair | V2 planned from a preliminary common amount but did not incorporate the hedge's min-notional chunk and both legs' quantity grids before the maker order. V1 plans a hedgeable chunk before maker submission. | Plan on the least common executable quantity step, align the V1 hedgeable minimum chunk to that joint grid, and use the plan's full target as both order quantities. |
| OKX quantity planning accepted `ctVal × lotSz` but omitted `ctVal × minSz` | A base quantity below OKX `minSz` could pass entry planning and later normalize the hedge to zero at the transport boundary. | Require dynamic `ctVal`, `lotSz`, and `minSz` together in live contract metadata; convert both step and minimum into canonical base quantity before maker submission. |

`risk.warning_triggered` and `risk.warning_cleared` were also valid normal
risk snapshots but absent from the V1 lifecycle mapping. They now map to
`OPEN_POSITION`; this changes no risk gate, warning threshold, or action.

### Fix

- Passive close writes `exit.closed` exactly once only after both local legs are
  zero and no residual task was created. The payload contains the complete
  position accounting totals, close-leg fill identity, and
  `terminal_accounting_status=final`. If entry-fee evidence is unavailable it
  writes the existing `exit.billing_evidence_unavailable` terminal path rather
  than inventing a final bill. If exchange truth is flat but no close order
  identity is available for venue reconciliation, it writes that same terminal
  as `provisional_close_execution_evidence_unavailable`, with no `net_quote`
  and the flat-truth evidence attached.
- Recovery converts an exchange wire symbol through that venue's registered
  `symbol_from_venue` converter only for owner-key construction and comparison.
  It does not broaden owner matching for an unknown venue/symbol.
- Entry dispatch obtains existing per-venue quantity metadata before execution
  planning, derives a rational least-common grid (for example `0.002` and
  `0.003` require `0.006`), and supplies V1's planner with the joint minimum
  hedgeable chunk. For OKX it requires `ctVal`, `lotSz`, and `minSz`, converts
  both the grid and minimum to base quantity, and fails closed if either is
  absent. A `5300` raw amount with a `100` grid and a `150 / 1.4` notional
  floor now submits `5200` on both legs, not an unhedged `5146/5100`.
- Snapshot fallback, stale quote, and risk-snapshot anomalies were reviewed but
  not behaviorally changed: their current event payloads already preserve
  observed time/age, fallback source, targeted revalidation result, and
  supported/stale risk-side state. They remain fail-closed until a
  venue-specific root cause is evidenced.
