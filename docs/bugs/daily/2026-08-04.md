## Cluster CL-093-confirmed-replay-fill-owner-terminalization

### GitNexus Keys

- Fingerprint: `pending-entry.confirmed-positive-fill-removal-before-finalization`
- Components: `pending-entry`, `startup-recovery`, `entry-reconciliation`, `v1-parity`, `lifecycle`
- Symbols: `LiveRuntime._reconcile_pending_entries_force`, `PendingEntryRuntime._reconcile_pending_state`, `PendingEntryRuntime._finalize_pending_entry`, `PendingEntry.has_any_fill`
- Files: `lightfee/engine/runtime.py`, `lightfee/engine/pending_entry_runtime.py`, `tests/test_pending_entry_v1_semantic_drift.py`
- Commits: baseline `e46fcf3`; deployed fix `3c42aea`
- Watch: `pending_entry.hedge_submit_result`, `entry.opened`, `pending_entry.removed_by_v1_lifecycle_closure`, `force_reconcile_pending_entry_resolved`, `pending_entry_reconcile_resolved`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Summary

A deterministic local replay showed that a journal-confirmed, fully matched
hedge fill could be restored with `uncertain_outcome=false` and then be removed
by either startup force reconciliation or the normal runtime tick. The removal
occurred before the existing V1-style finalizer created `OpenPosition` or
recorded `entry.opened`. This is a lifecycle-owner loss; it is not an exchange
or a new cloud incident claim.

### Root Cause

The two direct-removal gates used `not pending.uncertain_outcome` as though it
proved terminality. That field only describes submit certainty. Journal replay
can make a positive maker or hedge fill certain while the pending entry still
owns exposure that must be reconciled against exchange truth and finalized,
residualized, or retained fail-closed.

### V1 / Exchange Decision

- V1 reference: `src/execution_core/entry_sync.rs` finalizes a pending entry
  after balanced truth is established; it does not discard the pending owner
  merely because prior submit/fill evidence is certain.
- Exchange truth remains authoritative for live positions and order/fill
  reconciliation. This local regression uses synthetic adapter truth and does
  not submit, cancel, or mutate any exchange order.
- Rejected direction: do not add a separate replay-only state or special-case
  journal branch. The common ownership rule is positive fill -> reconciliation
  -> V1 finalizer/residual/fail-closed decision -> removal only after terminality.

### Attempts

| Attempt | Status | Why |
|---|---|---|
| Journal replay restored confirmed quantities but left `uncertain_outcome=false` | partial / ineffective | The restored quantity was correct, but both removal gates interpreted certainty as permission to delete the owner. |
| Require known zero fill for the existing direct-removal fast path | deployed; cloud health verified | Full and partial known fills now enter the existing reconciliation/finalizer path; no new parallel lifecycle is introduced. Commit `3c42aea` is live; a new replay-fill production trigger has not occurred in the deployment window. |

### Fix

Both startup and normal reconciliation now use the same direct-removal rule:
only a known zero-fill pending entry can bypass exchange reconciliation. Every
pending entry with any fill, including a journal-confirmed partial or full
hedge fill, remains owned until the existing finalizer opens managed state,
creates residual work, or defers/fails closed. The shared finalizer continues
to provide the single terminality decision.

## Cluster CL-096-pending-close-reconciliation-ack-truth-gap-billing-loop

### Scope and Evidence

Read-only local investigation of production events for HFTUSDT and COTIUSDT
Bybit positions. Each position had `kind=accepted_order_truth_gap` entries in
`pending_close_reconciliations` that CloseRuntime routed through the billing
(financial) reconciliation pipeline. When fill evidence was incomplete, this
emitted `exit.billing_unreconciled` in an infinite loop because:

1. A prior `exit.reconciled(final=true)` had already been emitted for the
   position.
2. The ACK truth-gap task remained in the queue (it was never resolved as an
   order-truth task — billing can't close uncertainty about whether an ACK
   became a fill).
3. Each processing cycle found incomplete billing evidence and emitted another
   `exit.billing_unreconciled`.
4. `exit.reconciled` couldn't clear subsequent `billing_unreconciled` because
   the ACK task was financially unaddressable.

Two production-diagnose false-greens masked this:
- **False-green #1 (temporal)**: The "any terminal event" set cleared
  `billing_unreconciled` events regardless of chronological order. A
  `billing_unreconciled` emitted AFTER a terminal `exit.reconciled` was
  treated as resolved.
- **False-green #2 (queue blind spot)**: Diagnose only read
  `pending_close_count` (counts pending closes, NOT reconciliation
  queue). Queue had 2 items while `pending_close_count` was 0.

### Root Cause

`_process_pending_close_reconciliations` treated all reconciliation kinds
uniformly, routing `accepted_order_truth_gap` through the same fill-fetch +
billing pipeline as `final` tasks. There was no three-layer separation
between physical terminal, order truth, and financial terminal.

### Fix

**local root fix; deploy pending; no cloud verification; no remote mutation.**

| Layer | Change | File |
|---|---|---|
| Routing | Split `order_truth_eligible` (kind=accepted_order_truth_gap) from `billing_eligible` (kind=final/partial). Order-truth tasks go exclusively through `_resolve_accepted_order_truth_gap` / `_probe_accepted_order_truth`. | `lightfee/engine/close_runtime.py` |
| Order-truth resolution | `_resolve_accepted_order_truth_gap`: terminal-flat supersede → shared-ledger identity probe → retain/backoff. When terminal-flat probe is unavailable, falls through to identity truth (was early-return → infinite retain). | `lightfee/engine/close_runtime.py` |
| Ledger-based identity probe | `_probe_accepted_order_truth` routes every unique (order_id, client_order_id, venue) through `ORDER_TRUTH_LEDGER.resolve_order_success()`. Only `terminal_fill` (CONFIRMED_FILL from confirmed execution source) resolves. Weak evidence (ACK, order detail, open/new), zero-qty, and unavailable responses all retain. Any unavailable identity blocks resolution — a fill on one leg is not permission to discard uncertainty on another. | `lightfee/engine/close_runtime.py` |
| State export | `EngineState.to_dict()` exports `pending_close_reconciliation_summary` (total_count, by_kind, backed_off_count, unknown_status_count). | `lightfee/engine/state.py` |
| Diagnose temporal ordering | `terminal_close_ts_by_position` tracks max timestamp per position. `billing_unreconciled` resolved only by terminal event at-or-after its timestamp. | `scripts/diagnose_live.py` |
| Diagnose queue gate | Reads `pending_close_reconciliation_summary` from authoritative state. Non-empty queue → gate blocked. Previously read `pending_close_count`. | `scripts/diagnose_live.py` |
| Event mappings | `exit.accepted_order_truth_gap_resolved` / `superseded` / `registered` mapped to PASSIVE_CLOSE. | `lightfee/engine/v1_lifecycle_closure.py` |

### Contract

- **Three-layer non-confusion**: physical terminal (positions zero + no open orders) → order truth (confirmed execution fill per identity) → financial terminal (evidence-complete final bill). These layers do not collapse.
- **ACK truth-gap → never billing**: `accepted_order_truth_gap` tasks never emit `exit.billing_unreconciled` or `exit.reconciled`. They are resolved/superseded exclusively through terminal-flat evidence or ledger-confirmed execution fills.
- **Weak evidence → retain**: ACK-only, order-detail-only, open/new status, zero-qty responses, and unavailable adapters all retain the task with backoff.
- **Mixed evidence → fail-closed**: A confirmed fill on one leg identity does not excuse unavailable truth on another. All identities must pass the ledger gate.
- **No identity-only no-fill**: Absent/zero-fill is never resolved by per-identity probe alone; it requires the remote terminal-flat + no-open-order probe as its exclusive resolving path.
- **COTI Bybit110017 terminal-zero**: Preserved unchanged.
- **No new parallel structures**: No new state machine, worker, config item, retry policy, data table, or large refactor.
