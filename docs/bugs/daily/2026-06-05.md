`docs/superpowers/specs/2026-06-05-exchange-truth-recovery-ledger-v1-parity-design.md`
and
`docs/superpowers/plans/2026-06-05-exchange-truth-recovery-ledger-v1-parity-implementation-plan.md`.
It is not a new CL-specific patch. The same production family now routes
through one ledger boundary:

|---|---|---|

### Root Cause

Previous fixes closed correct local branches for CL-048 / CL-049 / CL-050, but
the runtime still lacked the V1 structural ownership model. Exchange truth was
available to diagnostics and production verifier after the fact, while normal
runtime decisions could still treat empty local collections as sufficient.
That made `local open_positions=[]`, `pending_entries=[]`, and live exchange
artifacts an unhealthy split instead of first-class runtime recovery work.

### Fix

- Added sanitized incident fixtures for the current `TRXUSDT` local-flat/live
  open maker order and the historical `SEIUSDT` positive-fill local false-flat
  shape.
- Added `lightfee/engine/recovery_ledger.py`, a pure classifier that converts
  local work plus normalized exchange truth into recovery work items such as
  `orphan_maker_order`, `unpaired_live_position`,
  `owned_pending_entry`, `pending_residual_repair`,
  `pending_passive_close`, `ambiguous_exchange_truth`, and proven-flat states.
- Added `lightfee/engine/exchange_truth.py` so `diagnose_live.py`,
  `verify_production_services.py`, and runtime-adjacent checks share one
  normalized payload shape with probe evidence and `truth_available`.
- Added `lightfee/engine/recovery_owner_index.py` to map live orders and
  positions to proven/probable owners and leave insufficient evidence as orphan
  recovery work.
- Added `lightfee/engine/pending_entry_terminalizer.py` as the pure
  pending-entry terminality decision surface.
- Wired `LiveRuntime` with a recovery-ledger refresh helper, a ledger entry gate,
  and a shared post-terminal pending-entry removal helper. A grep now shows
  `state.pending_entries.pop()` only inside that helper.
- Updated production health so local flat plus live non-reduce open orders is a
  critical exchange-truth mismatch with `live_open_order` evidence, not green
  health.

### Summary

This is not a new independent CL bug. It is a V1 completeness follow-up for the
CL-048 / CL-049 / CL-050 pending-entry live-truth contract after post-deploy
review showed the same family producing repeated pending churn and quick
abort/cleanup windows.

The production evidence mapped to existing contract semantics:

| Evidence | Contract row | V1 decision |
|---|---|---|
| Hyperliquid insufficient margin after maker exposure on `WLDUSDT`, `XLMUSDT`, `MONUSDT`, and `MOVEUSDT` | `PE-11` | Treat as deterministic admission evidence; after the first proof, block new entries through the exhausted venue before maker submit. |
| `XLMUSDT` pending work could be followed by another same-symbol candidate with a venue overlap | `PE-17` | V1 pending-entry protection blocks same pair and same symbol with either venue overlapping until pending work terminalizes or cleanup proves flat. |
| `_finalize_pending_entry()` can defer because fill price/order/live truth is incomplete | `PE-18` | A deferred finalizer is retained pending work, not a resolved entry; callers must not append resolved ids or pop state. |
| Force-terminal zero-fill could bypass finalizer event semantics | `PE-13` | Even force-terminal zero-fill must route through the V1 finalizer, emit terminal no-fill evidence, and preserve positive/live evidence if discovered. |
| Post-deploy diagnose saw local flat but Bybit still had one non-reduce-only `TRXUSDT` open maker order | `PE-02`, `DG-02` | Live open-order truth blocks production acceptance. Do not call the system healthy until the open order is gone or owned recovery evidence closes it. |

### Root Cause

| Issue | Classification | Root cause |
|---|---|---|
| Hyperliquid margin reject only blocked the current symbol | V1/exchange admission scope drift | `Insufficient margin` proves account/venue capacity, not just a single symbol hedge. New candidates could still route through Hyperliquid and rediscover the same reject after maker exposure. |
| Same-symbol pending protection was narrower than V1 | V1 pending gate drift | V2 only blocked the exact long/short venue pair. V1 also protects the same symbol when either venue overlaps. |
| Deferred finalizer result was not a formal caller contract | Terminality boundary drift | `_finalize_pending_entry()` could return early on incomplete evidence, while callers historically treated the call shape as completion. |
| Force-terminal zero-fill had a direct pending removal branch | V1 terminality drift | V1 terminal maker state still goes through finalization/fallback/cooldown evidence; it is not a blind local pop. |

### Fix

- Hyperliquid insufficient-margin admission now writes both symbol and
  `hyperliquid:*` venue cooldown keys, and candidate admission blocks later
  Hyperliquid routes before maker submit.
- `has_pending_entry_for_symbol()` now matches V1 pending protection: exact pair
  or same symbol with either venue overlapping. Runtime now reports
  `pending_entry_protection`.
- `_finalize_pending_entry()` now returns `bool`. `True` means terminal
  open/residual/passive-unfilled evidence was emitted. `False` means the entry is
  still pending because live truth or fill details deferred finalization.
- Runtime callers that previously finalized then resolved/popped now check the
  boolean result. Deferred paths retain pending work and apply reconcile backoff.
- Force-terminal zero-fill now routes through `_finalize_pending_entry()`, so
  zero-fill completion emits `entry.passive_unfilled` /
  `pending_entry.pending_entry_finalized`, while positive/live evidence still
  blocks removal.

### Post-deploy Acceptance Blocker

Deployment itself completed, but production acceptance is not closed. The
service-env diagnose after deployment found high-confidence exchange truth with
no nonzero positions on all seven venues, but Bybit still had one
non-reduce-only open maker order:

| Venue | Symbol | Order id | Side | Quantity | Price | Reduce-only |
|---|---|---|---|---:|---:|---|
| Bybit | `TRXUSDT` | `a84df707-efb3-4e40-bab1-641a4eb0f3d4` | Buy | `72.0` | `0.33044` | false |

Read-only event review shows this order was created by the pre-deploy run:
`entry-1780595698673-TRXUSDT` selected Bybit/Hyperliquid passive entry at
`2026-06-05T01:55:00+08:00`, Bybit accepted maker order `a84df707...`, and V2
deferred maker progress because live Bybit position truth was present while
order terminality was uncertain. A second overlapping `TRXUSDT` pending entry
then appeared before the new V1 pending-protection code was deployed; that
second maker order filled, Hyperliquid hedge hit insufficient margin, and the
runtime submitted reduce-only cleanup for the Bybit exposure.

After the `3af002d` restart, local state settled to open/pending/close/residual
`0/0/0/0`, but the original Bybit open maker order remained visible to
credentialed exchange truth. No manual cancel, order submit, or runtime-state
edit was performed during this deployment. This maps to `PE-02` and `DG-02`: a
local-flat state with a live open order is not production healthy.

### Acceptance

Accepted locally and deployed to cloud at `3af002d`, but production acceptance
remains blocked by the Bybit `TRXUSDT` live open maker order above. Future
production recurrence in this family must map to the contract matrix first; if
`PE-11`, `PE-17`, or `PE-18` still pass locally and production truth is flat, do
not change runtime code. If the open-order blocker remains, resolve it through
operator-approved order handling or a RED-test-backed owner-recovery path, not a
local state edit.
