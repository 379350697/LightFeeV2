# Bug Ledger - 2026-08-01

## Cluster CL-173 - Selection Edge-Floor Evidence Lost Real BBO Without an L2 Lease

Status: local root fix verified; corrective deployment and natural-window proof pending

### Evidence and Root Cause

The same natural production candidate window that exposed CL-172 emitted
`runtime.funding_entry_reprice_blocked` for
`final_expected_edge_below_floor`. The economics inputs and thresholds were
recalculable, but both-leg BBO, aligned quantity, and final price evidence were
reported as zero whenever Local-L2 had not yet produced a final quote lease.

The selection repricer had already fetched valid market BBO and aligned the
requested quantity before calling the economics revalidator. Its evidence
builder nevertheless read every price and the aligned quantity exclusively
from the optional Local-L2 lease. This was an evidence-path implementation gap,
not permission to treat BBO as final Local-L2 depth or to weaken the final
dispatch gate.

### Root Fix

1. When a selection-stage economics rejection has no Local-L2 lease, preserve
   the actual two-leg market BBO, observation times, candidate revision, and
   aligned/final quantities in a clearly labelled
   `selection_market_quote_bbo` evidence object.
2. Keep L2 VWAP, capacity, and completeness explicitly unavailable/false; do
   not manufacture depth or call BBO a VWAP.
3. Emit separate fields for selection-BBO completeness, final execution quote
   availability, whether final L2 evidence is required at this stage, and
   whether evidence is complete for the selection-stage decision.
4. The final submission path remains fail-close and still requires its normal
   Local-L2 execution lease; no threshold, TTL, skew, or depth rule changes.

### Regression Proof and Remaining Boundary

A live-mode regression with Local-L2 enabled but no available L2 lease now
proves actual BBO/final prices, `0.47 -> 0.4` requested/aligned/final quantity,
the selection evidence source, and honest unavailable L2 fields. The existing
L2-complete economics proof remains green. Corrective deployment must reproduce
an economic blocker with nonzero BBO evidence, or naturally advance past that
stage; no order is submitted merely to generate proof.

## Cluster CL-172 - Post-Bridge Binance/Aster Range Check Reintroduced False Gaps

Status: local root fix verified; corrective deployment and natural-window proof pending

### Evidence and Root Cause

The 30-minute production acceptance window for `0606ab47`/`228bbce` reached a
natural funding candidate and repeatedly rebuilt Binance `BANKUSDT`. Every
captured event had an exact continuous WebSocket link (`raw_pu` equaled the
previous accepted `raw_u`), while `raw_U` was greater than `previous_u + 1`.
The same false rejection occurred during buffered replay after a valid REST
snapshot bridge. Gate did not reproduce this fingerprint after its separate
`with_id=true` snapshot fix.

This was not the historical CL-004 overflow/freshness problem and was not an
exchange gap. Commit `0606ab47` correctly introduced a one-generation
`U <= snapshot+1 <= u` bridge, but also applied that range predicate to every
subsequent Binance/Aster update. Binance USD-M and the approved V1 contract use
the range only for the REST-to-WS bridge; after the bridge, the authoritative
continuity rule is `pu == previous_u`. The earlier V2 hot path already followed
that split, which is why this exact fingerprint was absent before `0606ab47`.

### Root Fix

1. Keep the first snapshot bridge strict: the first accepted update must cover
   the snapshot boundary by `U/u`.
2. After the bridge, Binance/Aster accept an update only when `pu` is present
   and equals the previous accepted `u`; do not repeat the bridge range test.
3. Apply the same split to buffered replay: first replayed update uses `U/u`,
   later updates use strict `pu` linkage.
4. Preserve fail-close behavior for missing/mismatched `pu`, stale updates,
   old generations, and Gate's independent range-only contract.

### Regression Proof and Remaining Boundary

Production-shaped direct-HOT and buffered-replay samples cover Binance and
Aster with exact `pu` plus an advanced `U`, and retain the real `pu` mismatch
rebuild regression. The Local-L2 phase suite passes (`292 passed`); the full
entry/finalization phase suite passes (`737 passed, 10 skipped`); GitNexus
reports three changed files, three affected bootstrap flows, and MEDIUM risk in
the intended Local-L2 scope.

Corrective deployment must show that the BANKUSDT-style false-gap fingerprint
stops in a natural candidate window while real `pu` mismatches still rebuild.
Final strategy acceptance still requires a natural screen-to-close lifecycle;
no order is submitted merely to prove this fix.
