Cloud run `lightfee-1779546833786-1438044` had a stale local LYNUSDT passive close:

- V2 local `hedge_fill.quantity` stayed `0`, so live retried the same Bybit close and repeatedly got `retCode=110072`, `OrderLinkedID is duplicate`

### V1 Comparison

V1 has the missing behavior in two places:

- Bybit adapter recovers duplicate passive order ids by querying `/v5/order/realtime` with `orderLinkId`.
- Passive close hedge submit errors call `fetch_order_fill_reconciliation(symbol, "", hedge_client_order_id)` before treating the hedge as failed.

V2 had this V1 duplicate-client-id reconciliation in `CloseExecutor._submit_close_leg_with_retry`, but passive close hedge bypassed that path and called `adapter.place_order()` directly inside `PassiveCloseExecutor._submit_hedge_for_delta`. That was the drift.

### Shared Root Cause

V2 copied the aggressive close reconciliation behavior but did not copy it into the passive close hedge path. The same Bybit duplicate `orderLinkId` error meant "this client id already produced an order; reconcile it" in V1, but meant "hedge failed; retry later" in V2 passive close.

A second state-shape gap made the recovered production state harder to finalize: the pending record had cumulative `maker_fill` but no persisted `long_legs` / `short_legs`. Finalization based only on persisted legs could remove the pending record without decrementing `open_positions`. V2 now synthesizes missing close legs from cumulative pending fills when finalizing, so recovered state can be closed consistently.

### Fix Status

Fixed, deployed, and cloud verified.

- `_submit_hedge_for_delta()` now reuses the Bybit duplicate-orderLinkId detector and calls `adapter.fetch_order_fill_reconciliation(symbol, "", hedge_cid)` on submit errors.
- If reconciliation returns positive quantity, V2 records the hedge fill, persists the close leg, emits `exit.passive_close_hedge_duplicate_client_order_reconciled`, and returns success instead of `exit.passive_close_hedge_error`.
- Generic submit errors also get one V1-style reconciliation attempt by client id before being treated as failed.
- `_finalize_passive_close()` synthesizes missing persisted close legs from cumulative `maker_fill` / `hedge_fill` when recovered state has fills but empty leg arrays.
- Existing live-flat fallback remains the final guard: if local pending state is stale and both venues report flat, V2 clears pending/open state with `exit.passive_close_fallback_terminal_flat`, `recovery.flat`, and `runtime.position_drift_corrected`.

### Summary

After the passive-close fix deployment, the latest cloud audit no longer showed entry-blocked local-L2 selection recurrence and did not open new positions. The remaining local-L2 noise had two distinct classes:

- Dropped-pool books were retained in V2 runtime state and could be rebuilt by `sync_snapshots(scan_promoted=True)` once stale.
- Real exchange sequence gaps on Binance/Aster were handled correctly by rebuilding, but the diagnostic payload captured `status_before` after the transition and did not include enough sequence-domain evidence to prove whether a future recurrence is an exchange gap or local replay drift.

### V1 Comparison

Rust V1 does not treat `Dropped` local-L2 books as a passive cache. Books outside the active tracked/execution scope are pruned or retained only within an explicit retained budget. V2 created books during dynamic tracked-candidate activation but left their assignment as `DROPPED`, so stale HOT monitoring later rebuilt books V1 would have removed.

For sequence continuity, V1 and exchange documentation agree on the current rebuild rule for Binance/Aster range updates: if the incoming `previous_sequence` link does not match the book sequence and the update range does not bridge the expected sequence, the book must rebuild. The gap logic is not relaxed; only evidence logging was corrected.

### Shared Root Cause

V2's activation path started WS/bootstrap work but skipped the V1 assignment/retention side effect. That let runtime books survive with `book.pool=dropped`. Later, data-plane snapshot sync scanned all books during the post-shortlist phase and treated stale dropped HOT books as rebuild targets.

The sequence-gap observation was a different problem: the logic was correct for the observed Binance/Aster mismatches, but `_rebuild_evidence()` defaulted `status_before` from the already-transitioned book state. That made production audit evidence ambiguous.

### Fix Status

Fixed, deployed, and short-window cloud verified.

- `_ensure_l2_active_for_candidates()` now assigns tracked primary legs to `HOT_EXEC` and tracked shadow legs to `WARM`, refreshing leases on every activation tick.
- Execution-owned open positions, pending entries, and pending passive closes are included in the tracked key set so pruning does not remove active work.
- `LocalL2Runtime.prune_untracked_books()` removes untracked `DROPPED` books and prunes stale/over-budget `RETAINED` books.
- `LocalL2DataPlane.prune_untracked_books()` clears matching WS workers, snapshot state, buffered updates, and stream generation state, then emits `runtime.local_l2_books_pruned`.
- `sync_snapshots()` skips `DROPPED` books, so dropped cache entries cannot be demoted/rebuilt by stale HOT monitoring.
- `runtime.local_l2_hot_stale_rebuild` now records pre/post status and pool evidence.
- `runtime.local_l2_sequence_gap_rebuild` now records pre-transition status, post-transition status, pool before, expected sequence, incoming first sequence, policy buffer cap, and buffered sequence bounds.

### Summary

The 2026-05-24 OKX/residual audit found multiple V2 drifts that were masked by local tests but unsafe in live semantics:

- OKX REST positions in `posSide=net` used `abs(pos)`, so a net short could be parsed as BUY.
- OKX taker/passive order sizing treated engine base quantity and OKX derivative contract quantity too loosely; `base_qty / ctVal` could floor to zero contracts and still send `sz="0"`.
- OKX private WS defaulted missing `ctVal` to `1.0`, which could cache SWAP contract counts as base size.
- OKX passive cancel used a generic `DELETE spec.order_path`, producing the documented live `405` / `50115` failure class.
- V2 residual repairs were primarily startup-driven, so runtime `pending_residual_repairs` could remain queued without V1 attempt/deadline/dust terminal behavior.
- Entry sizing could create unavoidable residuals when an OKX SWAP leg required a coarser `ctVal * lotSz` base step than the other leg.

### V1 And Exchange-Doc Comparison

Rust V1 `src/live/okx.rs` treats OKX SWAP/FUTURES/OPTION order `sz` as contracts: base quantity is divided by `ctVal`, floored by `lotSz`, then validated before send. `validate_okx_order_request` rejects `contracts <= 0` locally. V1 position fetch preserves net-mode sign and multiplies signed contracts by `ctVal`.

The official OKX v5 docs confirm the same exchange semantics:

- `POST /api/v5/trade/cancel-order` is the single-order cancel endpoint.
- order `sz` for `FUTURES`/`SWAP`/`OPTION` is contract quantity.
- instrument `lotSz` and `minSz` are contract counts for derivatives.
- in net mode, positive `pos` means long and negative `pos` means short.

Rust V1 `src/execution_core/residual.rs` drives `process_pending_residual_repairs` as normal runtime work, not only startup recovery, and terminalizes dust/deadline/attempt-exhausted tasks instead of letting them hang forever.

### Shared Root Cause

V2 had copied OKX field names and broad residual concepts but lost two unit boundaries:

- Engine quantities are canonical base quantities; OKX derivative wire quantities are contracts.
- Private WS positions are only trustworthy after `ctVal` is known; a fallback `1.0` is not a safe default for known SWAP instruments.

The residual issue had the same shape at runtime level: V2 persisted pending residual tasks, but the normal tick loop did not continuously drive the V1 residual state machine.

### Fix Status

Fixed locally after post-review corrections. ### Summary

The post-fix review found four Hyperliquid/V1-parity gaps and one test-suite acceptance gap:

- Hyperliquid IOC cleanup / compensation orders with `price=None` were locally rejected, while V1 fetches a market snapshot and derives an IOC limit price from best bid/ask.
- `_finalize_pending_entry()` computed `residual_task` and `balanced_quantity` before final order-fill reconciliation. If reconciliation changed either leg quantity, V2 could queue a stale residual or miss a real one.
- Hyperliquid rounding initially avoided Python bankers rounding but still used Decimal string rounding, which did not match Rust V1 `f64::round()` on binary floating-point boundary cases such as `1.005` and `0.145`.
- Hyperliquid API-wallet configuration remains a fail-closed boundary: read-only account state does not prove an API wallet is authorized to trade for a different account address.
- After the local fixes, broad acceptance still fails in three pre-existing Hyperliquid fixture contract tests because those tests call `place_order()` without `price` / `price_hint` and mock only `place_order_success`. The new V1-equivalent path first requests `POST /info {"type":"l2Book"}` before exchange submit, so the old fixture mock is incomplete.

### V1 And Exchange-Doc Comparison

Rust V1 `src/live/hyperliquid.rs` resolves IOC order reference price by:

- using a valid `price_hint` when provided;
- otherwise fetching a market snapshot and calling `quote_fill`;
- then applying the V1 IOC slippage factor and `round_to_significant_and_decimal`;
- formatting wire price/size through `float_to_wire_string`.

V1 rounding uses Rust `f64::round()`, so V2 must operate on Python floats before applying half-away-from-zero rounding. Decimal string rounding is intentionally not equivalent for all V1 boundary vectors.

Hyperliquid official docs describe API wallets / agent wallets as a valid signer model, where the signer may differ from the account address. This working-tree fix does not implement authoritative API-wallet authorization verification; it deliberately fails closed when signer and account differ.

### Shared Root Cause

V2 had treated Hyperliquid "market-like" IOC as if a caller must always provide a positive price. That broke runtime cleanup paths that intentionally construct reduce-only IOC requests with `price=None`, relying on adapter-level quote fallback as in V1.

The entry-finalize bug had a different root: order-fill reconciliation was allowed to mutate pending fill quantities after residual computation. That made residual repair state depend on stale pre-reconciliation values.

The rounding bug was a parity trap: fixing Python bankers rounding with Decimal `ROUND_HALF_UP` still did not reproduce V1 because Rust rounds the already-represented binary `f64` value.

### Fix Status

Fixed locally, but acceptance is still blocked by three fixture contract tests.

- `VenueTransport.place_order()` for Hyperliquid now resolves asset metadata, uses `price_hint` / `mark_price_hint` / `price` when valid, otherwise fetches `l2Book` and uses best ask for BUY or best bid for SELL.
- If the L2 fallback is unavailable or the required side is empty, the order is locally rejected with diagnostics and no exchange submit.
- Hyperliquid IOC price/size now use V1-style slippage, significant-digit rounding, decimal rounding, and wire formatting.
- `_finalize_pending_entry()` calls `_ensure_pending_entry_open_fill_details()` before building fills, residual tasks, and `balanced_quantity`.
- Reconciliation can update pending quantity, price, and order id; residual repair and journal payloads are computed from the updated pending state.
- Hyperliquid direct wallet account preflight can trust `account==signer`; unverified API-wallet mode is explicit fail-closed with `api_wallet_authorization_unverified`.
- Remaining test work: update `tests/test_venues_contract.py` Hyperliquid fixture tests so no-price orders either provide an L2 fixture response before exchange response, or provide a positive `price` / `price_hint` when the test is not about fallback.

## 2026-06-10 HOMEUSDT OKX/Bybit Quantity Contract Drift

### Incident Chain

Production HOMEUSDT showed an entry sizing split that looked like "OKX more 10":

- Candidate raw quantity was about `720.569`.
- OKX HOMEUSDT SWAP can only trade whole contracts; with `ctVal=100` and `lotSz=1`, the maker leg executed `700` base units.
- Bybit was later hedged for `690`, so the local open position used `matched_quantity=690`.
- The extra OKX `10` became an entry residual repair. OKX normalized that residual to `0`, so it was terminalized as `exchange_min_quantity_dust` and later passive close live truth flattened the real exposure.

The root cause was not "close failed". The entry quantity chain did not enforce one non-drifting common executable quantity from raw candidate sizing through planner full target, initial maker target, pending target, and missing hedge.

### V1 / Exchange Rules

- V1 aligns both venues to a common executable quantity before opening; matched position quantity and residual repair are separate state.
- Bybit V5 instruments expose `lotSizeFilter` fields such as `minOrderQty`, `qtyStep`, and `minNotionalValue`.
- OKX V5 derivatives use contract `sz`; SWAP/FUTURES notional depends on `ctVal`, and valid size increments are governed by `lotSz`. For OKX SWAP entry sizing, V2 must convert `ctVal * lotSz` into a base-quantity step.

### Root Fix

- `lightfee/engine/runtime.py` now records `execution.entry_quantity_plan` with `raw_quantity`, `common_quantity`, venue quantity steps, planner `full_target_quantity`, and `initial_maker_target_quantity`.
- Entry dispatch now skips with `runtime.entry_skipped_quantity_metadata_missing` when either venue lacks executable entry quantity metadata. For non-OKX venues this requires positive `quantity_step`, positive `min_quantity`, and present non-negative `min_notional`; for OKX SWAP this requires confirmed `ctVal * lotSz` base step.
- When OKX contract step participates in entry sizing, passive incremental initial maker target is pinned to the common full target instead of being clipped into a later 700/690 split.
- `_drive_missing_hedge_live()` and `_recover_drive_missing_hedge()` now first normalize the full missing hedge quantity. If the hedge venue accepts `700`, V2 submits `700`; it only undercuts after exchange normalization/min-notional evidence and emits `pending_entry.hedge_quantity_undercut`.
- Entry residual dust tolerance is limited to unrepairable dust: `execution.entry_residual_dust_tolerated` is emitted only for `origin=entry_open`, `exchange_min_quantity_dust` / `exchange_min_notional_dust`, a known matched open position, and residual ratio `<=5%`.
- `scripts/diagnose_live.py` now reports `entry_residual_dust_tolerated_count`, `hedge_quantity_undercut_count`, `common_quantity_mismatch_count`, and `lifecycle_release_not_applied_count`. `common_quantity_mismatch_count` only treats common-vs-full target divergence as a quantity contract mismatch; normal passive incremental initial/full splits are not counted as abnormal.
