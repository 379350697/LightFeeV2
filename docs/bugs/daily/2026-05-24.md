### Summary

Cloud run `lightfee-1779546833786-1438044` had a stale local LYNUSDT passive close:

- `position_id=entry-1779551578130-LYNUSDT`
- long Binance, short Bybit, `matched_quantity=534`
- maker fill was already recorded on Binance: `order_id=1513843783`, `quantity=534`
- Bybit hedge order with `client_order_id=lfexfff815be1265da8d` was already filled on exchange: `orderId=95dbe960-6b01-4259-958b-02ef11bb6dbc`, `cumExecQty=534`, `avgPrice=0.04508`
- V2 local `hedge_fill.quantity` stayed `0`, so live retried the same Bybit close and repeatedly got `retCode=110072`, `OrderLinkedID is duplicate`

Read-only exchange probes showed Binance and Bybit LYNUSDT positions were already zero and open orders were zero. The risk was local state drift plus repeated duplicate reduce-only submissions, not an actual open exchange position.

### V1 Comparison

V1 has the missing behavior in two places:

- Bybit adapter recovers duplicate passive order ids by querying `/v5/order/realtime` with `orderLinkId`.
- Passive close hedge submit errors call `fetch_order_fill_reconciliation(symbol, "", hedge_client_order_id)` before treating the hedge as failed.

V2 had this V1 duplicate-client-id reconciliation in `CloseExecutor._submit_close_leg_with_retry`, but passive close hedge bypassed that path and called `adapter.place_order()` directly inside `PassiveCloseExecutor._submit_hedge_for_delta`. That was the drift.

### Shared Root Cause

V2 copied the aggressive close reconciliation behavior but did not copy it into the passive close hedge path. The same Bybit duplicate `orderLinkId` error meant "this client id already produced an order; reconcile it" in V1, but meant "hedge failed; retry later" in V2 passive close.

A second state-shape gap made the recovered production state harder to finalize: the pending record had cumulative `maker_fill` but no persisted `long_legs` / `short_legs`. Finalization based only on persisted legs could remove the pending record without decrementing `open_positions`. V2 now synthesizes missing close legs from cumulative pending fills when finalizing, so recovered state can be closed consistently.

### Fix Status

Fixed, deployed, and cloud verified.

- `_submit_hedge_for_delta()` now reuses the Bybit duplicate-orderLinkId detector and calls `adapter.fetch_order_fill_reconciliation(symbol, "", hedge_cid)` on submit errors.
- If reconciliation returns positive quantity, V2 records the hedge fill, persists the close leg, emits `exit.passive_close_hedge_duplicate_client_order_reconciled`, and returns success instead of `exit.passive_close_hedge_error`.
- Generic submit errors also get one V1-style reconciliation attempt by client id before being treated as failed.
- `_finalize_passive_close()` synthesizes missing persisted close legs from cumulative `maker_fill` / `hedge_fill` when recovered state has fills but empty leg arrays.
- Existing live-flat fallback remains the final guard: if local pending state is stale and both venues report flat, V2 clears pending/open state with `exit.passive_close_fallback_terminal_flat`, `recovery.flat`, and `runtime.position_drift_corrected`.
