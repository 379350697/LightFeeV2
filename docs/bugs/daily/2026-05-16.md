### Shared Root Cause

The current V2 live entry gate copied the visible V1 local-L2 safety labels but not the full V1 readiness propagation and diagnostics loop.

- local-L2 book lifecycle and venue-specific faults,
- entry-local-L2 session per-leg ready/fault/arming state,
- no-entry diagnostics that explain why primary tracked pairs are not ready.

V2 currently has these pieces partially split across modules, but the bridge from `LocalL2Runtime` books to `EntryLocalL2SessionRuntime` legs is missing or insufficiently observable. As a result, the existing safety gate can correctly refuse to trade while giving operators only coarse reasons.

### Issue CL-001-A: Entry Local-L2 Dual-Ready Is Not Runtime-Driven

#### Fingerprint

`production.entry-local-l2.dual-ready-never-driven`

#### Root Cause

`LiveRuntime._entry_local_l2_selection_blocker()` requires the candidate pair to have a session and `session.both_legs_ready()`. `EntryLocalL2SessionRuntime.track_opportunity()` creates/updates session legs, but tracking itself only sets `last_seen_at_ms`; it does not mark legs ready from local-L2 book state. `LocalL2DataPlane.bootstrap_book()` can apply a snapshot and transition a book to HOT, but the entry session leg does not receive that readiness.

#### Failed / Ineffective Attempts

The prior root-fix loop closed candidate identity/prewarm label issues, but production after 5.15 still showed `entry_local_l2_waiting_for_dual_ready` because the data-plane-to-session readiness bridge was not proven on the real path.

#### Fix Status

Partial/local fixed. Implemented:

- pure book-to-leg readiness mapper in `lightfee/engine/entry_local_l2.py`;
- `LiveRuntime` calls readiness refresh after local-L2 sync and before `_entry_local_l2_selection_blocker()`;
- missing/stale/degraded/crossed/bootstrapping books remain blocked with stable reason/detail fields;
- default entry local-L2 stale window now falls back to `300_000ms` unless `entry_local_l2_book_stale_after_ms`, `local_l2_quiet_book_grace_ms`, or `local_l2_max_age_ms` is explicitly configured;
- `runtime.entry_local_l2_readiness_diagnostics` and V1-style `scan.no_entry_diagnostics` are emitted locally.

Not closed: production code has not been deployed and current production dry-run evidence could not be collected due SSH connection failure.

### Issue CL-001-C: Exchange Order Path Risks Remain Behind the Current Gate

#### Fingerprint

`exchange-ack-fill-shared-risk.after-l2-unblocks`

#### Root Cause

Historical logs before the 5.15 filter showed exchange-layer failures: ACK-only or no-fill responses, Binance signature invalid, Hyperliquid/Aster signing dependency missing, precision errors, and insufficient available balance. These did not occur after 5.15 because no entry reached submission, but they are likely to reappear once local-L2 readiness is fixed.

Official exchange docs confirm that REST ACK/order id and final fill are separate for multiple venues.

#### Failed / Ineffective Attempts

Treating submit response as immediate fill is ineffective across Bybit, Bitget, Aster, Binance, OKX, Gate, and Hyperliquid. Retrying uncertain submits with new client order IDs would risk duplicate live orders.

#### Fix Status

Partial/local fixed:

- REST ACK-only remains uncertain and is not treated as fill;
- live startup emits sanitized `startup.order_path_preflight` for adapter signing/dependency visibility;
- `VenueTransport.place_order()` performs fail-closed quantity/price precision and min-notional preflight before live submit;
- sanitized `order.submit_attempt` / `order.submit_result` diagnostics include venue, symbol, endpoint/product type/category, client/order ids, raw and quantized price/qty, tick/step, and response classification;
- `EntrySyncExecutor` flushes adapter order diagnostics into the journal;
- `OrderReconciler` records sanitized `order.reconcile_result` diagnostics for reconcile probes;
- tests cover Gate integer contract size, Bybit tick/step, Binance/Aster step/tick, ACK-not-fill, and startup preflight redaction.

Open residual:

- Account/margin/leverage admission precheck is not root-fixed. The current code does not have enough reliable per-venue available/headroom evidence in this patch to block dual-leg notional before dispatch without risking false positives. This remains open and must be closed with risk/account snapshot evidence before marking the order path fully fixed.
- Production startup/order preflight logs are not verified because the code has not been deployed and SSH dry-run failed.
