### Summary

After the 2026-05-18 `book_hot`/`stale_hot_book` state-machine root fix (CL-002-B round 1), the remaining dominant blockers were `book_bootstrapping` (4,588), `book_rebuilding` (131), `book_timestamp_missing` (24), `book_empty_side` (139). These are data-plane class issues — the book lifecycle (bootstrap, rebuild, timestamp propagation) and readiness diagnostics.

This round fixes four confirmed V1→V2 drift points (Phase A), plus a Phase B correction found during acceptance review: `transition_to_bootstrapping()` was unconditionally clearing `fault_reason`, which broke the REBUILDING→BOOTSTRAPPING→`apply_book_readiness_to_leg` chain and caused `arming_reason` to always fall back to `BOOK_STATUS_TRANSITION`.

**Production status**: All fixes are local only. Production cloud runs `6c954d6` (deployed 2026-05-17). These fixes have NOT been deployed, sidecar/live have NOT been restarted, and production impact cannot be verified. Post-deploy verification must use absolute-path logs: `/opt/lightfee-v2/runtime/live-events.jsonl`.

### Shared Root Cause

V2 data-plane code matched V1's surface structure but drifted in three key areas:

1. **arming_reason was always BOOK_STATUS_TRANSITION**: V1's `ensure_candidate()` maps prior `EntryLocalL2LegFault` → specific `SessionArmingReason` (StaleBook→StaleBookRecovery, GateObuGap/OkxPrevSeqMismatch/OkxChecksumMismatch→SequenceGap, HyperliquidDisconnect→TransportFaultRecovery). V2's `apply_book_readiness_to_leg` always used `BOOK_STATUS_TRANSITION`, making it impossible to distinguish "book bootstrapping because of a sequence gap" from "book bootstrapping because it was just created".

2. **fault_reason not set on runtime failures**: V1's `session_fault_from_local_l2_event()` carries a specific fault detail string to the leg. V2's `handle_runtime_failure()` for SEQUENCE_GAP and CHECKSUM_MISMATCH only incremented metrics counters without setting `book.fault_reason`. This meant entry-L2 diagnostics couldn't report WHY a book was rebuilding.

3. **rebuild transitions missing fault_reason**: Multiple code paths triggered `book.transition_to_rebuilding()` without first setting `book.fault_reason` — the pre-snapshot buffer overflow in `ingest_external_update`, and four replay-buffer failure sites in `_replay_buffered_updates`. This meant `book_rebuilding` appeared in diagnostics without a clear trigger.

### Issue CL-002-B-round-2-DP-1: arming_reason always BOOK_STATUS_TRANSITION

#### Fingerprint

`v2.data-plane.arming-reason-no-bootstrap-context`

#### Root Cause

Two-phase root cause:

**Phase A** (initially confirmed): `apply_book_readiness_to_leg()` always called `leg.mark_arming(SessionArmingReason.BOOK_STATUS_TRANSITION)` for books in bootstrapping/rebuilding/cold/resume_waiting status.

**Phase B** (found during acceptance review): `transition_to_bootstrapping()` unconditionally cleared `self.fault_reason = ""`. Combined with the bootstrap worker calling `transition_to_bootstrapping()` on REBUILDING books, this erased the `fault_reason` that DP-2/DP-3 had written. The real production path REBUILDING → BOOTSTRAPPING → `apply_book_readiness_to_leg` always saw empty `fault_reason`, causing `arming_reason` to fall back to `BOOK_STATUS_TRANSITION`.

V1's `ensure_candidate()` maps prior `EntryLocalL2LegFault` → specific `SessionArmingReason`:
- StaleBook → StaleBookRecovery
- GateObuGap / OkxPrevSeqMismatch / OkxChecksumMismatch → SequenceGap
- HyperliquidDisconnect → TransportFaultRecovery
- CrossedOrLockedBook → BookStatusTransition
- None → FirstSession

#### Fix Status

Fixed in working tree (two commits):

1. New `_derive_arming_reason_from_book()` helper maps `book.fault_reason` keywords to specific `SessionArmingReason`
2. **`transition_to_bootstrapping()` no longer clears `fault_reason`** — preserves it so `apply_book_readiness_to_leg` can derive correct arming_reason
3. `transition_to_hot()` still clears `fault_reason` — the book has recovered
4. 7 real-path regression tests added covering REBUILDING(fault)→BOOTSTRAPPING→readiness for: sequence_gap, checksum_mismatch, transport_failure, stale_hot_book, buffer_overflow, HOT recovery, cold clean start

### Issue CL-002-B-round-2-DP-2: handle_runtime_failure does not set fault_reason

#### Fingerprint

`v2.data-plane.fault-reason-not-set-on-handle-runtime-failure`

#### Root Cause

`LocalL2Runtime.handle_runtime_failure()` incremented metrics counters for SEQUENCE_GAP, CHECKSUM_MISMATCH, TRANSPORT_FAILURE, RATE_LIMITED, and RESUME_EXPIRED, but did not set `book.fault_reason`. Without `fault_reason`, `apply_book_readiness_to_leg` and readiness diagnostics had no context for why the book was in its current state.

#### Fix Status

Fixed in working tree. `handle_runtime_failure` now sets `book.fault_reason` for all fault types:
- RATE_LIMITED: `rate_limited: {detail}`
- TRANSPORT_FAILURE: `transport_failure: {detail}`
- CHECKSUM_MISMATCH: `checksum_mismatch: {detail}`
- SEQUENCE_GAP: `sequence_gap: {detail}`
- RESUME_EXPIRED: `resume_expired: {detail}`
- QUOTE_AGE_TRIGGERED: already set via `transition_to_degraded(f"quote_age: {detail}")`
- BUDGET_SUSPENDED: already set via `transition_to_suspended("budget")`
- RUNTIME_SUSPENDED: already set via `transition_to_suspended("runtime")`
