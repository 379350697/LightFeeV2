## Cluster CL-002-D-maker-rejected-pending-v1-parity-drift

### GitNexus Keys

- Fingerprint: `v2.entry-sync.maker-rejected-created-pending.reconcile-position-hydrated-false-maker-progress`
- Components: `entry-sync`, `live-runtime`, `order-reconciliation`, `pending-entry`, `v1-parity`
- Symbols: `EntrySyncExecutor.execute`, `EntrySyncExecutor._make_pending_entry`, `LiveRuntime._dispatch_entry`, `LiveRuntime._reconcile_pending_state`
- Files: `lightfee/engine/entry_sync.py`, `lightfee/engine/runtime.py`, `tests/test_entry_sync.py`, `tests/test_runtime_entry_flow.py`, `tests/engine/test_v1_real_config_gap_semantics.py`
- Commits: N/A (working tree, not yet committed)
- Watch: `order.rejected`, `runtime.pending_entry_registered`, `runtime.rejected_pending_suppressed`, `reconciliation.rejected_pending_cleared`, `reconciliation.rejected_pending_retained_with_fill`, `pending_entry.maker_progress_applied`, `pending_entry.missing_hedge_detected`, `entry.abort_failed_pending_retained`

### Summary

Production showed a deterministic maker reject followed by a pending/reconcile loop. The representative chain was: `order.rejected` on maker with margin insufficient, then `runtime.pending_entry_registered` with `outcome=rejected`, then reconcile hydrated `pending_entry.maker_progress_applied` from venue position snapshot, then `pending_entry.missing_hedge_detected`, hedge deadline breaches, cleanup attempts, and repeated `entry.abort_failed_pending_retained`.

This was a V2 state-machine drift from V1. V1 treats deterministic `SubmitFailureClass::Rejected` as terminal and not exposure-bearing. Only uncertain submit failures may have created exposure.

### Root Cause

`EntrySyncExecutor.execute()` created `PendingEntry(outcome="rejected")` for maker reject. `_make_pending_entry()` also marked every non-`filled` outcome as `uncertain_outcome=True`, so `rejected` entered the reconciliation lane. `LiveRuntime._dispatch_entry()` registered any non-null pending entry without checking whether the execution was terminal. Then `LiveRuntime._reconcile_pending_state()` could hydrate maker fill from account-level position snapshots and drive hedge/cleanup against a pending entry that V1 would never have created.

V1 references checked during investigation:

- `order_error_may_have_created_exposure()` returns true only for `SubmitFailureClass::Uncertain`.
- deterministic `SubmitFailureClass::Rejected` rotates client order id but does not mark exposure.
- passive incremental entry constructs `PendingEntryHedge` only after maker `Ok(ack)`, not after initial maker reject.

### Fix Status

Fixed locally.

- Removed pending creation and `entry.aborted_failed_pending_retained` emission from maker rejected path.
- `_make_pending_entry()` now treats exact `outcome="rejected"` as non-uncertain.
- `LiveRuntime._dispatch_entry()` suppresses any defensive rejected pending instead of registering it.
- `LiveRuntime._reconcile_pending_state()` clears zero-fill rejected pending before any venue position snapshot hydration.
- If a rejected pending already has fill evidence, reconcile retains it and logs `reconciliation.rejected_pending_retained_with_fill` for manual recovery instead of hydrating/driving hedge from the rejected state.

### Issue CL-002-B-round-2-DP-1: arming_reason always BOOK_STATUS_TRANSITION

#### Fingerprint

`v2.data-plane.arming-reason-no-bootstrap-context`

#### Root Cause

Two-phase root cause:

**Phase A** (initially confirmed): `apply_book_readiness_to_leg()` always called `leg.mark_arming(SessionArmingReason.BOOK_STATUS_TRANSITION)` for books in bootstrapping/rebuilding/cold/resume_waiting status.

**Phase B** (found during acceptance review): `transition_to_bootstrapping()` unconditionally cleared `self.fault_reason = ""`. Combined with the bootstrap worker calling `transition_to_bootstrapping()` on REBUILDING books, this erased the `fault_reason` that DP-2/DP-3 had written. The real production path REBUILDING → BOOTSTRAPPING → `apply_book_readiness_to_leg` always saw empty `fault_reason`, causing `arming_reason` to fall back to `BOOK_STATUS_TRANSITION`.

V1's `ensure_candidate()` maps prior `EntryLocalL2LegFault` → specific `SessionArmingReason`:
- StaleBook → StaleBookRecovery
- GateObuGap / OkxPrevSeqMismatch / OkxChecksumMismatch → SequenceGap
- HyperliquidDisconnect → TransportFaultRecovery
- CrossedOrLockedBook → BookStatusTransition
- None → FirstSession

#### Fix Status

Fixed in working tree (two commits):

1. New `_derive_arming_reason_from_book()` helper maps `book.fault_reason` keywords to specific `SessionArmingReason`
2. **`transition_to_bootstrapping()` no longer clears `fault_reason`** — preserves it so `apply_book_readiness_to_leg` can derive correct arming_reason
3. `transition_to_hot()` still clears `fault_reason` — the book has recovered
4. 7 real-path regression tests added covering REBUILDING(fault)→BOOTSTRAPPING→readiness for: sequence_gap, checksum_mismatch, transport_failure, stale_hot_book, buffer_overflow, HOT recovery, cold clean start
