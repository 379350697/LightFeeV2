## CL-137 — Snapshot recovery replayed retained audit history as live work

Status: **deployed-awaiting-verification at `0e0cc7a`**. This repair changes
recovery interpretation only; it does not submit, cancel, or otherwise mutate
exchange state.

- Card: [recovery-snapshot-journal-boundary](../cards/recovery-snapshot-journal-boundary.md)

### Evidence and authoritative contract

A production-shaped zero-current-state snapshot plus the retained
`live-events.jsonl` history recreated 29 stale `pending_entries` and put
startup into `reconciling`. The retained journal had about 117k records / 80
MiB and its sequence values restarted across process runs, so `seq` cannot be
a durable checkpoint. Separately, a V1 lifecycle closure emitted
`pending_entry.removed_by_v1_lifecycle_closure`, but V2 replay had no inverse
handler for it. The same historical pending-owner records also expanded the
startup symbol-probe set.

V1 recovery semantics make a durable snapshot the recovery-state boundary;
exchange account truth remains authoritative for live exposure. Therefore a
normal restart must restore the snapshot and replay only durable events written
after it. A restart with no usable snapshot retains the V1-compatible emergency
full-journal recovery path. A legacy snapshot or missing/unprovable checkpoint
must never fall back to the entire retained audit log: restore the snapshot and
let existing account-wide exchange truth reconcile or fail closed.

### Root repair

Every production state snapshot now carries the journal file identity and byte
offset captured at its write boundary, including the runtime and the shared
operator-control CLI writer. Recovery reads the contiguous retained journal
tail after that marker, including a rotation chain; if continuity is not
provable, it reads no historical records. The journal's terminal pending entry
closure now removes its prior pending owner during replay. Startup owner
indexing applies the same exact pending-entry closure filter, so cleared owner
records cannot make old symbols trigger per-symbol recovery queries. It
deliberately keeps terminal close order evidence available for outstanding
accounting reconciliation.

This is an incremental **state-recovery** cursor, not a full-history polling
scheme: normal startup has one snapshot plus its bounded tail. It deliberately
does not use journal `seq`, which is process-local and has reset in production.

### Rejected repair patterns

- Do not full-scan retained audit history on every startup.
- Do not use `seq` alone as a cross-run cursor or add a parallel checkpoint
  store.
- Do not suppress all post-snapshot events: the crash window needs its tail.
- Do not merely add a terminal clear event while continuing to replay history
  from before the snapshot.
- Do not add a side snapshot writer without recording the same journal
  checkpoint; its later tail would otherwise be silently skipped as legacy.
- Do not suppress terminal close order evidence: a flat position can still
  have a legitimate exact-fill/fee accounting debt.
- Do not add per-debt, per-symbol, or venue-specific cleanup to compensate for
  the broken recovery boundary.

## CL-136 — Aster V3 one-way history row was misclassified as `no_candidate`

Status: **deployed-awaiting-verification at `079601f`**. This repair made no
production state, service, order, cancellation, or exchange mutation.

### Evidence and authoritative contract

The outstanding `entry-1787773965760-ONGUSDT` final accounting debt is
physically flat on both venues. Its Aster close leg has a unique read-only
exchange history record:

- V3 `GET /fapi/v3/userTrades` returns one `ONGUSDT` `BUY`, `positionSide=BOTH`
  execution for order `19932399`, client ID `lfex5432933e299cf15e`, quantity
  `149`, price `0.1569400`, quote fee `0`, and timestamp `1787774707050`.
  The row has no `reduceOnly` key.
- Exact V3 `GET /fapi/v3/order` for the same order returns `FILLED`,
  `reduceOnly=true`, matching side, identity, executed quantity, and average
  price. This is the proof that the one-way execution belongs to the close.

The automatic cleaner must never turn a weak history row into accounting
evidence. A history row may identify one bounded candidate only; settlement
requires the existing exact order recheck to prove identity, `FILLED`,
reduce-only ownership, quantity, price, and supported quote fees. This retains
the V1-compatible boundary: exchange-flat truth removes exposure, while exact
execution evidence owns financial accounting. Aster documents user-trade
history through [its API documentation](https://docs.asterdex.com/product/asterex-pro/api/api-documentation); the production V3 wire shape above is the
authoritative compatibility evidence.

### Root cause and affected path

CL-129 correctly added strict Aster V3 discovery but used the same
`_aster_history_row_closes_position_side` predicate for both candidate rows
and exact order rows. For `positionSide=BOTH`, that predicate demanded
`reduceOnly=true`. Since the actual `userTrades` row omits the field, its sole
candidate was discarded before the exact `/order` request. The runtime then
persisted generic `no_candidate`, marked the debt terminal, and the normal
automatic cleaner had no reason to revisit it.

The complete affected path is `CloseRuntime` final evidence debt →
`AsterAdapter.discover_historical_close_fill_reconciliation` → V3
`userTrades` candidate parser → exact V3 `/order` proof → existing billing
reconciliation. It affects only automatic Aster historical close accounting;
it does not affect open/close order submission, risk positions, or physical
flatness checks.

### Root repair and bounded migration

`find_aster_v3_historical_close_order_candidates` now accepts an omitted
`reduceOnly` value solely while identifying a `positionSide=BOTH` candidate.
The exact-order recheck still calls the predicate in strict mode, so
`reduceOnly=false`, missing, malformed, wrong side, non-`FILLED`, quantity or
identity mismatch cannot settle a debt.

The corrected scan reports `aster_v3_no_candidate` rather than generic
`no_candidate`. `CloseRuntime` reactivates only a legacy automatic final debt
whose terminal reason is generic `no_candidate` and whose nonzero legs include
Aster with implemented discovery. It runs once: a corrected scan with no
candidate records `aster_v3_no_candidate`, which remains terminal. Capability
upgrade reactivation for the existing `history_discovery_unsupported` contract
is unchanged. If an older persisted debt lacks `evidence_debt_reason`, the
same canonical debt predicate is saved during this narrow reactivation; without
that normalization the following billing pass would incorrectly treat the
record as operator-only. This is a data-compatible migration, not a new retry
loop.

### Rejected repair patterns

- Do not trust a user-trade row as proof, infer `reduceOnly`, or accept an
  explicit `false`/malformed value as a candidate.
- Do not remove the exact `/order`, `FILLED`, identity, quantity, price, or fee
  checks; do not infer a fee conversion.
- Do not reopen every terminal debt, ambiguous/incomplete outcomes, non-Aster
  debt, or a corrected-scan miss.
- Do not manually delete or mark the production ONG debt settled; deployment
  must let the same automatic read-only path resolve it.
- Do not add a polling worker, broad time window, fuzzy matcher, order retry,
  or venue-specific billing path.
