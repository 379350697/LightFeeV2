## Cluster CL-077: HOME lifecycle quick-flat recurrence

### GitNexus Keys

  `quick_flat_terminal_kind_counts`, `quick_flat_events_present`

### Production Symptom

Rotated production logs showed 27 HOMEUSDT `entry.opened` events and no clean
normal open/close lifecycle. Each HOME lifecycle included at least one abnormal
semantic: recovery flat, drift correction, residual repair, one-sided flatten,
missing L2/tick evidence, or exchange-error reconciliation. Several short
chains looked like local `entry.opened` followed about 18-22 seconds later by
drift/recovery flat.

### Root Cause

CL-064, CL-066, CL-067, and CL-076 fixed important pieces, but HOME proved the
same lifecycle still had split terminality:

- `summarize_quick_flat_events()` counted only `exit.closed`, so
  `entry.opened -> recovery.flat` and `entry.opened ->
  runtime.position_lifecycle_terminal` were invisible to the production
  quick-flat gate.
- `_finalize_pending_entry()` passed `PendingEntryLiveTruth(available=True)` for
  balanced positive fills, so matched local/reconciled fill evidence could emit
  `entry.opened` even when current live position truth was flat.
- `build_v1_lifecycle_closure_table()` used the terminalizer but did not require
  positive-fill pending rows to agree with live position truth, so ops surfaces
  could still present a locally terminal positive fill as a closure row when
  exchange truth was flat.

### Fix

- Quick-flat analysis now treats `recovery.flat` and
  `runtime.position_lifecycle_terminal` as terminal projections alongside
  `exit.closed`, deduplicated per position lifecycle, and exposes
  `quick_flat_terminal_kind_counts`.
- Live pending-entry finalization now probes positive-fill live truth in live
  mode. A balanced positive fill requires current non-flat live position truth
  before creating `OpenPosition` and emitting `entry.opened`; live-flat truth
  emits `pending_entry.positive_fill_live_truth_conflict`, retains pending, and
  backs off for reconciliation/recovery.
- `PendingEntryLiveTruth` carries
  `positive_fill_requires_live_position`, so runtime and lifecycle closure use
  the same terminalizer outcome instead of path-specific local conditions.
- The V1 lifecycle closure table now passes that positive-fill/live-position
  requirement for pending rows, keeping diagnose/production-health aligned with
  runtime terminality.

### Non-Changes

- No symbol-specific HOME freeze.
- No order submit, cancel, close execution, residual repair submission,
  strategy threshold, quantity sizing, OI/liquidity filter, WS-BBO/Local-L2
  budget, credential, or production config change.
- Bybit `110017`, Bybit `110072`, missing L2/tick, passive-close fallback, and
  residual repair remain their existing contracts; this fix ties their lifecycle
  evidence into the shared pending/recovery/diagnose gate rather than treating
  one retCode as the root.

## Cluster CL-076: V1 lifecycle closure table runtime gate/release unification

### GitNexus Keys

  `v1-lifecycle-closure-table-runtime-gate-release-unification +
  scattered-pending-passive-residual-recovery-semantics`
- Components:
  `live-runtime`, `v1-parity`, `pending-entry`, `passive-close`,
  `residual-repair`, `recovery-core`, `current-state`, `diagnose-live`,
  `production-health`
- Symbols:
  `build_v1_lifecycle_closure_table`, `entry_gate_from_closure`,
  `closure_event_fields`, `_refresh_v1_lifecycle_closure_state`,
  `_gate_recovery_ledger`, `_remove_pending_entry_after_terminal_decision`,
  `_terminalize_residual_repair_task`,
  `_emit_passive_close_terminal_resolution`, `_clear_live_flat_state`
- Watch:
  `v1_lifecycle_closure`, `closure_decision_id`,
  `unmapped_event_kinds`, `entry_allowed`, `recovery_block_policy`,
  `pending_entry.removed_by_v1_lifecycle_closure`,
  `exit.passive_close_resolved`, `execution.residual_repair_terminal`,
  `execution.entry_residual_dust_tolerated`, `recovery.ledger_blocked`,
  `recovery.ledger_clear`, `recovery.flat`,
  `runtime_progress.active_lane_overdue`,
  `performance_scope.full_universe_hot_path_detected`

### Production Symptom

The recent production fixes closed real issues, but their semantics were still
spread across several local decision sites: WS-BBO quote lease scope,
pending-entry terminality, passive-close live-flat resolution, residual dust
terminality, recovery block/clear, diagnose, and production health. That made a
future drift plausible even when every individual fix was correct: one path
could decide "flat", another could decide "clear", and a third could decide
"entry allowed" without all of them sharing the same V1 owner/evidence row.

### Root Cause

The code already had good V1-compatible pieces:

- `PendingEntryTerminalizer` for pending-entry terminal removal.
- `V1RecoveryDecisionCore` and `RecoveryLedger` for recovery truth.
- Residual dust rules that separate exchange-min dust from abnormal residuals.
- Passive-close terminal-flat paths that converge on exchange truth.
- WS-BBO primary+shadow scope fixes that keep execution-grade market data out
  of full-universe hot paths.

The remaining gap was architectural: runtime, diagnose, health, and event
surfaces could still independently reinterpret those facts. That is how fixes
become additive but not compositional.

### Source Truth

- V1 compatibility-sensitive trading semantics are authoritative for recovery,
  passive close, residual repair, pending terminality, and live-position truth.
- Exchange truth outranks local recovered state.
- Pending entry removal must pass through the terminalizer or equivalent
  terminal proof; live open order/live position/positive-fill evidence cannot be
  swallowed by local stale cleanup.
- Passive close/recovery/residual release must be tied to terminal exchange
  truth or explicitly tolerated exchange-min dust.
- WS-BBO effective entry quote lease may replace Local-L2 as the evidence
  source, but it must keep V1 primary+shadow tracked scope, freshness
  fail-closed behavior, post-only guard semantics, and close-price evidence
  boundaries.

### Fix

- Added pure `lightfee/engine/v1_lifecycle_closure.py`.
- The table emits rows for:
  `ENTRY_QUOTE_LEASE`, `PENDING_ENTRY`, `OPEN_POSITION`,
  `PASSIVE_CLOSE`, `RESIDUAL_REPAIR`, `RECOVERY_TRUTH`,
  `RUNTIME_PROGRESS`, and diagnostic-only event families.
- Every row carries `row_key`, `phase`, `owner_id`, `evidence_class`,
  `terminality`, `entry_policy`, `recovery_policy`, `diagnostic_severity`,
  `v1_anchor`, `input_hash`, and `closure_decision_id`.
- Runtime current-state export now writes `v1_lifecycle_closure`.
- Diagnose and production health render or rebuild the same closure payload
  instead of independently deriving V1 business semantics.
- Runtime entry recovery gate now reads `entry_gate_from_closure()` from
  `closure.summary`, not direct ad hoc recovery ledger conditions.
- Recovery block/clear journal events include closure row identity.
- Pending entry removal emits
  `pending_entry.removed_by_v1_lifecycle_closure` with
  `closure_decision_id`.
- Residual terminal and tolerated entry dust events include the same closure
  decision identity.
- Passive close normal terminal resolution, live-flat fallback terminal,
  position lifecycle terminal, and `recovery.flat` carry the passive-close
  closure identity captured before local state is popped.
- Closure building can reuse the runtime-owned `RecoveryLedger` and
  `V1RecoveryDecisionCore` result. This avoids a real potential drift where a
  second owner-unaware projection could misclassify an owned live order as an
  orphan.
- Row-level incremental reuse preserves `closure_decision_id` for unchanged
  rows.
- Cloud follow-up fixed the exported-state alias gap by normalizing
  `positions` into `open_positions` before building diagnose fallback closure
  rows. Without this, a cloud current-state payload could lose local owner
  evidence and misclassify an owned live artifact as orphan drift.
- Cloud follow-up registered the remaining runtime/startup diagnostic event
  kinds as closure rows or diagnostic-only rows:
  `runtime.booting`, `runtime.started`, `runtime.private_ws_started`,
  `runtime.live_scan_revalidate_required`,
  `runtime.live_scan_recovery_warmup`, `runtime.reconciling`,
  `runtime.recovery_block_reconcile_attempt`,
  `startup.order_path_preflight`, `startup.trading_preflight`,
  `runtime.running`, `runtime.stopped`, `runtime.shutdown_stage`,
  `runtime.order_quote_stale_health_summary`, and
  `scan.no_entry_diagnostics`.
- Cloud follow-up registered active-window WS-BBO, scanner/catalog, liquidity,
  and private websocket stop events surfaced by docs-only and restart-window
  diagnose:
  `runtime.entry_quote_evidence_resolved_by_ws_bbo`,
  `runtime.order_quote_stale_skipped`, `runtime.quote_stale`,
  `runtime.ws_bbo_dynamic_ws_started`, `runtime.candidate_symbol_skipped`,
  `runtime.candidates_tradeable`,
  `runtime.tradeable_candidates_catalog_filtered`, `scan.shortlist_ready`,
  `execution.entry_liquidity_advisory`,
  `execution.entry_liquidity_blocked`, and `runtime.private_ws_stopped`.
  Quote/WS-BBO events map to `ENTRY_QUOTE_LEASE`; scanner/catalog/liquidity
  events map to `DIAGNOSTIC_ONLY`; private websocket stop maps to
  `RUNTIME_PROGRESS`.

### Non-Changes

- No order submit, order cancel, runtime-state mutation, strategy threshold,
  liquidity/OI filter, sizing, exchange credential, production config, WS-BBO
  budget/TTL, Local-L2 opt-in, close executor, residual repair submit, or
  recovery flatten policy changed.
- This is a semantic projection and gate/release adapter change, not a trading
  aggressiveness change.
- It does not claim mathematical "no漏洞"; the engineering contract is:
  no unmapped lifecycle events, no release path without a closure decision id,
  no entry/recovery gate bypassing the table, and no full-universe hot-path
  quote/freshness projection in WS-BBO effective mode.
