### Issue CL-001-A: Maker Fill Did Not Drive Missing Hedge on Normal Tick

#### Fingerprint

`production.pending-entry.maker-fill-without-hedge-drive`

#### Root Cause

`LiveRuntime._reconcile_pending_state()` reconciled pending entries but did not fully mirror V1's normal tick behavior: when maker fill evidence exists and hedge quantity is missing, V1 immediately drives the hedge delta and finalizes the pending entry when balanced. V2's recovery-only helper was not sufficient because normal live ticks after a maker fill still needed to submit and reconcile the hedge.

#### Failed / Ineffective Attempts

Passing tests around pending-entry fields or helper-level behavior was ineffective. The missing behavior only appeared when constructing the real `LiveRuntime + fake reconciler + fake hedge adapter` path and invoking `_reconcile_pending_state()`.

#### Fix Status

Fixed in `7792db5`.

- `LiveRuntime._reconcile_pending_state()` writes back maker/hedge fill quantities and prices from `OrderReconciler`.
- Missing hedge quantity triggers `_drive_missing_hedge_live()` during normal ticks.
- Filled hedges call `_finalize_pending_entry()`, emit `entry.opened` and `runtime.position_opened`, and remove the pending entry.
- Both long-maker and short-maker directions were directly reproduced.

### Issue CL-001-B: Hedge Inflight CID Was Not Stable or Venue-Legal

#### Fingerprint

`production.hedge-inflight-cid.invalid-or-not-reconciled`

#### Root Cause

The hedge submit path originally generated a raw CID from `entry_id` and timestamp. For real production entry IDs this could exceed venue constraints. After an uncertain hedge submit, the next reconcile pass also needed to query the same inflight CID; using the old hedge client order id would leave the submitted hedge untraceable and could allow duplicate hedge submission pressure.

#### Failed / Ineffective Attempts

Checking only that `hedge_inflight` exists was insufficient. The CID also had to be valid for the target venue, written to both `hedge_client_order_id` and `hedge_inflight`, retained on `UNCERTAIN`, cleared only on confirmed reject/fill, and used by subsequent reconcile calls.

#### Fix Status

Fixed in `7792db5`.

- Hedge CIDs use `generate_exchange_cid(entry_id, "h", hedge_venue)`.
- `_reconcile_pending_state()` and force reconcile prefer `pending.hedge_inflight or pending.hedge_client_order_id`.
- Uncertain submit retains inflight evidence; reject clears it.
- Duplicate submit is blocked while `hedge_inflight` is set.

#### Verification

|---|---|---|---|
| 2026-05-17 | local direct runtime probe | uncertain hedge submit, second reconcile | second query used `hedge_inflight`, hedge submit count stayed `1` |

### Issue CL-001-D: Venue Reconciliation and OKX Evidence Gaps

#### Fingerprint

`venue-reconciliation.hyperliquid-missing-fill-query + okx-posmode-contract-sizing-evidence`

#### Root Cause

Hyperliquid did not expose enough order-fill reconciliation to close uncertain hedge outcomes by `oid`/`cloid`. OKX order placement also needed V1-style account `posMode`, correct `posSide`, contract sizing by `ctVal`, and row-level `sCode`/`sMsg` evidence instead of only top-level submit status.

#### Failed / Ineffective Attempts

Treating exchange ACKs as final fills or only recording top-level response codes was not enough to diagnose production blockers. OKX `code=1 msg=All operations failed` without row details left root cause ambiguous.

#### Fix Status

- `HyperliquidAdapter.fetch_order_fill_reconciliation()` queries `orderStatus` by `oid` or `cloid`, then falls back to `historicalOrders`.
- Hyperliquid order actions carry `cloid`.
- OKX lazy-refreshes account `posMode`, derives `posSide`, converts base quantity to contracts with symbol rules, and records sanitized diagnostics.
- OKX posMode refresh failures emit `order.okx_pos_mode_refresh` diagnostic instead of silently disappearing.

1. **`_cleanup_failed_leg_exposure` uses market orders** — on illiquid markets, a market order may get poor fill or fail. The two-tier cleanup (cleanup → hard_stop → fail_closed) provides defense-in-depth but cannot guarantee flattening in all market conditions.
2. **Legacy inflight (submitted_at_ms=0) skips deadline** — old states migrated from string format cannot compute elapsed time. They rely on `_try_clear_stale_hedge_inflight()` to clear via triple-evidence check.
3. **No automated hedge for min-notional residuals** — entries with `repair_state=hedge_residual_below_min_notional` require manual review or aggregate/flatten logic (not yet implemented). They are safely parked, not silently dropped.
