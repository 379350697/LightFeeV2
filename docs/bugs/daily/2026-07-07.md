### Symptom

After CL-154, new passive-close order IO stopped creating fresh `"None"`
order identities, but SIREN could still remain in `risk_only` with a known
owner-managed single-leg exposure. The runtime blocked new risk, but a live
Bitget reduce-only close order was not adopted, so the existing exposure could
stay visible instead of being actively recovered.

### Root Cause

CL-154 fixed new identity pollution at ACK/cancel/detail/progress boundaries.
It did not migrate older persisted `PendingPassiveClose` state already holding
`maker_order_id="None"`, and reduce-only adoption still matched only the naked
internal side. That missed Bitget Classic hedge close-short semantics, where
V1 and Bitget contract semantics use internal `Side.BUY` to close a short while
the exchange open order appears as `side=sell` with `tradeSide=close`.

The result was a correct fail-closed gate with incomplete recovery ownership:
`risk_only` blocked new entries, but the owned passive-close single-leg was not
recognized as recoverable work and could be reported as ownerless.

### Unified Business Decision

- `risk_only` is a temporary "block new risk + active recovery pending" state,
  not a valid long-lived terminal state for known single-leg exposure.
- Persisted passive-close identities are normalized on snapshot load and before
  each passive-close tick. `None`, `"None"`, `"null"`, and blanks are absent;
  client ids are retained.
- Owner adoption first matches normalized order id/client id. If ids are
  missing, it may match only by consistent venue, symbol, close-only intent,
  side/position-side semantics, and sufficient quantity.
- Bitget Classic hedge close-short maps internal close `Side.BUY` to exchange
  `side=sell + tradeSide=close`. Bitget UTA hedge may use `posSide=short`
  with normal `side=buy`. Both are close intent; neither is entry admission.
- Once an owned one-sided close order is adopted and the fallback deadline is
  hard-breached, runtime cancels the adopted close order, proves it terminal
  and open-order-flat, then uses the existing reduce-only IOC one-sided
  flatten path. If truth is unavailable or another open order remains, it stays
  fail-closed and does not double-submit.

### Fix

- `PassiveCloseExecutor.process_pending_passive_closes` now sanitizes pending
  passive-close phase state, maker/hedge fills, and identity history before
  retry filtering, and emits `recovery.identity_sanitized`.
- Snapshot recovery now normalizes restored pending passive-close maker/fill
  identities and identity history, so diagnose and owner ledgers do not see
  legacy `"None"` values after restart.
- Reduce-only adoption is venue-aware: Bitget `tradeSide=close` counts as
  close-only even without a separate reduce-only flag, Bitget Classic side
  inversion is accepted for hedge close, and UTA `posSide` is checked against
  close intent.
- Owned one-sided passive-close recovery now adopts the matching close order
  before ownerless blocking. If the V1 fallback deadline is already breached,
  it cancels the adopted close order, confirms terminal order truth plus
  open-order-flat truth, then falls through to reduce-only IOC cleanup.
- Diagnose now exposes active-recovery counters:
  `passive_close_active_recovery_pending_count`,
  `passive_close_identity_sanitized_count`,
  `passive_close_owned_ioc_handoff_count`, and
  `passive_close_owned_ioc_blocked_count`.
