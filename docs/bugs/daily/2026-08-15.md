# Bug Ledger Daily - 2026-08-15

## Cluster CL-108-aster-v3-position-mode-and-market-result-contract

### Contract

Aster V3 private order submission and live-position truth must retain V1's
account-mode semantics while using V3 endpoints:

- one-way orders may use `reduceOnly`; Hedge orders must send the mapped
  `positionSide` and must not send `reduceOnly`;
- the mode is account-wide slow data, fetched from
  `GET /fapi/v3/positionSide/dual` once per private-client lifetime and
  fail-closed when its documented boolean evidence is absent;
- a V3 `MARKET` order requests `newOrderRespType=RESULT`, so the existing fill
  parser receives the documented final fill instead of default `ACK`;
- V3 `positionRisk` LONG/SHORT rows are netted once per symbol before V2
  recovery, residual repair, and reconciliation consume them.

Passive `LIMIT/GTX` remains on its existing acknowledgement workflow.  No
strategy, candidate screening, pricing, L2, position policy, retry policy, or
other venue behavior changes.

### Root Cause

The V3 migration moved Aster live order placement to `AsterV3Client`, but left
the V1-compatible position-mode cache and side mapping in the unused legacy
`VenueTransport` path.  Consequently a Hedge-mode account would submit an
invalid V3 order (missing `positionSide` and potentially carrying
`reduceOnly`).  The same client selected only the first `positionRisk` row,
which is not live-position truth in Hedge Mode.  Separately, the market submit
path accepted V3's default `ACK` even though its immediate parser requires
`executedQty`; that produced an avoidable accepted-but-unconfirmed fill.

Official V3 documentation establishes all three boundaries: the V3 mode
endpoint returns a boolean and has weight 30; `positionSide` is mandatory in
Hedge Mode while `reduceOnly` is forbidden there; `ACK` is the default but
`RESULT` returns the final `MARKET` fill.  V1's Aster adapter independently
confirms the same side mapping and LONG/SHORT netting semantics.

### Repair

- Added one lock-protected `AsterV3Client` mode cache sourced only from the V3
  endpoint, with the official request weight and account limiter scope.
- Applied the V1 mapping at the shared V3 parameter builder for both taker and
  passive orders; invalid mode evidence blocks submission before an order HTTP
  request.
- Added `RESULT` only to the existing taker `place_order` path, matching its
  fill contract without changing passive maker acknowledgement behavior.
- Reused the existing Binance-like position parser to aggregate all same-symbol
  V3 risk rows in both single-symbol and all-position reads.

### Counterexample Matrix and Local Evidence

| Boundary | Required result |
|---|---|
| one-way entry / one-way reduce close | no `positionSide`; preserve existing true-only `reduceOnly` shape |
| Hedge entry BUY/SELL | `LONG` / `SHORT`; no `reduceOnly` |
| Hedge reduce close SELL/BUY | `LONG` / `SHORT`; no `reduceOnly` |
| mode response absent or malformed | rejected before POST `/fapi/v3/order` |
| two `positionRisk` Hedge rows for one symbol | one V1-compatible signed net snapshot |
| MARKET order | no `timeInForce`, explicit `RESULT`, parsed fill |
| passive `LIMIT/GTX` | retains ACK behavior and gets Hedge `positionSide` |

The real `AsterV3Client -> signed httpx.MockTransport` regression covers each
mode/order combination, cache reuse, fail-closed mode evidence, `RESULT`, and
position aggregation.  The Aster transport/adapter/contract/rate-limit suite
passes `651` tests locally.  This is **implemented and locally validated**;
cloud deployment and read-only live verification remain required for closure.

- Cards: [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md), [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Contract and Root Cause

Four confirmed boundary drifts were repaired without changing screening, L2
policy, strategy thresholds, or recovery priority:

1. V2 charged the V1 hedge hard deadline from maker fill through local dispatch,
   so a 1.7 s scheduling delay could fail-close before the hedge request. V1
   starts it immediately before the concrete `execute_order_leg` call and
   evaluates after its terminal result, including any required fill
   reconciliation. V2 had frozen completion at the raw adapter return and also
   skipped the gate when reconciliation fully removed the local hedge gap.
2. The same close execution could persist twice when a later observation had
   the same exchange order ID but no CID. Order ID is the authoritative identity;
   CID is only a fallback when that ID is absent.
3. A terminal zero-fill cycle marked itself for repost, then same-tick normal
   reconciliation, startup recovery, or stale abandonment cleared the owner
   before its scheduled maintenance action.
4. Live Binance IOC limit pricing used the static fallback tick although the
   existing exchange-rule preflight already had the symbol's dynamic tick;
   low-priced symbols could be rejected locally before HTTP submission.

### Repair

- Retained one post-submit V1 deadline gate, now measured from the actual
  submitted quantity through the terminal adapter or reconciliation result;
  added maker-to-submit and submit-duration fields to the existing hedge-fill
  event, and removed obsolete pre-submit deadline checks. A fully reconciled
  fill is still evaluated; only compensation uses the remaining real gap.
- Canonicalized close identity as `(venue, order_id)` when present, otherwise
  `(venue, client_order_id)`, across persisted legs, reconciliation, and queue
  identity. Exact replay remains suppressed; a real partial/new fill remains
  distinct.
- Added one shared zero-fill-retry predicate used by normal reconciliation,
  startup force recovery, startup hedge recovery, and stale abandonment.
- Reused the existing Binance/Aster rule-preflight branch for live Binance;
  no new cache, configuration, or fallback was added.

### Counterexamples and Verification

| Boundary | Required result | Local evidence |
|---|---|---|
| delayed dispatch / slow submit / slow full or partial reconciliation | dispatch delay does not consume deadline; slow terminal result fail-closes whether reconciliation closes the gap or leaves one | `tests/test_passive_close.py` `157 passed` |
| order ID plus missing CID / real second fill | exact duplicate suppressed; distinct fill retained | `close` validation profile passed `422`, including the complete close-execution file |
| same-tick retry / startup alternate paths | retry owner remains, then the real maintenance path reposts | harness plus persistence `67 passed` |
| Binance low-price live IOC | exchange dynamic tick is used before submit | `tests/test_venues_transport.py` `479 passed` |

Static checks: altered modules compiled and `git diff --check` passed. The
targeted cross-boundary selection passed `7`; ACK truth-gap regression passed
`25`; the repository `close` validation profile passed `422` in 39.08 s.

### Acceptance

**Implemented and locally validated; not production-closed.** Deployment and
read-only live verification must show no false pre-submit deadline failure, no
duplicate terminal close ledger, no disappeared zero-fill retry, and no Binance
local tick rejection. The real 1.7 s maker-to-submit delay and Local-L2 rebuild
mechanism remain evidence-only investigations: this repair adds timing evidence
for the former and does not alter either policy.

## Cluster CL-110-local-l2-ws-rest-bootstrap-bridge-readiness

### GitNexus Keys

- Fingerprint: `v2.local_l2.bridge_ws_not_ready_before_rest_snapshot + reconnect_generation_crosses_snapshot + registration_crosses_snapshot`
- Components: `local-l2-data-plane`, `local-l2-ws`, `entry-local-l2`, `v1-parity`
- Symbols: `LocalL2DataPlane.bootstrap_book`, `LocalL2DataPlane.start_background_bootstrap`, `LocalL2DataPlane.wait_for_ws_stream_ready`, `LocalL2WsClient._run_connection`
- Files: `lightfee/marketdata/local_l2_data_plane.py`, `lightfee/marketdata/local_l2_ws.py`, `tests/test_local_l2_ws.py`
- Watch: `runtime.local_l2_snapshot_error`, `runtime.local_l2_sequence_gap_rebuild`, `runtime.local_l2_books_pruned`
- Card: [local-l2-sequence-continuity](../cards/local-l2-sequence-continuity.md)

### Contract and Root Cause

For a venue whose REST snapshot is replayed with WS deltas, the delta receiver
is part of the snapshot's proof: it must be registered and able to receive
before REST starts, and it must remain in the same stream generation through
snapshot application.  This is the V1 buffered-bridge contract.  A reconnect
clears the buffer; a stream registered after a REST request began has no
pre-snapshot coverage.  Either case must leave the book bootstrapping rather
than make it ready from an unbridged snapshot.

V2 started the background REST bootstrap independently of the dynamic WS
connection.  Under scheduling pressure REST could start before an URL-auto WS
connection was established or before an explicit subscription ACK.  The same
gap allowed a snapshot to cross a reconnect or a late WS registration.  The
old code therefore had no single proof that its buffer covered the snapshot
boundary.

### Repair

- Added one per-symbol readiness event to the existing `LocalL2DataPlane`; it
  does not serialize other symbols or add an extra exchange request.
- URL-auto streams become ready after connection/reset; explicit subscriptions
  after their ACK; a valid first depth update is a conservative fallback.
- The existing bootstrap owner waits only for registered replay-bridge streams.
  Direct/periodic calls defer if such a stream is not ready.  Binance, Aster,
  OKX, Bitget, and Gate use this bridge policy; Bybit's WS-authoritative and
  Hyperliquid's stream-only policies remain unchanged.
- A snapshot is discarded if its expected WS generation changes or a bridge
  stream appears during the REST request.  Worker stop and pruning wake and
  remove waiters so a late REST result cannot recreate a removed book.

### Counterexamples and Local Evidence

| Boundary | Required result | Local evidence |
|---|---|---|
| URL-auto WS still connecting | no REST request before receiver readiness | real DataPlane+WS dynamic race regression |
| explicit subscribe has no ACK | bootstrap remains pending | subscription-ACK regression |
| reconnect while REST awaits | response discarded; no HOT book | generation-boundary regression |
| WS registers during REST | response discarded | registration-boundary regression |
| direct periodic bootstrap sees an unready bridge | no REST call | shared-boundary regression |
| worker stop/prune during wait | no stuck waiter or recreated book | lifecycle regression |

`scripts/validate_change.py --profile local-l2` passed (`355` tests), and the
V1 incident/replay/policy selection passed (`24` tests).  The changed modules

## Cluster CL-111-binance-live-order-fixture-dynamic-rule-contract

### Contract and Root Cause

Live Binance submission intentionally fails closed unless dynamic symbol rules
come from `GET /fapi/v1/exchangeInfo`.  Binance documents that endpoint as the
current exchange trading-rule and symbol-information source.  After CL-109
made that live preflight mandatory, two fixture-driven success tests continued
to return an order payload for every mocked request.  Their mocked
`exchangeInfo` response therefore lacked `symbols[].filters`, was correctly
classified as `spec_fallback`, and the real production submit path rejected
the test before its private order request.

This was a test-fixture contract omission, not a production open/close defect:
relaxing the production fail-closed guard would reintroduce precision guesses
for live orders.

### Repair and Verification

- Added the smallest Binance `exchange_info.json` fixture containing the
  documented `PRICE_FILTER`, `LOT_SIZE`, and `MIN_NOTIONAL` inputs consumed by
  the existing rule parser.
- The fixture-driven order test now serves that response and clears the shared
  rule cache around the case.
- The request-shape test now proves the order is preceded by
  `/fapi/v1/exchangeInfo?symbol=BTCUSDT`, then the position-mode request, then
  the signed order request.

The two original RED cases are GREEN, and
`tests/test_venues_contract.py` passes `135` tests.  No production code,
configuration, order type, request count, or live admission policy changed.

Commit `4d03ad7dcf37474600daa53f0ee794f3144b287e` containing this fixture-only
repair is deployed. Post-deploy exchange-truth checks found no positions or
open orders, so no live Binance order was submitted as part of verification;
that is intentional for a test-fixture-only repair.

### Repository-Wide Validation Waiver

The release `full` validation profile is green: compile, diff check, and its
eight production-path test selections pass (`1,538` tests total, including
all `135` venue-contract fixtures).  A separate repository-wide `pytest -q`
