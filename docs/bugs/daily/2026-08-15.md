# Bug Ledger Daily - 2026-08-15

## Cluster CL-108-aster-v3-position-mode-and-market-result-contract

### Contract

Aster V3 private order submission and live-position truth must retain V1's
account-mode semantics while using V3 endpoints:

- one-way orders may use `reduceOnly`; Hedge orders must send the mapped
  `positionSide` and must not send `reduceOnly`;
- the mode is account-wide slow data, fetched from
  `GET /fapi/v3/positionSide/dual` once per private-client lifetime and
  fail-closed when its documented boolean evidence is absent;
- a V3 `MARKET` order requests `newOrderRespType=RESULT`, so the existing fill
  parser receives the documented final fill instead of default `ACK`;
- V3 `positionRisk` LONG/SHORT rows are netted once per symbol before V2
  recovery, residual repair, and reconciliation consume them.

Passive `LIMIT/GTX` remains on its existing acknowledgement workflow.  No
strategy, candidate screening, pricing, L2, position policy, retry policy, or
other venue behavior changes.

### Root Cause

The V3 migration moved Aster live order placement to `AsterV3Client`, but left
the V1-compatible position-mode cache and side mapping in the unused legacy
`VenueTransport` path.  Consequently a Hedge-mode account would submit an
invalid V3 order (missing `positionSide` and potentially carrying
`reduceOnly`).  The same client selected only the first `positionRisk` row,
which is not live-position truth in Hedge Mode.  Separately, the market submit
path accepted V3's default `ACK` even though its immediate parser requires
`executedQty`; that produced an avoidable accepted-but-unconfirmed fill.

Official V3 documentation establishes all three boundaries: the V3 mode
endpoint returns a boolean and has weight 30; `positionSide` is mandatory in
Hedge Mode while `reduceOnly` is forbidden there; `ACK` is the default but
`RESULT` returns the final `MARKET` fill.  V1's Aster adapter independently
confirms the same side mapping and LONG/SHORT netting semantics.

### Repair

- Added one lock-protected `AsterV3Client` mode cache sourced only from the V3
  endpoint, with the official request weight and account limiter scope.
- Applied the V1 mapping at the shared V3 parameter builder for both taker and
  passive orders; invalid mode evidence blocks submission before an order HTTP
  request.
- Added `RESULT` only to the existing taker `place_order` path, matching its
  fill contract without changing passive maker acknowledgement behavior.
- Reused the existing Binance-like position parser to aggregate all same-symbol
  V3 risk rows in both single-symbol and all-position reads.

### Counterexample Matrix and Local Evidence

| Boundary | Required result |
|---|---|
| one-way entry / one-way reduce close | no `positionSide`; preserve existing true-only `reduceOnly` shape |
| Hedge entry BUY/SELL | `LONG` / `SHORT`; no `reduceOnly` |
| Hedge reduce close SELL/BUY | `LONG` / `SHORT`; no `reduceOnly` |
| mode response absent or malformed | rejected before POST `/fapi/v3/order` |
| two `positionRisk` Hedge rows for one symbol | one V1-compatible signed net snapshot |
| MARKET order | no `timeInForce`, explicit `RESULT`, parsed fill |
| passive `LIMIT/GTX` | retains ACK behavior and gets Hedge `positionSide` |

The real `AsterV3Client -> signed httpx.MockTransport` regression covers each
mode/order combination, cache reuse, fail-closed mode evidence, `RESULT`, and
position aggregation.  The Aster transport/adapter/contract/rate-limit suite
passes `651` tests locally.  This is **implemented and locally validated**;
cloud deployment and read-only live verification remain required for closure.

### Contract and Root Cause

Four confirmed boundary drifts were repaired without changing screening, L2
policy, strategy thresholds, or recovery priority:

1. V2 charged the V1 hedge hard deadline from maker fill through local dispatch,
   so a 1.7 s scheduling delay could fail-close before the hedge request. V1
   starts it immediately before the concrete `execute_order_leg` call and
   evaluates after its terminal result, including any required fill
   reconciliation. V2 had frozen completion at the raw adapter return and also
   skipped the gate when reconciliation fully removed the local hedge gap.
2. The same close execution could persist twice when a later observation had
   the same exchange order ID but no CID. Order ID is the authoritative identity;
   CID is only a fallback when that ID is absent.
3. A terminal zero-fill cycle marked itself for repost, then same-tick normal
   reconciliation, startup recovery, or stale abandonment cleared the owner
   before its scheduled maintenance action.
4. Live Binance IOC limit pricing used the static fallback tick although the
   existing exchange-rule preflight already had the symbol's dynamic tick;
   low-priced symbols could be rejected locally before HTTP submission.

### Repair

- Retained one post-submit V1 deadline gate, now measured from the actual
  submitted quantity through the terminal adapter or reconciliation result;
  added maker-to-submit and submit-duration fields to the existing hedge-fill
  event, and removed obsolete pre-submit deadline checks. A fully reconciled
  fill is still evaluated; only compensation uses the remaining real gap.
- Canonicalized close identity as `(venue, order_id)` when present, otherwise
  `(venue, client_order_id)`, across persisted legs, reconciliation, and queue
  identity. Exact replay remains suppressed; a real partial/new fill remains
  distinct.
- Added one shared zero-fill-retry predicate used by normal reconciliation,
  startup force recovery, startup hedge recovery, and stale abandonment.
- Reused the existing Binance/Aster rule-preflight branch for live Binance;
  no new cache, configuration, or fallback was added.
