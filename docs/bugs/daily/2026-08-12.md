### Summary

A recovered `CLUSDT` OKX/Bitget passive close remained `risk_only` even though
the read-only exchange probes showed both positions were zero. The Bitget
Classic pending-order endpoint returned a successful envelope with
`code="00000"` and `data.entrustedList=null`. V2's shared parser required a
list and therefore classified that exact response as untrusted instead of as
an empty pending-order collection. The passive-close owner was correctly
retained under the old interpretation, but the interpretation itself was too
strict for the observed successful Classic response.

### Root Cause

`parse_open_orders_response()` knew the field name but had no venue-success
contract. It sent every nullable `data.entrustedList` through the generic
list-only rule. This affected the shared direct transport fallbacks used by
passive-close live-flat recovery, startup recovery, and residual repair.

The earlier code must not be weakened into accepting arbitrary nullable data:
a failed Bitget business envelope with `entrustedList=null` is still not proof
that open orders are absent.

### V1 / Exchange Decision

- V1 `src/live/bitget.rs` validates Bitget's business `code` before consuming
  its data payload. V2 now follows that boundary on raw direct responses.
- Bitget's Classic [Get Pending Orders](https://www.bitget.com/api-doc/classic/contract/trade/Get-Orders-Pending)
  response names `data.entrustedList` as the pending-order collection. The
  production account returned `null` for that collection while `code="00000"`.
- Only a raw Bitget response with an explicit success code (`"00000"` or
  `"0"`) may normalize `data.entrustedList=null` to `[]`. A missing code,
  non-success code, unknown nullable field, malformed envelope, or transport
  error remains untrusted and keeps the fail-closed owner.
- Adapter-normalized collection responses remain supported; the stricter
  success-code requirement applies to the direct raw Bitget fallback.

### Fix

The existing shared parser gained optional venue and raw-success context; no
new recovery or screening stage was added.

1. Direct Bitget raw paths require a successful business code before they can
   yield empty open-order truth.
2. The exact successful `data.entrustedList=null` shape becomes an empty list.
3. Passive-close probing, startup recovery, and residual repair pass that raw
   context into the same parser. No caller synthesizes flat truth locally.
4. A non-success envelope with a null collection raises structured untrusted
   evidence rather than clearing a position or recovery owner.
