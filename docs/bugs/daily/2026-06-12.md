## Cluster CL-074: Runtime heartbeat health gate exporter-only false progress

### GitNexus Keys

- Fingerprint:
  `runtime-heartbeat-health-gate-exporter-only-false-progress`
- Components:
  `live-runtime`, `current-state`, `production-health`, `diagnose-live`,
  `production-observability`
- Symbols:
  `EngineState`, `LiveRuntime.run_loop`, `_current_state_heartbeat_loop`,
  `_export_current_state_snapshot`, `analyze_current_state`,
  `_build_state_consistency`, `_build_production_acceptance_gate`
- Watch:
  `live_tick_stale`, `exporter_only_progress`,
  `production_health.current_state.details.progress_source`,
  `runtime_progress.active_lane`,
  `runtime_progress.active_lane_overdue`

### Production Symptom

Several deployment reviews showed that a fresh
`runtime/live-state-current.json` could make the verifier look less severe even
when the actual live loop had not produced a recent scan or tick. That blurred
three different truths:

- the current-state exporter task is still writing a JSON file;
- the main runtime loop or a specific V1 lane is making business progress;
- exchange truth proves the account is flat and has no open orders.

The previous gate could treat fresh `generated_at_ms` / `current_state_age_ms`
as runtime progress. That was a surface fix: it could hide a stuck main loop as
long as the heartbeat exporter kept writing.

### Source Truth

- V1-compatible runtime health must be tied to business progress, not merely to
  file export freshness.
- Exchange truth remains the authority for flat/no-open-order acceptance, but
  flat truth alone does not prove the live loop is advancing.
- A bounded active lane is legitimate progress only while it is within its
  budget. Once `active_lane_age_ms > active_lane_budget_ms`, it must become a
  stale-loop signal again.

### Fix

- `EngineState` now carries optional `runtime_progress`.
- `LiveRuntime.run_loop()` records:
  `loop_iteration_started_ms`, `loop_iteration_completed_ms`,
  `last_lane_progress_ms`, `active_lane`, `active_lane_started_ms`,
  `active_lane_budget_ms`, and `active_lane_overdue`.
- Lane boundaries now cover the V1 runtime work lanes:
  `full_tick`, `active_positions`, `rate_limit_reload`, `local_l2_sync`,
  `passive_close`, `normal_exit`, `maker_event`,
  `pending_entry_maintenance`, and `housekeeping`.
- `_current_state_heartbeat_loop()` remains exporter-only. It does not advance
  `runtime_progress.last_lane_progress_ms`.
- Current-state export includes `runtime_progress` and derives
  `active_lane_overdue` from active lane age and budget.
- `analyze_current_state()` no longer uses `current_state_age_ms` to suppress
  `live_tick_stale`. Suppression now requires clean local state, flat exchange
  truth, and one of:
  recent `last_scan`, recent `runtime_progress.last_lane_progress_ms`, or a
  non-overdue bounded `active_lane`.
- A fresh exporter with stale business progress keeps `live_tick_stale` and
  adds `exporter_only_progress`; details expose `progress_source`,
  `exporter_only_progress`, and the normalized `runtime_progress`.
- `diagnose_live.py` exposes the same `runtime_progress` in both state
  consistency and production acceptance gate output.

### Regression Watch

- `current_state_age_ms` may prove only exporter freshness. It must not be the
  runtime progress source that suppresses `live_tick_stale`.
- `exporter_only_progress` should be treated as a diagnostic fingerprint, not a
  healthy runtime proof.
- `active_lane` suppresses stale tick only while it is within
  `active_lane_budget_ms`.
- The fix must remain observability/health-gate only: no entry sizing, order
  submit, cancel, close, residual repair, or exchange mutation semantics should
  change.

## Cluster CL-073: SAHARA entry residual dust 2% warning split

### GitNexus Keys

- Fingerprint:
  `sahara-entry-residual-dust-two-percent-diagnose-warning-split`
- Components:
  `live-runtime`, `residual-repair`, `diagnose-live`, `pending-entry`,
  `v1-parity`, `exchange-docs`
- Symbols:
  `_terminalize_residual_repair_task`,
  `_recover_residual_repairs`,
  `_build_entry_quantity_terminal_summary`
- Watch:
  `execution.entry_residual_dust_tolerated`,
  `pending_entry.hedge_quantity_undercut`,
  `execution.entry_quantity_plan`,
  `hedge_quantity_undercut_warning_count`,
  `common_quantity_mismatch_warning_count`,
  `account_wallet_signer_mismatch`

### Production Symptom

Cloud read-only review of deploy `6b92cd1` found the current runtime healthy and
flat: no open positions, pending entries, pending closes, passive closes,
residual repairs, or venue open orders. One post-deploy `SAHARAUSDT` lifecycle
opened and closed successfully. During that lifecycle, the maker leg filled
larger than the normalized OKX hedge quantity, then a residual repair closed the
remaining `11` units.

The event shape looked like a short single-leg window, but the residual was
about `11 / 2860 ~= 0.38%`. The desired V1-compatible acceptance rule is that
this is not an abnormal warehouse condition when exchange quantity rules prove
the remainder cannot form a valid order.

### Source Truth

- V1 processes pending entry hedges, passive closes, and residual repairs as
  separate lifecycle work. Residual repair remains the authority for live
  excess, but unrepairable exchange-min dust may terminalize.
- Bybit V5 open/closed order docs warn that recent closed-status visibility can
  be bounded and latency/restart-sensitive, so an early missing order query is
  not terminal proof by itself.
- OKX SWAP/FUTURES sizing depends on contract rules (`ctVal`, `lotSz`) and
  order/amend truth must retain live order identity when amend fails but the
  original order is still live.

### Fix

- Entry residual dust tolerance is tightened from `<=5%` to `<=2%`.
- The runtime still requires exchange-min terminal evidence:
  `exchange_min_quantity_dust` or `exchange_min_notional_dust`. A ratio alone
  cannot mark a residual tolerated.
- Exchange-min entry residuals above `2%` are paused with
  `entry_residual_dust_over_tolerance` and remain pending; the pair gate is not
  released.
- Repairable residuals still submit reduce-only repair, compensation, or block;
  missing exchange rule evidence does not get the tolerated-dust fast path.
- Diagnose now reports both raw quantity events and warning-only events:
  tolerated `<=2%` exchange-min dust entries are excluded from
  `hedge_quantity_undercut_warning_count` and
  `common_quantity_mismatch_warning_count`.
- Production acceptance now also exposes `short_window_warning_count`,
  `short_window_warning_families`, and `short_window_warning_details`, so a
  final flat state cannot hide entry quantity mismatch, hedge undercut,
  passive-close truth-gap, or passive zero-fill recovered windows.
- Hyperliquid `account_wallet_signer_mismatch` is tracked separately as a
  preflight/env identity issue. It is not classified as a SAHARA open/close
  residual bug.

- `execution.entry_residual_dust_tolerated` must always include
  `residual_ratio <= 2%` and exchange-min terminal evidence.

  but `hedge_quantity_undercut_warning_count` should stay zero when every
  undercut belongs to tolerated exchange-min dust.
- `common_quantity_mismatch_warning_count` must stay focused on true executable
  mismatch, not legal passive incremental slicing or tolerated dust.
- `account_wallet_signer_mismatch` should be investigated through the
  Hyperliquid credential/preflight family, not the SAHARA residual family.
