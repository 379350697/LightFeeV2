# Bug Ledger Daily - 2026-08-14

## Cluster CL-105-local-l2-decision-time-aster-overlap-primary-ownership

### Contract

The live entry path remains:

`manual coin list -> lightweight shortlist -> existing primary/shadow Local-L2
preparation -> true-L2 final-cost reprice -> existing risk/order flow`.

There is no BBO fallback, new screening stage, shadow trading, or threshold
relaxation in this repair.  Local-L2 must make its readiness decision in the
current clock domain; Aster must follow V1's covered-range sequence rule; and
a primary that remains in the current primary+shadow scope must retain its
hold/session ownership across normal rank churn.

### Root Cause

Three independent interpretations of the same Local-L2 ownership path could
block every otherwise eligible candidate:

1. `tick()` captured `now_ms`, awaited network work, then passed that old time
   to Local-L2 sync/readiness/final selection.  A WS observation that arrived
   during the await looked impossibly future-dated and triggered a stale-clock
   rebuild.
2. V2 required Aster `pu == book.sequence` in both hot WS ingest and buffered
   replay.  V1 accepts the narrower case `U <= book.sequence + 1 <= u`, even
   when Aster's `pu` lags; the prior V2 code rebuilt the exact live sample.
3. V2 reassigned primary purely by the newest rank every scan and reset its
   hold timestamp on every refresh.  The existing hold window could therefore
   never mature, and rank churn repeatedly cold-started the session.

The historical diagnostic classifier also called the Aster overlap an official
exchange reset, which could conceal this V1 parity drift in blocker analysis.

### Repair

- `_sync_local_l2_data()` obtains a fresh decision clock at the data-plane
  boundary; post-shortlist readiness and final entry selection also use their
  current decision time.  The stale and clock-skew thresholds are unchanged.
- The existing venue policy owns the Aster-only covered-range exception.  Both
  data-plane entrances and the shared `LocalL2Runtime` book owner use it;
  Binance, OKX, and Gate keep their strict paths.
- The existing tracked-primary set now feeds the existing selector.  Current
  primaries are retained before rank fill, their hold start is initialized only
  on actual promotion, and demotion clears it.  The existing bounded sticky
  session set is now used and untracked nonsticky sessions close.
- Offline incident classification no longer treats the covered Aster range as
  official rebuild evidence.

### Deterministic Reproduction / Verification

| Probe | Old behavior | Fixed behavior |
|---|---|---|
| `test_runtime_l2_sync_uses_decision_time_not_tick_start_time` | an old tick time made a fresh book rebuild | real `LiveRuntime` preserves HOT using decision time |
| `test_aster_overlapping_previous_link_survives_ws_and_buffered_replay` | hot WS and bootstrap replay rebuilt on stale `pu` | real DataPlane + Runtime accept only the V1-covered `U..u` case |
| `test_runtime_scope_preserves_primary_across_rank_churn` | next scan demoted the existing primary | real runtime scope preserves the primary and its session hold |

Local evidence: the dedicated harness/sequence/runtime set passed `275`; the
repository `local-l2` validation profile passed `337` tests, with compileall
and `git diff --check` green.  The full validation profile passed all `10/10`
steps.

### Validation Follow-up

The diagnostic and production-verifier scripts previously loaded systemd
environment-file credentials into the process environment without restoring
them.  A later diagnostic test could therefore make real private read-only
exchange requests and stall the test process.  Both entry points now use the
same temporary environment scope: the exchange-truth probe sees systemd
credentials, but injected values are removed immediately afterward.  RED/GREEN
tests cover both scripts, and `test_diagnose_live.py` now completes `104/104`
in one process.

This is an **implemented, locally validated** repair.  It is not cloud-closed
until deployment and read-only live evidence show that the rebuilt/hold-blocker
family no longer blocks current candidates.

## Cluster CL-106-local-l2-rest-bridge-and-clock-domain

### Contract

For Binance-style Local-L2, REST is a bootstrap/rebuild anchor only.  Once a
book is HOT, WebSocket deltas keep it fresh; a stale HOT book must be demoted
and rebuilt, never periodically replaced with a second REST snapshot.  After a
REST snapshot, V1 accepts one first `U..u` delta that covers `snapshot + 1`
despite a mismatched `pu`; every later delta remains strict.  A book's
`observed_at_ms` must be in the same local decision-clock domain as readiness.

### Root Cause

V2 contradicted its own V1 comment by polling REST for a fresh HOT
`REST_SNAPSHOT_BUFFERED_REPLAY` book.  Each replacement snapshot raced with the
live Binance stream, so the next valid boundary delta could fail strict `pu`
continuity and force another rebuild.  V2 also omitted V1's one-time initial
snapshot-overlap state, and wrote raw exchange event time directly into the
book even when it was ahead of the local receiver clock.  The latter produced
the observed false `clock_skew` rebuilds.

### Repair

- Removed HOT periodic REST refresh and its obsolete slow-data state.  HOT now
  stays WS-owned; only stale/non-HOT books enter the existing rebuild path.
- Added one private data-plane marker, armed only by REST bootstrap, consumed
  by the first valid covered-range delta in both buffered replay and live WS
  ingress, and cleared on apply, rebuild, reset, error, and pruning.
- Clamped a future source timestamp to the local receipt time at the shared
  runtime book-owner boundary.  This is the V2 equivalent of V1's
  server-offset normalization when the data plane has no offset object.

### Deterministic Reproduction / Verification

| Probe | Old behavior | Fixed behavior |
|---|---|---|
| `test_binance_rest_snapshot_accepts_one_overlapping_first_delta_then_restores_strict_link` | buffered first `U..u` bridge rebuilt | it applies once; the following bad `pu` rebuilds |
| `test_binance_rest_snapshot_allows_the_same_overlap_on_the_live_ws_path` | direct WS bridge rebuilt | direct first bridge applies |
| `test_rest_buffered_replay_hot_book_uses_ws_without_proactive_rest_refresh` | 60 REST replacements in 30 minutes | zero REST replacements with WS deltas |
| `test_future_exchange_timestamp_uses_local_receive_time_for_l2_freshness` | future `E` entered the book | `observed_at_ms` equals local receipt time |
| `test_failed_first_bridge_clears_the_one_time_overlap_marker` | failed bridge retained its allowance | rebuild clears it before any next bridge |

RED: all five new contract probes failed on the previous code.  GREEN: the

passed `153`, and the `local-l2` profile passed `341` tests with compile and

groups) without a failure.  Cloud deployment and read-only post-deploy evidence

## Cluster CL-107-aster-v3-market-ioc-wire-contract-and-trigger-causality

### Contract

For Aster V3, every `MARKET` order omits `timeInForce`.  `IOC` remains the V2
domain-level execution intent used by hedge and reduce-only close callers; the
Aster adapter translates it by selecting `MARKET`, not by emitting an unsupported
wire field.  `LIMIT` behavior is unchanged: passive/post-only uses `GTX`; other
limits use `GTC`.

V1 is authoritative: `AsterClient::submit_market_order_once` builds `symbol`,
`side`, `type=MARKET`, `quantity`, identity and position/reduce-only fields, but
no `timeInForce`.  All V1 market retry directions use that same builder.

### Production Evidence and Causality Rule

The deployed CYSUSDT recovered passive-close dual-taker fallback sent an Aster
V3 `MARKET`, `BUY`, `reduceOnly=true`, `timeInForce=IOC` request.  Aster returned
HTTP `400`, code `-1106`: `Parameter 'timeInForce' sent when not required.`

The offending wire branch was introduced by `dc056068` (2026-06-08, Aster V3
migration).  `b1ace220` later removed it on the divergent `v3` history, but
that commit is not an ancestor of deployed `main` (merge base `279039cb`): the
correct repair was never merged into the production lineage.  This is not a
later textual reintroduction; it is an unpropagated prior fix.  The
passive-close/recovery correction in `002ed90` did not edit the line, but drove
the recovered close through the previously dormant market fallback and therefore
**triggered the production incident**.

Future incident records must state `introduced_by`, `prior_fix_unmerged` when
applicable, and `triggered_by`.  A line that predates the latest deploy is not
grounds to call the deployment unrelated, and a fix in another branch is not a
production fix until it is an ancestor of deployed `main`.

### Root Cause and Repair

`AsterV3Client._order_params()` treated `TimeInForce.IOC` as a field that must
be serialized after it had already selected `type=MARKET`.  Aster V3 rejects
that combination.  The shared request builder now emits `timeInForce` only for
`LIMIT`; no close, retry, recovery, candidate, or strategy policy changes.

The coverage gap was a missing `AsterV3Client.place_order` MARKET-IOC wire
regression.  Existing tests covered the passive `LIMIT/GTX` route and generic
signed-request construction, so neither proved the params emitted by the real
market submit path.  The branch-local `b1ace220` deletion also carried no
mainline regression to prevent its omission from production history.

### Counterexample Matrix

| Boundary | Required result |
|---|---|
| MARKET IOC entry hedge | no `timeInForce`; no `reduceOnly` |
| MARKET IOC reduce-only close/recovery | no `timeInForce`; preserve `reduceOnly=true` |
| passive/post-only LIMIT | retain existing `GTX` behavior |
| non-passive LIMIT | retain existing `GTC` behavior |

The first two rows run through the real `AsterV3Client.place_order -> signed
HTTP request` path.  Existing Aster adapter passive-submit regression retains
the prepared `LIMIT/GTX` request, guarding the recovery/passive-close work that
activated this bug.  This is locally implemented; cloud read-only confirmation
is still required before closure.
