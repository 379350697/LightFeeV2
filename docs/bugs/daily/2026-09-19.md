# Bug Ledger Daily - 2026-09-19

## CL-156 — venue 查单失败炸穿主循环（P0 crash loop） → closed

### Symptom

09-19 00:25:09 起 `lightfee-live` 进入确定性崩溃循环：每 ~15-30 秒退出重启，
至 16:58 共 **2,376 次**（NRestarts=2376），journal 累计 1.4 万+ ERROR 行。
期间 trading 停摆、startup recovery 每个生命周期都走
`truth_unavailable_for_required_recovery → RISK_ONLY_WAIT_FOR_TRUTH` 后
即崩。

### Root cause

运营事件触发代码缺陷的复合：**Bybit API key 于 09-19 00:25 过期**
（retCode=33004 "Your api key has expired"）。台账里三条含 bybit 正量腿的
final 债务（LSK×2 + BRUSDT）每次精确 recheck 都让
`fetch_order_fill_reconciliation` 抛 TransportError，而
`_fetch_close_leg_reconciliations`（close_runtime.py:196）对该调用**无
try/except**，异常沿 `_process_pending_close_reconciliations →
_reconcile_pending_state → run_loop` 炸穿主循环。同文件的 order-truth 路径
（close_runtime.py:1997-2002）本有 `except Exception → any_unavailable`
护栏，计费精确查单唯独缺失。既有测试漏它：无"venue 查单抛错"反例。

### Contract

venue 对账查单失败（过期 key、5xx、网络）是 evidence-unavailable，不是
进程致命错误：记 typed 事件 `reconciliation.close_leg_lookup_error`，按
既有 None 语义降级（存储零量腿跳过、正量腿保持不可用 → owner 落
evidence debt fail-closed）。

### Repair (`f9fa2463`)

`_fetch_close_leg_reconciliations` 每腿 fetch 加护栏（事件 + 降级），
与 order-truth 路径约定一致。
`tests/test_close_leg_lookup_error.py`：bybit 腿 33004 反例，RED 于
pre-fix 树（异常直接抛出），GREEN 后 owner 保留为 evidence debt、零
`exit.reconciled`。

### Production evidence（部署后 90 秒内自然发生）

16:58:25-27 对账循环对三条债撞上同一个 33004，打出三条
`reconciliation.close_leg_lookup_error`（LSK×2 + BRUSDT）并安全降级；
进程自 16:58:10 起单一连续生命周期存活（对比之前 15-30 秒一崩），
NRestarts=0。

   bybit 对冲因 key 过期未能建立；本地 `pending_entry: 1` 与 live truth
   冲突，recovery 判 `owned_pending_entry_live_conflict →
   BLOCK_OR_FLATTEN_LIVE_ARTIFACT`，fail-closed 等待 bybit 真值。

**恢复路径：用户在 Bybit 续期/更换 API key → 重启服务 → startup
recovery 取得 bybit 真值 → 冲突 pending entry 走对冲/清理 → 债务查单恢复。**
