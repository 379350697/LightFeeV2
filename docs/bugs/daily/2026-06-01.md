### Production Evidence

After CL-026 deployment, live stayed `risk_only` / `fail_closed` because of an
older `ARIAUSDT` pending entry created before that deployment. This was not a
Local-L2 or WS BBO provider regression. The causal chain was after entry
dispatch:

| Time CST | Evidence |
|---|---|
| `2026-06-01 19:52:43` | first `ARIAUSDT bybit->binance` pending entry submitted a Bybit passive maker; reconciliation briefly saw `not_found` and finalized it as `zero_fill_unfilled_removal` |
| `2026-06-01 19:52:52` | second `ARIAUSDT bybit->binance` pending entry submitted another Bybit passive maker |
| `2026-06-01 19:53:28` | second maker reconciled as filled; Binance hedge had filled `619`, leaving only a tiny missing hedge residual |
| later cycles | `pending_entry.hedge_quantity_below_min_notional` repeated instead of terminalizing the balanced entry |
| post-deploy read-only truth | Bybit `ARIAUSDT` buy `1238`, Binance `ARIAUSDT` sell `619`, open orders `0`; local state had `open_position_count=0`, `pending_entry_count=1` |

The early `runtime.entry_blocked_local_l2_selection` records for ARIA were
pre-entry blockers. They did not create the mismatch; the mismatch came from
pending-entry reconciliation after actual order submission.

### Root Cause

Two V2 pending-entry evidence gaps combined:

1. A balanced pending entry with a remaining hedge residual below exchange
   quantity/notional rules was parked as `hedge_quantity_below_min_notional`
   instead of finalizing the balanced open position. That kept the runtime in
   pending-entry recovery and prevented live-truth drift repair from seeing the
   actual balanced position.
2. Startup live hydration could absorb an older ghost maker fill into the same
   pending entry, producing a recovered local shape like
   `maker_leg_filled=1238` / `hedge_leg_filled=619`. V2 then interpreted the
   live Bybit excess as missing Binance hedge instead of finalizing the
   balanced `619` and letting live-truth drift repair flatten the Bybit excess.
3. `_ensure_pending_entry_open_fill_details()` treated a planned
   `hedge_client_order_id` as queryable during finalize even when no hedge was
   submitted. That could produce noisy "order does not exist" evidence on the
   hedge venue and obscured the difference between planned and submitted hedge
   IDs.

This is the pending-entry live-truth family, not Local-L2 sequence continuity
and not WS quote provider lifecycle.

### Fix

- Added terminal hedge-dust handling for pending entries that already have a
  balanced fill. If the remaining hedge quantity normalizes to zero or is below
  official venue notional rules, V2 now records
  `pending_entry.hedge_residual_below_min_notional_terminalized`, finalizes the
  balanced open position, and lets existing residual/drift repair handle any
  live excess from exchange truth.
- Wired that terminal branch into normal reconciliation, passive maker
  maintenance, and startup pending-entry recovery.
- Startup live hydration now handles trusted imbalanced live truth with no open
  orders: it clamps pending fill quantities to the live balanced quantity,
  finalizes the balanced open position, and leaves any live excess for existing
  drift repair.
- Stopped querying a planned hedge CID during pending-entry finalize unless
  there is evidence the hedge was actually submitted: hedge order id, inflight
  hedge, hedge attempt count, or existing hedge fill evidence.

No Local-L2, WS BBO provider, entry selection, sizing, or order submit semantics
changed.

| Venue | Official contract | Implementation decision |
|---|---|---|
| Binance USD-M | Individual symbol `bookTicker` pushes best bid/ask updates in real time; current docs route public market streams through `/public/ws/...`. | Keep `bookTicker`, update URL to the routed public endpoint to match current docs. |
| Aster | Binance-compatible futures `bookTicker` stream is real-time and symbols are lowercase in stream names. | Keep existing Aster raw stream and parser. |
| OKX | Public `tickers` channel carries `bidPx`, `askPx`, sizes, and millisecond `ts`; OKX also requires ping/reconnect if no data is received for under 30s. | Keep `tickers` for BBO lease, keep fail-closed freshness budget, and surface subscribe/control errors. |
| Bybit | Linear public ticker uses `tickers.{symbol}`, has snapshot/delta semantics, and missing fields in deltas mean unchanged values. | Keep last-value merge for deltas; keep linear public URL. |
| Bitget | Futures ticker channel returns `bidPr`/`askPr` with roughly 300-400ms updates on change. | Keep ticker channel; keep TTL/freshness gate. |

### Root Cause

This is not a Local-L2 sequence-continuity failure. It is a new provider
lifecycle bug:

1. WS BBO streams were activated from the post-snapshot-freshness `tradeable`
   list. If a candidate was filtered before final selection, the provider did
   not prewarm BBO for it, so later entry windows could hit missing quote on
   first sight.
2. Per-venue stream budget used `set` plus alphabetical `sorted(symbols)`.
   That could spend a small venue budget on a lower-ranked symbol and leave the
   highest-ranked candidate without BBO coverage.
3. Subscription/control errors were swallowed as non-data messages, so a venue
   reject looked the same as "connected but no quote yet."

The safe behavior stayed fail-closed: missing or stale quote blocked entry.
The instability was opportunity coverage, not wrong-price entry.

### Fix

- `LiveRuntime.tick()` now prewarms WS BBO from the catalog-supported discovery
  list before final snapshot-quote freshness can remove candidates from the
  final tradeable list.
- `LiveRuntime._ensure_entry_bbo_active_for_candidates()` now preserves
  candidate ranking order when filling per-venue BBO budgets; it no longer
  alphabetically truncates symbols.
- Binance BBO URL now uses the current official routed public endpoint:
  `wss://fstream.binance.com/public/ws/<symbol>@bookTicker`.
- `BboWsClient._handle_message()` now records WS control/subscription errors
  in `last_error` and includes `subscribed` / `last_control_message` in stream
  state evidence.

No Local-L2, entry execution, order placement, close, residual repair, sizing,
or recovery semantics changed.

### Post-Deploy Production Check

The code fix is deployed, but the live runtime is not a clean CL-026 effect
window yet. After restart, production entered `risk_only` / `fail_closed`
because of a pre-existing `ARIAUSDT` pending-entry recovery block whose
`recovery_blocked_at_ms` was before this deployment. Credentialed read-only
truth for the pending symbol reported nonzero live exposure on both legs and no
open orders:

| Venue | Symbol | Live side | Quantity | Open orders |
|---|---|---|---:|---:|
| Bybit | `ARIAUSDT` | buy | 1238 | 0 |
| Binance | `ARIAUSDT` | sell | 619 | 0 |

That state-consistency failure is not evidence that CL-026 regressed. It does
mean post-deploy entry-path counters cannot yet prove the new provider in live
selection because entry remains blocked by the older pending-entry/live-truth
condition. Track that separately under the pending-entry live-truth family
before using production order counts as CL-026 acceptance evidence.

### Acceptance

Accepted locally and deployed in `7745e86`. This cluster changes only the WS BBO
quote provider's activation order, per-venue budget ordering, current Binance
public endpoint alignment, and stream error evidence. The expected production
effect is fewer `entry_ws_bbo_quote_lease_missing_quote` blocks after provider
warmup and better evidence when a venue rejects or stalls a subscription.
`stale_quote_lease` remains a correct fail-closed guard when a venue does not
send a fresh BBO update within the configured TTL/age budget. Full production
behavior still needs a clean post-ARIA recovery window because current
`risk_only` / `fail_closed` state prevents new entry-path exercise.
