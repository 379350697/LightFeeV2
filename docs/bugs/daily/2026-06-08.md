### Scope

This pass covers production issue 2
(`recovery.live_position_bulk_probe_error`) and issue 3
(`recovery.residual_repair_failed` ACK-only). Hyperliquid margin admission and
unrelated passive-close proof-gate work stay out of scope. No order, cancel, or
production runtime-state mutation is claimed by local verification.

### Summary

- Recovery startup truth probe is now bulk-diagnostic plus bounded fallback for
  recovery-owned/truth-required symbols. Pending residual/passive/pending-entry
  recovery work cannot be cleared by a venue-level bulk timeout, including OKX.
- Bounded fallback uses only recovery-owned or explicit truth-required symbols,
  preventing a drift back into full configured-universe fan-out or OKX 429
  amplification.
- Residual repair ACK-only submit responses now enter a shared accepted-order
  uncertainty resolver before the state machine can submit another reduce-only.
- The resolver completes on confirmed fill, completes on trusted live-flat plus
  empty open-order truth, and retains the task with accepted ids when an open
  order remains or truth is unavailable.

### Root Cause

Issue 2 was a method drift from V1-style narrow truth probe to V2 bulk-first
startup recovery. When `fetch_all_positions()` timed out, V2 could either rely
on venue-specific fallback behavior or, for OKX, return an empty snapshot-like
result. That made a truth-required recovery path capable of seeing "flat" from
missing bulk truth.

Issue 3 was an incomplete ACK-only closure. Transport already recognized
accepted order ids, but residual repair only recorded evidence/rescheduled at
the `OrderSubmitError` boundary. The same loop did not immediately reconcile
execution/order/open-order/live-position truth, so a later tick could repeat
reduce-only work before proving whether the accepted order filled, stayed open,
or left the account flat.

### V1 / Exchange Decision

- V1 semantics require residual/recovery progress to be driven by narrow live
  truth for the symbols that actually own recovery work.
- Bybit order create responses are asynchronous ACKs with `orderId` /
  `orderLinkId`, not terminal fill truth; fill/order/open-order/live-position
  truth must decide the next state.
- OKX bulk position timeout is missing truth, not flatness, when recovery-owned
  work requires truth.

### Fix

- Split startup live-position probe into recovery-required symbol source
  classification and bounded fallback.
- Kept full bulk fetch as diagnostic/supplemental evidence, while required
  recovery work falls back to per-symbol truth probes for only bounded symbols.
- Added risk-only blocker evidence for required recovery truth unavailable
  instead of accepting a timeout as empty positions.
- Added residual accepted-order resolver that reuses existing
  `fetch_order_fill_reconciliation()`, open-order truth, and position truth.
- Stored accepted order ids on retained residual tasks and made the next retry
  reconcile those ids before any repeat reduce-only submit.

### RED / GREEN Evidence

- OKX/Bybit bulk timeout plus truth-required residual work now requires bounded
  symbol fallback; fallback success can complete as flat, fallback failure
  blocks as required truth unavailable, and OKX timeout is not false flat.
- Bybit residual repair ACK-only with execution-list fill completes without a
  second submit.
- ACK-only with no fill but live position flat and open orders empty completes
  and releases the task.
- ACK-only with open order still present retains accepted ids and next tick
  reconciles before resubmitting.

## Cluster CL-056: production error evidence contract split

### GitNexus Keys

- Fingerprint: `production-error-evidence-contract-split`
- Components: `recovery-truth-probe`, `entry-admission`,
  `snapshot-diagnostics`, `diagnose-live`
- Symbols:
  `LiveRuntime._fetch_startup_live_position_snapshots`,
  `LiveRuntime.tick`,
  `_build_production_acceptance_gate`
- Files:
  `lightfee/engine/runtime.py`,
  `scripts/diagnose_live.py`,
  `tests/live_harness/test_okx_recovery_probe_rate_limit_incident.py`,
  `tests/test_runtime_snapshot_freshness.py`,
  `tests/test_diagnose_live.py`
- Commits: `6608e38`
- Cards:
  [local-l2-sequence-continuity](../cards/local-l2-sequence-continuity.md),
  [residual-repair-live-truth](../cards/residual-repair-live-truth.md)

### Scope

This pass does not reopen CL-055 order-state behavior. Residual repair,
pending entry, and passive close still use accepted-order truth reconciliation
before repeat order submission. The change is an evidence-contract hardening
pass so production diagnostics can distinguish:

- blocking required recovery truth gaps,
- contained deterministic admission blocks,
- nonblocking health diagnostics from best-effort bulk/snapshot evidence.

No order, cancel, sizing, signing, or live runtime-state mutation path is
changed by this local implementation.

### Root Cause

After CL-055, the trading-risk core was closed, but production evidence still
had overloaded names. `recovery.live_position_bulk_probe_error` could describe
both missing truth needed for recovery work and a best-effort full-position
diagnostic timeout when there was no recovery work. Similarly, stale quote
diagnostics were built by scanning the entire `snapshot.quotes` map, so a large
non-candidate quote universe could look like an entry blocker even though V1
tracks shortlist/selected entry legs. Hyperliquid margin admission was already
deterministic, but since-deploy diagnosis did not classify the venue cooldown as
contained evidence before Local-L2/quote readiness.

### V1 / Exchange Decision

- V1 recovery progress is driven by narrow live truth for recovery-owned work,
  not by interpreting full bulk timeout as account flatness.
- V1 entry readiness is candidate/shortlist scoped. Whole-snapshot quote health
  can be useful evidence, but it must not become an entry blocker for symbols
  that are not selected/tracked/recovery-owned.
- Hyperliquid insufficient-margin responses are deterministic venue/account
  admission evidence. Runtime should downgrade the venue before Local-L2/quote
  tracking, and diagnosis should classify that as contained evidence when the
  payload has official/source evidence and no evidence gap.

### Fix

- Split bulk timeout events:
  - `recovery.live_position_bulk_diagnostic_error` for no-work best-effort bulk
    timeouts, with `diagnostic_scope=best_effort_bulk_positions`,
    `truth_required_by=[]`, `blocking=false`, and
    `decision=running_with_nonblocking_health_diagnostic`.
  - `recovery.required_position_bulk_fallback_planned` for recovery-required
    bulk timeouts when bounded fallback is available, with
    `fallback_planned=true`, `blocking=false`, and
    `decision=bounded_symbol_fallback_required`.
  - `recovery.required_position_truth_unavailable` only when no bounded fallback
    is available or bounded fallback fails, with `blocking=true` and
    `decision=truth_unavailable_for_required_recovery`.
- Kept OKX recovery fallback bounded to recovery-owned/truth-required symbols so
  no full configured-universe fan-out is introduced.
- Limited `runtime.order_quote_stale_skipped` to quote keys that belong to
  admission-filtered entry-relevant candidate legs. Non-candidate or
  admission-blocked stale quotes now emit only rate-limited
  `runtime.order_quote_stale_health_summary` with `blocking=false`.
- Updated `diagnose_live.py` production acceptance classification with
  `blocking_required_truth`, `contained_admission`, and
  `nonblocking_health_diagnostic` counters/conclusions.

### RED / GREEN Evidence

- No recovery work plus OKX bulk timeout now emits only the nonblocking bulk
  diagnostic event and does not enter risk-only semantics.
- Truth-required residual work plus OKX bulk timeout records
  `recovery.required_position_bulk_fallback_planned`, then probes only the owned
  symbol and does not emit `recovery.required_position_truth_unavailable` unless
  fallback is unavailable or fails.
- 3000 stale non-candidate quotes do not produce
  `runtime.order_quote_stale_skipped`, do not produce `runtime.quote_stale`, and
  do not set candidate quote-stale freshness blockers.
- A stale quote on a Hyperliquid admission-blocked candidate is pruned before
  entry quote tracking, so it does not produce
  `runtime.order_quote_stale_skipped` or `runtime.quote_stale`.
- `diagnose_live.py` accepts contained Hyperliquid admission plus nonblocking
  bulk health diagnostic as a healthy window when local/exchange truth is clean.
- `diagnose_live.py` blocks when `recovery.required_position_truth_unavailable`
  is explicitly blocking.

### Root Cause

`credential_has_aster_v3_signer()` only checked that a credential value existed
and that `eth-account` was installed. It did not verify that the configured
legacy Aster secret was an API-wallet private key that can derive a signer.
`AsterAdapter.__init__()` therefore created `AsterV3Client`, which attempted
signer derivation during live startup and crashed the whole runtime.

This is a deploy/startup safety bug, not a trading-state transition. Invalid or
missing Aster Pro API V3 signing material must disable Aster private operations
with explicit auth-failure evidence; it must not prevent public market data or
the rest of the runtime from starting.

### Fix

- `credential_has_aster_v3_signer()` now normalizes the configured key and
  requires `_derive_signer_address()` to succeed before returning true.
- Aster live transport no longer treats an invalid Aster signer as a public
  transport startup failure.
- `AsterAdapter` creates the private V3 client only when the signer is
  deterministic. If private signing is unavailable, private truth/order methods
  fail closed with `TransportErrorCategory.AUTH_FAILURE` and
  `aster private API disabled` evidence instead of falling back to legacy
  Binance-HMAC paths or returning false empty truth.
