### Root Cause

This cluster is not a single missing branch. The root issue was that several
already-fixed V1/exchange-semantics paths still lacked deterministic evidence
for deployment review:

1. live mismatch flatten could succeed or fail without enough post-cleanup truth
   to prove whether the exchange artifact was actually gone.
2. passive maker timeout cancel evidence did not explicitly say that ACK is not
   terminal and reconciliation must continue through order/progress truth.
3. open-interest structural degraded diagnostics had the decision but not enough
   venue/source/floor/current-value/revalidate fields to avoid over-broad
   `snapshot_degraded` interpretation.

### V1 / Exchange Decision

- V1 recovery decision core semantics stay authoritative for live artifact
  ownership and clear/block decisions. A successful cleanup must return to truth
  and core-owned clear/block evidence.
- Bybit/OKX-style ACK-only order responses are not terminal fills. They must
  preserve order identifiers and route to order/progress/live truth before
  terminal close/recovery decisions.
- Snapshot/OI degraded data is domain-scoped evidence. It should not be treated
  as a global trading blocker unless the affected truth is required by entry,
  close, or recovery.

### Fix

- Added read-only `_post_cleanup_position_truth()` evidence after live mismatch
  cleanup. Exceptions become `truth_available=false` evidence, not state-machine
  failures.

  `recovery.live_mismatch_flattened` and
  `recovery.live_mismatch_flatten_failed`.
- Added `cancel_ack_terminal=false`,
  `truth_required_by=pending_entry_passive_reconciliation`,

## Cluster CL-053-aster-v3-invalid-signer-startup-crash

- Status: fixed, deployed, and cloud verified
- Severity: critical
- Fingerprint:
  `aster_v3.invalid_legacy_secret_startup_crash + adapter_creation_failed + live_service_auto_restart`
- Components: `venue-aster`, `venue-transport`, `live-runtime`,
  `production-deploy`
- Symbols: `credential_has_aster_v3_signer`,
  `AsterAdapter.__init__`, `VenueTransport._validate_live_credentials`
- Files: `lightfee/venues/aster_v3.py`, `lightfee/venues/aster.py`,
  `lightfee/venues/transport.py`, `tests/test_venues_transport.py`

### Production Evidence

Cloud deploy to `e63d70e` fast-forwarded successfully, wrote
`.deploy_version=e63d70e`, passed deploy manifest verification for all 14
critical files, and passed remote `compileall`. `lightfee-sidecar.service`
restarted active/running, but `lightfee-live.service` entered
`activating/auto-restart`.

`journalctl -u lightfee-live.service` showed startup crashing in
`lightfee/venues/aster_v3.py::_derive_signer_address`:

- `binascii.Error: Non-hexadecimal digit found`
- `ValueError: failed to derive aster signer from private key`

Credentialed read-only diagnosis after the failed start reported:

- `deploy_status.git_head=e63d70e`
- `deploy_status.deploy_version=e63d70e`
- `version_mismatch=false`
- `health.ok=false`
- `fingerprints=["service_lightfee-live_activating"]`
- Aster exchange-truth status `adapter_creation_failed`
- Other venue position/open-order probes succeeded and were flat/no-open-orders

No manual order, cancel, or runtime-state edit was performed.

### Root Cause

`credential_has_aster_v3_signer()` only checked that a credential value existed
and that `eth-account` was installed. It did not verify that the configured
legacy Aster secret was an API-wallet private key that can derive a signer.
`AsterAdapter.__init__()` therefore created `AsterV3Client`, which attempted
signer derivation during live startup and crashed the whole runtime.

This is a deploy/startup safety bug, not a trading-state transition. Invalid or
missing Aster Pro API V3 signing material must disable Aster private operations
with explicit auth-failure evidence; it must not prevent public market data or
the rest of the runtime from starting.

### Fix

- `credential_has_aster_v3_signer()` now normalizes the configured key and
  requires `_derive_signer_address()` to succeed before returning true.
- Aster live transport no longer treats an invalid Aster signer as a public
  transport startup failure.
- `AsterAdapter` creates the private V3 client only when the signer is
  deterministic. If private signing is unavailable, private truth/order methods
  fail closed with `TransportErrorCategory.AUTH_FAILURE` and
  `aster private API disabled` evidence instead of falling back to legacy
  Binance-HMAC paths or returning false empty truth.

### RED / GREEN Evidence

- `test_aster_private_truth_reports_auth_failure_when_signer_invalid` failed
