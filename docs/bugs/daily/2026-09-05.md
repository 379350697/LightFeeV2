# Bug Ledger Daily - 2026-09-05

## Bitget historical close discovery is now wired to the unified adapter contract

Status: **deployed; post-hotfix observation complete**.

### Root cause

When a Bitget close had no durable exact order identity, `CloseRuntime` already
called the shared `VenueAdapter.discover_historical_close_fill_reconciliation`
contract. Bitget implemented account-family-specific order history contracts and
exact order-status lookup, but had no implementation of that discovery method.
The runtime therefore classified every eligible Bitget history debt as
`history_discovery_unsupported` and could not complete an otherwise recoverable
audit record. Existing tests covered Bitget status/detail requests, but never
called the Bitget adapter through the runtime discovery interface.

The authoritative contract is: query a bounded, account-family-correct history
window; require exactly one close-owned row whose **executed** quantity matches;
then recheck that order through the existing exact status path and require a
complete fee field. Classic uses `entrustedList`/`endId` with
`productType=USDT-FUTURES`; UTA uses `list`/`cursor` with
`category=USDT-FUTURES`. In hedge mode, `posSide` plus the already-matched
opposite order side is sufficient for UTA (its order contract does not send
`tradeSide`); an explicit open marker is still rejected. In one-way mode,
`reduceOnly` or a documented close `tradeSide` is required. This matches the
existing operation contracts and Bitget's documented [Classic order
history](https://www.bitget.com/api-doc/classic/contract/trade/Get-Orders-History)
and [UTA order history](https://www.bitget.com/api-doc/uta/trade/Get-Order-History)
schemas.

### Repair

`BitgetAdapter.discover_historical_close_fill_reconciliation` now owns the
bounded Classic/UTA history lookup and calls the existing
`fetch_order_fill_reconciliation` for the exact recheck. It does not change
position truth, retry indefinitely, infer a fill from submitted `size`, or add
a second reconciliation queue. Candidate matching uses `baseVolume`/`cumExecQty`
and close ownership (`posSide`, `tradeSide`, `reduceOnly`); an explicit executed
quantity of zero is authoritative and cannot fall back to submitted size.

The Bitget order-status parser now records `fee_evidence_complete`. A literal
fee of zero, including a zero in UTA `feeDetail`, is complete evidence; missing
or malformed fees remain incomplete and fail closed.

### Post-deploy evidence and follow-up repair

The first deployment of this change (`cfbf4134`) was read-only verified on the
cloud at `2026-09-05 02:07 CST`. All seven exchange position/order probes were
high-confidence flat with no open orders, and both services were active as
singletons. The new Bitget history path was exercised naturally for four
existing debts, but the live log recorded `ValueError: Bitget order history
rows are malformed` for each Classic history query. Bitget's empty history
window is allowed to encode the collection as JSON `null`; treating that
normal empty page as malformed kept the debt retryable and prevented the
adapter from reaching its ordinary `no_candidate` result.

The follow-up repair (`98875c29`) normalizes a null `entrustedList`/`list`
collection to an empty page while retaining strict rejection for other
malformed shapes. A production-path regression covers both Classic and UTA
null collections. This is a response-shape compatibility fix at the shared
history parser boundary, not a retry or state-clearing workaround.

After deployment at `2026-09-05 02:13 CST`, the same four Bitget debts were
queried naturally. All four now return the ordinary bounded `no_candidate`
terminal result (`candidate_count=0`, `retryable=false`); no
`history_query_error` or malformed-row error appears in the post-hotfix run.
The debts remain immutable evidence debt because no unique execution/fee
candidate exists; they are not positions, orders, or new trading risk.

### Regression evidence

- Real `BitgetAdapter` Classic and UTA discovery tests exercise the family

### Closure boundary

The unified-contract implementation and null-collection fix are deployed at
`98875c29` and passed a read-only production observation. Existing terminal
debts remain immutable unless a unique candidate and exact execution/fee
recheck satisfy the contract; no order or cancel should be forced for
verification. A future unique match may close an evidence debt, while a
continued no-candidate result is a valid terminal outcome.
