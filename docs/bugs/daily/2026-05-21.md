## Cluster CL-001-live-order-mode-and-recovery-latch-root-fix

### Summary

After the `1029089` Hyperliquid/fail-closed deployment and subsequent local-L2 catalog fixes, the old live run entered a new set of real opening blockers:

- Binance maker orders rejected with `HTTP 400 {"code":-4061,"msg":"Order's position side does not match user's setting."}` on `IRYSUSDT` and `CHIPUSDT`.
- Bybit maker cancel during pending-entry cleanup failed with `HTTP 404`, then recovery entered `recovery.maker_cancel_failed_fail_closed`.
- The state became clean but stuck: `lifecycle=risk_only`, `risk_mode=fail_closed`, `open_position_count=0`, `pending_entry_count=0`, `pending_close_count=0`, `recovery_blocked_reason=null`, operator override absent.

This was not a local-L2 parser issue. It was live order/exchange semantics plus a V1 fail-closed latch gap after live recovery cleanup.

### Root Cause

Three root causes were confirmed:

- Binance/Aster order placement did not query actual Futures position mode. It omitted `positionSide` for Hedge Mode accounts and used `reduceOnly` for reduce-only in all modes. Binance USD-M New Order docs specify `positionSide` defaults to `BOTH` in One-way Mode, but must be `LONG` or `SHORT` in Hedge Mode, and `reduceOnly` cannot be sent in Hedge Mode.
- Bybit passive cancel reused `spec.order_path`, which is `/v5/order/create`, and sent `DELETE /v5/order/create`. Bybit V5 docs specify cancel as `POST /v5/order/cancel` with `category`, `symbol`, and either `orderId` or `orderLinkId`.
- `1029089` fixed startup/supervisor clean fail-closed recovery, but the live post-entry recovery path could still clean all work after a fail-closed event and remain in `risk_only/fail_closed` until a startup or specific supervisor branch cleared it.

### Fix Status

Fixed and deployed in `f0e5b39`.

- `VenueTransport._refresh_fapi_position_mode()` queries `/fapi/v1/positionSide/dual` once per Binance/Aster transport and caches Hedge vs One-way.
- Binance/Aster market and passive order bodies now send `positionSide=LONG/SHORT` only in Hedge Mode. In One-way Mode they omit `positionSide` and keep reduce-only semantics.
- `VenueTransport.cancel_passive_order()` now routes Bybit cancel to `POST /v5/order/cancel` and treats a successful Bybit cancel response as a CANCELED passive ack.
- `LiveRuntime._post_tick_housekeeping()` calls the same V1-style clean fail-closed latch clearing used by startup recovery: no operator fail-closed, no `recovery_blocked_reason`, and no `needs_reconciliation(state)` work.
