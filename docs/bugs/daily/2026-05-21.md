## Cluster CL-004-bybit-hedge-resting-limit-and-aster-buffer-v1-drift

### Summary

Current cloud evidence showed Bybit was not actually out of funds: a read-only Bybit open-order probe found 12 live USDT-linear resting orders. One was a passive maker order; 11 were hedge legs for `IRYSUSDT` and `LYNUSDT`.

The live event chain for the hedge orders was:

- `pending_entry.hedge_submit_attempt`
- `order.submit_attempt` with `orderType=Limit`, rounded price hints such as `0.04` / `0.05`, `reduceOnly=false`, and Bybit hedge `positionIdx=2`
- `order.submit_result` ack accepted
- `pending_entry.hedge_submit_result` with `outcome=error` and text like `order accepted ... fill not confirmed`

That made the funds appear unavailable because hedge repair orders rested on Bybit instead of executing as taker/IOC orders.

In the same investigation, the remaining data-plane branch with concrete V1 drift was Aster/Binance-style pre-snapshot buffering: V2 treated buffer overflow itself as rebuild evidence, while V1 keeps the newest 4096 buffered updates and lets snapshot replay decide whether a rebuild is needed.

### Root Cause

Two V1/V2 parity gaps were confirmed:

- V1 Bybit `place_order` sends normal taker orders as `orderType=Market`; only `submit_passive_entry_order` sends `orderType=Limit` with `PostOnly`. V2 `VenueTransport.place_order()` treated any non-null `OrderRequest.price` as a limit order. Missing-hedge repair passes a hedge price hint, so Bybit hedge repair became a resting limit order.
- V1 Aster/Binance pre-snapshot buffering drops the oldest update at cap 4096 and continues waiting for the REST snapshot. V2 cleared the buffer, reset the book sequence, transitioned to rebuilding, and emitted `runtime.local_l2_buffer_overflow_rebuild` at overflow time. V2 replay also missed the V1 previous-link anchor bridge where `previous_sequence == snapshot_anchor`.

The order-mode drift had the same class risk for Binance/Aster, OKX, and Gate because their transport branches also changed to limit/GTC when `request.price` was present. Hyperliquid already had a dedicated IOC path and Bitget already sends market orders.

### Fix Status

Fixed locally, not deployed.

- Bybit `place_order()` now ignores price hints when `time_in_force=IOC` and sends `orderType=Market` without `price`.
- Binance/Aster, OKX, and Gate `place_order()` now respect `time_in_force=IOC`; hedge/taker IOC requests do not become limit/GTC orders solely because a price hint exists.
- `LiveRuntime._drive_missing_hedge_live()` and `LiveRuntime._recover_drive_missing_hedge()` now set `TimeInForce.IOC` on missing-hedge repair orders.
- `LocalL2DataPlane.ingest_external_update()` now follows V1 Aster/Binance semantics during bootstrapping/rebuilding overflow: drop oldest, keep newest window, and do not rebuild until replay evidence says so.
- `LocalL2DataPlane._replay_buffered_updates()` now accepts the V1 start conditions: anchor in update range, expected next sequence in update range, or explicit previous-link match to snapshot anchor.

This prevents new hedge/taker repair orders from becoming orphaned resting limits. It does not cancel the 12 currently open Bybit orders; canceling live exchange orders is a separate state-changing operation and needs explicit operator approval or an owned-order cleanup run.

## Cluster CL-001-live-order-mode-and-recovery-latch-root-fix

### Summary

After the `1029089` Hyperliquid/fail-closed deployment and subsequent local-L2 catalog fixes, the old live run entered a new set of real opening blockers:

- Binance maker orders rejected with `HTTP 400 {"code":-4061,"msg":"Order's position side does not match user's setting."}` on `IRYSUSDT` and `CHIPUSDT`.
- Bybit maker cancel during pending-entry cleanup failed with `HTTP 404`, then recovery entered `recovery.maker_cancel_failed_fail_closed`.
- The state became clean but stuck: `lifecycle=risk_only`, `risk_mode=fail_closed`, `open_position_count=0`, `pending_entry_count=0`, `pending_close_count=0`, `recovery_blocked_reason=null`, operator override absent.

This was not a local-L2 parser issue. It was live order/exchange semantics plus a V1 fail-closed latch gap after live recovery cleanup.

### Root Cause

Three root causes were confirmed:

- Binance/Aster order placement did not query actual Futures position mode. It omitted `positionSide` for Hedge Mode accounts and used `reduceOnly` for reduce-only in all modes. Binance USD-M New Order docs specify `positionSide` defaults to `BOTH` in One-way Mode, but must be `LONG` or `SHORT` in Hedge Mode, and `reduceOnly` cannot be sent in Hedge Mode.
- Bybit passive cancel reused `spec.order_path`, which is `/v5/order/create`, and sent `DELETE /v5/order/create`. Bybit V5 docs specify cancel as `POST /v5/order/cancel` with `category`, `symbol`, and either `orderId` or `orderLinkId`.
- `1029089` fixed startup/supervisor clean fail-closed recovery, but the live post-entry recovery path could still clean all work after a fail-closed event and remain in `risk_only/fail_closed` until a startup or specific supervisor branch cleared it.

### Fix Status

Fixed and deployed in `f0e5b39`.

- `VenueTransport._refresh_fapi_position_mode()` queries `/fapi/v1/positionSide/dual` once per Binance/Aster transport and caches Hedge vs One-way.
- Binance/Aster market and passive order bodies now send `positionSide=LONG/SHORT` only in Hedge Mode. In One-way Mode they omit `positionSide` and keep reduce-only semantics.
- `VenueTransport.cancel_passive_order()` now routes Bybit cancel to `POST /v5/order/cancel` and treats a successful Bybit cancel response as a CANCELED passive ack.
- `LiveRuntime._post_tick_housekeeping()` calls the same V1-style clean fail-closed latch clearing used by startup recovery: no operator fail-closed, no `recovery_blocked_reason`, and no `needs_reconciliation(state)` work.

## Cluster CL-003-pending-entry-hedge-submit-reconciliation-v1-drift

### Summary

Cloud run `lightfee-1779339979926-1296893` produced shortlist and finallist entries, then registered three pending entries (`IRYSUSDT`, `LAYERUSDT`, `CHIPUSDT`). They eventually self-cleared: `/opt/lightfee-v2/runtime/live-state-current.json` moved from `pending_entry_count=3` to `pending_entry_count=0`, with `entry.aborted` events using `pending_entry_max_lifetime_exhausted` and cleanup legs. Therefore the system was not unable to recover.

However, the recovery took the hard-ceiling path. V1 does an earlier closure attempt inside `hedge_pending_entry_delta()`: after a hedge submit error, it immediately calls `fetch_order_fill_reconciliation(symbol, "", client_order_id)` before leaving the pending entry unresolved. V2 `_drive_missing_hedge_live()` only logged `pending_entry.hedge_submit_result` and retained non-rejected `hedge_inflight` for later reconciliation.

The same cloud and older-run samples also showed a separate Hyperliquid request-shape failure: `order.submit_result` for `CHIPUSDT`, `FOGOUSDT`, `JTOUSDT`, `SAGAUSDT`, and `LAYERUSDT` returned `HTTP 422: Failed to deserialize the JSON body into the target type`. The recorded body had top-level fields `["action", "cloid", "nonce", "signature", "vaultAddress"]`, order `c` equal to internal CIDs such as `ef9430593b928d105d7a6b009d26188664db`, and `tif="Gtc"` even though the path was a hedge/taker repair order. Hyperliquid official docs require cloid to be an optional 128-bit hex string inside order field `c`, not a top-level request field, and V1 maps internal CIDs through `hyperliquid_cloid_for_client_order()` while submitting taker orders as IOC. V1 also defaults `account_address` to the wallet address and keeps `vault_address=None`; V2 had no wallet fallback and treated `account_address` as `vaultAddress`.

### Root Cause

V2 had a V1 parity gap in the normal live pending-entry hedge path:

- V1 `src/execution_core/entry_sync.rs` lines 5116-5231 reconciles by hedge `client_order_id` immediately after submit error.
- V1 increments `hedge_attempt_count` and seeds each hedge retry CID with the attempt; V2 reused the same hedge CID for repeated zero-fill/uncertain retries.
- V1 Hyperliquid maps internal CIDs to `0x` + 16-byte SHA-256 prefix cloids and sends taker order `tif="Ioc"`; V2 sent internal CIDs directly and used `Gtc` when a hedge price hint was present.
- V1 Hyperliquid `new_with_wallet_policy()` uses configured account address only when present, otherwise `wallet.address()`, and sets `vault_address: None`; V2 required an explicit account address for private WS/reconciliation and sent that account as `vaultAddress`.
- Hyperliquid official exchange endpoint docs list request body fields as `action`, `nonce`, `signature`, optional `vaultAddress`/`expiresAfter`; `cloid` is only order field `c` and must be a 128-bit hex string.
- Production evidence matched these drifts: Bybit returned `order accepted ... fill not confirmed`, Hyperliquid returned `HTTP 422: Failed to deserialize the JSON body into the target type`, and pending entries only cleared after `pending_entry_max_lifetime_exhausted`.

### Fix Status

Fixed locally, not deployed.

- `LiveRuntime._drive_missing_hedge_live()` now calls `adapter.fetch_order_fill_reconciliation(pending.symbol, "", hedge_cloid)` inside the `OrderSubmitError` branch.
- If reconciliation returns positive quantity, V2 applies the hedge fill, stores `hedge_order_id` / `hedge_fill_price`, clears `hedge_inflight`, emits `pending_entry.hedge_submit_result` with `outcome=filled` and `reconciled=true`, and returns success so the caller can finalize the pending entry.
- If reconciliation is absent, rejected/uncertain handling remains unchanged: rejected clears inflight; uncertain keeps inflight for later reconciliation.
- `PendingEntry.hedge_attempt_count` is persisted/restored and each hedge retry now uses an attempt-scoped CID seed, matching V1 retry semantics.
- Hyperliquid live `place_order()` now converts internal client IDs to official 128-bit wire cloids, puts that value only in order field `c`, omits top-level `cloid`, and uses IOC for hedge/taker orders even when a price hint is present.
- Hyperliquid live credentials now default `account_address` from the wallet when the config omits account env, so private WS and order reconciliation use the same user identity as V1.
- Hyperliquid `/exchange` signing now passes `vault_address=None` instead of reusing `account_address` as `vaultAddress`, matching V1 non-vault account semantics.
- Hyperliquid order reconciliation converts internal CIDs to wire cloids before querying `orderStatus` and parses the official nested `{"status":"order","order":{"order":...,"status":"filled"}}` shape.
