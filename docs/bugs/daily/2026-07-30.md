# Bug Ledger - 2026-07-30

## Cluster CL-166 - Broad Sidecar Observation Was Coupled to Final BBO/L2 Freshness

Status: local root fix verified; deployment and controlled live entry proof pending

### Evidence and Root Cause

`runtime.max_market_age_ms` was serving two incompatible owners: the strict
selected-pair BBO/Local-L2 execution lease and the main sidecar's aggregate
multi-venue collection watermark.  The latter is produced after broad quote,
funding, contract, and candidate work, so a normal slow scan could exceed the
3--5 second execution budget.  `decide_snapshot_freshness(...)` then treated a
publish-fresh snapshot as `LAST_GOOD_FALLBACK` for up to the ten-minute V1
recovery window.  This obscured producer latency and made global recovery
semantics decide whether a current candidate was considered.

The sidecar is a discovery publisher: broad public funding metadata, contract
availability, top-of-book hints, 24-hour volume/liquidity evidence, candidate
ranking inputs, lifecycle/degradation facts, and a deferred-OI handoff.  It is
not the executable quote owner.  The selected pair still requires current
funding evidence plus candidate-scoped BBO/Local-L2, OI/liquidity, account
truth, and final execution validation before an order can be dispatched.

### Root Fix

1. Add `runtime.sidecar_market_observation_max_age_ms` with a 30-second
   default.  This is the broad-universe observation health budget;
   `max_market_age_ms` remains the strict execution BBO/Local-L2 budget.
2. Change `runtime.sidecar_snapshot_max_age_ms` from 10 to 30 seconds.
   The actual sidecar collection/publish cadence was 9–15 seconds, so 10
   seconds was an availability deadline that could expire during a healthy
   collection cycle. `runtime.sidecar_snapshot_publish_warn_ms=10000` is now
   the nonblocking producer SLO and emits the rate-limited
   `runtime.snapshot_publish_slow` diagnostic.
   `scripts/diagnose_live.py` uses the same 30-second default, so a healthy
   9--15 second main-sidecar collection cycle cannot be reported as stale only
   by the diagnostic path.
3. A publish-fresh snapshot with an over-budget broad observation is now
   classified as `STALE`, never substituted by a global last-good snapshot.
   Runtime may retain only that current publish-fresh snapshot as degraded
   candidate discovery and records targeted revalidation.
4. Snapshot acquisition provenance is global.  It can report an unrelated
   venue/symbol fallback, so it cannot discard a pair that has current scoped
   evidence.  Per-pair freshness and final BBO/L2/OI gates make that decision.
5. Publication stale or missing snapshots retain V1's bounded last-good
   recovery behavior.  No BBO/L2, OI, funding, liquidity, account-truth, or
   final entry threshold was widened.

### Regression Proof and Remaining Boundary

Local tests prove a 9–15-second published snapshot remains available (rather
than entering last-good), records the 10-second producer SLO as a nonblocking
diagnostic, and keeps the 30-second unavailable boundary. A broad-market stale
snapshot still does not enter global last-good fallback even when the 10-minute
V1 recovery window is present; a publish-fresh pair with fresh scoped evidence
remains eligible for its existing final checks; publish stale/missing recovery
is unchanged; configuration validation rejects invalid availability/SLO bounds.
Deployment must confirm that `runtime.snapshot_fallback_last_good` no longer
represents normal slow broad scans, while `runtime.snapshot_degraded` carries
the targeted revalidation marker and real orders still require fresh final
evidence.

## Cluster CL-167 - Slow OI/Liquidity Evidence Was Mixed with Execution Leases

Status: local root fix verified; deployment and controlled live entry proof pending

### Evidence and Root Cause

V2 had accumulated incompatible time controls: the sidecar's broad discovery
snapshot carried both 24-hour volume/OI and non-executable quote hints, while
the old `sidecar_perp_liquidity_budget_ms` was used as an entry freshness
budget.  A hard 30-second floor in the runtime then silently defeated smaller
configuration values.  This made a normal 9--15 second sidecar cycle look too
old for slow data and caused per-candidate targeted OI repair requests.

At the same time, `entry_min_first_funding_remaining_secs`, batch-candidate
settings, transfer timers, and generic lifecycle-SLA fields appeared in V2
configuration without owning the actual runtime business decision.  The
selected-entry 300-second SLA could even overrule V1's pending-entry 60/120
second terminality contract.  Private-WS reconnect settings had the opposite
failure: they existed in configuration but venue workers used literals.

### Root Fix

1. Introduce the explicit `runtime.slow_evidence_max_age_ms=600000` contract
   for locally persisted sidecar OI and 24-hour-volume evidence. It is bounded
   to ten minutes and never applies to BBO, Local-L2, quote skew, funding, or
   account truth. Targeted OI is now a repair only after that local proof is
   missing or too old; its 750 ms request deadline remains bounded.
2. Remove the obsolete liquidity-budget and liquidity-timeout configuration,
   including the hidden 30-second floor. Old keys fail configuration loading
   rather than silently changing a different business contract.
3. Remove V2 pseudo-controls that were not wired to the corresponding flow.
   Funding entry uses V1's `min_scan_minutes_before_funding`; pending entries
   use V1's 60-second zero-fill force-terminal and 120-second hard ceiling;
   the retained 15-second selected-to-submit deadline is real. The lifecycle
   table remains diagnostic/quote-rewarm metadata, not a parallel deadline
   control plane. Transfer capability remains unsupported rather than claiming
   unimplemented cache/fallback behavior.
4. Wire the existing private-WS reconnect settings into the transport before a
   worker starts; all venue workers consume that single policy. No worker
   lifecycle, subscription, or exchange order semantics changed.

The earlier CL-160 SQLite-store narrative did not match the current production
source: that store is absent and its configuration has been rejected. The
atomic persisted sidecar snapshot is the actual local slow-evidence store.
This correction intentionally does not claim a separate OI SQLite durability
guarantee.

### Regression Proof and Remaining Boundary

Regression coverage verifies the ten-minute cap, a timed-out targeted OI
repair remains hard-deadlined, OI cache fallback expires after ten minutes,
an explicitly narrower slow-data budget is honoured without a 30-second
floor, V1 funding/pending-entry semantics remain sole owners, and each private
WS worker receives the transport policy. Live deployment must show that valid
local slow evidence suppresses per-candidate OI HTTP repair; final entry still
requires its unchanged strict BBO/Local-L2 and other admission evidence.

## Cluster CL-168 - Remaining Local-L2/OI/Lifecycle Time Contracts Were Not Single-Owner

Status: local root fix verified; deployment and controlled live entry proof pending

### Evidence and Root Cause

The V2 entry session selected a Local-L2 readiness age from an ad-hoc field,
quiet-book grace, or normal book age, then silently fell back to 300 seconds.
Final entry, maker fill, and close still required a five-second executable
liquidity snapshot. The same book could thus be session-ready for five minutes
while unable to pass its final executable gate. The V1 OKX exception was also
not resolved per leg. Separately, an OI cache marker could widen a configured
slow-evidence limit, and diagnosis fabricated `action_taken` from elapsed
lifecycle budgets without a proving journal event.

### Root Fix

1. Restore V1 Local-L2 defaults: 1-second normal book age, 10-second
   quiet-book readiness grace, and a per-leg OKX 65-second exception. The
   retired 300-second precedence field now fails config loading. Session
   readiness, selection, activation, HOT-book stale/rebuild and refresh,
   snapshots, entry gate, and passive reprice consume the same per-venue
   resolver; the final five-second executable check is unchanged.
2. Keep untracked Local-L2 books for the V1 60-second scan-idle cleanup only;
   retention is not readiness or executable quote evidence.
3. Remove the runtime-level OI fallback TTL. `slow_evidence_max_age_ms` is the
   sole total bound; cache-source metadata may narrow it but cannot widen it.
4. Diagnostics retain budget labels, but `action_taken` is journal/contract
   evidence only. An elapsed phase without proof is
   `action_evidence_status=not_observed`. Quote rewarm remains a business
   contract handoff because that contract supplies terminal evidence.

### Regression Proof and Remaining Boundary

Tests cover per-leg Binance/OKX readiness divergence, retired-field rejection,
a cache marker wider than a 60-second total OI bound, final-submit stale
fallback rejection, and no-action lifecycle diagnostics. No BBO, L2 sequence,
OI floor, close truth, or order guard is relaxed. Deployment must confirm real
candidate sessions do not linger falsely ready and that OI HTTP repair only
starts after the persisted slow proof is older than its total bound.
