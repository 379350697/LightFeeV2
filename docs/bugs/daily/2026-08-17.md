- Status: implemented locally on `e15c132`; not committed, deployed, or

### Authoritative Contract

V1-compatible reconciliation gives each exchange the identity belonging to its
live long/short leg, not the maker/hedge storage order. A pending entry can
become a managed open position only after trusted positive quantity **and**
price evidence exists for both legs. A local recovery id such as
`entry-...-recovery-long` is not an exchange order id.

Bybit's accepted order acknowledgement is asynchronous, and order lookup gives
`orderId` priority over `orderLinkId`. Therefore a recovery placeholder must
not shadow a valid submitted `orderLinkId`; without a client id it remains an
evidence gap and the existing live-position path is used. Sources:
[Bybit create order](https://bybit-exchange.github.io/docs/v5/order/create-order),
[get open and closed orders](https://bybit-exchange.github.io/docs/v5/order/open-order),
and [execution list](https://bybit-exchange.github.io/docs/v5/order/execution).

### Root Cause and Broken Path

When `maker_leg == "short"`, the normal-tick pending-entry reconciler sent
maker identifiers to the long venue and hedge identifiers to the short venue.
Startup recovery had separate correct mapping, so the two production paths
disagreed. The normal Bybit order lookup also treated the V2 synthetic
`-recovery-` id as `orderId`, preventing its valid client id from resolving
the actual order and executions. Finally, live-position hydration returned
before inspecting prices whenever live matched quantity was already known.

The resulting path was:

`ACK-only hedge -> wrong/masked reconciliation identity -> valid Bybit price
not recovered -> finalizer rejects zero hedge price -> no managed owner ->
passive close cannot own the balanced live pair -> risk_only`.

Earlier tests covered quantity increases and Binance placeholder handling, but
missed the combination of a short maker, an equal live/local quantity with a
missing price, and Bybit's distinct `orderId`/`orderLinkId` semantics.

### Repair

- One shared pending-entry identity mapper now maps stored maker/hedge
  identities into long/short venue order. Both normal tick and startup force
  recovery use it.
- Bybit now clears a local `-recovery-` placeholder when a client id exists,
  resolves through `orderLinkId`, then fetches executions by the real
  `orderId`. With no client id it records an explicit evidence gap and makes
  no malformed request.
- Live-position hydration now updates a missing price when exchange balanced
  quantity covers the known local quantity. It still requires positive price
  evidence and never opens from quantity alone.

No strategy, OI/liquidity filter, sizing, admission, order placement, retry,
or close-submission behavior changed. Normal reconciliation performs the same
requests; the recovery-placeholder branch replaces an invalid Bybit lookup
with the existing valid client-id lookup.

### Counterexample Matrix

| Boundary | Expected result |
|---|---|
| short maker in normal tick | maker identity queries short venue; hedge identity queries long venue |
| short maker at startup | exactly the same identity mapping as normal tick |
| equal local/live quantity, one positive live price missing locally | hydrate that price and finalize through existing V1 path |
| equal quantities, exchange price absent | retain pending; do not create an open position |
| Bybit recovery placeholder plus client id | query `orderLinkId`, resolve true `orderId`, then executions |
| Bybit recovery placeholder without client id | no exchange request; explicit evidence gap |
