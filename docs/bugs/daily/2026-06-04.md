### Summary

V1/V2 source comparison found several close-path semantic gaps behind the
question "why did force close not trigger?" The deployed V2 code had helpers
for some V1 concepts, but several were not connected to the active runtime
path or did not propagate into inner force/compensation paths.

### Root Cause

| Issue | Classification | Root cause |
|---|---|---|
| `settlement_force_close` did not trigger | V2 semantic drift | `force_close_due()` existed only as a helper/test surface; runtime normal exit called `standard_close_reason()` directly, so aligned force-close deadlines degraded into `funding_capture`. |
| Death-line single-side protection touched both legs | V2 semantic drift | `RiskExecutionPlan` did not carry V1 `select_single_side_protection_target()` venue/side/stage. Supervisor logged single-side protection but called full `execute_close()`. |
| Residual repair repeated Bybit `110072` | Coverage split | Ordinary close and entry cleanup had duplicate-client reconciliation, but residual repair used deterministic `residual_repair` CID and only rescheduled on duplicate. |
| Close compensation/hard-stop duplicate lacked evidence | Coverage split | `_compensate_close_leg_exposure()` swallowed placement errors into flat rechecks and did not query Bybit order evidence or record a reconciled compensation leg. |
| Risk/protection PnL buckets stayed zero | V1 state fidelity drift | V2 had `risk_delever_*` and `protection_*` state fields but close writeback only updated generic realized PnL/fees. |
| Full V1 risk-delever L2 sizing | Still open | GitNexus impact for `build_risk_execution_plan` is HIGH. V2 still lacks the full V1 `risk_delever_sizing_plan()` integration with true-L2/top-book capacity, slippage, hot local-L2 requirement, and min-notional residual checks. This needs a dedicated high-risk change, not a cosmetic frequency reduction. |

### V1 / Exchange Decision

- V1 copy: `settlement_force_close` is evaluated outside standard close
  reasons and overrides ordinary funding close once force deadline is due.
- V1 copy: death-line protection selects exactly one venue/side/stage before
  entering fail-closed; it must not silently become a synchronized two-leg
  close.
- Exchange semantics: Bybit `110072 OrderLinkedID is duplicate` is an
  idempotency conflict. Existing V2 duplicate reconcile helper is reused for
  residual repair and compensation instead of creating a new exchange rule.
- V1 state fidelity: risk-delever and protection close PnL remain separately
  attributable in position state.

### Attempts

| Attempt | Status | Why |
|---|---|---|
| Treat force-close as ordinary `standard_close_reason` | ineffective | It returns `funding_capture` before `settlement_force_close`, losing V1 priority. |
| Reuse full `execute_close()` for death-line protection | ineffective | It submits both legs, which violates V1 single-side protection semantics. |
| Let residual/compensation duplicate paths retry blindly | ineffective | Deterministic CIDs can reproduce Bybit `110072` and leave insufficient order evidence. |
| Implement full risk-delever L2 sizing in this patch | deferred | Impact is HIGH and requires wiring runtime/local-L2 execution-liquidity snapshots into risk planning. |

### Fix

- Runtime normal exit now checks `force_close_due()` first and routes due
  aligned positions as `settlement_force_close`.
- `RiskExecutionPlan` now carries single-side protection target
  `protection_venue`, `protection_side`, and `protection_stage`, derived from
  degraded venue or health ratio.
- Supervisor now executes death-line protection through a single-leg reduce-only
  IOC close path, logs success/failure/unavailable evidence, and then enters
  fail-closed.
- `CloseExecutor.execute_single_side_protection()` submits one selected
  reduce-only IOC leg and reuses the existing close-leg retry and Bybit
  duplicate reconciliation machinery.
- Residual repair now reconciles Bybit duplicate CIDs with
  `reconcile_bybit_duplicate_client_order()`, clears live-flat/full evidence,
  retries partial live exposure with a fresh CID, and records structured
  `recovery.residual_repair_duplicate_client_order_reconcile_result`.
- Close compensation now reconciles Bybit duplicate compensation orders,
  records `exit.compensation_duplicate_client_order_reconcile_result`, and
  returns a reconciled fill leg when the old order is proven filled.
- Close writeback now fills V1 risk/protection realized PnL buckets based on
  close reason.

### Summary

Bybit account history showed a serious V2/V1 parity gap family: entries such
as `MEUUSDT` opened around `2026-06-03 20:12`, outside the expected Bybit
settlement-close window; multiple Bybit legs closed after seconds; and at
least one position stayed exposed for more than eight hours before close. The
incident is dual-leg by definition: Bybit maker/fill evidence must correspond
to the opposite venue leg before V2 can finalize an entry or drive close.

### Root Cause

| Issue | Classification | Root cause |
|---|---|---|
| Bybit maker zero-fill finalized while order was not terminal | V2 semantic drift | `_finalize_pending_entry()` treated a zero maker reconciliation as removable even when the maker order still had nonterminal `new` / unresolved evidence. V1 keeps the pending entry until terminal no-fill/fill evidence exists. |
| Later stale zero reconciliation erased known hedge fill | V2 semantic drift | A subsequent zero order reconciliation could overwrite a confirmed positive leg fill. That converted a real two-leg position/residual into a false unmatched branch and could trigger one-sided cleanup. |
| Pending passive close ignored settlement force deadline | V2 semantic drift | Passive close retry state could keep a future `next_retry_at_ms` after the V1 force window, so overdue close work was not armed into DUAL_TAKER promptly. |
| Passive close fallback retried forever after executor/zero-fill failure | V2 semantic drift | `_fallback_to_aggressive_close()` kept applying short backoff when `close_executor` was unavailable, invalid, returned `None`, or returned zero fill without a pending close, even after the V1 exit hedge deadline was hard-breached. |
| Hedge gap kept retrying after hard breach | V2 semantic drift | Unhedged maker/hedge gaps were allowed to attempt more hedge/retry work instead of entering fail-closed with compensation and exchange-truth flat probing. |
| Maker-leg live-flat truth could race another close path | V2 mutual-fight drift | `_resolve_flat_maker_leg_from_live_truth()` could submit or continue maker work in the same drive cycle after live truth proved the maker leg already flat and one-sided flatten had been submitted on the opposite leg. Runtime drift correction could also compete while the passive-close live action was still settling. |

### V1 / Exchange Decision

- V1 pending-entry terminality is order/fill evidence based. A zero quantity
  result is not enough if maker status is nonterminal or unresolved.
- V1 never lets later stale zero evidence erase already-confirmed positive
  fill progress.
- V1 passive exit has a hedge/fallback hard deadline. After hard breach the
  system must stop passive retry backoff, enter fail-closed, compensate where
  possible, and probe live flat truth.
- V1 passive close fallback is dual-leg close work: Bybit close actions must
  correspond to the opposite leg and cannot be accepted as isolated local
  terminality.

### Attempts

| Attempt | Status | Why |
|---|---|---|
| Let zero maker reconciliation finalize as passive unfilled | ineffective | It can drop a live/open maker order and leave later Bybit fills to recovery/cleanup. |
| Let zero reconciliation overwrite known fill | ineffective | It can erase a confirmed opposite-leg fill and create false residual/cleanup. |
| Only arm DUAL_TAKER after normal passive phase retry time | ineffective | A future retry can miss the V1 settlement-force deadline and create long exposure. |
| Keep fallback retrying on no executor / zero aggressive fill | ineffective | This preserves retry noise but does not close risk after the V1 hard deadline. |
| Let drift correction keep acting while passive close live action settles | ineffective | It can create left/right control-loop contention: passive close submits the required one-sided flatten, then runtime drift correction tries to repair the same exposure before exchange truth has settled. |

### Fix

- Pending-entry finalize now defers zero-balanced finalization when maker order
  evidence exists but terminal no-fill evidence is missing, and emits
  `pending_entry.finalize_deferred_unresolved_maker_zero_fill`.
- Fill reconciliation now ignores stale zero results when a positive fill was
  already known for that leg, and records
  `pending_entry.finalize_fill_reconciliation_ignored_stale_zero`.
- `passive_close_fallback_due()` mirrors V1 settlement force timing for
  pending passive closes, including staggered second-stage semantics.
- Runtime now arms overdue pending passive closes into `DUAL_TAKER`, resets
  phase/cycle timestamps, clears retry delay, and records
  `runtime.passive_close_deadline_fallback_armed`.
- Passive close executor now carries `maker_hedge_deadline_ms`, computes V1
  adaptive hedge/fallback hard-deadline decisions, and converts hard breaches
  into fail-closed events instead of continuing retry backoff.
- Hedge hard breaches call compensation through `compensate_failed_full_close`
  when available, then use live-flat probing before clearing local state.
- Maker-leg live-truth resolution is now terminal for the current drive cycle:
  both-flat truth clears local state; one-sided live flatten submits the
  opposite-leg close and returns without placing/continuing a maker order in
  that same tick.
- Runtime drift correction now respects pending passive close ownership while
  a live close action has `next_retry_at_ms` in the future, so the passive-close
  loop and drift-repair loop do not fight over the same dual-leg close.

### Summary

Two post-deploy concerns were separated from the order/close main loop. First,
`snapshot_fallback_blocking=insufficient_evidence` was an acceptance-gate
classification bug: candidate-scoped snapshot fallback evidence was being
counted as insufficient global diagnostic evidence. Second, Bybit `10002` is
a timestamp / `recv_window` exchange-window problem, not passive-close mutual
fighting. V1 already uses Bybit server time and a 1500ms auth timestamp
backoff; V2 matched that intent but still lost precision by preferring
`timeSecond`, and did not retry Bybit's 200-envelope `retCode=10002` response.

### Root Cause

| Issue | Classification | Root cause |
|---|---|---|
| Scoped snapshot fallback blocked acceptance as insufficient evidence | Diagnostic classification drift | `diagnose_live.py` and `analyze_production_blockers.py` detected candidate `blocked/block_reason`, but only `v1_parity_evidence` could classify it as closed. Candidate/domain/venue/age evidence was ignored. |
| Bybit 10002 did not clear server-time offset | Transport retry gap | `_is_time_offset_retryable()` only covered Binance/Aster timestamp errors, while Bybit returns V5 auth window failures as `retCode=10002` in a JSON envelope. |
| Bybit server time lost sub-second precision | V1 parity drift | V2 parsed Bybit `result.timeSecond` before `time` / `timeNano`, throwing away up to almost 1000ms inside a 5000ms `recv_window`. |
| Repeated Bybit 10002 lacked enough local evidence | Evidence gap | If a refreshed retry still failed, the error text did not include the server-time endpoint, auth timestamp, or recv-window used for the signed request. |

### V1 / Exchange Decision

- V1-style snapshot fallback is candidate/domain scoped. A stale global
  market-observed sample does not become a global production failure when the
  payload proves the affected candidate/domain/venue and source age.
- Bybit official V5 auth requires the request timestamp to satisfy the
  documented server-time / `recv_window` window, with the timestamp sent in
  `X-BAPI-TIMESTAMP` and the window in `X-BAPI-RECV-WINDOW`.
- Bybit official V5 error `10002` means the request time exceeds the time
  window. The deterministic V2 response is to clear cached server-time offset,
  fetch `/v5/market/time`, re-sign, and retry once. If it still fails, the
  remaining evidence must be explicit enough to diagnose clock/header drift.

### Fix

- `diagnose_live.py` now distinguishes "is snapshot fallback blocking" from
  "does the blocking payload have scoped evidence." Candidate-scoped fallback
  with candidate/domain/venue/age evidence classifies as `v1_parity`, not
  `insufficient_evidence`; global fallback without scope still blocks as
  insufficient evidence.
- `analyze_production_blockers.py` uses the same scoped snapshot fallback
  classifier so daily/window blocker reports and acceptance gate do not drift.
- Bybit server-time parsing now prefers top-level millisecond `time`, then
  `result.timeNano`, and only falls back to second-level `timeSecond`.
- Private Bybit requests now treat 200-envelope `retCode=10002` as a
  timestamp/recv-window retryable error, clear cached server-time offset,
  fetch fresh server time, and re-sign exactly once.
- If the refreshed retry still returns a time-window error, V2 raises a
  `TransportError` containing method, path, status, `server_time_path`,
  `auth_timestamp_ms`, `recv_window_ms`, and the response body prefix.
- Bybit success envelopes containing ordinary timestamp text are not retryable;
  the 200-response path is restricted to `retCode=10002`.
