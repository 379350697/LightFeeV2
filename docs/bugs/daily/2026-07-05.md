# Bug Ledger - 2026-07-05

## Cluster CL-153 - Pending Close Dedupe And Venue Order Truth Compatibility

Status: local verified; deploy pending.

### GitNexus Keys

- Fingerprints: `truth_gap_candidate_count=0`, duplicate
  `pending_close_reconciliations`, `start_time_ms=None`, `end_time_ms=None`
- Components: `engine-state`, `passive-close-accounting`,
  `bybit-order-truth`, `bitget-order-truth`
- Symbols: `EngineState.enqueue_pending_close_reconciliation`,
  `BybitAdapter.fetch_order_fill_reconciliation`,
  `BitgetAdapter.fetch_order_fill_reconciliation`
- Files: `lightfee/engine/state.py`, `lightfee/venues/bybit.py`,
  `lightfee/venues/bitget.py`

### Symptom

Full-suite verification after CL-152 exposed two contract drifts:

- Enqueuing a duplicate pending-close reconciliation with the same
  `(position_id, kind)` could mutate the existing record by copying arbitrary
  duplicate metadata such as `reason=duplicate` and adding
  `truth_gap_candidate_count=0`.
- Bybit/Bitget `fetch_order_fill_reconciliation()` always passed
  `start_time_ms=None` and `end_time_ms=None` into `fetch_order_status()`, which
  broke transports and tests that only implement order id / client id lookup.

### Root Cause

The close accounting layer had two business concepts mixed together:

- Duplicate enqueue should be idempotent for owner fields and should only merge
  append-only close statement/order candidates.
- Historical order-truth probing may need a time window, but normal CID/order
  reconciliation should not force optional window kwargs through every
  transport implementation.

### Unified Business Decision

- `pending_close_reconciliations` dedupe keeps one owner record per
  `(position_id, kind)`. It may merge long/short legs, statement probe
  candidates, backfill state, and positive truth-gap candidate counts, but it
  must not let a later duplicate overwrite ordinary owner metadata.
- Bybit/Bitget order-fill reconciliation passes `start_time_ms`/`end_time_ms`
  only when a real historical window is requested. Plain CID/order lookup stays
  compatible with V1-style order-status transports.

### Fix

- `EngineState.enqueue_pending_close_reconciliation()` no longer sets
  `truth_gap_candidate_count` when the merged count is zero and no longer fills
  missing `reason` from a duplicate row.
- Bybit and Bitget adapters now build order-status kwargs conditionally, adding
  historical window fields only when non-null.
- Retained accounting-only close backfill now records a deterministic retained
  evidence key. A retry with the same fills, missing leg, and exchange-truth
  hash updates queue/backoff state but does not emit a second `exit.reconciled`
  or duplicate retained audit event.

| local RED/GREEN | Bybit/Bitget CID reconciliation tests | transports without window kwargs still work |

## Cluster CL-152 - Entry Single-Leg Risk Invariant Across Hedge Reject And Maker Reprice

Status: local verified; deploy pending.

### GitNexus Keys

- Fingerprints: `entry-1783219929535-LABUSDT`,
  `hedge_rejected_after_maker_exposure`,
  `runtime.maker_event_reprice_blocked`,
  `insufficient_margin_admission_blocked`,
  `exchange_truth_nonzero_position`
- Components: `pending-entry`, `entry-admission`, `passive-maker-event`,
  `v1-lifecycle-closure`, `bug-ledger`
- Symbols: `_drive_missing_hedge_live`, `_recover_drive_missing_hedge`,
  `_maybe_tick_maker_event`, `_maker_event_reprice_reject_reason`,
  `pending_entry_has_unhedged_maker_exposure`
- Files: `lightfee/engine/runtime.py`,
  `lightfee/engine/passive_maker_runtime.py`,
  `lightfee/engine/business_contract.py`,
  `lightfee/engine/v1_lifecycle_closure.py`,
  `lightfee/persistence/projection_contracts.py`
- Cards:
  [pending-entry-hedge-admission](../cards/pending-entry-hedge-admission.md),
  [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Production Symptom

The latest deployed runtime created/retained `entry-1783219929535-LABUSDT` with
Binance true LABUSDT long exposure and no matching Aster hedge fill.
Credentialed exchange truth showed:

- Binance `LABUSDT` position amount `+19`, entry price reported as `0`.
- Aster, Bitget, OKX, Bybit, Gate, and Hyperliquid were flat for the probed
  scope.
- Open orders were empty, so the current risk was a nonzero position rather than
  a live order.
- The pending entry retained maker fill evidence (`maker_leg_filled=19`) while
  `hedge_leg_filled=0`.
- Aster hedge submit returned a generic V3 HTTP 400 reject shape:
  `aster_v3 POST /fapi/v3/order rejected status=400`.
- Binance maker-event reprice then repeated errors including Binance `-2019`
  `Margin is insufficient` and post-only `-5022` noise.

### Root Cause

The business contract already said PE-11/PE-16/RC-11: once a pending entry has
positive maker exposure and the hedge side is not covered, runtime must either
clean up/fail closed or keep risk blocked. The implementation drift was that the
same invariant was not consumed by all execution paths:

- The normal missing-hedge path only aborted on known classified admission
  families. A generic exchange `REJECTED` response after maker exposure fell
  through as ordinary hedge submit error.
- The recovery missing-hedge path cleared inflight and then registered rejected
  hedge work as accepted-order truth gap, even though no hedge order was
  accepted.
- The maker-event lane could keep trying to reprice the maker side after the
  pending entry was already a one-sided exposure, adding fee/capacity churn
  instead of treating it as cleanup-only risk.
- Binance `-2019` was not classified with the same admission semantics as the
  rest of the runtime, so repeated maker-event errors looked like retryable
  execution noise.

### Unified Business Decision

- Any pending entry with maker fill greater than hedge fill is
  `unhedged_single_leg_risk` until exchange truth proves cleanup/flatness or a
  verified hedge fill covers the target.
- The quantity predicate must be the V1 `missing_hedge_quantity()` contract,
  including remainder-slice consumption and target-capped legacy fallback, not
  an ad hoc raw `maker_leg_filled > hedge_leg_filled` comparison.
- If a hedge submit is exchange-rejected after maker exposure and no accepted
  hedge order exists, it is `hedge_rejected_after_maker_exposure`. Runtime must
  abort through pending-entry cleanup, arm symbol-scoped cooldown, and retain
  fail-closed if cleanup cannot prove flat.
- A rejected hedge submit without accepted order identity must not become
  `accepted_order_truth_gap`.
- Maker-event reprice is never allowed to increase or churn risk for a pending
  entry that is already single-leg or in repair state. It must emit one
  diagnostic block and stop.
- Binance `-2019` is an opening admission/capacity block for maker-event reprice,
  not a generic retryable maker error.

### Fix

- Added shared business-contract helpers:
  `pending_entry_has_unhedged_maker_exposure()` and
  `classify_maker_event_reprice_reject_reason()`.
- `pending_entry_has_unhedged_maker_exposure()` delegates to
  `PendingEntry.missing_hedge_quantity()` when available, preserving the V1
  hedge-gap semantics used by recovery and terminal cleanup.
- The normal pending-hedge path now turns an unclassified exchange reject after
  maker exposure into `hedge_rejected_after_maker_exposure`, records admission
  evidence, arms a symbol cooldown, and aborts through the existing cleanup path.
- The recovery pending-hedge path now uses the same admission/cleanup path before
  it can register order-truth work; rejected no-order hedge attempts no longer
  become accepted-order truth gaps.
- The maker-event local L2, WS-BBO, and sidecar-price branches all call the same
  block helper before repricing. `unhedged_single_leg_risk` and
  `pending_entry_repair_state` terminally block maker reprice and journal
  `runtime.maker_event_reprice_blocked` once per reason.
- Binance `-2019` now maps to
  `insufficient_margin_admission_blocked` through the shared classifier.
- `runtime.maker_event_reprice_blocked` is journal-only diagnostic evidence and
  maps into V1 lifecycle closure as `PENDING_ENTRY`.
