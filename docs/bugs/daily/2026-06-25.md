## Cluster CL-120 - Aster Account Funds vs Remaining-Openable Advisory Zero

Status: local green; deploy pending.

### GitNexus Keys

- Fingerprint: `aster_account_has_funds_remaining_openable_zero + symbol_scoped_max_notional_cooldown + advisory_headroom_truth`
- Components: `venues`, `entry-dispatch`, `entry-gate`, `diagnose-live`, `bug-ledger`
- Symbols: `_aster_reject_new_risk_without_headroom`, `fetch_account_risk_snapshot`, `_entry_admission_block_state_keys`, `_candidate_admission_block`, `_build_entry_admission_cooldown_summary`
- Files: `lightfee/venues/transport.py`, `lightfee/venues/aster.py`, `lightfee/venues/aster_v3.py`, `lightfee/engine/runtime.py`, `lightfee/engine/entry_gate_runtime.py`, `lightfee/engine/entry_dispatch_runtime.py`, `scripts/diagnose_live.py`
- Watch: `runtime.entry_admission_headroom_advisory`, `aster_headroom_advisory_zero`, `remaining_openable_endpoint_value`, `required_margin_estimate`, `available_balance_quote`, `position_flat`, `open_orders_empty`, `aster:*`
- Card: [pending-entry-hedge-admission](../cards/pending-entry-hedge-admission.md)

### Summary

Production evidence and the Aster UI both showed the account had funds:
`availableBalance` was about `60.5` USDT, `LABUSDT` was flat, there were no
open orders, and the requested notional was about `16.093`. The Aster UI showed
LAB 4x `Max` above that request. V2 nevertheless treated
`remainingOpenableNotionalValue(LABUSDT, 4)=0` as hard admission truth and wrote
venue-wide Aster cooldowns, so unrelated Aster symbols could be blocked by one
symbol/leverage advisory-zero response.

### Root Cause

Two meanings were collapsed into one. `remainingOpenableNotionalValue` was used
as if it were account wallet capacity, but live probes showed it returned zero
for `LABUSDT` at leverages 4-10 while the same account had usable margin and
the UI allowed the order size. At the same time Aster V3
`accountWithJoinMargin` snapshots returned `None` for flat accounts because
`totalMaintMargin=0`, so the runtime discarded the actual account-balance
truth exactly when no positions were open. Finally, Aster max-notional/headroom
cooldowns were expanded to `aster:*`, letting a single-symbol advisory or real
reject suppress unrelated Aster candidates.

### Fix

- Kept `remainingOpenableNotionalValue` as advisory/risk-cap evidence instead
  of account-funds truth.
- For Aster V3 private precheck, when endpoint headroom is zero, fetch
  `accountWithJoinMargin`, current position, and open orders; if available
  balance covers `requested_notional / leverage`, position is flat, and open
  orders are empty, allow submit and record
  `runtime.entry_admission_headroom_advisory`.
- Preserved hard blocking for positive endpoint headroom that is below the
  requested notional and for real exchange submit rejects such as `-5018`, but
  scoped those cooldowns to `aster:SYMBOL`.
- Fixed Aster V3 account risk snapshots so flat funded accounts still expose
  `available_balance_quote`.
- Stopped writing Aster max-notional/headroom blocks to `aster:*`, and made
  legacy persisted `aster:*` max-notional/headroom cooldowns nonblocking.
- Flushed successful precheck diagnostics so advisory-zero account-truth
  evidence is visible in the same runtime journal path.
- Updated diagnose wording and rollups to report account/headroom truth fields
  instead of the old mixed advice
  `check_aster_account_leverage_position_limit_or_capital`.

### Acceptance

Local acceptance is closed for the code path. This fix does not change entry
strategy, sizing, Aster leverage targets, or taker/post-only policy. Aster
account balance insufficiency must now come from account-level balance/margin
truth or a real exchange reject, not from a single
`remainingOpenableNotionalValue=0` advisory response. Deployment and cloud

## Cluster CL-119 - Pending-Entry Maker-Terminal Release Gate Drift

Status: `3a3da74` deployed/cloud verified; production Bitget `ESPORTSUSDT`
open-order risk manually cleared before deployment.

### GitNexus Keys

- Fingerprint: `pending_entry_single_leg_flat_release_without_maker_terminal_truth + bitget_esportsusdt_maker_order_live_after_cleanup`
- Components: `pending-entry-runtime`, `diagnose-live`, `v1-lifecycle-closure`, `bug-ledger`
- Symbols: `_cleanup_owned_single_leg_live_truth_conflict`, `_ensure_pending_entry_maker_terminal_before_single_leg_release`, `_build_single_leg_exposure_recovery_summary`, `map_lifecycle_event_kind`

- Watch: `pending_entry.release_maker_cancel_requested`, `pending_entry.release_retained_maker_open_order`, `pending_entry.owned_live_conflict_cleanup_failed`, `maker_order_not_terminal_before_pending_release`, `pending_entry.terminalized_after_single_leg_recovery`
- Card: [pending-entry-terminality-live-truth](../cards/pending-entry-terminality-live-truth.md)

### Summary

Latest production truth showed no nonzero exchange position but one live Bitget
maker order remained open: `ESPORTSUSDT` order
`1453886799619977220`, client order id
`3a113653919f22fadcf3e382ded6e41e0b0a`, side buy, quantity `739.0`.
The order identity matched the pending-entry maker order recorded in
`runtime/live-events.jsonl` for `entry-1782359532641-ESPORTSUSDT`. The prior
CL-118 statement was correct for that deploy window, but current production
was later broken by a different pending-entry release drift: owner release
after single-leg cleanup did not require maker order terminal truth.

### Root Cause

`owned_live_conflict` single-leg cleanup proved fresh positions flat and then
allowed `_complete_pending_entry_terminal_removal` to release the pending owner.
That release path did not share the abort/release maker-order terminality
contract: it did not require a maker order reference in live mode, did not
prove cancel/absent-open-order truth for the maker order, and did not fail
closed on truth unavailable, still-open maker order, or positive-fill drift
after cleanup. As a result, a pending entry could be terminalized while its
maker order was still live on the exchange.

### Fix

- Added a shared single-leg maker-release gate inside pending-entry runtime.
- Before `owned_live_conflict_cleanup_succeeded` and terminal owner removal,
  live pending entries with maker order references must now prove: cancel or
  terminal maker progress, open-order query explicitly absent for the same
  order id/client order id, no extra positive fill, and fresh flat positions.
- Missing maker order reference in live mode, cancel failure, open-order truth
  unavailable, still-matched open order, or positive-fill drift now retains the
  pending entry, marks `uncertain_outcome`, sets backoff, and emits
  `maker_order_not_terminal_before_pending_release`.
- Added maker-release journal events to projection/lifecycle visibility and
  mapped `runtime.auto_fail_closed_entered` plus
  `runtime.auto_fail_closed_cleanup_failed` to `RECOVERY_TRUTH`.
- Diagnose now includes maker-release blocker events in the single-leg
  recovery summary so this shape remains unresolved/current instead of being
  hidden as historical terminalized noise.

## Cluster CL-118 - Gate Empty-Position Reduce-Only Terminal-Flat Diagnostic Closure

Status: `95e03d7` deployed/cloud verified.

### GitNexus Keys

- Fingerprint: `gate_reduce_exceeded_empty_position_reduce_only_terminal_flat + diagnose_resolved_close_artifact_drift + exit_reconciliation_abandoned_unmapped`
- Components: `business-contract`, `diagnose-live`, `v1-lifecycle-closure`, `passive-close`
- Symbols: `close_order_error_resolution_contract`, `_payload_is_reduce_only_terminal_flat_reject`, `_order_error_resolved_by_close_terminal_truth`, `map_lifecycle_event_kind`
- Files: `lightfee/engine/business_contract.py`, `scripts/diagnose_live.py`, `lightfee/engine/v1_lifecycle_closure.py`
- Watch: Gate `REDUCE_EXCEEDED`, `empty position`, `exit.passive_close_maker_submit_error`, `reduce_only_terminal_flat_count`, `order_error_evidence`, `diagnostic_noise_summary.current_blocker_count`, `unmapped_event_kinds`
- Card: [passive-close-terminal-flatness](../cards/passive-close-terminal-flatness.md)

### Summary

The latest deploy evidence shape had a Gate passive-close maker submit error
with `exchange_code=REDUCE_EXCEEDED` and `empty position` while current
exchange truth was already clean: flat positions, no open orders, and the same
close lifecycle later reached terminal flat truth. Runtime already had enough
terminal evidence to treat this as a resolved reduce-only close artifact, not a
current abnormal position or open-order blocker.

### Root Cause

The semantic contract was incomplete for Gate. The shared close-order contract
recognized Binance-style reduce-only terminal-flat rejects, but did not
recognize Gate's structured `REDUCE_EXCEEDED + empty position` payload. The
diagnose path also had a local reduce-only terminal-flat helper with the same
gap, so production diagnostics could keep the historical Gate close submit
error in `order_error_evidence` even when current exchange truth, order
identity, and lifecycle terminal truth were clean. Separately,
`exit.reconciliation_abandoned` was not in the V1 lifecycle closure mapping,
which could leave an unrelated `unmapped_event_kinds` residue on the same
incident.

### Fix

- Extended the shared business contract reduce-only terminal-flat reject
  classifier for Gate `REDUCE_EXCEEDED + empty position`.
- Kept the existing safety gates intact: `request_context.reduce_only=true`,
  current exchange truth clean, terminal lifecycle truth, and strong order or
  position identity must still match before the artifact is downgraded.
- Explicitly excluded Gate pending-order conflict text from this terminal-flat
  classification.
- Review found and closed a contract/diagnose drift where a generic outer
  `error` could hide the structured Gate label in nested
  `exchange_error.raw_body`.
- Aligned the diagnose-local reduce-only terminal-flat helper with the same
  Gate shape so resolved historical close artifacts are removed from
  `order_error_evidence` and top exchange-error noise.
- Mapped `exit.reconciliation_abandoned` to `PASSIVE_CLOSE` in the V1 lifecycle
  closure table without broadening prefix rules.
