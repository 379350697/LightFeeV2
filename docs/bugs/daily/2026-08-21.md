## Cluster CL-116-background-accounting-debt-deploy-gate

### Status

**Closed for the deployment-gate defect.** The shared root repair `f174bce`
was deployed in `76e6f914`. Neither change clears, imports, or alters a
pending close-accounting owner.

### Symptom and Production Evidence

The 2026-08-20 read-only production verifier reported one warning and exited
non-zero after the COTI position was physically flat with no open orders. The
only remaining owner was a final `evidence_debt` reconciliation missing the
Binance short close identity. The recovery decision was
`RUNNING_WITH_EVIDENCE_GAP/background_close_reconciliation` and allowed new
entries, but the deployment verifier treated every pending close owner as a
failed health check.

The COTI owner is new work from the same execution run, not a historical record
reappearing. Its Binance order ID, fill price, and fee remain unavailable; the
debt must remain durable until exact exchange evidence is supplied.

### Authoritative Contract

V1 recovery distinguishes live execution work from durable accounting work.
When exchange truth is high-confidence flat with no open orders, and the only
remaining close owner is a background reconciliation, restarting the process
is deploy-safe. The accounting owner must remain visible in state and recovery
diagnostics. Any live position, open order, pending close/passive close,
residual repair, missing/low-confidence exchange truth, or unresolved order
truth remains a failing health condition.

### Root Cause and Repair

`analyze_current_state` counted all three close-owner classes in one `clean`
predicate and emitted `pending_close_owner_present` for all of them. This
overrode the V1 recovery decision that had already classified a reconciliation
as non-blocking background work. The production verifier converts that warning
to a non-zero exit, so a durable billing debt indefinitely prevented deploys.

The health boundary now recognizes only the V1
`background_close_reconciliation` decision when there are no execution owners
or other local risk owners. It exposes
`background_close_reconciliation_pending` in report details and permits a
green deploy gate only after the existing high-confidence exchange-flat checks
also pass. It does not weaken exchange-truth, open-order, passive-close,
residual, or weak-order-truth checks.

The post-deploy `diagnose_live --since-deploy` check showed that its separate
production-acceptance gate still counted every close owner as execution work.
It therefore concluded `unhealthy` despite the green deployment verifier and
the same high-confidence flat/no-order truth. The repair moves the exact
non-blocking predicate into `recovery_decision_core` and makes both consumers
use it. Unknown reconciliation status is explicitly fail-closed.

## Cluster CL-117-close-evidence-lineage-and-residual-classification

### Status

**Implemented locally and regression-tested; not deployed and not closed.**
The first local lineage attempt preserved an identity by copying it into a
second final reconciliation. The ownership review rejected that attempt: it
could leave a complete `partial` and a `final` as two billable owners for the
same execution. The replacement transfers the complete unsettled partial into
the final owner and records that transfer for recovery replay. This follow-up
does not mutate the current COTI accounting owner, submit or cancel orders, or
treat missing execution evidence as a zero fill.

### Observed Production Facts

The current read-only production trace has no live position, pending passive
close, or pending residual-repair owner. Its only acceptance-gate blocker is
`residual_events_present` for a prior ONT passive close. The event sequence is
`exit.passive_close_unhedged_residual`, then same-position trusted flat
terminal events. The first event means the passive hedge will retry; it is not
an `execution.residual_repair_*` owner. Treating every string containing
`residual` as an unfinished repair produced a false deployment/diagnostic
block.

The current COTI evidence debt is also not arbitrary legacy debris. During the
same close lifecycle, the first durable reconciliation retained both close-leg
identities. A later live-flat fallback saw `short_leg_count=0`, compared only
the complete order-key tuple, and registered a second, weaker reconciliation
without the Binance short identity. `CloseRuntime` correctly classified that
new record as `missing_close_order_identity` evidence debt rather than polling
forever. The COTI event occurred after the earlier durable close-intent work,
so it is a remaining sibling input-loss path, not a debt created before that
repair.

### Authoritative Contract and Root Repair

V1 allows a physically flat close to hand off durable billing reconciliation,
but one exchange fill must have exactly one accounting owner. A later reduced
snapshot must neither discard known query identity nor copy it into a second
billable task. At the live-flat registration boundary, V2 now absorbs a prior
`partial` into its `final` only when the partial is still unsettled, complete
on both legs, belongs to the same position/symbol/venues, predates the final,
and supplies every currently absent final leg. The final records the absorbed
partial's kind and close timestamp in its critical journal event; replay
removes the same predecessor after restoring the final. Recovery placeholders,
evidence-debt partials, a partial with a missing leg, and a current
blank/unknown submitted-order record are not eligible. Therefore an actually
unknown close remains an evidence debt rather than being guessed or deleted.

`diagnose_live` now has one residual-marker classifier shared by its count and
lifecycle summary. It uses V1's event-phase taxonomy instead of matching the
word `residual` in an event kind or `reason`; the passive-close residual
producer is explicitly classified as `RESIDUAL_REPAIR` because it creates a
durable repair task. Only the exact passive retry event may be released by a
later flat terminal for the *same position*; explicit residual repair still
requires its own completion evidence. Tolerated entry dust is terminal
evidence, not a newly opened repair. The production acceptance gate also
requires its existing clean local state and trusted flat/no-open-order exchange
truth before such a released diagnostic event is non-blocking.
