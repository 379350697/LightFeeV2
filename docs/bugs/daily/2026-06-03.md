| Category | Issue | Decision |

| Root-fixed locally | Binance recovery placeholder order id sent as Binance `orderId` | Binance USD-M query-order semantics distinguish exchange `orderId` from `origClientOrderId`; V2 recovery synthetic ids such as `entry-...-recovery-short` are not numeric exchange order ids and must not be sent as `orderId`. |

### Fix

- `VenueTransport._fetch_order_status_binance()` now sends Binance `orderId`
  only when the id is numeric. When recovery supplies a synthetic placeholder
  and a client id is available, it queries `/fapi/v1/order` with
  `origClientOrderId`. If only a nonnumeric id exists, it is treated as
  `origClientOrderId` instead of malformed `orderId`.
- `LiveRuntime._resolve_ws_bbo_close_mid()` now emits
  `runtime.close_price_evidence_missing` for active `ws_bbo_quote_lease`
  fallback branches where the quote-lease budget, cache, quote, or fallback
  path is unavailable. It keeps the same fail-closed return value `0.0`.
- No WS BBO budget increase, TTL widening, Local-L2 lifecycle change, order
  submit behavior, close executor behavior, residual repair, or recovery policy
  changed.

## Cluster CL-036-startup-live-position-probe-static-universe-fanout

### GitNexus Keys

- Fingerprint: `startup-live-position-probe.empty-requested-symbols + static-config-universe-fanout + binance-positionrisk-429 + live_tick_stale`
- Components: `live-runtime`, `startup-recovery`, `venue-binance`,

- Symbols: `LiveRuntime._fetch_startup_live_position_snapshots`,
  `LiveRuntime._startup_position_probe_symbols`, `LiveRuntime.start`
- Files: `lightfee/engine/runtime.py`, `tests/test_live_startup_preflight.py`
- Commits: `a272b6b`, working tree follow-up
- Watch: `live_tick_stale`, Binance `HTTP/1.1 429 Too Many Requests`,
  `GET /fapi/v2/positionRisk`,
  `recovery.live_position_static_config_probe_skipped`

### Production Evidence

The first `a272b6b` deploy updated `.deploy_version` and restarted both
services. `lightfee-live.service` and `lightfee-sidecar.service` were active
with `NRestarts=0`, but `verify_production_services.py --json` stayed red:
`critical_count=1`, fingerprint `live_tick_stale`, tick age growing from
`17082ms` to `136029ms`. Current local trading state was otherwise flat:
open/pending/passive/residual counts were `0` and
`exchange_truth_mismatches=[]`.

Recent live logs showed startup recovery repeatedly calling Binance
`GET /fapi/v2/positionRisk` and finally receiving
`HTTP/1.1 429 Too Many Requests`. The exported state file existed, but its
payload had no fresh `ts_ms`, so production health correctly rejected the
deploy as stale.

### Root Cause

`LiveRuntime._startup_position_probe_symbols()` correctly returned an empty
list for clean startup state, matching the existing rule that startup recovery
must not expand clean state to the configured trading universe. But
`LiveRuntime._fetch_startup_live_position_snapshots([])` had a later fallback:
if a venue did not return bulk positions and no per-venue requested symbols
remained, it rebuilt the probe set from `config.symbols`.

That preserved small local false-clean tests, but in production the configured
universe is large. For Binance, where the fallback endpoint is
`/fapi/v2/positionRisk`, this created an unbounded per-symbol private REST
fanout during startup, hit Binance rate limits, and prevented the runtime from
reaching fresh ticking health.

### Fix

- Keep existing false-clean protection for a single explicitly configured
  symbol by allowing static fallback only when `len(config.symbols) <= 1`.
- When the static universe is larger, skip per-symbol fallback and emit
  `recovery.live_position_static_config_probe_skipped` with venue, static
  symbol count, limit, requested symbol count, and decision evidence.
- Requested/recovery symbols, local open/pending/passive/residual work,
  catalog filtering, bulk position APIs, mismatch flattening, balanced
  hydration, and all trading execution paths are unchanged.

## Cluster CL-037-runtime-live-recovery-stale-startup-block

### GitNexus Keys

- Fingerprint: `runtime-live-position-probe.recovered-balanced-position + stale startup_recovery_pending_work_without_open_positions + lifecycle_risk_only`
- Components: `live-runtime`, `startup-recovery`, `pending-entry-recovery`,

- Symbols: `LiveRuntime._maybe_recover_clean_live_positions`,
  `LiveRuntime._finalize_startup_recovery`,
  `clear_stale_recovery_block_if_recovery_clean`
- Files: `lightfee/engine/runtime.py`, `tests/test_live_startup_preflight.py`
- Commits: `cb1abbe`, working tree follow-up
- Watch: `recovery.blocked`, `runtime.started lifecycle=risk_only`,
  `pending_entry.missing_hedge_detected`,
  `pending_entry.hedge_submit_result`, `recovery.live_detected`,
  `runtime.running reason=startup_recovery_completed_with_positions`

### Production Evidence

Post-`cb1abbe` cloud verification showed services active with fresh ticks, but
`verify_production_services.py --json` stayed red:
`critical_count=1`, fingerprint `live_lifecycle_not_running`,
`risk_mode=running`, `lifecycle=risk_only`, `open_position_count=1`,
`pending_entry_count=0`, and no local close/residual work.

Credentialed read-only `diagnose_live.py --since-deploy --json` showed high
confidence exchange truth for the same recovered position: Binance
`HIVEUSDT` long `394`, Bybit `HIVEUSDT` short `394`, and no open orders on
either venue. Local state held
`live-recovered:HIVEUSDT:binance->bybit` quantity `394`.

The deploy-window event chain was:

| Seq | Event | Evidence |
|---|---|---|
| 23 | `order.reconcile_result` | Binance maker `HIVEUSDT` filled `394` |
| 28 | `recovery.blocked` | `reason=startup_recovery_pending_work_without_open_positions` |
| 31 | `runtime.started` | `lifecycle=risk_only`, `risk_mode=running` |
| 43 | `pending_entry.missing_hedge_detected` | retained HIVE pending needed hedge recovery |
| 45-48 | hedge submit/result | Bybit hedge submitted with exchange order id |
| 51 | `recovery.live_detected` | recovered balanced `HIVEUSDT` Binance->Bybit quantity `394` |

Old tracks in the same window did not recur: concrete
`runtime.local_l2_hot_stale_rebuild=0`, sequence gaps `0`, old WS BBO
`waiting_for_subscription=0`, and no Binance `-1102` finalize errors in the
54 parsed deploy-window events.

### Root Cause

This is a V2/V1 lifecycle-release semantic drift. `_finalize_startup_recovery()`
already encodes the V1 rule that open positions after recovery are normal
managed positions and should transition to `RUNNING` when they do not exceed
the configured maximum. But the stale block was created before the runtime
live-position probe recovered the balanced HIVE position.

After runtime housekeeping submitted the missing hedge and
`_maybe_recover_clean_live_positions()` hydrated the balanced live position,
the stale startup block was not re-finalized. The generic
`clear_stale_recovery_block_if_recovery_clean()` could not clear it because it
treats any `open_positions` as reconciliation work, which is correct for
startup classification but wrong after a balanced live position has just been
recovered as the managed state.

### Fix

- `LiveRuntime._maybe_recover_clean_live_positions()` now records the open
  position count before the runtime live probe.
- If that probe creates a new open position while the only block is
  `startup_recovery_pending_work_without_open_positions`, no pending
  entry/close/passive-close work remains, and the operator has not requested
  fail-closed, it reuses `_finalize_startup_recovery()`.
- The fix is intentionally narrow: no order submit path, Local-L2, WS BBO,
  residual repair, close executor, mismatch flattening, or generic recovery
  block clearing behavior changed.
