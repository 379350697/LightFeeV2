### Production Evidence

The first `a272b6b` deploy updated `.deploy_version` and restarted both
services. `lightfee-live.service` and `lightfee-sidecar.service` were active
with `NRestarts=0`, but `verify_production_services.py --json` stayed red:
`critical_count=1`, fingerprint `live_tick_stale`, tick age growing from
`17082ms` to `136029ms`. Current local trading state was otherwise flat:
open/pending/passive/residual counts were `0` and
`exchange_truth_mismatches=[]`.

Recent live logs showed startup recovery repeatedly calling Binance
`GET /fapi/v2/positionRisk` and finally receiving
`HTTP/1.1 429 Too Many Requests`. The exported state file existed, but its
payload had no fresh `ts_ms`, so production health correctly rejected the
deploy as stale.

### Root Cause

`LiveRuntime._startup_position_probe_symbols()` correctly returned an empty
list for clean startup state, matching the existing rule that startup recovery
must not expand clean state to the configured trading universe. But
`LiveRuntime._fetch_startup_live_position_snapshots([])` had a later fallback:
if a venue did not return bulk positions and no per-venue requested symbols
remained, it rebuilt the probe set from `config.symbols`.

That preserved small local false-clean tests, but in production the configured
universe is large. For Binance, where the fallback endpoint is
`/fapi/v2/positionRisk`, this created an unbounded per-symbol private REST
fanout during startup, hit Binance rate limits, and prevented the runtime from
reaching fresh ticking health.

### Fix

- Keep existing false-clean protection for a single explicitly configured
  symbol by allowing static fallback only when `len(config.symbols) <= 1`.
- When the static universe is larger, skip per-symbol fallback and emit
  `recovery.live_position_static_config_probe_skipped` with venue, static
  symbol count, limit, requested symbol count, and decision evidence.
- Requested/recovery symbols, local open/pending/passive/residual work,
  catalog filtering, bulk position APIs, mismatch flattening, balanced
  hydration, and all trading execution paths are unchanged.

### Root Cause

This is a V2/V1 lifecycle-release semantic drift. `_finalize_startup_recovery()`
already encodes the V1 rule that open positions after recovery are normal
managed positions and should transition to `RUNNING` when they do not exceed
the configured maximum. But the stale block was created before the runtime
live-position probe recovered the balanced HIVE position.

After runtime housekeeping submitted the missing hedge and
`_maybe_recover_clean_live_positions()` hydrated the balanced live position,
the stale startup block was not re-finalized. The generic
`clear_stale_recovery_block_if_recovery_clean()` could not clear it because it
treats any `open_positions` as reconciliation work, which is correct for
startup classification but wrong after a balanced live position has just been
recovered as the managed state.

### Fix

- `LiveRuntime._maybe_recover_clean_live_positions()` now records the open
  position count before the runtime live probe.
- If that probe creates a new open position while the only block is
  `startup_recovery_pending_work_without_open_positions`, no pending
  entry/close/passive-close work remains, and the operator has not requested
  fail-closed, it reuses `_finalize_startup_recovery()`.
- The fix is intentionally narrow: no order submit path, Local-L2, WS BBO,
  residual repair, close executor, mismatch flattening, or generic recovery
  block clearing behavior changed.
